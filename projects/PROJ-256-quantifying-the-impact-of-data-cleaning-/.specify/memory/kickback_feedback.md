## Unresolved concerns

- The plan treats each cleaning variant as a bundled combination of outlier removal, imputation, and recoding, then evaluates the bundle as a whole. This design conflates the individual contributions of each preprocessing step, making it impossible to attribute observed changes in effect size or p‑value to a specific operation (confound control). A factorial or at‑least a step‑wise isolation design is needed to isolate the effect of each cleaning component.
- Effect‑size change is used as the primary construct (SC‑031) across heterogeneous statistical tests (t‑tests, linear regressions). Cohen’s d and R‑squared are not directly comparable, so aggregating them into a single ‘effect_size_change’ metric threatens construct validity. The plan should define a unified effect‑size metric or keep separate metrics per test type.
- The sample size justification relies on a power analysis (FR‑016, FR‑030) but the plan does not present the calculations or show that 10–15 datasets (the lower bound of the range) satisfy the required power (≥ 0.8 for detecting d = 0.5). Without explicit power calculations, the study may be under‑powered, especially for the Wilcoxon signed‑rank test across datasets.
- Multiple‑comparison correction is applied both within each dataset (Holm‑Bonferroni across all cleaning‑variant p‑values) and across Wilcoxon tests (Bonferroni). This double‑layer correction is extremely conservative and will dramatically reduce power to detect true systematic changes, conflicting with the goal of demonstrating an association.
- The permutation‑based false‑positive‑rate estimation permutes the outcome before any cleaning step, then re‑applies the missingness mechanism and cleaning. While this estimates FPR under the null, it does not account for the fact that cleaning operations can induce structure that inflates false positives differently across variants. The design should also include a null‑benchmark (FR‑020) analysis to validate FPR estimates.
- FR-024 (Power Analysis Artifact) is absent from the plan; there is no phase that generates or validates the required `power_analysis.txt` artifact.
- SC-005 (Outcome variable verification) is not covered by any listed phase, so the plan does not guarantee that `dataset_metadata.json` contains a verified, numeric outcome column.
- SC-016 (Robust test identification) is missing from the plan; no phase explicitly records the `robust_test_used` field when robust alternatives are invoked.
- The listed dataset **UCI Human Activity Recognition (HAR)** is a multi‑class activity classification dataset, not a binary or continuous outcome variable as required by FR‑001. Using this dataset would violate the functional requirement that each dataset have a clearly documented binary or continuous outcome.
- Only five verified datasets are enumerated, whereas FR‑001 specifies downloading **10–15** public datasets covering three size bins and four missingness levels. The current list does not satisfy the required quantity or guaranteed coverage of all size/missingness bins.
- The data model defines `bootstrap_metrics.json` and `sensitivity_metrics.json` with corresponding schemas (`bootstrap_metrics.schema.yaml`, `sensitivity_metrics.schema.yaml`). The plan describes bootstrap variance estimation and sensitivity analysis but never explicitly states that the resulting JSON files will be validated against their schemas. Add explicit validation steps (or mention) for these artifacts to keep plan ↔ data‑model ↔ contracts aligned.
- The plan does not mention the generation or validation of `hypothesis_test_results.json` (paired Wilcoxon test on `effect_size_change`). Since the data model includes this artifact, the plan should reference its creation and any contract validation (if a schema exists) to maintain full coverage.
