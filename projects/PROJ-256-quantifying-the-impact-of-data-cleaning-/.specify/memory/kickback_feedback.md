## Unresolved concerns

- The a‑priori power analysis (FR‑016) is framed to detect a minimum effect size for the *primary* statistical tests (binary proportion Δ = 0.2, continuous Cohen’s d = 0.5). The research question, however, is about detecting *changes* in inference caused by cleaning (p‑value delta, CI‑overlap, effect‑size change). Power calculations that ignore the variability of these delta metrics are mis‑aligned; the study may be under‑powered to observe the cleaning‑induced shifts it aims to describe.
- Delta metrics (p_value_delta, direction, ci_overlap, effect_size_change) are computed across heterogeneous test families (chi‑square/Fisher vs. logistic regression for binary outcomes; Welch t‑test vs. OLS for continuous outcomes). Because the scale and interpretation of p‑values and effect sizes differ between test types, a raw delta is not a construct‑valid measure of “impact of cleaning” when aggregating across outcome types. The plan should either standardise the metric (e.g., log‑odds ratio change) or analyse binary and continuous outcomes separately.
- When assumption checks fail, the pipeline automatically switches to a robust alternative (Welch’s t, rank‑based regression) and flags `assumptions_met: false`. This introduces a confound: a change in p‑value or effect size may be driven by the test substitution rather than the cleaning operation itself. The current design does not isolate the cleaning effect from the methodological change, jeopardising causal attribution (even associative claims).
- The plan generates 120 cleaned variants (2 outlier thresholds × 3 imputations × encoding) and reports unadjusted p‑values (FR‑007). No multiple‑comparison correction is applied when summarising across variants, yet the success criteria (SC‑001) require per‑dataset delta reporting. With dozens of tests, the risk of spurious “significant” deltas rises, and the descriptive conclusions may be inflated. A correction or at least a discussion of the false‑positive rate is needed.
- Success Criterion SC-010 (Assumption checks and robust fallback) is absent from the phase‑to‑SC mapping, so the plan provides no explicit task to satisfy this criterion.
- The plan states it will acquire “≥ 10 UCI/OpenML datasets … and all three size bins” (binary/continuous outcomes, size bins < 64, 64‑200, > 200). However, the dataset list in research.md misclassifies the Breast Cancer Wisconsin Diagnostic dataset (569 rows) as `< 64` and provides no dataset actually under 64 rows. This violates FR‑001, which requires at least one dataset in each size bin, making the dataset selection inappropriate for the research question.
- The contract file `contracts/analysis_result.schema.yaml` is defined in the repository but never referenced or exercised by any phase in the implementation plan. Every contract should be validated by at least one pipeline step.
- Functional Requirement FR‑023 (Power Analysis Output Validation) is not addressed: the plan writes `power_analysis.txt` but does not include a validation step to ensure the file exists, is parseable, and meets the sample‑size thresholds required by the specification.
- Functional Requirement FR‑024 (Bin Power Adequacy) is missing: the plan ensures at least one dataset per size bin, but does not verify that each bin reaches the cumulative sample‑size minimum of 130 rows as mandated.
- The plan computes `p_value_delta` and `direction` by directly subtracting the baseline p‑value (derived from a standard test such as Welch t‑test or chi‑square) from the cleaned‑variant p‑value, which may be obtained from a *different* robust fallback test (e.g., rank‑based regression) when baseline assumptions fail. Mixing p‑values from fundamentally different statistical procedures makes the delta metric non‑comparable and can lead to misleading conclusions about the impact of cleaning. The methodology should enforce that the same statistical test type is used for both baseline and cleaned analyses (or otherwise flag and exclude cases where test types differ) before computing delta metrics.
