# Research Methodology: Evaluating the Impact of Code Generation on Code Review Time

## Overview

This document outlines the scientific methodology employed to evaluate the causal impact of LLM-generated code on code review duration. The study uses a quasi-experimental design with propensity score matching to control for confounding variables.

## Research Question

Does the use of LLM-generated code in pull requests significantly affect the time required for code review compared to human-written code, when controlling for code complexity, file size, and repository activity?

## Study Design

### Population
- Pull requests from GitHub repositories with ≥1,000 stars
- Timeframe: Last 12 months
- Inclusion criteria: Python code changes, review duration available

### Intervention
- **Treatment Group**: Code snippets classified as "LLM-like" or synthetically generated
- **Control Group**: Human-written code snippets

### Outcome Measure
- **Primary**: Review duration (time from PR creation to first comment or merge)
- **Secondary**: Review depth (number of comments), merge time

## Methodology

### 1. Data Acquisition

GitHub PR metadata is acquired using the GitHub API v3, filtering for repositories with significant activity (≥1,000 stars) to ensure sufficient sample size and review quality.

### 2. Code Classification

Code snippets are classified using a CodeBERT-based classifier to distinguish between "LLM-like" and "Human" generated code. Additionally, synthetic LLM code is generated using CodeLlama for validation purposes.

### 3. Feature Extraction

Key covariates extracted:
- **File Size**: Lines of code (LOC)
- **Complexity**: Cyclomatic complexity (via radon)
- **Activity**: Repository commit frequency, PR activity metrics
- **Style Metrics**: Indentation consistency, line length distribution, naming conventions

**Note**: Semantic similarity scores are computed for diagnostic purposes but explicitly EXCLUDED from matching covariates to avoid collider bias (see Deviation Report).

### 4. Propensity Score Matching

We employ propensity score matching to create comparable treatment and control groups:

1. Estimate propensity scores using logistic regression with covariates: file size, complexity, activity
2. Match LLM-like and human commits using nearest-neighbor matching (1:1 ratio)
3. Assess balance using Standardized Mean Difference (SMD)
4. Iterate up to 3 times with interaction terms if SMD > 0.1

**Balance Criterion**: SMD < 0.1 for all covariates indicates successful matching.

### 5. Statistical Analysis

- **Normality Test**: Shapiro-Wilk test
- **Primary Test**:
 - If normal: Independent samples t-test
 - If non-normal: Mann-Whitney U test
- **Effect Size**: Cohen's d (or rank-biserial correlation for non-parametric)
- **Significance Level**: α = 0.05

### 6. Sensitivity Analysis

To assess robustness, we stratify the analysis by repository star-count quartiles and verify consistency of results across strata.

**Consistency Criterion**: p < 0.05 in ≥80% of strata.

### 7. Validation Cohort

A "Prompt-Based" cohort is generated by deriving natural language prompts from commit messages and generating code without access to the original file content. This validates the causal claim by testing a different generation mechanism.

## Ethical Considerations

- All data is publicly available on GitHub
- No personally identifiable information (PII) is collected
- Repository owners' terms of service are respected
- Rate limiting is implemented to prevent API abuse

## Limitations

1. **Observational Study**: Causal inference is limited by potential unmeasured confounders
2. **Selection Bias**: High-star repositories may not represent all code review contexts
3. **Classification Accuracy**: LLM vs. human classification is not perfect
4. **Temporal Effects**: Code review practices evolve over time

## Reproducibility

- All code is open-source and version-controlled
- Random seeds are fixed for reproducibility
- Data processing pipelines are fully automated
- Detailed logs are maintained for all operations
