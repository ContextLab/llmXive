## Unresolved concerns

- The plan classifies MetS status using ATP‑III criteria on post‑mortem donor data. ATP‑III was designed for clinical, in‑vivo measurements; post‑mortem changes (e.g., fluid shifts, PMI effects) may bias BMI, glucose, BP, triglycerides, and HDL, threatening construct validity of the MetS label.
- Power analysis is performed only for the logistic‑regression model (binary outcome) and does not address the massive multiple‑testing burden of tissue‑stratified differential expression (ANCOVA) or gene‑trait correlations, leaving those analyses potentially under‑powered.
- Tissue‑stratified ANCOVA requires ≥ 20 donors per group per tissue; given the strict exclusion of donors with any missing ATP‑III variable, many tissues may be dropped, dramatically reducing effective sample size and inflating false‑negative risk. No mitigation (e.g., pooling similar tissues or hierarchical modeling) is described.
- MESA is a blood‑based RNA‑seq cohort, whereas GTEx DE is performed per solid tissue. Replicating tissue‑specific DE results in a different tissue type may be infeasible, yet the plan expects a ≥ 30 % gene‑overlap metric without addressing this biological mismatch.
- The logistic regression includes all core circadian genes plus several covariates (≈ 15 predictors). With the limited number of MetS cases after exclusions, the predictor‑to‑sample ratio may approach or exceed recommended limits, risking over‑fitting despite cross‑validation.
- Success Criterion SC-002 (number of core circadian genes with significant differential expression) is not addressed; the plan’s Milestones table reports only tissue‑processing coverage and does not specify a metric for counting significant DE genes.
- Success Criterion SC-003 (AUC measured against a baseline random classifier) is missing; the plan reports mean AUC and confidence intervals (Phase 6‑7) but does not include a comparison to the random‑classifier baseline (AUC = 0.5).
- Success Criterion SC-004 (magnitude of correlation coefficient measured against the null hypothesis) is not covered; Phase 4‑5 describe computing ρ and applying FDR, but no explicit evaluation of the coefficient against the null (ρ = 0) is stated.
- Success Criterion SC-005 (sensitivity analysis varying ATP‑III thresholds ±5 % and requiring ≥ 90 % label stability) is absent; Phase 1 phenotype processing mentions classification but does not include the required threshold‑variation sensitivity analysis.
- The plan cites GTEx v8 TPM matrices and phenotype files as the primary dataset for Metabolic Syndrome (MetS) classification (see "download GTEx v8 RNA‑seq TPM matrices and phenotype files"). GTEx does not provide the required clinical laboratory variables (fasting glucose, triglycerides, HDL, blood pressure) needed to apply ATP‑III criteria, making it an inappropriate dataset for the core research question. Replace GTEx with a dataset that includes these metabolic measurements (e.g., a cohort with linked electronic health records) or adjust the methodology to use only variables actually available in GTEx.
- Phase 0 describes downloading GTEx and MESA data but does not reference the `dataset.schema.yaml` contract that defines the expected raw GTEx schema. Without an explicit contract check, the pipeline may accept malformed input, violating the contract‑validation requirement.
- Phase 1 performs MetS classification yet never mentions the `classification.schema.yaml` (or `donor_phenotype.schema.yaml`) contract that validates the classification output. The plan should state that the resulting `donors.parquet` will be validated against these schemas.
- The DE step produces `de_results.csv` but does not cite the `de_results.schema.yaml` (or `differential_expression.schema.yaml`) contract that governs its structure. Explicit contract usage is required for downstream schema tests.
- Correlation results are written to `correlation_results.csv` yet the plan never references the `correlation_results` schema (no dedicated contract file exists). The plan should either create/use a schema contract or clarify that `output.schema.yaml` will validate these rows.
- Logistic regression outputs (`logistic_model_coefficients.csv`, `cv_performance.csv`) are generated, but the plan does not mention the `logistic_regression.schema.yaml`, `model.schema.yaml`, or `output.schema.yaml` contracts that are intended to validate these files.
- The validation step creates `validation_results.csv` but the plan never ties this to the `output.schema.yaml` (or a dedicated validation contract). Contract linkage is required to ensure the replication metrics conform to the expected schema.
- The Constitution table lists Principle IV (Single Source of Truth) but the plan stores processed files under `data/processed/` while the data‑model defines them directly under `data/`. Align the directory naming (e.g., use `data/processed/` consistently) to avoid ambiguity about the SSoT location.
- FR‑009 requires reporting odds ratios for individual metabolic traits (BMI, glucose, BP, triglycerides, HDL) alongside gene‑expression odds ratios in the logistic regression model. Including these traits as predictors to predict MetS creates a circular validation because the same variables (or thresholds thereof) define the MetS outcome (ATP‑III criteria). This makes the predictive performance largely a function of the input criteria rather than an independent test of circadian gene contribution, violating independence of predictors and validation target.
