# Research: llmXive follow-up: extending "EvoPolicyGym: Evaluating Autonomous Policy Evolution in Interactive En"

## 1. Problem Statement & Hypothesis

**Problem**: Standard evolutionary algorithms optimize for scalar rewards, which often leads to brittle policies that overfit to specific environmental dynamics. When the environment shifts (e.g., reward function changes), these policies fail catastrophically.
**Hypothesis**: Providing agents with **natural language counterfactual explanations** for their failures (e.g., "You failed because you violated Rule X; you should have moved away from the wall") during evolution will result in policies that generalize better to **dynamic shifts** than policies evolved with scalar rewards alone.
**Null Hypothesis**: There is no difference in generalization performance (post-shift retention) between the counterfactual feedback group and the scalar reward baseline.

**Training vs. Evaluation Clarification**:
- **Training Phase**: The agent evolves entirely in a **static** version of the environment (no shift). Feedback (scalar or counterfactual) is generated based on this static interaction.
- **Evaluation Phase**: The evolved policy is tested on a **held-out** version of the environment where a dynamic shift occurs at [deferred] of the budget. The agent *never* saw this shift configuration during training.
- **Metric**: Retention of performance (score after shift / score before shift) on this *held-out* dynamic test set.

## 2. Literature & Methodological Basis

### 2.1 Counterfactual Explanations in RL
Counterfactual explanations provide a "what-if" reasoning mechanism. In RL, they are often used to debug agent behavior. Recent work suggests that natural language feedback can guide policy search more effectively than scalar rewards by reducing the search space of valid behaviors.
*   **Method**: Use a lightweight LLM to map a trajectory failure (state, action, reward) to a specific rule violation and a **heuristic** corrective action.
*   **Distinction from Supervised Learning**: The "corrective action" is **not** the ground-truth optimal action (which would make the agent simply imitate the oracle). Instead, it is a **heuristic correction** derived from the rule (e.g., "If you hit a wall, move away"). The agent must still *discover* the specific policy via evolution, guided by this heuristic. This prevents the validation from being tautological.
*   **Validation**: The explanation must explicitly cite the violated rule ID (from the environment schema) to ensure it is not hallucinating.

### 2.2 Dynamic Shifts & Generalization
Generalization in RL is typically tested by holding out a set of environments. This project introduces a **temporal shift**: the environment changes *during* the episode or between episodes in a way that was not present during the initial training phase.
*   **Metric**: Retention of performance (score after shift / score before shift) on a **held-out** shift configuration.
*   **Statistical Test**: Mixed-effects model (LMM) to account for the hierarchical structure of the data (multiple runs per seed, multiple seeds per condition).

### 2.3 Complexity Control
Policies evolved with richer feedback (natural language) might become more complex. To ensure that any performance gain is not simply due to increased capacity, we report **cyclomatic complexity** and **branch count** using `radon`.
*   **Role of Complexity**: Complexity is treated as a **descriptive mediator**, not a strict control variable that might mask the mechanism. We will report the correlation between Condition and Complexity, and Complexity and Performance. However, the primary hypothesis test will focus on the Condition effect *before* over-controlling, to avoid removing the very mechanism (richer internal representations) that explains success.

## 3. Dataset Strategy

### 3.1 Source Dataset
The primary "dataset" is the **EvoPolicyGym** environment suite, which consists of 16 distinct interactive environments.
*   **Source**: The environments are defined in the `EvoPolicyGym` repository (referenced in spec: arXiv 2607.02440).
*   **Availability**: The source code is open and programmatically modifiable. No external download is required; the environments are instantiated in memory.
*   **Variables**:
    *   *Predictors*: Environment ID, Condition (Baseline vs. Counterfactual), Seed, Policy Complexity.
    *   *Outcome*: Generalization Score (post-shift performance on held-out test set).
    *   *Covariates*: Pre-shift performance, Rule violation count.

### 3.2 Data Generation & Collection
Data is **synthetically generated** by the simulation pipeline:
1.  **Trajectory Logs**: Recorded for every step of every evolutionary run (Training Phase).
2.  **Explanation Logs**: Generated by the LLM module for every failure.
3.  **Policy Artifacts**: Python source code saved for every evolved agent.
4.  **Metrics**: Extracted via `radon` and simulation evaluation (Evaluation Phase).

**Feasibility Check**: The data generation is entirely local and CPU-bound. No external API calls for data retrieval are needed. The "dataset" size is determined by the number of evolutionary runs, which is planned to fit within the 6-hour CI window.

## 4. Statistical Analysis Plan

### 4.1 Model Specification
We will fit a linear mixed-effects model (LMM) to test the effect of the feedback condition on generalization scores.

**Model Formula**:
`Generalization_Score ~ Condition + PreShift_Score + (1 | Seed)`

*   **Fixed Effects**:
    *   `Condition`: Categorical (Baseline, Counterfactual). *Hypothesis: Counterfactual > Baseline.*
    *   `PreShift_Score`: Continuous control (initial performance).
    *   *Note*: Complexity is reported descriptively and checked for correlation, but not included as a primary control to avoid masking the mechanism.
*   **Random Effects**:
    *   `(1 | Seed)`: Accounts for the non-independence of runs sharing the same random seed.

### 4.2 Power & Sample Size
*   **Constraint**: CPU limits (2 cores, 6h limit).
*   **Plan**: We will run **5 evolutionary runs per condition per environment** (total 160 runs).
* **Power Analysis**: With N=160 (5 runs × 16 envs × 2 conditions), the study is **underpowered to detect small effect sizes** (Cohen's d < 0.5) with [deferred] power using a standard LMM. However, it is sufficient to detect **large effect sizes** (d > 0.8), which are typical for significant algorithmic interventions in evolutionary RL.
*   **Robust Alternative**: If the LMM fails to converge due to the low number of levels per group (N=5 per condition), or if residual assumptions are violated, the analysis will switch to a **permutation test** (cluster-robust) or **bootstrap confidence intervals**. This ensures the statistical conclusion remains valid even with small sample sizes.
*   **Correction**: Since we are testing one primary hypothesis (Counterfactual > Baseline) across all environments, we will use a one-tailed test. If we perform separate tests per environment, we will apply a Bonferroni correction or False Discovery Rate (FDR) control.

### 4.3 Assumptions & Risks
*   **Normality**: LMM assumes normally distributed residuals. We will check residual plots. If violated, we will use a non-parametric cluster-robust test (permutation).
*   **Collinearity**: Complexity and performance might be correlated. We will check Variance Inflation Factors (VIF) and report these correlations descriptively.
*   **Causal Claims**: The study is observational within the simulation. We can claim that "Counterfactual feedback *is associated with* better generalization," but causal language regarding the *mechanism* requires careful framing.

## 5. Compute Feasibility (CPU-First)

### 5.1 Environment Simulation
*   **Method**: `gymnasium`-style step function.
*   **Feasibility**: Fully CPU-tractable. 16 environments × 5 runs × 1000 steps = 80,000 steps. Negligible compute.

### 5.2 Counterfactual Generation (LLM)
*   **Method**: Lightweight, quantized model (e.g., `distilbert` or a small 1-2B parameter model loaded in 8-bit/4-bit via `transformers` on CPU).
*   **Feasibility**:
    *   **Risk**: LLM inference on CPU can be slow.
    *   **Mitigation**:
        1.  Use a very small model (e.g., `DistilBERT` for classification of rule violations, or a tiny decoder like `TinyLlama` for text generation if necessary).
        2.  **Hard Timeout**: 30 seconds per request (FR-006).
        3.  **Fallback**: If timeout or error, use a deterministic template: "Failure: Rule [ID] violated. Correction: [Heuristic Action]."
    *   **Decision**: We will prioritize a **template-based generator** for the primary experiment if a lightweight LLM proves too slow for the 6-hour window, using the LLM only for a small subset of validation runs. This ensures the study completes.

### 5.3 Statistical Analysis
*   **Method**: `statsmodels` (mixedlm) or `linearmodels`.
*   **Feasibility**: Trivial on CPU for N < 1000.

## 6. Decision Rationale

| Decision | Rationale |
| :--- | :--- |
| **CPU-Only Execution** | The project must run on GitHub Actions free-tier (no GPU). |
| **Template Fallback for LLM** | Ensures robustness against CPU inference latency; prevents pipeline crashes. |
| **Mixed-Effects Model** | Necessary to handle the nested structure of the data (runs within seeds) and control for confounds. |
| **5 Runs per Condition** | Balances statistical power with the 6-hour compute budget; acknowledges power limitation for small effects. |
| **No External Datasets** | The "data" is generated by the simulation; no external download risks or access issues. |
| **Held-Out Test Set** | Ensures the generalization metric is not circular (agent tested on unseen shift dynamics). |
| **Heuristic Correction** | Ensures the agent must still discover the policy via evolution, preventing a supervised learning tautology. |
