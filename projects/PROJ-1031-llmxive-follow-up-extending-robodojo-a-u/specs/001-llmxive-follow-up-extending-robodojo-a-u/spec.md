# Feature Specification: llmXive Follow-up: Extending RoboDojo with Symbolic Abstractions

**Feature Branch**: `001-symbolic-dojo-extend`  
**Created**: 2026-09-03  
**Status**: Draft  
**Input**: User description: "To what extent do topological task constraints versus continuous physical dynamics independently contribute to failure modes, regardless of the planning architecture?"

## User Scenarios & Testing

### User Story 1 - CPU-Tractable Symbolic Planner Execution (Priority: P1)

The researcher MUST be able to generate valid action sequences for long-horizon tasks using a high-level symbolic planner (e.g., A* or MCTS) that operates entirely on a CPU, without requiring GPU acceleration or high-fidelity physics simulation.

**Why this priority**: This is the core hypothesis test. If the symbolic layer cannot execute on CPU or fails to generate plans, the entire premise of reducing computational barriers collapses. It directly addresses the "CPU-tractable" motivation.

**Independent Test**: The system can be tested by feeding a RoboDojo task specification (semantic embeddings) into the planner and verifying that a discrete action sequence is output within a specific time bound on a standard CPU instance, independent of any real-world robot execution.

**Acceptance Scenarios**:

1. **Given** a RoboDojo task specification converted to semantic embeddings, **When** the symbolic planner is invoked on a GitHub Actions runner instance (multi‑core, 7 GB RAM), **Then** it MUST output a valid sequence of discrete sub-goals within ≤ 60 seconds.  
2. **Given** a task requiring multi-step assembly, **When** the planner generates a sequence, **Then** the sequence MUST consist of valid SymbolicState predicates that respect object affordances defined in the input graph, verified against the defined SymbolicState schema validator.  
3. **Given** a CPU environment with multiple cores and 7 GB RAM, **When** the planner processes 18 distinct RoboDojo tasks, **Then** the total memory usage MUST remain ≤ 6 GB and the process MUST NOT crash due to OOM errors.  
4. **Given** a semantic embedding that maps to multiple candidate SymbolicState nodes, **When** the mapping step runs, **Then** the system MUST log an `AmbiguousMapping` event, mark the task as `skipped`, and flag it for manual review. *(See FR-011, US-1)*

### User Story 2 - Real-World Execution Validation (Priority: P2)

The researcher MUST be able to execute the generated symbolic action sequences on a real-world robot to measure the binary task completion rate, distinguishing between planner infeasibility and low-level controller failure.

**Why this priority**: This validates the "sim-to-real" bridge. Success in the symbolic planner is meaningless if the physical execution fails. This step provides the ground-truth success rate against which the null hypothesis is tested.

**Independent Test**: The system is tested by taking the output of the symbolic planner and running it in the real-world environment (the specific RoboDojo real-world benchmark suite) to record a binary pass/fail outcome for each task, with explicit logging of failure mode.

**Acceptance Scenarios**:

1. **Given** a discrete action sequence generated by the symbolic planner, **When** executed on the physical robot for a specific RoboDojo task, **Then** the system MUST record a binary outcome (Success/Failure) based on task completion criteria defined in the RoboDojo benchmark (object pose deviation ≤ 5 cm and orientation deviation ≤ 15°).  
2. **Given** the 18 real-world RoboDojo tasks, **When** the hybrid system (Symbolic Planner + Adapted Low-Level Controller) is run sequentially, **Then** it MUST produce a completion‑rate report for all 18 tasks within a total wall‑clock time of ≤ 4 hours. *(See SC-007, US-2)*  
3. **Given** a task failure, **When** the system logs the event, **Then** it MUST capture the specific step in the symbolic sequence where the failure occurred AND explicitly label it as either "Planner Infeasibility" or "Controller Execution Failure".  
4. **Given** a failure occurring mid‑sequence, **When** the failure is logged, **Then** the system MUST attempt to replan from the last successfully executed sub‑goal, log the replanning outcome, and if replanning is impossible, record the task as a hard failure. *(See FR-012, US-2)*

---

### User Story 3 - Comparative Statistical Analysis (Priority: P3)

The researcher MUST be able to statistically compare the success rates and compute overhead of the symbolic approach against the original RoboDojo baseline policies, and to run an ablation study over state‑representation granularity.

**Why this priority**: This addresses the research question directly ("To what extent..."). It transforms raw execution data into a scientific conclusion regarding the necessity of high-fidelity physics and the impact of representation detail.

**Independent Test**: The system is tested by running the statistical analysis module on the collected success rates and compute metrics, verifying that the output includes the correct test statistic, p‑value, effect size, and ablation results.

**Acceptance Scenarios**:

1. **Given** success‑rate data for the symbolic approach, the Neural Policy baseline, and the Oracle control across the 18 tasks, **When** the analysis module runs, **Then** it MUST perform an exact McNemar test (α = 0.05) and output a p‑value and odds‑ratio effect size. *(See FR-005, US-3)*  
2. **Given** compute metrics (CPU cycles, memory) for both approaches, **When** the analysis module runs, **Then** it MUST calculate the percentage reduction in compute overhead for the symbolic approach. *(See FR-007, US-3)*  
3. **Given** the system is executed in ablation mode with two representation levels (Full Affordance Graph vs. Simplified Connectivity Graph), **When** the analysis runs, **Then** it MUST report success‑rate and compute‑overhead metrics for each level, enabling a direct comparison. *(See FR-008, US-3)*  
4. **Given** the statistical plan, **When** the power analysis is performed, **Then** it MUST demonstrate that the test has ≥ 0.80 power to detect a medium effect size (Cohen's h = 0.5) with N = 18 paired tasks, and the analysis report must include this power statement. *(See FR-014, SC-012, US-3)*

---

### User Story 4 - Physics Fidelity Isolation Control (Priority: P4)

The researcher MUST be able to run a control experiment using a deterministic rule‑based verifier (Oracle) to isolate the impact of the symbolic abstraction from the low‑level controller's limitations.

**Why this priority**: This addresses the scientific soundness concern regarding the inability to isolate the "loss of physical fidelity" variable. It allows the researcher to quantify how much failure is due to the planner vs. the controller.

**Independent Test**: The system is tested by running the symbolic planner against the deterministic Oracle and comparing the success rate to the real‑world execution rate.

**Acceptance Scenarios**:

1. **Given** a set of symbolic plans generated by the planner, **When** executed against the deterministic Oracle, **Then** the system MUST record a success rate representing the theoretical maximum of the symbolic planner. *(See FR-010, US-4)*  
2. **Given** the success rates from the Oracle and the Real‑World execution, **When** the analysis module runs, **Then** it MUST calculate the "Physics Fidelity Gap" (difference between Oracle success rate and Real‑World success rate). *(See FR-010, SC-006, US-4)*

## Requirements

### Functional Requirements

- **FR-001**: System MUST convert RoboDojo visual observations into high-level semantic embeddings using a frozen, CPU‑efficient vision encoder (e.g., MobileViT) to strip continuous physics dynamics. (See US-1)  
- **FR-002**: System MUST map semantic embeddings into a discrete SymbolicState representing object affordances and connectivity, explicitly excluding continuous physics dynamics. (See US-1)  
- **FR-003**: System MUST implement a hierarchical policy where a high-level symbolic planner generates a sequence of discrete sub-goals based on a SymbolicState graph derived from semantic embeddings. (See US-1)  
- **FR-004**: System MUST integrate a low‑level controller using pre‑trained RoboDojo weights, adapted via a Sim‑to‑Real protocol, to execute generated sub-goals in the real‑world environment. (See US-2)  
- **FR-005**: System MUST perform an exact McNemar test (α = 0.05) to compare the success rates of the symbolic approach versus the original RoboDojo Neural Policy baseline, reporting p‑value and odds‑ratio effect size. (See US-3)  
- **FR-006**: System MUST log the specific step in the symbolic sequence where a real‑world execution failure occurs AND label the failure mode as "Planner Infeasibility" or "Controller Execution Failure". (See US-2)  
- **FR-007**: System MUST calculate and report the percentage reduction in compute overhead (CPU cycles and memory) compared to the GPU‑based baseline. (See US-3)  
- **FR-008**: System MUST support an ablation study mode that varies the level of detail in the state representation (e.g., full affordance graph vs. simplified connectivity graph). (See US-3)  
- **FR-009**: System MUST implement a Sim‑to‑Real Adapter or Fine‑tuning Protocol using a set of real‑world videos to adapt the low‑level controller for domain shift. (See US-2)  
- **FR-010**: System MUST execute a control experiment using a deterministic rule‑based verifier (Oracle) that checks symbolic action sequences against the ground‑truth task graph without invoking any physics simulation. (See US-4)  
- **FR-011**: System MUST detect ambiguous or non‑unique mappings from semantic embeddings to SymbolicState, log an `AmbiguousMapping` event, and flag the affected task for manual review. (See US-1)  
- **FR-012**: System MUST attempt to replan from the last successfully executed sub‑goal when a mid‑sequence real‑world failure occurs, log the replanning outcome, and record a hard failure only if replanning is impossible. (See US-2)  
- **FR-013**: System MUST evaluate the precision and recall of the embedding‑to‑SymbolicState mapping against a manually annotated ground‑truth dataset of at least 30 tasks, and report these metrics. (See US-1)  
- **FR-014**: System MUST perform a statistical power analysis for the McNemar test, targeting power ≥ 0.80 for a medium effect size, and include the result in the final report. (See US-3)  
- **FR-015**: System MUST report effect‑size measures (odds ratio) alongside p‑values for all statistical comparisons. (See US-3)  
- **FR-016**: System MUST evaluate the Neural Policy using the deterministic Oracle (Neural+Oracle) to isolate planning‑versus‑execution effects. (See US-4)  
- **FR-017**: System MUST obtain baseline GPU‑based compute metrics (cycles, memory, wall‑clock time) from the published RoboDojo benchmark numbers and use them for percentage‑reduction calculations. (See SC-002)  

### Key Entities

- **SemanticEmbedding**: High-level vector representation of visual observations, stripped of continuous physics dynamics.  
- **SymbolicState**: Discrete state in PDDL‑like format representing object affordances and connectivity.  
- **ActionSequence**: Ordered list of discrete sub-goals generated by the symbolic planner.  
- **ExecutionOutcome**: Binary record (Success/Failure) of a task execution in the real‑world environment, including failure‑mode label.  
- **ComputeMetric**: Record of CPU cycles, memory usage, and wall‑clock time for a specific task execution.  

## Success Criteria

### Measurable Outcomes

- **SC-001**: Task‑completion success rate is measured against the original RoboDojo Neural Policy baseline success rate to determine if symbolic abstraction suffices. (See US-3)  
- **SC-002**: Wall‑clock time to generate valid action sequences is measured against the GPU‑based baseline time to quantify computational savings. (See US-1)  
- **SC-003**: Memory usage and CPU utilization are measured against the standard RAM and CPU core constraints of the GitHub Actions free‑tier runner to ensure feasibility. (See US-1)  
- **SC-004**: The p‑value from the exact McNemar test is measured against the significance threshold of α = 0.05 to determine statistical significance of the difference. (See US-3)  
- **SC-005**: Catastrophic failure rate must be ≤ 1 of 18 tasks (≤ 5 %). (See US-3)  
- **SC-006**: The "Physics Fidelity Gap" (difference between Oracle success rate and Real‑World success rate) is measured to isolate the impact of low‑level controller limitations. (See US-4)  
- **SC-007**: Total wall‑clock time to execute all 18 real‑world tasks must be ≤ 4 hours. (See US-2)  
- **SC-008**: Power analysis must demonstrate ≥ 0.80 power to detect a medium effect size (Cohen's h = 0.5) with N = 18 paired tasks; the analysis report must include this statement. (See US-3)  

## Assumptions

- The RoboDojo dataset (a set of simulation task specifications and real‑world task videos) is accessible and the pre‑processing pipeline for semantic embeddings can run on a standard CPU without GPU acceleration.  
- A total of **42 simulation tasks** are available; **18** of these are selected for real‑world validation, matching the tasks used in US‑1 and US‑2.  
- The pre‑trained weights for the RoboDojo low‑level controller can be adapted via a fine‑tuning protocol to function effectively in the real‑world environment.  
- The symbolic abstraction layer (SymbolicState) is sufficient to represent the necessary object affordances and connectivity for the RoboDojo tasks without requiring continuous physics variables like friction or mass.  
- The McNemar exact test is appropriate for paired binary success outcomes across the 18 tasks.  
- The compute overhead of the symbolic planner (A* or MCTS) on a CPU will not exceed the time limit of the GitHub Actions free‑tier runner for the full set of tasks.  
- The semantic embeddings generated by the frozen MobileViT encoder will be robust enough to handle variations in lighting and object pose in the real‑world tasks.  
- The deterministic Oracle is a rule‑based verifier that checks symbolic sequences against the ground‑truth task graph; it does **not** invoke any physics simulation.  
- The statistical power analysis (FR‑014) will be performed using standard formulas for McNemar tests, targeting power ≥ 0.80.
