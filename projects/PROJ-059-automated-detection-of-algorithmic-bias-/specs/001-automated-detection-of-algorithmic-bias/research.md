# Research: Automated Detection of Algorithmic Bias in Public Code Repositories

## 1. Problem Statement & Hypothesis

**Hypothesis**: There is a statistically significant positive correlation between the frequency of demographic/stereotyping language in Python code artifacts (variables, comments) and the **sensitivity** of a simulated system to bias injection (i.e., the slope of fairness metric degradation as `injected_skew_magnitude` increases).

**Methodological Note**: This is an **observational study**. The "Outcome" is not a fixed fairness metric, but a **derived property** (sensitivity slope) of the repository's simulated model behavior.
- The simulation uses an independent `injected_skew_magnitude` parameter to generate a *family* of models.
- The "Bias Sensitivity Slope" is calculated as the linear regression coefficient of Fairness Metric vs. `injected_skew_magnitude`.
- This design tests whether "Textual Bias" predicts "System Fragility" (high slope), avoiding the tautology of correlating text with a random number. The outcome is a function of the repository's specific simulated logic, not the independent parameter itself.

## 2. Dataset Strategy

### 2.1 Predictor Data: Code Repositories
- **Source**: Public GitHub repositories (Python).
- **Acquisition**: Programmatic download via GitHub API (rate-limited) or direct `git clone` of curated list.
- **Constraint**: Must handle 500 repos within 6h/7GB RAM. Strategy: Stream processing (clone → parse → delete) to avoid disk bloat.
- **Validation**: Filter for Python files only; skip binary-only or non-Python repos (Edge Case).

### 2.2 Predictor Data: Sentiment Lexicon
- **Source**: VADER Sentiment Lexicon.
- **Verified URL**: ` (and variants).
- **Loading Strategy**: Use `datasets.load_dataset` with the verified URL. Extract `term` and `sentiment_compound`.
- **Usage**: Match normalized code tokens against this lexicon to compute "Textual Bias Score".
- **Citation**: Only use the verified URLs listed in the `# Verified datasets` block.

### 2.3 Outcome Data: Bias Sensitivity Slope
- **Source**: Generated locally via `numpy` and `scipy`.
- **Strategy**: For each repository, generate synthetic data with a **range** of `injected_skew_magnitude` values (e.g., 0.0, 0.1, 0.2, 0.3, 0.4).
- **Simulation**: For each skew level, generate domain-neutral synthetic data (Gaussian/Uniform) with controlled class imbalance.
- **Metric Calculation**: Compute Demographic Parity and Equalized Odds for each skew level using `fairlearn`.
- **Slope Derivation**: Fit a linear regression (Fairness Metric ~ Skew Magnitude). The **slope** is the outcome variable.
- **Independence Check**: Perform string-hash comparison (FR-015) between synthetic data seeds and code tokens to ensure zero overlap.

### 2.4 Validation Data: Manual Labels
- **Source**: Curated set of 200 comments manually labeled for stereotyping.
- **Strategy**: Generated via `tests/validation/` script or provided as a static CSV in `data/validation/`.
- **Purpose**: Validate VADER thresholds (FR-013) via Cohen's Kappa.

### 2.5 Error Injection Data
- **Source**: Curated set of 100 repos with known syntax errors (generated by test harness).
- **Purpose**: Validate error handling robustness (SC-005, SC-006).

## 3. Methodology & Statistical Rigor

### 3.1 Static Analysis (Predictor)
1. **AST Parsing**: Use Python `ast` module to extract variable names, function names, and string literals (FR-001).
2. **Normalization**: Convert `camelCase` and `snake_case` to token streams (e.g., `gendered_user_name` → `gendered`, `user`, `name`).
3. **Lexicon Matching**: Count matches against VADER demographic terms (FR-002).
4. **Sentiment Analysis**: Apply VADER to string literals to compute compound scores (FR-003).
5. **Aggregation**: Compute repository-level score as arithmetic mean of file scores (FR-009).

### 3.2 Simulation (Outcome)
1. **Parameter Sweep**: For each repository, iterate over `injected_skew_magnitude` ∈ {0.0, 0.1, 0.2, 0.3, 0.4} (FR-012).
2. **Data Generation**: Create synthetic dataset with `N=1000` samples, realistic class imbalance (FR-004) for each skew level.
3. **Bias Injection**: Apply the controlled `injected_skew_magnitude` to simulate bias in the prediction model (FR-005).
4. **Metric Calculation**: Compute Demographic Parity and Equalized Odds using `fairlearn` for each skew level.
5. **Slope Derivation**: Fit a linear regression model (Fairness Metric = β₀ + β₁ * Skew). The coefficient **β₁** is the "Bias Sensitivity Slope".
6. **Independence Verification (Step 3.2)**: Compute SHA-256 hash of the synthetic seed and the code token stream. Assert zero overlap (FR-015). Log result to `Independence Verification Log`.
7. **Noise Baseline**: Verify that for `injected_skew_magnitude=0`, the model yields a baseline disparity ≤ 0.01 (FR-011).

### 3.3 Correlation & Validation
1. **Correlation**: Compute Spearman's rank correlation (FR-006) between "Textual Bias Score" (X) and "Bias Sensitivity Slope" (Y).
2. **Multiple Comparison Correction**: Apply Bonferroni correction for all hypothesis tests (FR-007).
3. **Sensitivity Analysis**: Sweep alpha levels {0.01, 0.05, 0.10} and report flagged repo counts (FR-008).
4. **Threshold Validation**: Ensure Cohen's Kappa ≥ 0.6 for VADER vs. manual labels (FR-013).

### 3.4 Statistical Rigor Checklist
- **Multiple Comparisons**: Bonferroni correction applied to all p-values (FR-007).
- **Sample Size**: N=500 repos (power analysis deferred to pilot, but N=500 is standard for repo-scale studies).
- **Causal Framing**: Explicitly stated as **associational** only (Assumption). We claim text predicts *fragility*, not *causality* of bias.
- **Measurement Validity**: VADER validated against manual labels (FR-013).
- **Collinearity**: Predictors (variable names vs. comments) analyzed separately or with collinearity checks; no claim of independent effects if definitionally related.

## 4. Compute Feasibility

- **CPU-First**: All methods (AST parsing, VADER, `fairlearn` on synthetic data) are CPU-tractable.
- **Memory**: Streaming repo processing keeps RAM ≤ 2 GB per repo; total pipeline ≤ 7 GB.
- **Time**: A substantial number of repositories × (avg 5 min parsing + 5 min sim [5 skew levels]) [deferred]? **Correction**: Parsing is fast (seconds). Simulation of 5 points is ~1 min. 500 repos × 1.5 min = 12.5 hours. Optimization: Parallelize repo processing (multiprocessing) to fit 6h window.
- **GPU**: Not required. Synthetic data generation and fairness metrics are lightweight.

## 5. Decision Rationale

| Decision | Rationale |
|:--- |:--- |
| **Slope-Based Outcome** | Avoids the tautology of correlating text with a random number. Tests the hypothesis that "biased text" predicts "fragile systems" (high sensitivity). |
| **VADER Lexicon** | Standard, validated, and available via verified HuggingFace URL. |
| **Synthetic Outcome (Family)** | Ensures independence (Constitution VI) while allowing derivation of a repository-specific property (slope). |
| **Spearman Correlation** | Robust to non-normal distributions and zero-inflated bias scores. |
| **Bonferroni Correction** | Required by FR-007 to control family-wise error rate in multiple tests. |
| **CPU-Only** | Fits GitHub Actions free-tier constraints; no need for GPU escape hatch. |
