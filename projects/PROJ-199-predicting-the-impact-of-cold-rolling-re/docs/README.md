# Project Documentation: Predicting the Impact of Cold Rolling Reduction on Texture Evolution in FCC Metals

## Overview
This project implements an automated scientific pipeline to predict texture evolution in Face-Centered Cubic (FCC) metals (Aluminum, Copper, Nickel) under cold rolling reduction. The pipeline acquires EBSD data, extracts texture descriptors, trains predictive models, and validates results against physical constraints.

## Model Limitations
The predictive models in this pipeline are subject to the following limitations:

1. **Data Scope**: Models are trained exclusively on EBSD data for Al, Cu, and Ni. Extrapolation to other FCC metals (e.g., Austenitic Stainless Steel) is unvalidated and may yield unreliable predictions.
2. **Reduction Range**: Predictions are reliable only within the reduction range present in the training data (typically 0% to 80%). Predictions outside this range are flagged as "extrapolated" with reduced confidence, as the underlying physical mechanisms (e.g., transition from rolling to shear bands) may differ.
3. **Missing Microstructural Variables**: The current feature set focuses on reduction percentage and material type. Variables such as grain size, stacking fault energy (SFE), and initial texture are not explicitly modeled. The variance decomposition analysis (see `code/analysis/robustness.py`) quantifies the residual variance attributable to these missing factors.
4. **Symmetry Constraints**: While orientations are re-indexed to FCC symmetry, the models do not explicitly enforce crystallographic symmetry constraints on the output. The "Physics Check" module validates trends but does not guarantee physically permissible orientation distributions.

## Associational Framing
All findings and model outputs generated by this pipeline are **associational** in nature.

- **Correlation vs. Causation**: The models identify statistical relationships between cold rolling reduction and texture descriptors (e.g., Brass component volume fraction). They do not establish causal mechanisms.
- **Interpretation**: Trends observed (e.g., "Brass component increases with reduction") should be interpreted as observed associations consistent with known metallurgical physics, not as proof of specific dislocation slip mechanisms without further experimental validation.
- **Reporting**: The `code/analysis/physics_check.py` module explicitly frames findings as associational relationships. Users are advised to avoid language implying direct causation when reporting results derived solely from this pipeline.

## Sensitivity Analysis Methodology
To ensure model robustness, a sensitivity analysis is performed on the interpolation tolerance used during model validation.

### Procedure
1. **Parameter Sweep**: The interpolation tolerance parameter is swept across the set {0.01, 0.05, 0.1}.
2. **Metric Calculation**: For each tolerance value, the model is re-evaluated using k-fold cross-validation.
3. **Stability Check**: The variation in the coefficient of determination ($R^2$) across the swept tolerances is calculated.
4. **Acceptance Criteria**: The model is considered robust if the $R^2$ variation remains $\le 0.02$ across the tested range.

### Output
The results of this analysis are written to `data/processed/sensitivity_analysis.csv`, containing the $R^2$ and RMSE for each tolerance level.

## Testability (SC-001)
The testability of the pipeline, specifically regarding data availability (SC-001), is ensured by calculating the "total available" baseline dynamically:

1. **Source Discovery**: The `code/data/download.py` module scans the configured source repositories (e.g., HuggingFace datasets) for files matching the defined reduction levels for each metal.
2. **Deferred Handling**: If a specific reduction level is marked `[deferred]` in `research.md`, it is excluded from the "available" count but logged as a warning.
3. **Baseline Calculation**: The "total available" count is the sum of all valid files found for non-defered levels.
4. **Validation**: The pipeline proceeds if the available count > 0. If all levels for a metal are deferred or missing, the pipeline either fails loudly (if real data is strictly required) or falls back to synthetic generation (only for structural validation, as per T011/T012 logic).

This ensures that the testability metric reflects the actual data present in the source repositories rather than hardcoded assumptions.

## Running the Pipeline
See `quickstart.md` for end-to-end execution instructions.
To run specific modules:
```bash
# Data Acquisition
python code/data/download.py
python code/data/preprocess.py

# Feature Extraction
python code/features/export_descriptors.py

# Modeling
python code/models/train.py
python code/models/validate.py

# Analysis
python code/analysis/robustness.py
python code/analysis/physics_check.py
```
