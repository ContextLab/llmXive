## Unresolved concerns

- The plan states: 'Replace visual embedding layers with a randomly initialized discrete projection layer. This layer is trained alongside the rest of the model.' This creates a confound: if the model fails to converge or shows high error, it is impossible to distinguish whether the failure is due to the *modality shift* (discrete data) or the *random initialization* of the new layer. To isolate the effect of modality shift, the new layer should either be pre-trained on a proxy task, initialized with a heuristic (e.g., uniform mapping), or the baseline comparison must use a model with a *randomly initialized* continuous layer to ensure fair comparison.
- The plan defines 'Model Error' as 'Total MSE - Quantization Noise Floor'. This assumes the quantization noise is additive and independent of the model's prediction error. However, in a predictive model, quantization noise in the input propagates non-linearly through the temporal attention mechanism, potentially amplifying or dampening errors in ways not captured by a simple subtraction. The analytical noise floor calculation may not accurately represent the *effective* noise floor in the prediction space, leading to invalid 'Model Error' metrics and incorrect stability thresholds.
- The plan proposes a 'paired t-test' on error rates 'paired by (episode_id, timestep)'. However, the plan also specifies 'N=10 independent runs with different noise seeds'. If the noise is injected into the *input* data (as per Phase 1), then the 'ground truth' for the discrete model changes with every seed. You cannot pair a discrete prediction from Seed A with a continuous baseline from Seed A if the continuous baseline was trained on the *original* continuous data (which is static). The pairing logic is flawed: the baseline must be re-generated or the pairing must be at the 'run' level (comparing mean error of Run A discrete vs mean error of Run A continuous), not at the timestep level across different noise realizations.
- The plan injects Gaussian noise with std dev = 0.1 * quantization_step *after* quantization. This creates a 'double noise' effect: the quantization error (uniform distribution) plus the injected Gaussian noise. The plan does not clarify if the 'Quantization Noise Floor' calculation accounts for this combined noise distribution. If the noise floor is calculated based solely on quantization step size, the 'Model Error' will be artificially inflated by the injected noise, potentially causing the stability threshold to be reached prematurely (false positive for instability).
- FR-007 requires logging CPU utilization, peak RAM, and latency to `resource_profile.json`. The plan.md 'Technical Context' and 'Project Structure' sections mention resource profiling in `utils/logging.py` and `results/resource_profile.json`, but the 'Methodology' section (Phase 2) does not explicitly describe the mechanism for capturing these metrics (e.g., `psutil` usage, logging hooks) or how they are aggregated into the final artifact. The plan assumes this is handled but lacks the specific task description to ensure the FR is satisfied.
- FR-010 requires detecting 1-bit collapse and halting the run. The plan.md 'Methodology' Phase 1 mentions a 'Degeneracy Check' and '1-bit collapse detection' in `data/validator.py`. However, the plan does not explicitly state the *action* taken upon detection (e.g., 'raise exception', 'write error log', 'exit with code 1'). Without an explicit 'halt' or 'fail' action defined in the plan's workflow, the implementer might only log a warning, failing the FR requirement to 'halt the run'.
- SC-003 requires measuring computational feasibility against GitHub Actions Free Tier constraints. The plan.md 'Technical Context' lists the constraints (2 vCPU, 7GB RAM, 6h) and 'Compute Feasibility' discusses them, but the plan lacks a specific 'Validation' or 'Verification' step in the workflow that explicitly compares the logged metrics (from FR-007) against these thresholds to produce a pass/fail result for SC-003. The plan describes *generating* the data but not the *measurement* logic required to satisfy the success criterion.

The plan.md 'Methodology' Phase 3 describes 'Error Decomposition' and calculating the 'Quantization Noise Floor'. However, the plan does not explicitly define the formula or method for 'separating' them in the output (e.g., 'model_error = total_mse - noise_floor'). While implied, the lack of an explicit definition in the plan for how this separation is performed and recorded risks the implementer omitting the specific 'separation' logic required by the SC.

- Error Decomposition: 'Total MSE = Model Error + Quantization Noise Floor' is mathematically invalid for this setup. The 'Quantization Noise Floor' is calculated analytically from the input bit-depth (a constant), while the 'Total MSE' is the result of a non-linear model prediction on quantized inputs. The model error is not the residual of a linear subtraction; the quantization noise interacts with the model's non-linearities (attention, activation functions) to produce error that is not additive. Subtracting a theoretical floor from an empirical MSE to isolate 'Model Error' creates a tautological artifact that does not represent the true model capacity loss.
- Stability Threshold Definition: Defining the threshold as 'Model Error > 1.20 × Baseline Error' where 'Model Error' is derived via the invalid subtraction above (see previous concern) renders the threshold scientifically meaningless. If the 'Model Error' is artificially deflated by subtracting a constant noise floor, the ratio will be skewed, potentially masking actual instability or creating false positives. The baseline comparison must be against the *Total MSE* of the continuous model vs. the *Total MSE* of the discrete model, or a proper variance decomposition (e.g., ANOVA) must be used, not a simple arithmetic subtraction of a theoretical constant.
- Velocity Derivation: Computing velocities via finite differencing ($v_t = (pos_t - pos_{t-1}) / \Delta t$) on *quantized* position data introduces a systematic bias. Quantization error is non-uniform and discrete; finite differencing amplifies high-frequency quantization noise, creating a velocity signal that is dominated by quantization artifacts rather than true physical motion. This violates the assumption that the derived velocity is a valid proxy for the continuous state. The plan should either derive velocity from the *continuous* ground truth before quantization (if available) or explicitly model the quantization noise in the velocity derivation step, rather than treating the derived velocity as a clean input feature.
- Statistical Validation: The plan proposes a 'paired t-test... paired by (episode_id, timestep)'. This assumes independence of errors across timesteps within an episode, which is false for a temporal model (autoregressive error accumulation). The errors are serially correlated. A standard t-test will underestimate the variance and inflate the Type I error rate (false positives). The analysis must use a method that accounts for temporal autocorrelation, such as a mixed-effects model with random effects for episode, or a block-bootstrap approach, rather than a simple paired t-test on raw timestep errors.
