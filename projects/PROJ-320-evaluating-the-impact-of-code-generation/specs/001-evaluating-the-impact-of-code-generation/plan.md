# Implementation Plan: Evaluating the Impact of Code Generation on Code Review Quality Using LLMs

**Branch**: `001-evaluating-llm-code-review-impact` | **Date**: 2024-05-21 | **Spec**: `spec.md`
**Input**: Feature specification from `specs/001-evaluating-llm-code-review-impact/spec.md`

## Summary

This feature implements an observational study to determine if LLM-generated code alters code review metrics (comment density, resolution time, defect density) compared to human-authored code. The technical approach involves:
1.  **Data Acquisition**: Fetching PR metadata from GitHub APIs for `psf/requests`, `microsoft/vscode`, and `numpy/numpy`.
2.  **Classification**: Labeling PRs as `llm` or `human` using commit message signatures (e.g., "Generated by Copilot") and a secondary statistical detector (code entropy/n-gram analysis) trained on external data.
3.  **Metric Extraction**: Calculating review metrics, code complexity (cyclomatic complexity, LOC), and temporal covariates.
4.  **Statistical Analysis**: Performing **Mann-Whitney U tests** as the primary analysis (due to expected small N and non-normality) and t-tests as sensitivity analysis.
5.  **Validation**: Conducting a manual audit of a stratified sample to verify classification accuracy, using human judgment as ground truth and detector scores as validation metrics.

## Technical Context

**Language/Version**: Python 3.11  
**Primary Dependencies**: `requests`, `pandas`, `scipy`, `networkx` (for complexity), `matplotlib`, `seaborn`, `pyyaml`, `statsmodels` (for robust regression)  
**Storage**: Local JSON/CSV artifacts in `data/` (raw and processed), checksummed per Constitution.  
**Testing**: `pytest` for unit tests on classification logic and statistical calculations; integration tests for API rate-limit handling.  
**Target Platform**: Linux (GitHub Actions Runner).  
**Project Type**: Research Data Pipeline / Statistical Analysis.  
**Performance Goals**: Complete data acquisition and analysis within 6 hours on a 2-core/7GB RAM runner.  
**Constraints**: Strict adherence to GitHub API rate limits (batching, exponential backoff); memory usage < 7GB; no PII in artifacts.  
**Scale/Scope**: Up to 200 PRs total across 3 repositories; manual audit of ~10 PRs (or [deferred] if N_LLM < 10).

## Constitution Check

*Gates determined based on `constitution.md`:*

1.  **Reproducibility (Principle I)**:
    *   **Plan**: All random seeds for sampling and statistical resampling will be pinned in `code/utils/seeds.py`.
    *   **Plan**: External data (GitHub API) is fetched programmatically via `code/data/fetch_github.py` on every run; no static snapshots are committed as the source of truth.
    *   **Plan**: `requirements.txt` will pin exact versions of `pandas`, `scipy`, `statsmodels`, etc.

2.  **Verified Accuracy (Principle II)**:
    *   **Plan**: All citations in `research.md` regarding LLM detection methods or GitHub API limits will be linked to the specific URLs provided in the `# Verified datasets` block or official documentation.
    *   **Plan**: The Reference-Validator Agent will run against this plan before `research_accepted`, enforcing a **Title-token-overlap >= 0.7** threshold for all external citations.

3.  **Data Hygiene (Principle III)**:
    *   **Plan**: Raw JSON from GitHub will be saved to `data/raw/` with SHA-256 checksums recorded in `state/`.
    *   **Plan**: Derived CSVs (labeled, metrics) will be saved to `data/processed/` with new checksums.
    *   **Plan**: No PII (user emails) will be stored; only public usernames and PR IDs will be retained.

4.  **Single Source of Truth (Principle IV)**:
    *   **Plan**: All statistics in the final report will be generated by `code/analysis/statistical_tests.py` and `code/analysis/sensitivity_analysis.py` and traced to specific rows in `data/processed/results.json` (aggregated) and `data/processed/prs_metrics.csv` (raw).
    *   **Plan**: No hand-typed numbers in `paper/`.

5.  **Versioning Discipline (Principle V)**:
    *   **Plan**: Content hashes for `plan.md`, `research.md`, and `data-model.md` will be updated in `state/projects/PROJ-320-evaluating-the-impact-of-code-generation.yaml`.

6.  **API Rate-Limit and Batch Processing (Principle VI)**:
    *   **Plan**: `code/data/fetch_github.py` will implement batch processing (PRs processed in batches) and exponential backoff (max limited retries) as specified in the spec.
    *   **Plan**: The pipeline will include a "watchdog" to check elapsed time and exit gracefully if > 5.5 hours.

7.  **Automated Classification Validation (Principle VII)**:
    *   **Plan**: The pipeline includes a `code/audit/manual_validation.py` script.
 * **Plan**: **Audit Sample Size Rule**: The script will select a minimum number of PRs based on a predefined threshold or a fraction of $N_{LLM}$. If `N_LLM < 10`, it will audit [deferred] of the cohort.
    *   **Plan**: The audit logic will use **Human Expert Judgment** as the ground truth label and the **Secondary Detector Score** as the validation metric (satisfying SC-004).
    *   **Plan**: The final analysis script will block execution if the manual audit error rate (Human vs. Primary Signature) exceeds a predetermined threshold.

## Complexity Tracking

| Violation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|-------------------------------------|
| Secondary Statistical Detector (FR-007) | Required to avoid tautological classification (FR-002) and validate against the "Assumption about classification fidelity". | Relying solely on commit messages is insufficient due to potential false positives/negatives and the need for robust validation per Constitution Principle VII. |
| Manual Audit Loop (Principle VII) | Required to measure labeling error rate (<5%) before reporting results. | Automated-only validation cannot satisfy the "Verified Accuracy" requirement for a study relying on heuristic classification. |
| Batch Processing with Backoff (Principle VI) | Required to stay within GitHub API limits and 7GB RAM constraint. | Fetching all 200 PRs in one call risks rate-limiting (403) and memory spikes; streaming/batching is the only compliant approach. |
| **Mann-Whitney U as Primary Test** | Required due to expected small sample size (N<30) and non-normal distribution of review metrics. | T-tests (FR-004) are demoted to sensitivity analysis only; using them as primary would violate statistical rigor given the power constraints. |
| **Temporal Covariates** | Required to control for confounding factors (maintainer availability) in resolution time. | Ignoring time-of-day/day-of-week would conflate code quality with external scheduling factors. |
| **Sensitivity Analysis Script** | Required by FR-008 to re-define the cohort using only secondary detector results. | Skipping this would leave a critical robustness check unimplemented. |
