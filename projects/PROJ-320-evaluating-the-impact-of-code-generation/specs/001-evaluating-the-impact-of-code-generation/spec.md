# Feature Specification: Evaluating the Impact of Code Generation on Code Review Quality Using LLMs

**Feature Branch**: `001-evaluating-llm-code-review-impact`  
**Created**: 2024-05-21  
**Status**: Draft  
**Input**: User description: "Does the use of LLM-generated code significantly alter code review metrics (comment density, resolution time, defect density) compared to human-written code in public repositories?"

## User Scenarios & Testing

### User Story 1 - Data Acquisition and LLM Classification (Priority: P1)

**As a** research analyst, **I want** to automatically download the last 200 pull requests (or all available if fewer) from a prioritized list of repositories (`psf/requests`, `microsoft/vscode`, `numpy/numpy`) and classify them as "LLM-generated" or "human-authored" based on commit message patterns, bot signatures, and a secondary statistical detector, **so that** I can establish the two distinct cohorts required for comparative analysis.

**Why this priority**: This is the foundational step. Without a labeled dataset distinguishing LLM vs. human code, no statistical comparison can be performed. It directly addresses the "Data Acquisition" and "Data Filtering" steps of the methodology.

**Independent Test**: This can be fully tested by running the data extraction script against the GitHub API for the primary repository. If the LLM count is < 10, the script must automatically query the next repository in the list. Verification requires confirming that the output CSV contains exactly the target number of rows (up to 200), with a `source_type` column populated as either `llm` or `human` for every row, and that the classification logic correctly identifies known LLM bot users (e.g., `copilot-bot`, `github-copilot`) as `llm` while correctly excluding infrastructure bots (e.g., `dependabot`, `github-actions`) as `human`.

**Acceptance Scenarios**:

1. **Given** the `psf/requests` repository has at least 200 recent pull requests, **When** the data extraction script executes, **Then** a CSV file is generated containing metadata for up to 200 PRs with a `source_type` label assigned to each.
2. **Given** the primary repository yields fewer than 10 LLM-classified PRs, **When** the extraction script executes, **Then** the system automatically fetches PRs from the next repository in the fallback list until the target count (up to 200) is met or the list is exhausted.
3. **Given** a PR commit message contains a known LLM-bot signature (e.g., "Generated by Copilot" or specific bot user), **When** the classification filter runs, **Then** that PR is labeled `llm` in the dataset.
4. **Given** a PR commit message lacks any LLM indicators and is from a standard human user or an infrastructure bot (e.g., `dependabot`), **When** the classification filter runs, **Then** that PR is labeled `human` in the dataset.

### User Story 2 - Metric Extraction and Statistical Comparison (Priority: P2)

**As a** research analyst, **I want** to calculate review metrics (comment count, time-to-merge, review cycles) for each PR and perform independent two-sample t-tests comparing the `llm` and `human` groups, **so that** I can determine if there is a statistically significant difference in code review quality and efficiency.

**Why this priority**: This implements the core "Feature Extraction" and "Statistical Analysis" steps. It transforms raw data into the primary findings of the research question.

**Independent Test**: This can be fully tested by running the analysis script on a static, pre-saved dataset (snapshot of 200 PRs) and verifying that the output includes a JSON report containing t-statistic values, p-values, and effect sizes (Cohen's d) for comment density and time-to-merge between the two groups.

**Acceptance Scenarios**:

1. **Given** a labeled dataset of up to 200 PRs, **When** the metric extraction script runs, **Then** a table is produced with columns for `comment_count`, `time_to_merge_minutes`, and `review_cycles` for every PR.
2. **Given** the extracted metrics are grouped by `source_type`, **When** the statistical test runs, **Then** the output includes a p-value indicating the significance of the difference in mean comment density between LLM and human groups.
3. **Given** the statistical test results, **When** the script completes, **Then** the output indicates whether the null hypothesis (no difference) is rejected at a significance level of α = 0.05 and includes the calculated effect size.

---

### User Story 3 - Complexity Scoring and Visualization (Priority: P3)

**As a** research analyst, **I want** to score code complexity using standard metrics (cyclomatic complexity, lines of code) and generate boxplots comparing the distributions of review metrics, **so that** I can visualize the impact of LLM code patterns and control for code complexity as a confounding variable.

**Why this priority**: This addresses the "Quality Proxy" and "Visualization" steps. It provides necessary context for the statistical results (e.g., is higher comment density due to LLM code or just higher complexity?) and delivers the final visual artifacts for the report.

**Independent Test**: This can be fully tested by running the scoring and plotting script on the processed dataset and verifying that a PDF report is generated containing boxplots for comment density and time-to-merge, and that the complexity scores are numeric values derived from standard metrics.

**Acceptance Scenarios**:

1. **Given** the code diffs for the PRs, **When** the complexity scoring script runs, **Then** a `complexity_score` is generated for each PR without triggering out-of-memory errors on the CI runner.
2. **Given** the metric distributions for both groups, **When** the visualization script runs, **Then** a PDF is generated containing side-by-side boxplots for comment density and time-to-merge.
3. **Given** the complexity scores and review metrics, **When** the correlation analysis runs, **Then** the output includes a correlation coefficient indicating the relationship between code complexity and comment density.

### Edge Cases

- What happens if the GitHub API rate limit is hit during the download of PRs? (System must implement exponential backoff retry logic with a maximum of 3 retries).
- How does the system handle PRs where the commit message is ambiguous (neither clearly LLM nor clearly human)? (System must default to `human` but flag them in a `confidence_score` column if the signature match confidence is < 0.6. These flagged cases are included in the manual audit sample).
- What if the pre-trained `bert-base` model fails to load due to memory constraints on the runner? (System must fallback to a simpler heuristic-based complexity metric, e.g., lines of code + cyclomatic complexity, if memory usage > 6GB).
- What if the primary repository (`psf/requests`) has no LLM-generated PRs? (System must automatically proceed to the next repository in the fallback list `microsoft/vscode`, then `numpy/numpy`).

## Requirements

### Functional Requirements

- **FR-001**: System MUST download up to 200 pull requests from a prioritized list of repositories (`psf/requests`, `microsoft/vscode`, `numpy/numpy`) via the GitHub API and store the raw JSON payload. (See US-1)
- **FR-002**: System MUST classify each PR as `llm` or `human` based on commit message patterns and bot signatures. If the signature match confidence is < 0.6 or conflicting signatures exist, the system MUST label the PR as `human` and flag it with a `confidence_score` < 0.6. (See US-1)
- **FR-003**: System MUST calculate `comment_count`, `time_to_merge_minutes`, and `review_cycles` for every PR in the dataset. (See US-2)
- **FR-004**: System MUST perform independent two-sample t-tests to compare the mean values of review metrics between the `llm` and `human` groups, outputting p-values and effect sizes (Cohen's d). (See US-2)
- **FR-005**: System MUST compute a code complexity score for each PR using standard metrics (cyclomatic complexity, lines of code). If a pre-trained model is used, it MUST fallback to these standard metrics if memory usage > 6GB. (See US-3)
- **FR-006**: System MUST generate boxplots and histograms visualizing the distribution of comment density and time-to-merge for both groups. (See US-3)
- **FR-007**: System MUST run a secondary statistical detector (e.g., code entropy or n-gram anomaly score) on the code diff of all PRs initially classified as `llm` to confirm non-human patterns, ensuring the label is not purely tautological. (See US-1, US-2)
- **FR-008**: System MUST include a sensitivity analysis in the final report where the `llm` cohort is re-defined using only the secondary detector (FR-007) results to verify the robustness of the primary findings. (See US-2)

### Key Entities

- **PullRequest**: Represents a single PR, containing attributes: `pr_id`, `source_type` (llm/human), `comment_count`, `time_to_merge_minutes`, `review_cycles`, `complexity_score`, `confidence_score`.
- **StatisticalResult**: Represents the outcome of a hypothesis test, containing attributes: `metric_name`, `group_a_mean`, `group_b_mean`, `t_statistic`, `p_value`, `effect_size`, `is_significant`.

## Success Criteria

### Measurable Outcomes

- **SC-001**: The difference in mean comment density between LLM and human groups is measured against the statistical significance threshold (p < 0.05) to determine if LLM code attracts significantly more/fewer comments. (See FR-004, US-2)
- **SC-002**: The difference in mean time-to-merge between LLM and human groups is measured against the statistical significance threshold (p < 0.05) to determine if LLM code accelerates or delays the review process. (See FR-004, US-2)
- **SC-003**: The correlation between code complexity scores and review metrics is measured against a baseline of zero to assess if complexity confounds the relationship between LLM code and review outcomes. (See FR-005, US-3)
- **SC-004**: The classification accuracy of the LLM detection logic is measured against a manually validated stratified random sample of 20 PRs (10% of the expected LLM cohort, minimum 10) to ensure the labeling error rate is < 5%. The manual audit must use a defined checklist (e.g., presence of boilerplate patterns) AND the secondary detector score (FR-007) as ground truth, distinct from the automated signature filter. (See FR-002, FR-007, US-1)

## Assumptions

- **Assumption about data availability**: The prioritized list of repositories (`psf/requests`, `microsoft/vscode`, `numpy/numpy`) contains sufficient PRs with identifiable LLM-generated content (e.g., from Copilot or similar bots) to form a statistically viable sample size for the `llm` group (minimum 10). If the total LLM count across all repos is < 10, the analysis will be underpowered, and results will be noted as exploratory.
- **Assumption about classification fidelity**: Commit messages, bot signatures, and the secondary statistical detector (FR-007) are valid proxies for "LLM-generated code." This assumes that human-authored PRs do not frequently mimic LLM patterns in a way that triggers the secondary detector, and that LLM-generated PRs do not always hide their origin. Ambiguous cases (confidence < 0.6) are conservatively labeled as `human` and included in the manual audit.
- **Assumption about computational constraints**: The complexity scoring script (using standard metrics or a fallback model) can be executed on a GitHub Actions runner with 7 GB RAM and 2 CPU cores without exceeding the 6-hour job limit, provided the input data is processed in batches.
- **Assumption about metric validity**: `time_to_merge_minutes` is a valid proxy for "resolution time" and `comment_count` is a valid proxy for "comment density," assuming that the time-to-merge is driven primarily by the review process rather than external factors (e.g., waiting for CI builds or maintainers' availability).
- **Assumption about statistical framing**: The study is observational (no random assignment of code to LLM or human generation). Therefore, any significant differences found will be framed as **associational** rather than causal in the final report.
- **Assumption about threshold justification**: A significance level of α = 0.05 is used as the standard community threshold for statistical significance. No multiple-comparison correction (e.g., Bonferroni) is applied beyond the primary metrics (comment density, time-to-merge) as the number of hypotheses is limited to 2-3 primary comparisons, but the limitation is acknowledged in the discussion.
- **Assumption about selection bias**: The study acknowledges that developers who use LLMs may not always tag their commits, and bots may generate code that is heavily modified by humans. The inclusion of the secondary detector (FR-007) and sensitivity analysis (FR-008) is designed to mitigate this bias.
