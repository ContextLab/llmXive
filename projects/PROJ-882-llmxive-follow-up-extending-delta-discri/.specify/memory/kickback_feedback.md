## Unresolved concerns

- The plan defines 'Semantic Similarity' as 'cosine similarity between the token's context and a reference set... using a separate frozen embedding model'. However, FR-003 in spec.md explicitly requires 'cosine similarity on the Llama-3-8B last-layer embedding space'. Using a separate model (e.g., MiniLM) violates the 'Static-Input Independence' principle if the hypothesis is about Llama-3-8B's internal state, as the features would not represent the specific model's semantic space. If the hypothesis is general, the spec must be clarified to allow external models; otherwise, this creates a construct validity failure where the predictor measures a different semantic space than the oracle.
- The plan proposes using 'n-grams' and 'POS tags' as features. DelTA coefficients are token-level gradients. N-gram counts are typically sentence-level or window-level aggregates. The plan fails to specify how these aggregate features are mapped to individual tokens (e.g., centering, sliding window, or token-specific counts). Without a defined mapping strategy, the feature vector dimensionality and alignment with the target (token-level coefficient) are undefined, making the regression task ill-posed.
- The power analysis assumes '~10,000 data points' (500 examples * 20 tokens) are independent. However, tokens within a single GSM8K example are highly correlated (contextual dependency). Treating them as independent samples inflates the effective sample size and invalidates the p-value from the permutation test. The analysis must account for clustering at the example level (e.g., using cluster-robust standard errors or aggregating to example-level metrics) to avoid false positives.
- The plan states: 'If the CPU run fails... auto-offload to a Kaggle GPU'. While this addresses feasibility, it introduces a confound: the quantization (8-bit) required to fit the model on 16GB VRAM may alter the gradient magnitudes compared to the full-precision CPU run (if it had succeeded). If the 'Oracle' values differ based on the hardware path (CPU vs. GPU-quantized), the ground truth is not stable. The plan must specify that the quantization strategy is fixed and validated to ensure the 'Oracle' is consistent regardless of the execution path.
- FR-003 requires 'semantic similarity scores... using cosine similarity on the Llama-3-8B last-layer embedding space of those traces.' The plan (Phase 3) states features are extracted using 'a separate embedding model (e.g., sentence-transformers/all-MiniLM-L6-v2)'. This contradicts the spec's requirement to use the Llama-3-8B embedding space for the reference set similarity calculation, potentially violating the specific feature definition in FR-003.
- FR-002 mandates a subset of 'at least 500 examples'. The plan (Phase 1) asserts 'min 500 examples', but the 'Compute Feasibility Note' and 'Complexity Tracking' suggest a fallback to a 'smaller subset' or '8-bit quantization' if the 8B model fails. The plan does not explicitly state that the 500-example minimum is a hard constraint that must be met even if it requires the 'GPU escape hatch' or extended runtime, creating ambiguity on whether the FR-002 count requirement is flexible.
- SC-005 requires measuring variance against a threshold of > 1e-9. The plan mentions 'Validate variance > 1e-9' in Phase 2, but does not explicitly define the failure mode or the specific action (e.g., 'abort pipeline', 'retry with different seed') if this threshold is not met, whereas the spec implies a strict validation gate.
- The plan assumes running Llama-3-8B gradient backpropagation on a CPU-only GitHub Actions runner (2 CPU, 7GB RAM) or auto-offloading to Kaggle. Llama-3-8B requires ~16GB+ VRAM for 8-bit quantization and significantly more for full precision backprop. The 'GPU escape hatch' to Kaggle (16GB VRAM) is insufficient for 8B model backpropagation (which typically requires A100 40GB+ or multi-GPU setups for stable gradients). The proposed compute path is physically infeasible for the stated model size and operation, rendering the core Oracle generation step impossible as designed.
- The plan proposes using Llama-3-8B for the Oracle step but acknowledges CPU limits. The fallback to Kaggle (16GB VRAM) is cited as a solution. However, 8B parameter models with gradient backpropagation (required for DelTA) cannot fit in 16GB VRAM even with 8-bit quantization due to the memory overhead of storing gradients and optimizer states. The dataset (GSM8K) is appropriate, but the model/compute pairing is wrong for the required operation.
- The plan states: 'using a separate embedding model... to avoid circularity'. It does not cite the specific model (e.g., 'sentence-transformers/all-MiniLM-L6-v2') or provide a URL/DOI for this resource. While the upstream resolver guarantees URL reachability for *cited* datasets, this resource is mentioned as a tool dependency without a formal citation block or inline link, making it impossible to verify if the 'separate' model is actually distinct from the oracle or if it is a valid, accessible resource.
- The plan states 'No GPU access for Oracle/Training (CPU-only)' but immediately contradicts this in the 'Compute Feasibility Note' by allowing an 'auto-offload to a Kaggle GPU'. This violates Constitution Principle VII (Oracle Ground-Truth) which mandates coefficients be generated via 'real-time gradient backpropagation' on the 'specified' model. If the CPU run fails, the plan does not specify if the 'specified' model (Llama-3-8B) can actually run on the fallback GPU without architectural changes (e.g., quantization) that might alter the gradient signal. The plan must explicitly define the fallback hardware constraints to ensure the 'Oracle' remains the same algorithm on the same model, not a different approximation.
- The plan states features are computed using 'a separate embedding model... not the oracle's forward pass'. However, the Spec (FR-003) and Constitution (Principle VI) explicitly require semantic similarity to be calculated using 'Llama-3-8B last-layer embedding space'. The plan's description of using a 'separate frozen embedding model (e.g., sentence-transformers)' contradicts the Spec and Constitution. This is a critical violation of the 'Static-Input Independence' principle as defined in the project's own requirements, potentially invalidating the hypothesis test if the embedding space differs from the oracle's.
- The plan mentions 'Validate variance > 1e-9' but does not explicitly reference the specific contract file (`oracle_output.schema.yaml`) or the data model entity (`delta_coefficient`) that enforces this check. The plan should explicitly name the method to ensure it aligns with the requirement to classify null results.
- Circular Validation via Shared Embedding Space: The plan defines 'semantic similarity' features using 'Llama-3-8B last-layer embedding space' (Spec FR-003) while the Oracle target (DelTA Coefficients) is derived from the *same* Llama-3-8B's gradient backpropagation. Since DelTA coefficients are mathematically determined by the model's internal representations (gradients of loss w.r.t. hidden states), and the predictor uses those same hidden states (via embeddings) as input, the validation target is definitionally dependent on the predictor. This creates a tautological correlation where the model predicts the signal it was derived from, invalidating the hypothesis test of 'emergent vs. static' properties.
- Independence Violation in Feature Extraction: The plan states features are 'strictly external' but then specifies using 'Llama-3-8B last-layer embedding space' for semantic similarity. If the Oracle (DelTA) and the Feature Extractor both rely on the forward pass of the *same* model instance (Llama-3-8B), the 'static' features are not independent of the 'dynamic' oracle. The DelTA signal is a function of the model's internal state; using that state (even just the embedding) as a predictor guarantees a non-zero correlation, rendering the 'emergent' hypothesis untestable.
- Contradictory Independence Constraint: FR-003 forbids using 'contextual embeddings from the oracle model' but simultaneously mandates using 'Llama-3-8B last-layer embedding space' for semantic similarity. This is a logical contradiction. If the embeddings are from the oracle model, they are forbidden. If they are from a different model, the plan must specify a distinct, frozen embedding model (e.g., Sentence-BERT) to ensure true independence. As written, the plan allows the predictor to 'cheat' by using the oracle's own internal representation as a feature.
