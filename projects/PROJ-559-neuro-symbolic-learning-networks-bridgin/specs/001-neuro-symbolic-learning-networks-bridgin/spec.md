# Feature Specification: Neuro‑Symbolic Learning Networks: Bridging Neural and Symbolic Reasoning in Education

**Feature Branch**: `[PROJ-559-neuro-symbolic]`  
**Created**: 2026‑06‑24  
**Status**: Draft  
**Input**: User description: "Implement a lightweight neuro‑symbolic explanation framework, generate neural‑only, symbolic‑only, and neuro‑symbolic explanations for mathematics/logic problems, simulate student responses, and compare reasoning accuracy, response time, and self‑reported comprehension across the three conditions."

## User Scenarios & Testing *(mandatory)*

### User Story 1 – Generate and Deliver Explanations (Priority: P1)

A researcher wants to obtain three types of explanations (neural‑only, symbolic‑only, neuro‑symbolic) for each problem in the ASSISTments/Khan Academy dataset and present one of them to a simulated student.

**Why this priority**: Without reliable generation and delivery of explanations the entire comparative study cannot proceed.

**Independent Test**: Run the explanation generator on a single problem and verify that three distinct explanation files are produced and displayed in the simulated‑student UI.

**Acceptance Scenarios**:

1. **Given** a problem ID from the dataset, **When** the system is invoked with the "neural‑only" mode, **Then** it outputs a natural‑language explanation generated by the fine‑tuned LLM and stores it as `explanation_neural.txt`.
2. **Given** the same problem ID, **When** the system is invoked with the "neuro‑symbolic" mode, **Then** it outputs a hybrid explanation that combines the LLM narrative with a formal symbolic trace and stores it as `explanation_neuro-symbolic.txt`.

---

### User Story 2 – Simulate Student Interaction (Exploratory) (Priority: P2)

A researcher needs to collect simulated student responses (answer correctness, response time, and self‑reported comprehension) for each explanation condition **as an exploratory step**. Primary causal claims will be based on real‑student data (see FR‑010 and FR‑011).

**Why this priority**: The simulator provides rapid hypothesis generation and helps identify plausible effect directions before costly human data collection.

**Independent Test**: Execute the simulation on one problem‑explanation pair and verify that answer correctness, elapsed time, and a 1‑5 Likert rating are logged.

**Acceptance Scenarios**:

1. **Given** an explanation displayed to the BKT‑based student simulator, **When** the simulator submits an answer, **Then** the system records a binary correctness flag, the time elapsed (in seconds, rounded to the nearest 0.1 s), and a 1‑5 Likert rating for perceived comprehension.

---

### User Story 3 – Run Comparative Analysis (Priority: P3)

A researcher wants to run a mixed‑effects regression across all collected data to compare the three explanation conditions on reasoning accuracy, response time, and comprehension.

**Why this priority**: This story delivers the empirical result that addresses the research question, using **real‑human data** as the primary evidence; simulated data are reported only as exploratory checks (see SC‑009).

**Independent Test**: Trigger the analysis script on a pre‑populated CSV of ≥ 1 000 records and verify that it produces a regression table and effect‑size estimates for each pairwise condition comparison.

**Acceptance Scenarios**:

1. **Given** a CSV containing student‑simulation logs for all three conditions, **When** the analysis pipeline is executed, **Then** it outputs (a) a mixed‑effects model summary, (b) Cohen's d effect sizes with 95% confidence intervals for each pairwise comparison, (c) a concise results markdown file, and (d) a summary table of exploratory simulation diagnostics (see SC‑009).

---

### User Story 4 – CI Resource Limits (Priority: P2)

A CI engineer must ensure that the entire pipeline runs within the free‑tier GitHub Actions runner resources.

**Why this priority**: FR‑008 (CPU/memory limits) currently has no story anchor; this story provides the necessary context.

**Independent Test**: Run the full CI workflow on a fresh runner and verify that CPU usage remains within a modest multi‑core range and memory stays within a reasonable bound.

**Acceptance Scenarios**:

1. **Given** the CI job executing the full pipeline, **When** resource monitoring is enabled, **Then** the peak CPU usage is ≤ 2 cores and peak memory usage is ≤ 7 GB.

---

### User Story 5 – Human Pilot Validation (Priority: P3)

A researcher collects a small set of real‑student interactions to calibrate the BKT simulator and verify that simulated outcomes are not biased by explanation condition.

**Why this priority**: Addresses scientific‑soundness concerns about circular validation and reliance on simulation alone. This calibration must occur BEFORE the full simulation run to avoid circularity.

**Independent Test**: Collect data from ≥ 50 human participants across the three explanation conditions, compare simulator predictions to human outcomes, and confirm that calibration metrics (e.g., RMSE) meet a predefined threshold (≤ 0.15).

**Acceptance Scenarios**:

1. **Given** a human pilot dataset, **When** the calibration routine runs, **Then** it produces calibration statistics showing (a) RMSE difference across explanation conditions ≤ 0.02, (b) absolute RMSE ≤ 0.15, and (c) a TOST equivalence test (90% CI) confirms the difference is within the ±0.02 margin (p ≥ 0.10 for non‑equivalence).

---

### User Story 6 – Handle Dataset Download Failures (Priority: P2)

A CI engineer needs the pipeline to fail gracefully if the public ASSISTments or Khan Academy datasets cannot be downloaded within the CI timeout.

**Why this priority**: Guarantees robustness of the workflow and directly anchors FR‑007.

**Independent Test**: Simulate a network timeout during dataset download using the mock URL ` Name or service not known)"))] and verify that the CI job aborts with exit code 1 and logs a clear error message indicating which dataset failed and that the configurable timeout (default 300 s) was exceeded.

**Acceptance Scenarios**:

1. **Given** a forced download failure via the mock URL, **When** the CI job reaches the download step, **Then** it exits with exit code 1 and logs a clear error message such as "ERROR: Failed to download [dataset name] after 300 seconds – aborting pipeline."

---

### User Story 7 – Integrate Real‑Student Data into Final Analysis (Priority: P2)

A researcher must incorporate real‑student interaction data (≥ 200 participants) into the final comparative analysis to ensure scientific validity.

**Why this priority**: Addresses the scientific‑soundness concern that simulation alone cannot answer the research question about real learners. Human validation is required to support generalizable claims per educational research methodology standards.

**Independent Test**: Append a CSV of ≥ 200 human interaction records to the simulated logs and rerun the analysis pipeline; verify that the regression model includes a `data_source` fixed effect and that effect‑size estimates are reported for the combined dataset.

**Acceptance Scenarios**:

1. **Given** a merged dataset of simulated + real interactions, **When** the analysis script runs, **Then** the output includes a term for `data_source` (simulated vs. real) and shows that primary condition effects remain statistically significant (p < 0.05) in the combined analysis.

### Edge Cases

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST ingest problem statements and meta‑data from the public ASSISTments and Khan Academy datasets (downloaded automatically by the CI workflow). (See US-1)
- **FR-002**: System MUST generate **three** distinct explanation artifacts per problem: `neural`, `symbolic`, and `neuro-symbolic`, storing them as `explanation_neural.txt`, `explanation_symbolic.txt`, and `explanation_neuro-symbolic.txt` respectively. (See US-1)
- **FR-003**: System MUST present a selected explanation to the BKT‑based student simulator via a deterministic API call. (See US-2) *Note: this interaction is exploratory only; causal claims rely on real‑human data (FR‑010, FR‑011).*
- **FR-004**: System MUST record for each interaction (simulated **or** human) the following fields: (a) answer correctness (binary), (b) response time (seconds, measured with appropriate precision), and (c) self‑reported comprehension on a 5‑point Likert scale. (See US-2)
- **FR-005**: System MUST aggregate logs into a single CSV file with columns `problem_id`, `condition`, `student_id`, `correct`, `rt_seconds`, `comprehension_rating`, `prior_knowledge_score`, `difficulty`, `data_source`. (See US-2)
- **FR-006**: System MUST execute a mixed‑effects regression (using `lme4` or equivalent) that includes fixed effects for **explanation condition**, **prior‑knowledge score**, and **problem difficulty**, random intercepts for **problem_id** and **student_id**, and compute Cohen's d effect sizes with 95% confidence intervals for each pairwise condition comparison. (See US-3)
- **FR-007**: System MUST fail gracefully with a clear error message if any external dataset cannot be downloaded within the configurable timeout (default 300 seconds). (See US-6)
- **FR-008**: System MUST limit total CPU usage to ≤ 2 cores and memory to ≤ 7 GB to stay within the free‑tier GitHub Actions runner constraints. (See US-4)
- **FR-009**: System MUST simulate at least **2 000** students per explanation condition to achieve stable statistical estimates for the simulated analysis. (See US-2) *Exploratory only; not used for primary inference.*
- **FR-010**: System MUST calibrate the BKT‑based student simulator against a human pilot dataset of ≥ 50 participants, ensuring that (a) RMSE difference across explanation conditions ≤ 0.02, (b) absolute RMSE ≤ 0.15, and (c) a TOST equivalence test (90% CI) confirms the difference lies within ±0.02 (p ≥ 0.10). Calibration must occur BEFORE the full simulation run. (See US-5)
- **FR-011**: System MUST incorporate real‑student interaction data from ≥ 200 participants into the final comparative analysis, and the analysis must include a `data_source` fixed effect distinguishing simulated from real records. (See US-7)
- **FR-012**: System MUST sample problems stratified across both ASSISTments and Khan Academy sources and include `dataset_source` as a covariate in the regression to mitigate single‑source bias. (See US-1)
- **FR-017**: System MUST enforce a configurable explanation‑generation timeout (default set to a reasonable duration, e.g., several minutes); if exceeded, it aborts generation for that problem, logs a clear timeout error, and proceeds to the next problem. (See US-4)
- **FR-018**: System MUST detect missing or corrupt problem records, log a warning, skip the affected entry, and continue processing the remaining dataset. (See US-4)
- **FR-019**: System MUST validate that comprehension ratings are integers 1‑5; non‑numeric or out‑of‑range values trigger a validation error log and the record is omitted from the aggregated CSV. (See US-4)
- **FR-020**: System MUST treat all simulation‑generated interaction data as *exploratory diagnostics* and must NOT be used for primary hypothesis testing; the final inferential conclusions shall be based solely on real‑human data. (See US-3)
- **FR-021**: System MUST ensure that the unified problem set contains at least **[deferred]** of problems from each source (ASSISTments, Khan Academy) to guard against source‑specific bias. (See US-1)
- **FR-022**: System MUST run the Reference‑Validator Agent on all external dataset URLs before pipeline execution, using the Constitution‑mandated `CITATION_TITLE_OVERLAP_THRESHOLD` of 0.8; if any URL fails validation, the pipeline aborts with a clear error. (See US-6)

### Key Entities *(include if feature involves data)*

- **Problem**: Represents a single mathematics or logic exercise; key attributes are `problem_id`, `prompt_text`, `solution`, `dataset_source`.
- **Explanation**: Represents an artifact generated for a problem under a specific condition; attributes include `condition` (`neural`, `symbolic`, `neuro-symbolic`) and `content`.
- **SimulationLog**: Captures a single simulated (or human) student interaction; attributes are `problem_id`, `condition`, `student_id`, `correct`, `rt_seconds`, `comprehension_rating`, `prior_knowledge_score`, `difficulty`, `data_source`.

## Success Criteria *(mandatory)*

### Measurable Outcomes

> Planning docs state *what* will be measured and the *source/reference* it is measured against; defer specific empirical values (counts, dataset sizes, measured quantities, percentages) to the implementation/research phase.

- **SC-001**: ≥ 95 % of problems in the selected subset have successfully generated all three explanation types without runtime errors.
- **SC-002**: The analysis pipeline completes on a dataset of **≥ 5 000** logged interactions and produces a regression table (no missing coefficients).
- **SC-003**: Reported effect‑size 95% confidence‑interval width for the primary comparison (neuro‑symbolic vs. neural‑only) is ≤ 0.20, indicating sufficient precision for interpretation. (See US-3)
- **SC-004**: The analysis runs on the combined simulated + real dataset and reports p‑values and Cohen's d effect sizes for the primary condition comparison. (See US-7)
- **SC-005**: ≥ 99 % of simulated interaction logs contain all required fields; the distribution of response times covers a broad range with no gaps larger than 5 s (histogram bin width = 1 s, no more than 2 consecutive empty bins). (See US-2)
- **SC-006**: During CI execution, peak CPU usage does not exceed 2 cores and peak memory usage does not exceed 7 GB; these metrics are captured and reported in the CI job summary. (See US-4)
- **SC-007**: Calibration on the human pilot dataset yields (a) RMSE difference across explanation conditions ≤ 0.02, (b) absolute RMSE ≤ 0.15, and (c) TOST equivalence test (90% CI) confirms the difference lies within ±0.02 (p ≥ 0.10). (See US-5)
- **SC-008**: If a dataset download exceeds the configurable timeout (default 300 s), the CI job aborts with exit code 1 and logs a clear error message identifying the failed dataset and timeout duration. (See US-6)
- **SC-009**: Exploratory simulation diagnostics (from FR‑020) are reported in the CI summary, showing that ≤ 2 % of problems encounter explanation‑generation timeouts, ≤ 1 % have missing/corrupt records, and ≤ 0.5 % have invalid comprehension ratings. These figures are logged but not used for inferential claims. (See US-2, US-3)
- **SC-010**: Explanation‑generation timeout events (FR‑017) occur for ≤ 2 % of problems; counts are reported in the CI summary. (See US-4)
- **SC-011**: Missing or corrupt problem records (FR‑018) are ≤ 1 % of total; counts are reported. (See US-4)
- **SC-012**: Non‑numeric or out‑of‑range comprehension ratings (FR‑019) are ≤ 0.5 % of records; such records are excluded and logged. (See US-4)

## Assumptions

- Public ASSISTments and Khan Academy datasets are freely downloadable and fit within the modest CPU and memory limits of the continuous integration environment.
- A distilled 1 B‑parameter LLM can generate a neural‑only explanation for a problem in ≤ 2 seconds on the free‑tier runner.
- The BKT implementation **accurately approximates real student learning trajectories for the purposes of exploratory hypothesis generation**; it is **calibrated against a human pilot dataset (see FR‑010) before any simulation runs** and **is not used for primary causal inference**.
- All statistical analyses are performed in R (version ≥ 4.3) or Python (statsmodels ≥ 0.14) available on the CI image.
- No GPU resources are required; inference is performed on CPU only.
- The human pilot validation (≥ 50 participants) will be conducted **before** the full simulation run and its results incorporated before the final regression analysis; an additional larger real‑student dataset (≥ 200 participants) will be gathered for the final analysis (see FR‑011).
- Human pilot and final real‑student data are sourced from the publicly available “EdTech Human Learning Corpus” (current version) with documented provenance, satisfying reproducibility requirements.
- Problem sampling is stratified across both datasets; `dataset_source` is used as a covariate to control for single‑source bias (FR‑012) and the unified set contains at least 30 % of problems from each source (FR‑021).
- The Reference‑Validator Agent will be invoked automatically at pipeline start to verify all external URLs, using a title‑overlap threshold of 0.8 as mandated by the Constitution (see FR‑022).
