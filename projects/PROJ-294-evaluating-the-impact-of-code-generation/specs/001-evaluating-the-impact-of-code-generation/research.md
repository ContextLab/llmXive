# Research: Evaluating the Impact of Code Generation Models on Code Testability

## Summary

This research investigates whether code generated by Large Language Models (LLMs) exhibits different **testability** characteristics compared to human-written reference solutions. The study utilizes the HumanEval benchmark as the ground truth and employs a CPU-first statistical pipeline to ensure feasibility on free-tier CI runners.

**Key Construct Definition**:
- **Testability**: Operationalized as **Mutation Score** (resistance to perturbation via `mutmut`). This measures the code's ability to detect faults, distinct from passing the original test suite.
- **Correctness**: Operationalized as **Pass Rate** (binary pass/fail on HumanEval tests).
- **Complexity**: Operationalized as Cyclomatic Complexity and Halstead Volume (static metrics).

## Methodology

### 1. Code Generation (FR-002, FR-009)
- **Models**:
 - **Primary**: `Salesforce/codegen-mono-350M` (CPU-tractable).
 - **Sensitivity**: `CodeLlama-7b` (via GPU Escape Hatch).
- **GPU Escape Hatch**: If `GENERATE_WITH_GPU` is set, the pipeline triggers a remote Kaggle kernel to run `CodeLlama-7b` (8-bit quantized). If this fails or the flag is unset, the pipeline **automatically falls back** to `codegen-mono-350M` to ensure FR-009 is implemented.
- **Process**: For each task in HumanEval, construct the prompt from `prompt` + `entry_point`.
- **Retry Logic**: Implement exponential backoff for API failures (A limited number of retries).
- **Output**: Store generated code in `data/analysis/model_outputs/` with a unique filename per `task_id`.

### 2. Metric Calculation (FR-003, FR-005)
- **Complexity**: Use `radon` to calculate Cyclomatic Complexity (CC) for both human and LLM code.
- **Halstead Volume**: Calculate Halstead metrics using `radon`'s Halstead module.
- **Testability (Mutation Score)**: Use `mutmut` to generate mutants of the code and run the HumanEval test suite against them. The **Mutation Score** (percentage of mutants killed) is the primary metric for testability.
- **Correctness (Pass Rate)**: Use `coverage.py` to execute the `test` string from HumanEval against the generated code. Record `pass_rate` (0.0 or 1.0).
- **Collinearity Note**: Complexity and Halstead volume are often correlated. The analysis will treat these as **covariates** in a regression model predicting Mutation Score, not as independent primary outcomes.

### 3. Statistical Analysis (FR-004, FR-008)
- **Hypothesis**: $H_0$: There is no difference in testability (Mutation Score) and correctness (Pass Rate) between Human and LLM code.
- **Tests**:
 - **Wilcoxon Signed-Rank Test**: For paired continuous metrics (Complexity, Mutation Score).
 - **McNemar's Test**: For paired binary outcomes (Pass/Fail).
 - **Fisher's Exact Test**: If sample sizes are small (N < 25).
 - **Permutation Test**: As a robustness check for non-parametric distributions.
- **Multiple Comparison Correction**: Apply **Bonferroni correction** (or Benjamini-Hochberg) to p-values since multiple tests are run.
- **Power Analysis**:
 - **A Priori**: Estimate required sample size (N) for 80% power at $\alpha=0.05$ based on expected effect sizes from literature.
 - **Post-Hoc**: Calculate achieved power given the actual N (a substantial cohort) and observed effect sizes.
- **Causal Inference**: This is an **observational** comparison (Human vs. Model). Claims will be framed as **associational** differences, not causal effects of "model usage" on code quality.

### 4. Sensitivity Analysis (FR-009)
- **Models**: Compare `codegen-mono` against `CodeLlama-7b` (if GPU available) or `CodeLlama-13b` (if accessible via API).
- **Method**: Re-run the metric pipeline for each model variant and compare distributions. If GPU is unavailable, the comparison is between `codegen-mono` and `codegen-mono` (repeated) to verify stability, or the plan falls back to a different CPU-tractable model if available.

## Decision/Rationale

| Decision | Rationale |
|:--- |:--- |
| **CPU-First** | The HumanEval dataset is small. Statistical tests and static analysis are CPU-tractable. No GPU is needed for the primary analysis. |
| **No Stratified Sampling** | The panel flagged "stratified sampling based on pass-rate quartiles" as scope creep. The plan uses the **full HumanEval set** to maintain statistical power and avoid bias. |
| **Mutation Score for Testability** | Replaces `branch_coverage_pct` because coverage on the HumanEval test suite is circular (measures correctness, not testability). Mutation score is a valid proxy for testability. |
| **Bonferroni Correction** | Required to control Family-Wise Error Rate (FWER) when running multiple hypothesis tests (Complexity, Mutation Score, Pass Rate) on the same data. |
| **Paired Design** | Essential for controlling problem difficulty. Each LLM output is compared directly to its human reference for the *same* task. |
| **GPU Escape Hatch** | Ensures FR-009 is implemented regardless of local GPU availability by falling back to a CPU-tractable model if remote execution fails. |

## Risk Assessment

| Risk | Mitigation |
|:--- |:--- |
| **API Rate Limits** | Implement exponential backoff and caching of generated code to `data/analysis/model_outputs/`. |
| **Mutation Testing Failures** | Wrap execution in `try/except` blocks; record `mutation_error` flag if execution fails. |
| **Model Hallucination** | Filter out code that does not parse (SyntaxError) before metric calculation. |
| **Compute Limits** | If `CodeLlama-7b` fails on CPU, fall back to a smaller model or use the GPU escape hatch (Kaggle) for that specific step only. **Hard Cap**: If runtime exceeds a predefined threshold, abort and re-run on a random sample of tasks. |
