# Research: Evaluating the Impact of Code Generation Models on Code Testability

## Objective
To determine if code generated by LLMs (specifically `Salesforce/codegen-mono-350m` and `CodeLlama` variants) exhibits statistically significant differences in testability metrics (Complexity, Halstead Volume, Branch Coverage) compared to human reference solutions from the HumanEval benchmark.

## Dataset Strategy

The study relies on the **HumanEval** benchmark, a standard dataset for code generation.

| Dataset | Source | Verified URL | Usage |
| :--- | :--- | :--- | :--- |
| **HumanEval** | HuggingFace Datasets | `https://huggingface.co/datasets/openai/openai_humaneval` | Primary input. Contains a set of programming tasks with canonical solutions and unit tests. |

**Access Method**:
The implementation will use the `datasets` library to fetch the data programmatically:
```python
import datasets
ds = datasets.load_dataset("openai/openai_humaneval", split="test")
```
This ensures reproducibility and checksum verification (FR-001). No access-gated data (e.g., ADNI, HCP) is required; HumanEval is fully open.

**Variable Fit Verification**:
- **Predictors**: Model ID (Human vs. CodeGen-350m vs. CodeLlama-7b/13b), Code Length.
- **Outcomes**: Cyclomatic Complexity, Halstead Volume, Branch Coverage %, Pass Rate.
- **Fit**: The HumanEval dataset provides `prompt` (for generation), `canonical_solution` (for baseline metrics), and `test` (for execution). This perfectly matches the study's need to compare generated code against the reference.

## Methodology

### 1. Code Generation (FR-002, FR-009)
- **Models**: `Salesforce/codegen-mono-350m` (baseline, explicitly selected to satisfy FR-002's requirement for "Salesforce/codegen-mono" due to its balance of capability and CPU-feasibility; larger variants like 1B/6B rejected for memory constraints), `codellama/CodeLlama-7b-hf`, `codellama/CodeLlama-13b-hf`.
- **Strategy**:
  - Load prompts from HumanEval.
  - Generate code samples using a temperature of 0.2 (deterministic-ish) and max_tokens=512.
  - **Compute Feasibility**: 
    - `codegen-350m`: Runs on CPU (2 cores) within reasonable time.
    - `CodeLlama-7b/13b`: Likely too large for 7GB RAM on CPU. **Plan**: If CPU inference fails or exceeds time budget, the execution runner will auto-offload to a Kaggle GPU (16GB VRAM) using `device="cuda"` and 8-bit quantization (`load_in_8bit=True`).
  - **Retry Logic**: Implement exponential backoff for HF Hub rate limits.

### 2. Static & Dynamic Analysis (FR-003, FR-005)
- **Cyclomatic Complexity**: Calculated using `radon.cc`.
- **Halstead Volume**: Calculated using `radon.halstead` (standard validated implementation) to ensure construct validity and adherence to standard definitions (Halstead, 1977).
- **Branch Coverage**:
  - **Dynamic**: `coverage.py` is used to measure actual branch coverage *only* if the code executes successfully against the HumanEval test suite. This is a mandatory step for FR-005.
  - **Static Fallback**: If the code fails to execute (SyntaxError, IndentationError, Timeout), a static AST walker counts the number of branch nodes (`if`, `for`, `while`, `try`, `except`). This is recorded as `static_branch_count` for descriptive purposes only.
  - **Error Handling**: The dynamic execution step is wrapped in a `try/except` block. If an exception occurs, `branch_coverage_pct` is set to `null`, and the static count is recorded.
- **Output**: JSON record per task per model.

### 3. Statistical Analysis (FR-004, FR-008)
- **Hypothesis**: $H_0$: There is no difference in testability metrics between Human and LLM code.
- **Scope Limitation**: The 164 HumanEval tasks are treated as the *entire population of interest* for this benchmark study. Statistical tests are framed as differences *within this set*, not as generalizations to "all code". The 164 tasks are a convenience sample, not a random sample of "all code", so claims are restricted to the HumanEval population.
- **Tests**:
  - **Wilcoxon Signed-Rank Test**: For paired continuous metrics (Complexity, Halstead).
  - **McNemar's Test**: For paired binary outcomes (Pass/Fail). **Fisher's Exact Test is explicitly excluded** as it is invalid for paired data.
  - **Permutation Test**: Non-parametric validation for any metric.
  - **Coverage Analysis**: Dynamic Branch Coverage is analyzed *only* on the subset of samples where both Human and LLM code executed successfully (complete-case analysis). This avoids selection bias and invalid comparisons between percentages and raw counts. For non-executable LLM samples, the static count is recorded but NOT included in the paired statistical tests.
- **Multiple Comparison Correction**: Apply Bonferroni or Holm-Bonferroni correction across the family of tests (Complexity, Halstead, Coverage) to control Family-Wise Error Rate (FWER).
- **Power Analysis**:
 - **A Priori**: Estimate required sample size (164 tasks) to detect a medium effect size (Cohen's d=0.5) with [deferred] power.
  - **Post-Hoc**: Calculate achieved power given observed effect sizes.
- **Causal/Associational Framing**: Since this is an observational comparison of code properties (not a randomized trial of developers), claims will be framed as **associational** differences in code properties within the benchmark.

### 4. Sensitivity Analysis (FR-009)
- Compare results across different CodeLlama model sizes (7b vs 13b) to assess robustness of findings to model scale.

### 5. Reporting & Validation (FR-006, FR-010, FR-011)
- Generate Markdown report with figures (boxplots, violin plots).
- **Citation Validation**: `code/validate_citations.py` extracts titles from the report, fetches metadata from verified URLs (or local cache), and computes the Levenshtein/Token Overlap score. It fails the build if the score is < 0.7. Output: `state/validation_report.yaml`.
- Compute SHA256 hashes for all artifacts and store in `state/artifact_hashes.yaml`.

## Decision/Rationale

| Decision | Rationale |
| :--- | :--- |
| **CPU-First for Analysis** | Static analysis and statistical tests are computationally light and fit easily within the 7GB RAM / 2 CPU limit. |
| **GPU Escape Hatch for Generation** | Large LLMs (7B+) require significant VRAM. A CPU simulation is a fabrication. The plan uses the Kaggle auto-offload mechanism for the *generation* step only, ensuring real results. |
| **Open Dataset (HumanEval)** | HumanEval is fully open, programmatic, and verified. No access-gated data is used, avoiding CI failure. |
| **Multiple Statistical Tests** | Code metrics are non-normal and paired. Using only a t-test would be statistically invalid. Wilcoxon and Permutation tests provide robustness. McNemar's Test is used for paired binary data; Fisher's is excluded. |
| **Coverage Methodology** | Dynamic coverage is only valid for executable code. Non-executable code uses a static count. Statistical tests for coverage are restricted to the complete-case subset to avoid selection bias. |
