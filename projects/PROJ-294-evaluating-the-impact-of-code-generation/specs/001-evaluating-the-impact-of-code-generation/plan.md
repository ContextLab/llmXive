# Implementation Plan: Evaluating the Impact of Code Generation Models on Code Testability

**Branch**: `[294-evaluating-code-testability]` | **Date**: 2026-06-25 | **Spec**: `specs/294-evaluating-code-testability/spec.md`
**Input**: Feature specification from `specs/294-evaluating-code-testability/spec.md`

## Summary

This feature implements a reproducible pipeline to evaluate how code generated by Large Language Models (LLMs) compares to human-written code regarding structural complexity and test suite sensitivity. The system downloads the verified HumanEval dataset, generates code samples using Salesforce/codegen-mono (and CodeLlama for sensitivity), runs static analysis via `radon` and dynamic execution via `coverage.py`, and performs rigorous statistical hypothesis testing (Wilcoxon, McNemar, Fisher, Permutation) with sensitivity analysis (MDES). The output is a validated Markdown report and structured JSON/YAML artifacts.

**Methodological Note**: While the spec mentions "A Priori" power analysis, the fixed sample size of the HumanEval benchmark (N=164) makes "Sensitivity Analysis" (calculating the Minimum Detectable Effect Size) the methodologically correct approach. This plan implements Sensitivity Analysis to satisfy the intent of FR-008.

## Technical Context

**Language/Version**: Python 3.11  
**Primary Dependencies**: `datasets` (HuggingFace), `radon`, `coverage`, `scipy`, `statsmodels`, `transformers`, `torch`, `pandas`, `pytest`, `matplotlib`  
**Storage**: Local file system (`data/raw`, `data/analysis`, `state`)  
**Testing**: `pytest` (unit tests for metrics, integration tests for pipeline)  
**Target Platform**: Linux (GitHub Actions Free Tier: 2 CPU, 7GB RAM)  
**Project Type**: Research CLI / Data Pipeline  
**Performance Goals**: Process 164 HumanEval tasks within 6 hours on CPU; generate statistical reports in <30 mins.  
**Constraints**: 
- **Full Dataset**: The study uses the full HumanEval set (N=164) or a simple random subset if compute limits arise. **Strictly NO stratified sampling** based on pass-rates or complexity.
- Must run on CPU-first; GPU only for LLM inference if CPU fails (scaled down).
- No external data modification; all derivations are new files.
- All citations must be verified against primary sources.
- **Metric Definition**: "Branch Coverage" is treated as "Test Suite Sensitivity" (coverage of the fixed oracle), not intrinsic code testability. "Pass Rate" is a measure of functional correctness, not testability.

> Dataset: HumanEval (a benchmark comprising a set of programming tasks). Metrics: Complexity, Halstead, Coverage Sensitivity, Pass Rate (Binary).

## Phase Breakdown

### Phase 0: Data Acquisition & Integrity
- **Input**: HumanEval dataset.
- **Task**: Download via HF, verify SHA256, store in `data/raw/`.
- **Output**: `data/raw/humaneval.parquet`, `state/artifact_hashes.yaml` (partial).
- **FR Mapping**: FR-001, FR-011.

### Phase 1: Code Generation
- **Input**: `data/raw/humaneval.parquet`.
- **Task**: Generate code for all tasks using Salesforce/codegen-mono. Handle retries.
- **Output**: `data/generated/` (JSONL with code).
- **FR Mapping**: FR-002, FR-007 (logging).

### Phase 2: Metrics Calculation
- **Input**: `data/generated/`, `data/raw/`.
- **Task**: 
  - Static: `radon` for Cyclomatic Complexity and Halstead Volume.
  - Dynamic: Execute test strings via `coverage.py` to get Pass Rate (Binary) and Branch Coverage.
- **Output**: `data/analysis/metrics.json`.
- **FR Mapping**: FR-003, FR-005, FR-011 (hash update).

### Phase 3: Statistical Analysis
- **Input**: `data/analysis/metrics.json`.
- **Task**: 
  - Wilcoxon (Complexity/Halstead).
  - McNemar (Pass Rate/Fail Rate).
  - Fisher/Permutation (Validation).
  - **Sensitivity Analysis**: Calculate MDES for N=164 (FR-008).
  - Collinearity check (VIF) and PCA if needed.
- **Output**: `data/analysis/results.yaml`, `data/analysis/power_results.yaml`, `state/validation_results.yaml`.
- **FR Mapping**: FR-004, FR-008, SC-002, SC-003.

### Phase 4: Reporting & Validation
- **Input**: All analysis outputs.
- **Task**: 
  - Generate Markdown report with figures.
  - **Citation Validation**: Run `validate_citations.py` (subprocess). Exit on failure.
  - **Artifact Integrity**: Run `integrity_checker.py` to finalize `state/artifact_hashes.yaml`.
- **Output**: `report.md`, `state/validation_report.yaml`, `state/artifact_hashes.yaml` (final).
- **FR Mapping**: FR-006, FR-010, FR-011.

## Logging Strategy (FR-007)
- **Configuration**: `code/main.py` configures Python `logging` module at startup.
- **Format**: `%(asctime)s - %(levelname)s - [TaskID: %(task_id)s] - %(message)s`.
- **Task ID**: Generated at the start of the run and passed to all modules.
- **Output**: `logs/pipeline_run.log` and console.

## Citation Validation Workflow (FR-010)
1. `code/validate_citations.py` is called with the path to `state/citations.yaml`.
2. It invokes the external **Reference-Validator Agent** via `subprocess.run`.
3. It parses the JSON report from the agent.
4. If any citation is `unreachable` or `mismatch`, it writes `state/validation_report.yaml` and exits with `SystemExit(1)`.
5. If all pass, it writes `state/validation_report.yaml` with status `PASS`.

## Artifact Integrity Workflow (FR-011)
1. After every data generation step, `code/integrity_checker.py` is called.
2. It recursively scans `data/` and `state/`.
3. It computes SHA256 for each file.
4. It writes/updates `state/artifact_hashes.yaml`.
