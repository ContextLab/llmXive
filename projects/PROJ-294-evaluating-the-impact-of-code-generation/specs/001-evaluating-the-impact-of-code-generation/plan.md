# Implementation Plan: Evaluating the Impact of Code Generation Models on Code Testability

**Branch**: `294-evaluating-impact-code-gen-testability` | **Date**: 2026-06-25 | **Spec**: `specs/294-evaluating-impact-code-gen-testability/spec.md`
**Input**: Feature specification from `specs/294-evaluating-impact-code-gen-testability/spec.md`

## Summary

This project implements a reproducible pipeline to evaluate how code generated by Large Language Models (LLMs) compares to human-written code in terms of testability. The pipeline downloads the **HumanEval** benchmark, generates code samples using `Salesforce/codegen-mono-350m` (baseline) and `CodeLlama` variants, calculates static metrics (Cyclomatic Complexity via `radon`, Halstead Volume via `radon.halstead`), and performs rigorous statistical hypothesis testing (Wilcoxon, McNemar) with power analysis. The output is a validated Markdown report and a structured JSON dataset, ensuring all results are reproducible on a standard GitHub Actions runner (CPU-first, with GPU offload for generation if needed).

**Key Methodological Corrections**:
- **Coverage**: Dynamic Branch Coverage is measured *only* for executable code. Non-executable code uses a Static Branch Count for descriptive purposes only. Statistical tests for coverage are restricted to the subset of samples where both Human and LLM code executed (complete-case analysis) to avoid selection bias.
- **Statistics**: Fisher's Exact Test is explicitly removed as it is invalid for paired data. McNemar's Test is used for binary outcomes.
- **Validation**: A local script `code/validate_citations.py` implements the Reference-Validator logic (token overlap >= 0.7) to satisfy FR-010 without external dependencies. This script IS the implementation of the Reference-Validator Agent required by the Constitution.

## Technical Context

**Language/Version**: Python 3.11  
**Primary Dependencies**: `datasets`, `transformers`, `torch`, `radon`, `coverage`, `scikit-learn`, `scipy`, `pandas`, `pyyaml`, `rich`  
**Storage**: Local filesystem (`data/` for artifacts, `state/` for metadata)  
**Testing**: `pytest` (unit/integration), `jsonschema` (contract validation)  
**Target Platform**: Linux (GitHub Actions Free Tier: CPU, 7GB RAM)  
**Project Type**: Data Science / Research Pipeline  
**Performance Goals**: Complete analysis of 164 HumanEval tasks (or a defined subset) within 6 hours on CPU; GPU offload for model inference if generation exceeds memory/time limits.  
**Constraints**: Must run without external API keys (use open weights via HF Hub); must strictly adhere to checksum verification (SHA256); must not fabricate data or metrics.  
**Scale/Scope**: tasks (HumanEval full set) or a statistically powered subset; ~ models for sensitivity analysis.

> **Dataset Note**: The HumanEval dataset is small and fits entirely in memory. The primary computational cost is LLM inference (CPU-possible but slow, or GPU-offloaded) and static analysis.

## Complexity Tracking

| Violation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|-------------------------------------|
| **GPU Offload Logic** | Inference of `codegen` or `CodeLlama` on a representative batch of samples may exceed 6h on 2 CPU cores. | Pure CPU inference is too slow for a reliable CI run. The plan includes a GPU escape hatch (Kaggle) for the generation phase only, while analysis remains CPU-first. |
| **Multiple Statistical Tests** | FR-004 requires Wilcoxon, McNemar. | A single test (e.g., t-test) is insufficient for paired, non-normal code metrics and binary pass/fail data. Multiple tests ensure robustness. Fisher's Exact Test is explicitly excluded as it is invalid for paired data. |
| **Reference-Validator Integration** | Constitution Principle II requires citation validation. | Skipping validation risks hallucinated citations. A local script `code/validate_citations.py` implements the exact logic (token overlap >= 0.7) to satisfy the gate without external dependencies. |
| **Coverage Handling** | `coverage.py` fails on non-executable code. | Dynamic coverage is only calculated for executable code. A static branch count is used as a fallback for non-executable code, but statistical tests for coverage are restricted to the complete-case subset (both Human and LLM executable) to avoid selection bias. |
