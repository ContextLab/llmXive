## Unresolved concerns

- The primary construct for ‘vulnerability’ is the raw output of Semgrep and SonarQube. Static‑analysis findings are known proxies and can miss true vulnerabilities or flag false positives, especially on LLM‑generated code that may use unconventional patterns. The plan does not describe any supplemental validation beyond the 20 % audit, risking construct validity of the vulnerability measure.
- Functional equivalence is verified by either ≥ 90 % unit‑test coverage *or* a semantic‑similarity score ≥ 0.85. Neither criterion guarantees that security‑relevant behavior (e.g., input sanitisation) is preserved, which could introduce systematic bias between human and LLM samples and threaten the paired‑design validity.
- The power statement (“Target ~300 paired samples … >80 % power for detecting an odds‑ratio ≈ 2.0”) lacks a concrete power analysis (e.g., assumed baseline prevalence, effect size per OWASP category). For low‑frequency vulnerability types this sample may be insufficient, so the study may be under‑powered for several categories.
- No explicit control for confounding variables such as code length, cyclomatic complexity, or language‑specific idioms is described. Differences in these attributes between human and LLM code could affect static‑analysis detection rates, violating the assumption that the only systematic difference is the code source.
- McNemar’s test is applied per vulnerability type, assuming each pair contributes a single binary outcome per type. However, a single code sample can contain multiple distinct findings of the same type, violating the independence assumption of the test and potentially inflating Type I error.
- Functional Requirement FR‑007 (handle cases where the dataset lacks specific vulnerability labels by excluding those samples) is not explicitly addressed in the implementation plan. The plan’s Phase 0 steps mention filtering and logging counts, but they do not reference exclusion of unlabeled samples or tie to FR‑007.
- The plan’s Constitution Check states “Citations are limited to the three verified URLs in the “Verified datasets” block,” but the research.md only lists two distinct verified URLs (the OWASP Top 10 LLM Dataset URL and the Mahabharat OWASP SQL‑Injection CSV URL). This contradicts Constitution Principle II (Verified Accuracy) and constitutes a requirement‑level violation.
- The plan applies bias‑correction factors (derived from a held‑out 10 % subset) to the raw vulnerability counts **before** performing McNemar’s paired test (steps 2.2‑2.4). McNemar’s test assumes raw paired binary outcomes; weighting or adjusting the counts breaks the test’s distributional assumptions and can lead to invalid p‑values. Either (a) perform McNemar on the unadjusted paired flags and report bias‑corrected effect sizes separately, or (b) use a statistical method that accommodates weighted paired data (e.g., generalized estimating equations).
