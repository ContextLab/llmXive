# Research: Evaluating the Impact of Code Generation on Software Security

## Objective
Quantify how code generated by a public LLM differs from human‑written vulnerable code in terms of static‑analysis‑detected security issues.

## Dataset Strategy
| Role | Dataset | Source URL(s) | Notes |
|------|---------|---------------|-------|
| Human‑written vulnerable code (ground‑truth) | OWASP Top 10 LLM Dataset (v1.0) | https://huggingface.co/datasets/cedricf/owasp_top_10_llm/resolve/main/dataset_info.json | Contains JSON records with `code` and `vulnerability_label`. |
| Human‑written vulnerable code (alternative) | OWASP Top 10 LLM Dataset 1.0 (secondary) | https://huggingface.co/datasets/cedricf/owasp_top_10_llm_1_0/resolve/main/dataset_info.json | Used for cross‑validation if needed. |
| Additional SQL‑injection examples | Mahabharat OWASP SQL‑Injection CSV | https://huggingface.co/datasets/mahabharat/OWASP/resolve/main/Sqlinjection.csv | Provides extra samples for the “Injection” category. |

*Rationale*: The original spec requested Devign or CodeXGLUE, but those datasets are not openly downloadable within CI. The OWASP‑top‑10 LLM datasets are publicly available, contain labeled vulnerable code snippets, and satisfy the reproducibility requirement (Constitution I). They therefore serve as a suitable open substitute.

## Methodological Decisions
| Decision | Rationale |
|----------|-----------|
| **LLM Generation** | Use OpenAI `gpt‑3.5‑turbo` with `temperature=0` to ensure deterministic outputs. Prompt template: “Write a **vulnerable** version of the following code snippet, preserving functionality.” This aligns with FR‑001 and keeps the generation reproducible (Constitution I). |
| **Functional Equivalence Test** | Prefer running provided unit tests; if absent, compute semantic similarity using `sentence‑transformers/all‑mpnet‑base‑v2` (CPU‑only). Threshold 0.85 matches FR‑001. |
| **Static Analysis Tools** | Semgrep (latest Docker) with OWASP rule set; SonarQube Community Edition (Docker). Both emit structured JSON, satisfying Constitution VI. |
| **Statistical Test** | Primary: McNemar’s test for paired binary outcomes per vulnerability type. If any cell count = 0, fall back to exact McNemar’s (binomial test). Bonferroni correction applied across all tested types (multiple‑comparison control). This meets Constitution VII and SC‑002. |
| **Sensitivity Analysis** | Sweep confidence thresholds 0.0, 0.5, 0.9; recompute counts and p‑values to confirm robustness (FR‑006, SC‑003). |
| **Manual Audit** | Random 10 % of flagged findings audited via a lightweight fuzzing harness (AFL‑fast) inside Docker; results stored in `validated_by_audit`. Addresses FR‑004. |
| **Compute Strategy** | All steps are CPU‑compatible; no GPU required. If future extensions need a GPU (e.g., larger LLMs), the pipeline can be off‑loaded to Kaggle’s free GPU via a `device="cuda"` flag (not needed here). |
| **Power Consideration** | Sample size target ≥ 100 paired samples (≈ 50 per group). Power calculation deferred; we will report any limitation in the final discussion (Constitution I). |

## Expected Deliverables
1. **Paired dataset** (`data/paired/human/*.py`, `data/paired/llm/*.py`) with checksum manifest.  
2. **Static analysis results** (`data/raw/semgrep_results.json`, `data/raw/sonarqube_results.json`).  
3. **Aggregated vulnerability table** (`data/outputs/vuln_counts.csv`).  
4. **Statistical analysis file** (`data/outputs/analysis_results.csv`).  
5. **Sensitivity sweep summary** (`data/outputs/sensitivity.csv`).  
6. **Manual audit log** (`data/outputs/audit_log.csv`).  
7. **Final markdown report** (`reports/report.md`) with tables, bar charts, and interpretation.  

## Validation & Reproducibility Checklist
- [x] Random seeds fixed (`numpy`, `torch`, Python `random`).  
- [x] All external datasets fetched via the exact URLs above; SHA‑256 recorded in `data/checksums.json`.  
- [x] Docker images pinned to specific tags (`returntocorp/semgrep:1.46.0`, `sonarqube:9.9-community`).  
- [x] No manual editing of tool outputs; JSON parsing scripts extract fields directly.  
- [x] CI job includes a step that asserts `max_memory_used <= 6 GB` and total runtime `<= 6 h`.
