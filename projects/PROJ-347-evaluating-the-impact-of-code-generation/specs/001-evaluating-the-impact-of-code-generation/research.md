# Research: Evaluating the Impact of Code Generation on Software Security

## Objective
Quantify how code generated by a public LLM differs from human‑written vulnerable code in terms of static‑analysis‑detected security issues.

## Dataset Strategy
| Role | Dataset | Source URL(s) | Notes |
|------|---------|---------------|-------|
| Human‑written vulnerable code (ground‑truth) | **Juliet Test Suite (SARD)** – vulnerable C/Python snippets | | Open‑source collection of human‑authored vulnerable code with precise CWE labels. |
| LLM‑generated vulnerable code | **OWASP Top 10 LLM Dataset** (v1.0) | https://huggingface.co/datasets/cedricf/owasp_top_10_llm/resolve/main/dataset_info.json | Used **only** as the source of prompts for generation; not a ground‑truth human dataset. |
| Additional SQL‑injection examples | Mahabharat OWASP SQL‑Injection CSV | https://huggingface.co/datasets/mahabharat/OWASP/resolve/main/Sqlinjection.csv | Provides extra samples for the “Injection” category. |

*Rationale*: The original spec requested Devign or CodeXGLUE, which are not directly downloadable in CI. The **Juliet Test Suite** is a fully open, programmatically downloadable repository that contains human‑written vulnerable code and aligns with the success criterion SC‑005 (≥ 5 distinct OWASP types). The OWASP LLM dataset is retained **only** for prompting the LLM; it does **not** serve as the human baseline.

## Methodological Decisions
| Decision | Rationale |
|----------|-----------|
| **LLM Generation** | Use the open‑source **StarCoder** model (`bigcode/starcoder` revision `2023-11-01`) via HuggingFace `transformers`. Temperature = 0 for deterministic output, max_new_tokens = 1024. This satisfies free‑model constraints and ensures reproducibility (Constitution I). |
| **Functional Equivalence Test** | Require **both** (a) successful execution of any provided unit tests with ≥ 90 % coverage **and** (b) semantic similarity ≥ 0.90 using `sentence‑transformers/all‑mpnet‑base‑v2`. An optional runtime‑behavior check on a tiny synthetic input set adds extra safety. |
| **Static Analysis Tools** | Semgrep (Docker) with OWASP rule set; SonarQube Community Edition (Docker). Both emit structured JSON, meeting Constitution VI. |
| **Statistical Test** | Primary: McNemar’s test for paired binary outcomes per vulnerability type (`statsmodels.stats.contingency_tables.mcnemar`). If any cell is zero, re‑run with `exact=True`. Bonferroni correction applied across all tested types (multiple‑comparison control). |
| **Sensitivity Analysis** | Sweep confidence thresholds 0.0, 0.5, 0.9; recompute counts and p‑values to confirm robustness (FR‑006, SC‑003). |
| **Manual Audit** | Random **[deferred]** stratified sample of flagged findings audited via a lightweight fuzzing harness (`afl‑fast`) or manual reviewer script; results stored in `validated_by_audit`. Increases power to detect systematic tool bias (addresses methodology‑c3f559e9). |
| **Compute Strategy** | All steps are CPU‑compatible; no GPU required. |
| **Power Consideration** | Target **200** paired samples (≈ 100 per group) to achieve >80 % power for medium effect sizes with McNemar’s test (see Power Analysis in plan.md). Limitations will be reported if the dataset cannot meet this size. |
| **Tool Validation** | On a held‑out [deferred] subset of Juliet, compute precision/recall for each static analysis tool to quantify false‑positive/false‑negative rates (methodology‑a8e3016c). |

## Expected Deliverables
1. **Paired dataset** (`data/paired/human/*.py`, `data/paired/llm/*.py`) with checksum manifest.  
2. **Static analysis results** (`data/raw/semgrep_results.json`, `data/raw/sonarqube_results.json`).  
3. **Aggregated vulnerability table** (`data/outputs/vuln_counts.csv`).  
4. **Statistical analysis file** (`data/outputs/analysis_results.csv`).  
5. **Sensitivity sweep summary** (`data/outputs/sensitivity.csv`).  
6. **Manual audit log** (`data/outputs/audit_log.csv`).  
7. **Final markdown report** (`reports/report.md`) with tables, bar charts, and interpretation.
