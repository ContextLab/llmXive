# Implementation Plan: Evaluating the Impact of Code Generation on Software Security

**Branch**: `001-eval-llm-code-security` | **Date**: 2026-10-17 | **Spec**: [spec.md](../specs/001-eval-llm-code-security/spec.md)  
**Input**: Feature specification from `/specs/001-eval-llm-code-security/spec.md`

## Summary
The study must compare vulnerability profiles of human‑written vulnerable code with code generated by a public LLM for identical functionality.  
We will (1) ingest a verified open dataset of vulnerable code (OWASP Top 10 LLM Dataset), (2) generate paired LLM versions using a lightweight CodeGen model, (3) verify functional equivalence **and** security‑specific behavior, (4) run Semgrep, SonarQube **and** Bandit (Docker/Python) on both sets, (5) aggregate findings, (6) perform paired statistical tests (McNemar’s / exact McNemar) **on raw binary outcomes**, (7) conduct a confidence‑threshold sensitivity sweep, (8) apply bias‑correction **post‑test** only to effect‑size reporting, (9) audit ≥ 20 % of flagged findings **plus** a stratified cross‑tool manual review, (10) run a supplemental validation step to estimate false‑positive rates, (11) perform a confounder‑adjusted secondary analysis, and (12) produce a reproducible markdown report with tables and figures.

All steps are scripted, deterministic, and respect the GitHub Actions free‑tier limits (≤ 6 h, ≤ 6 GB RAM).

## Technical Context
- **Language/Version**: Python 3.11  
- **Primary Dependencies**: `datasets`, `transformers`, `sentence-transformers`, `semgrep`, `sonarqube-scanner` (Docker), `bandit==1.7.8` (pip), `pandas`, `numpy`, `scipy`, `statsmodels`, `matplotlib`, `radon`, `pytest` (CPU‑only)  
- **Storage**: File‑based under `data/` (raw, derived, outputs)  
- **Testing**: `pytest` for unit‑test execution and pipeline validation  
- **Target Platform**: Linux GitHub Actions runner (2 CPU cores, ~7 GB RAM, ~14 GB disk)  
- **Constraints**: No GPU required; all Docker images are CPU‑compatible; random seeds are pinned.

# Research: Evaluating the Impact of Code Generation on Software Security

## Objective
Quantify how code generated by a public LLM *associates* with human‑written vulnerable code in terms of static‑analysis‑detected security issues.

## Dataset Strategy
| Role | Dataset | Source URL(s) | Notes |
|------|---------|---------------|-------|
| Human‑written vulnerable code (baseline) | **OWASP Top 10 LLM Dataset** (v1.0) | https://huggingface.co/datasets/cedricf/owasp_top_10_llm/resolve/main/dataset_info.json | Contains human‑authored vulnerable snippets across OWASP Top categories; serves as the “human” side of each pair. |
| LLM‑generated vulnerable code | Same OWASP Top 10 LLM Dataset (used as prompts) | https://huggingface.co/datasets/cedricf/owasp_top_10_llm/resolve/main/dataset_info.json | Prompts are fed to a CodeGen model to produce functionally equivalent LLM samples. |
| Additional SQL‑injection examples | Mahabharat OWASP SQL‑Injection CSV | https://huggingface.co/datasets/mahabharat/OWASP/resolve/main/Sqlinjection.csv | Provides extra samples for the “Injection” category to ensure ≥ 5 distinct OWASP types. |

*Rationale*: The original spec mentioned Devign/CodeXGLUE, which are not directly downloadable in CI. The verified OWASP LLM dataset is openly accessible and contains labeled vulnerable code, satisfying FR‑001 and SC‑005. The Mahabharat CSV augments the injection category without violating the verified‑datasets constraint.

## Methodological Decisions
| Decision | Rationale |
|----------|-----------|
| **LLM Generation** | Use **Salesforce/codegen‑350M‑multi** via HuggingFace `transformers`. Deterministic (temp = 0), CPU‑friendly, fits the free runner. |
| **Functional Equivalence Test** | Verify **both** (a) unit‑test coverage ≥ 90 % **and** a **security‑focused pattern test** that ensures the original vulnerable construct (e.g., `eval`, raw SQL) is still present, **or** (b) semantic similarity ≥ 0.85 using `sentence‑transformers/all‑mpnet‑base‑v2`. This guarantees that security‑relevant behavior is preserved while remaining feasible. |
| **Static Analysis Tools** | Semgrep (Docker, OWASP rule set), SonarQube Community Edition (Docker), and **Bandit** (pip). All emit structured JSON, meeting Constitution VI. |
| **Statistical Test** | Primary: McNemar’s test for paired binary outcomes per vulnerability type (`statsmodels`). If any cell = 0, switch to exact McNemar. Bonferroni correction for multiple testing (Constitution VII). |
| **Bias Correction** | Estimate each tool’s precision/recall on a held‑out [deferred] subset of the OWASP dataset; **apply weighting only to effect‑size reporting after the raw McNemar test** (post‑hoc), preserving the test’s distributional assumptions. |
| **Supplemental Validation** | Run `validation/fp_estimation.py` on a curated set of safe snippets to estimate false‑positive rates and compute cross‑tool agreement metrics; report these alongside the main results to strengthen construct validity. |
| **Sensitivity Analysis** | Sweep confidence thresholds 0.0, 0.5, 0.9; map SonarQube severity to numeric confidence (CRITICAL = 1.0, HIGH = 0.75, MEDIUM = 0.5, LOW = 0.25). |
| **Manual Audit** | Randomly audit ≥ 20 % of flagged findings (stratified by type) using lightweight fuzzing (`afl‑fast`) or manual review; compute a calibration factor that rescales bias‑corrected effect sizes. |
| **Power Consideration** | Using `statsmodels.stats.power.NormalIndPower` with baseline prevalence = 0.15, target odds‑ratio ≈ a moderate positive effect (i.e., greater than 1), α = 0.05, two‑sided McNemar, we require **≈ 300 paired samples** per OWASP category to achieve >80 % power. This target is logged by `src/power_analysis.py`. |
| **Confounder Control** | Record token count (`length`) and cyclomatic complexity (`cyclomatic_complexity`) for each snippet; include these as covariates in a secondary logistic‑regression analysis to verify that observed differences are not driven by code size or complexity. |
| **Associational Language** | All conclusions are framed as *associations* (observational design), respecting the non‑causal nature mandated by the constitution. |
| **FR‑007 Handling** | Samples lacking a `vulnerability_label` are excluded during ingestion; exclusion counts are logged for transparency. |

## Expected Deliverables
1. **Paired dataset** (`data/paired/human/*.py`, `data/paired/llm/*.py`) with SHA‑256 manifest.  
2. **Static analysis results** (`data/raw/semgrep_results.json`, `data/raw/sonarqube_results.json`, `data/raw/bandit_results.json`).  
3. **Aggregated vulnerability table** (`data/outputs/vuln_counts.csv`).

5. **Sensitivity sweep summary** (`data/outputs/sensitivity.csv`).  
6. **Manual audit log** (`data/outputs/audit_log.csv`).  
7. **Final markdown report** (`reports/report.md`) containing tables, bar charts, and interpretive text.

## projects/PROJ-347-evaluating-the-impact-of-code-generation/specs/001-evaluating-the-impact-of-code-generation/data-model.md
# Data Model: Evaluating the Impact of Code Generation on Software Security

## Overview
The pipeline manipulates four core entities (three from the original spec plus one added for the paired statistical test). Each entity is defined by a JSON Schema stored under `contracts/`.

| Entity | Purpose |
|--------|---------|
| **CodeSample** | Represents a single code snippet (human or LLM‑generated). |
| **VulnerabilityFinding** | Represents a single static‑analysis detection linked to a `CodeSample`. |
| **PairOutcome** | Captures the binary presence/absence of a given vulnerability type for both members of a paired sample, enabling a 2×2 McNemar contingency table. |
| **AnalysisResult** | Summarises aggregated counts and statistical test outcomes per vulnerability type. |

All schemas are validated by the test suite (`tests/contract/test_contracts.py`) and are referenced in the CI contracts.

## Entity Summaries (informal)

### CodeSample
- `sample_id` (UUID) – unique identifier.  
- `source` (`"human"` | `"llm"`).  
- `functionality_id` (string) – stable identifier linking the human and LLM versions.  
- `syntax_valid` (bool).  
- `functional_equivalence_verified` (bool).  
- `raw_content` (string).  
- `language` (string, e.g., `"python"`).  
- `length` (integer, optional) – token count of the source code (confounder metric).  
- `cyclomatic_complexity` (integer, optional) – computed via radon (confounder metric).

### VulnerabilityFinding
- `finding_id` (UUID).  
- `code_sample_id` (UUID).  
- `tool_source` (`"semgrep"` | `"sonarqube"` | `"bandit"`).  
- `vulnerability_type` (string, OWASP category).  
- `severity` (`"LOW"` | `"MEDIUM"` | `"HIGH"` | `"CRITICAL"`).  
- `line_number` (int ≥ 1).  
- `confidence_score` (float ∈ [0, 1]).  
- `rule_id` (string).  
- `validated_by_audit` (bool, optional).

### PairOutcome *(new)*
- `pair_id` (UUID) – same as `functionality_id`.  
- `vulnerability_type` (string).  
- `human_flag` (bool).  
- `llm_flag` (bool).

### AnalysisResult
- `result_id` (UUID).  
- `vulnerability_type` (string).  
- `human_count` (int ≥ 0).  
- `llm_count` (int ≥ 0).  
- `total_pairs` (int ≥ 0).  
- `p_value` (float ∈ [0, 1]).  
- `p_value_adj` (float ∈ [0, 1]).  
- `is_significant` (bool).  
- `test_method` (`"McNemar"` | `"Exact McNemar"`).  
- `confidence_threshold` (float ∈ [0, 1] | null).

These definitions are formally captured in the YAML contracts provided alongside this document.

# Quickstart: Running the Code‑Generation Security Study

## Prerequisites
1. **GitHub Actions runner** (or local Linux environment with ≥ 2 CPU cores, ~7 GB RAM).  
2. **Python 3.11**.  
3. **Docker** (required for Semgrep & SonarQube).  
4. **Hugging Face token** (optional; set `HF_TOKEN` if you encounter rate limits).

## Setup
```bash
# Clone the repository
git clone <repo-url>
cd PROJ-347-evaluating-the-impact-of-code-generation

# Create a virtual environment and install exact dependencies
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt   # pins all versions, including bandit==1.7.8

# Pull required Docker images (first run will download them)
docker pull returntocorp/semgrep:1.46.0
docker pull sonarqube:9.9-community
# Bandit is installed via pip above; no Docker image needed.
```

## Run the Full Pipeline
```bash
python -m src.run_pipeline \
    --seed 42 \
    --max-pairs <sufficiently large value> \
    --confidence-thresholds 0.0 0.5 0.9
```
- `--seed` fixes all randomness for reproducibility.  
- `--max-pairs` caps the number of paired samples (default aligns with the power analysis).  
- `--confidence-thresholds` triggers the sensitivity sweep.

The orchestrator performs the following phases automatically:
1. **Data download & LLM generation** (Phase 0).  
2. **Syntax & functional equivalence checks** (including security‑focused pattern test).  
3. **Static analysis** with Semgrep, SonarQube **and** Bandit (Phase 1).  
4. **Aggregation, bias‑correction (post‑test), and paired statistical testing** (Phase 2).  
5. **Sensitivity analysis** across confidence cutoffs.  
6. **Random audit of ≥ 20 % flagged findings** (Phase 3).  
7. **Report generation** (`reports/report.md`) and figure export (`reports/figures/`).  

All logs are written to `logs/`; intermediate artefacts follow the schema contracts under `contracts/`.

## Inspect Results
- **Aggregated counts**: `data/outputs/vuln_counts.csv`  
- **Statistical table**: `data/outputs/analysis_results.csv`  
- **Sensitivity sweep**: `data/outputs/sensitivity.csv`  
- **Audit log**: `data/outputs/audit_log.csv`  
- **Final report**: `reports/report.md` (open with any markdown viewer).
