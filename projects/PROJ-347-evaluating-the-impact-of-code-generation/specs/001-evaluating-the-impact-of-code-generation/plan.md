# Implementation Plan: Evaluating the Impact of Code Generation on Software Security

**Branch**: `001-eval-llm-code-security` | **Date**: 2026-10-17 | **Spec**: [spec.md](../specs/001-eval-llm-code-security/spec.md)  
**Input**: Feature specification from `/specs/001-eval-llm-code-security/spec.md`

## Summary
The study compares vulnerability profiles of human‑written vulnerable code with code generated by a public LLM for identical functionality. We will (1) ingest a verified open dataset of vulnerable code, (2) generate paired LLM versions using a lightweight CodeGen model, (3) verify functional equivalence **via BOTH** unit‑test coverage ≥ 90 % **and** semantic similarity ≥ 0.85 (plus a security‑focused pattern test performed *after* static analysis), (4) run Semgrep, SonarQube Community Edition, and CodeQL on both sets, (5) aggregate findings, (6) perform paired McNemar’s tests (exact when needed), (7) conduct a ±0.05 confidence‑threshold sensitivity sweep, (8) audit ≥ 20 % of flagged findings, (9) report results with tables and figures, and (10) enforce SC‑001 compliance (≥ 85 % valid LLM samples). All steps respect the GitHub Actions free‑tier limits (≤ 6 h, ≤ 7 GB RAM) and the project constitution.

## Phase‑wise Implementation Plan (covers every FR/SC)

| Phase | Step | Description | FR / SC addressed |
|-------|------|-------------|-------------------|
| **0 – Data Ingestion & Pairing** | 0.0 | Filter out human snippets lacking a `vulnerability_label` (FR‑007). | FR‑007 |
| | 0.1 | Download **OWASP Top 10 LLM Dataset** via `datasets.load_dataset`; verify SHA‑256 checksum. | FR‑001, FR‑007 |
| | 0.2 | Keep only Python snippets (`language=="python"`). | FR‑001 |
| | 0.3 | Generate LLM equivalents using **Salesforce/codegen‑350M‑multi** (`temperature=0`, `max_new_tokens=512`); retry up to 3 times, log failures. | FR‑001 |
| | 0.4 | Syntax validation with `ast`; flag invalid LLM samples, **exclude from downstream analysis but retain in intent‑to‑treat accounting**. | FR‑001, SC‑001 |
| | 0.5a | Execute bundled unit tests on both human and LLM code; require **≥ 90 % coverage**. | FR‑001 |
| | 0.5b | Compute semantic similarity with `sentence‑transformers/all‑mpnet‑base‑v2`; require **≥ 0.85**. | FR‑001 |
| | 0.5c | **Both** criteria must be satisfied (AND). If either fails, mark `functional_equivalence_verified = false` and retain sample for intent‑to‑treat reporting. | FR‑001 |
| | 0.6 | Record `functional_equivalence_verified = true` only when both checks pass **and** the security‑focused pattern test (see Phase 3) later confirms the vulnerable construct is present. | FR‑001 |
| | 0.7 | Compute confounders: **lines_of_code** via `radon` and **cyclomatic_complexity**. | methodology‑1156e948 |
| | 0.8 | Perform **McNemar‑appropriate power analysis** using `statsmodels.stats.power.GofPower(method='mcnemar')` targeting ≥ 80 % power for odds‑ratio ≈ 2.0. Log required pair count; aim for ≥ 300 pairs. | methodology‑2a7f48be |
| **1 – Static Analysis Execution** | 1.1 | Run Semgrep Docker image (`returntocorp/semgrep:1.46.0`) with OWASP rule set; output `semgrep_results.json`. | FR‑002 |
| | 1.2 | Run SonarQube Community Docker (`sonarqube:9.9-community`) via scanner; export `sonarqube_results.json`. | FR‑002 |
| | 1.3 | Run CodeQL Docker image (`ghcr.io/github/codeql-action:latest`) on each sample; export `codeql_results.json`. | FR‑009 (secondary validator) |

### Success‑Metric Checks
- After Phase 1 a CI step asserts `max_memory_used <= 6 GB` and total runtime `<= 6 h`.  
- After Phase 2 a CI step asserts `vuln_counts.csv` lists ≥ 5 distinct `vulnerability_type` values.  
- After Phase 0 a CI step asserts `valid_llm_ratio >= 0.85` (SC‑001).

All heavy computation runs on CPU; the 350M CodeGen model fits comfortably on the free runner. No GPU is required.
