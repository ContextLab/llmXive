# Implementation Plan: Evaluating the Impact of Code Generation on Software Security

**Branch**: `001-eval-llm-code-security` | **Date**: 2026-10-13 | **Spec**: [spec.md](../specs/001-eval-llm-code-security/spec.md)  
**Input**: Feature specification from `/specs/001-eval-llm-code-security/spec.md`

## Summary
The project must compare vulnerability profiles of human‑written vulnerable code with code generated by a public LLM for the same functionality.  
The plan builds a paired dataset (human ↔ LLM), validates functional equivalence, runs two open‑source static analysis tools (Semgrep, SonarQube) inside Docker, aggregates findings, performs paired statistical tests (McNemar’s / exact McNemar’s), conducts a confidence‑threshold sensitivity sweep, audits a random [deferred] subset, and finally produces a reproducible markdown report with tables and figures.

## Technical Context
**Language/Version**: Python 3.11  
**Primary Dependencies**: `datasets`, `transformers` (for StarCoder), `sentence-transformers`, `semgrep`, `sonarqube-scanner` (Docker), `pandas`, `numpy`, `scipy`, `statsmodels`, `matplotlib`, `pytest` (all CPU‑compatible)  
**Storage**: File‑based under `data/` (raw, derived, outputs)  
**Testing**: `pytest` for unit‑test execution of generated code; `pytest` also validates pipeline steps.  
**Target Platform**: Linux GitHub Actions runner (2 CPU cores, ~7 GB RAM, ~14 GB disk)  
**Performance Goals**: Entire pipeline ≤ 6 h, peak RAM ≤ 6 GB (safety buffer)  
**Constraints**: All external datasets must be fetched from the verified URLs listed in the research document; Docker images for Semgrep and SonarQube must match versions documented in the methodology; random seeds pinned for reproducibility.  
**Scale/Scope**: Target **200** paired samples (≥ 100 human + 100 LLM) to achieve >80 % power for detecting a medium effect size with McNemar’s test across up to 10 OWASP categories (see Power Analysis below).  

## Power Analysis
A rough power calculation (α = 0.05, power = 0.80, medium effect size ≈ 0.3 for McNemar’s) indicates a minimum of ~180 paired observations. We therefore target **200** pairs, acknowledging that if the dataset cannot provide this many, the limitation will be reported transparently.

## Constitution Check
| Principle | Compliance Statement |
|-----------|----------------------|
| I. Reproducibility | All steps are scripted, random seeds are fixed (`numpy.random.seed(42)`, `torch.manual_seed(42)`, model temperature = 0). Data is downloaded from the same canonical URLs on every runner execution. |
| II. Verified Accuracy | Citations are limited to the three verified dataset URLs (see Research.md). No unverified external references are introduced. |
| III. Data Hygiene | Raw dataset files are checksum‑verified (SHA‑256 recorded in `data/checksums.json`). Every transformation writes a new file (`*_derived.csv/json`) with provenance metadata. |
| IV. Single Source of Truth | Every figure/table in the final report references a specific row in the aggregated CSVs (`data/aggregated/vuln_counts.csv`, `data/aggregated/analysis_results.csv`). |
| V. Versioning Discipline | All artifacts are stored under `data/` with content hashes in `state/projects/PROJ-347-evaluating-the-impact-of-code-generation.yaml`. |
| VI. Static‑Analysis Tool Fidelity | Semgrep and SonarQube are executed via official Docker images (`returntocorp/semgrep:1.46.0`, `sonarqube:9.9-community`). JSON outputs are parsed directly without manual editing. |
| VII. Statistical Significance Threshold | McNemar’s test results are reported with raw and Bonferroni‑adjusted p‑values; non‑significant results are labeled “inconclusive”. |

## Phase‑wise Implementation Plan (maps FR/SC)

| Phase | Step | Description | FR/SC addressed |
|-------|------|-------------|-----------------|
| **0 – Data Acquisition & Pairing** | 0.1 | Download **Juliet Test Suite (SARD)** human‑written vulnerable snippets (verified URL). Verify SHA‑256 checksums. | FR‑001, FR‑007 |
| | 0.2 | Filter rows that contain a `code` field and a `vulnerability_label`. Exclude unlabeled rows. | FR‑007 |
| | 0.2a | Keep only **Python** samples (language detection via file extension). Log number of excluded non‑Python files. | FR‑001, addresses methodology‑00663914 |
| | 0.3 | For each human code sample, generate a functionally equivalent vulnerable version using the open‑source **StarCoder** model (`bigcode/starcoder` revision `2023-11-01`) via HuggingFace `transformers` pipeline (temperature = 0, max_new_tokens = 1024). Retry up to 3 times on error. | FR‑001, data_resources‑0e062179, plan_consistency‑cea9fa3a |
| | 0.4 | Syntax validation using language‑specific parsers (Python `ast`). Flag invalid samples; log count. | FR‑001 |
| | 0.5 | **Functional equivalence**: (a) run available unit tests with `pytest` (≥ 90 % coverage required); (b) compute semantic similarity using `sentence‑transformers/all‑mpnet‑base‑v2`; accept **≥ 0.90**; (c) optional runtime‑behavior check on a tiny synthetic input set. Record `functional_equivalence_verified`. | FR‑001, methodology‑3c1018c3 |
| | 0.6 | Compute SC‑001 metric: `valid_llm / total_prompts`. | SC‑001 |
| **1 – Static Analysis Execution** | 1.1 | Pull Semgrep Docker image (`returntocorp/semgrep:1.46.0`), run with OWASP rule set on both code directories, output JSON (`semgrep_results.json`). | FR‑002 |
| | 1.2 | Pull SonarQube community Docker image (`sonarqube:9.9-community`), start scanner, run analysis, export findings via SonarQube REST API to `sonarqube_results.json`. | FR‑002 |
| | 1.3 | `memory_monitor.py` watches each tool; if RAM > 6 GB, terminate process, log OOM, continue. | FR‑002 |
| | 1.4 | **Tool validation**: on a held‑out labeled subset ([deferred] of Juliet), compute precision/recall for each tool and log the rates. | methodology‑a8e3016c |
| | 1.5 | Parse both JSONs, normalise fields to `VulnerabilityFinding` schema (add `confidence_score` from Semgrep `confidence` or map SonarQube severity → numeric). | FR‑003 |
| **2 – Aggregation & Statistical Comparison** | 2.1 | For each **pair** and each vulnerability type, build a 2×2 contingency table (Human = 1/0, LLM = 1/0). Store per‑type tables. | FR‑003, scientific_soundness‑71b2733f |
| | 2.2 | Apply **McNemar’s test** (`statsmodels.stats.contingency_tables.mcnemar`) on each table. If any cell = 0, re‑run with `exact=True`. | FR‑004, scientific_soundness‑71b2733f |
| | 2.3 | Apply Bonferroni correction across all tested types; store adjusted p‑values. | SC‑002, VII |

**Success‑Metric Checks (SC‑004, SC‑005)**  
- After Phase 1, a CI step asserts `max_memory_used <= 6 GB` and total runtime `<= 6 h`.  
- After Phase 2, verify that `vuln_counts.csv` contains ≥ 5 distinct `vulnerability_type` values (OWASP Top 10 subset).  

**Decision / Rationale (Research.md)**  
All heavy computation runs on CPU; no GPU is required. LLM generation uses the open‑source StarCoder model, which runs comfortably on the free runner. Semgrep and SonarQube are pure CPU Docker containers, fitting the 2‑core runner.
