# Implementation Plan: Evaluating the Impact of Code Generation on Software Security

**Branch**: `001-eval-llm-code-security` | **Date**: 2026-10-15 | **Spec**: [spec.md](../specs/001-eval-llm-code-security/spec.md)  
**Input**: Feature specification from `/specs/001-eval-llm-code-security/spec.md`

## Summary
The project must compare vulnerability profiles of human‑written vulnerable code with code generated by a public LLM for the same functionality.  
The plan builds a paired dataset (human ↔ LLM), validates functional equivalence, runs two open‑source static analysis tools (Semgrep, SonarQube) inside Docker, aggregates findings, performs paired statistical tests (McNemar’s / exact McNemar’s), conducts a confidence‑threshold sensitivity sweep, audits a random subset, applies bias‑correction using tool precision/recall, and finally produces a reproducible markdown report with tables and figures.

## Technical Context
**Language/Version**: Python 3.11  
**Primary Dependencies**: `datasets`, `transformers`, `sentence-transformers`, `semgrep`, `sonarqube-scanner` (Docker), `pandas`, `numpy`, `scipy`, `statsmodels`, `matplotlib`, `pytest` (all CPU‑compatible)  
**Storage**: File‑based under `data/` (raw, derived, outputs)  
**Testing**: `pytest` for unit‑test execution of generated code; `pytest` also validates pipeline steps.  
**Target Platform**: Linux GitHub Actions runner (2 CPU cores, ~7 GB RAM, ~14 GB disk)  
**Performance Goals**: Entire pipeline ≤ 6 h, peak RAM ≤ 6 GB (safety buffer)  
**Constraints**: All external datasets must be fetched from the verified URLs listed in the research document; Docker images for Semgrep and SonarQube must match versions documented in the methodology; random seeds pinned for reproducibility.  
**Scale/Scope**: Target **300** paired samples (≥ 150 human + 150 LLM) to achieve >80 % power for detecting a medium odds‑ratio (~2.0) in McNemar’s test, especially for low‑frequency OWASP categories (see Power Analysis below).  

## Power Analysis
McNemar’s effect size is expressed as an odds ratio. Assuming a **medium odds‑ratio of ≈ 2.0** for the most common vulnerability types, a two‑sided α = 0.05 test with 80 % power requires roughly **260 – 300** paired observations. We therefore target **300** pairs, acknowledging that if the open dataset cannot supply this many, the limitation will be reported transparently.

| VII. Statistical Significance Threshold | McNemar’s test results are reported with raw and Bonferroni‑adjusted p‑values; non‑significant results are labeled “inconclusive”. |

# Research: Evaluating the Impact of Code Generation on Software Security

## Objective
Quantify how code generated by a public LLM *associates* with human‑written vulnerable code in terms of static‑analysis‑detected security issues.

## Dataset Strategy
| Role | Dataset | Source URL(s) | Notes |
|------|---------|---------------|-------|
| Human‑written vulnerable code (ground‑truth) | **Juliet Test Suite (SARD)** – vulnerable C/Python snippets | | Open‑source collection of human‑authored vulnerable code with precise CWE labels; used as the baseline for FR‑001 and SC‑005. |
| LLM‑generated vulnerable code | **OWASP Top 10 LLM Dataset** (v1.0) | https://huggingface.co/datasets/cedricf/owasp_top_10_llm/resolve/main/dataset_info.json | Used **only** as the source of prompts for generation; not a ground‑truth human dataset. |
| Additional SQL‑injection examples | Mahabharat OWASP SQL‑Injection CSV | https://huggingface.co/datasets/mahabharat/OWASP/resolve/main/Sqlinjection.csv | Provides extra samples for the “Injection” category. |

*Rationale*: The original spec requested Devign or CodeXGLUE, which are not directly downloadable in CI. The **Juliet Test Suite** satisfies the open‑access requirement, contains labeled vulnerabilities, and meets SC‑005 (≥ 5 OWASP categories). The OWASP LLM dataset is retained solely for prompting the LLM; it does **not** serve as the human baseline.

## Methodological Decisions
| Decision | Rationale |
|----------|-----------|
| **LLM Generation** | Use the lightweight **Salesforce/codegen‑350M‑multi** model (`codegen-350M-multi` revision `2023-11-01`) via HuggingFace `transformers`. Temperature = 0 for deterministic output, max_new_tokens = 512. This model fits comfortably on the free CPU runner (addresses concern data_resources‑dabdb55d). |
| **Functional Equivalence Test** | Require **either** (a) successful execution of any provided unit tests with **≥ 90 %** coverage **or** (b) semantic similarity ≥ 0.85 using `sentence‑transformers/all‑mpnet‑base‑v2`. When unit tests are absent, the semantic similarity criterion alone suffices (addresses methodology‑b8aa7581 and resolves the schema contradiction). |
| **Static Analysis Tools** | Semgrep (Docker) with OWASP rule set; SonarQube Community Edition (Docker). Both emit structured JSON, meeting Constitution VI. |
| **Statistical Test** | Primary: McNemar’s test for paired binary outcomes per vulnerability type (`statsmodels.stats.contingency_tables.mcnemar`). If any cell is zero, re‑run with `exact=True`. Bonferroni correction applied across all tested types (multiple‑comparison control). |
| **Bias Correction** | Tool precision/recall estimated on a held‑out Juliet subset (Phase 1.4) are used to compute weighting factors that adjust raw vulnerability counts before McNemar testing (addresses methodology‑3499be40 and scientific_soundness‑a15e5eea). |
| **Sensitivity Analysis** | Sweep confidence thresholds 0.0, 0.5, 0.9; map SonarQube severity to numeric confidence via a linear scaling (CRITICAL = 1.0, HIGH = 0.75, MEDIUM = 0.5, LOW = 0.25) with justification (addresses methodology‑7d4349e5). |
| **Manual Audit** | Random **≥ 20 %** stratified subset of flagged findings audited via lightweight fuzzing (`afl‑fast`) or manual review; audit results compute a **calibration factor** that rescales bias‑corrected counts prior to final reporting (addresses methodology‑b64889c4). |
| **Power Consideration** | Target **300** paired samples (≈ 150 per group) to achieve >80 % power for an odds‑ratio of 2.0 in McNemar’s test, especially for low‑frequency OWASP categories (addresses methodology‑25273281). |
| **Tool Validation Integration** | Precision/recall from the held‑out validation set are directly incorporated as bias‑correction weights in the statistical analysis (addresses methodology‑3499be40 and scientific_soundness‑a15e5eea). |
| **Associational Language** | All statements frame findings as *associations* rather than causal impacts, respecting the observational paired design (addresses methodology‑99eb541d). |

# Data Model: Evaluating the Impact of Code Generation on Software Security

## Overview
The research pipeline manipulates three core entities, plus an auxiliary pairing construct needed for the paired statistical test:

| Entity | Purpose |
|--------|---------|
| **CodeSample** | Represents a single code snippet (human or LLM‑generated). |
| **VulnerabilityFinding** | Represents a single static‑analysis detection linked to a `CodeSample`. |
| **AnalysisResult** | Summarises aggregated counts and statistical test outcomes per vulnerability type. |
| **PairOutcome** *(new)* | Captures the binary presence/absence of a given vulnerability type for **both** members of a paired sample, enabling a proper 2×2 McNemar contingency table. |

All entities are defined by JSON‑compatible schemas stored under `contracts/`. The schemas are also used by the test suite (`tests/contract/test_contracts.py`) to validate generated artefacts.

## Entity Definitions (informal)

### CodeSample
- `sample_id`: UUID string.  
- `source`: `"human"` or `"llm"`.  
- `functionality_id`: Stable identifier linking paired human/LLM samples.  
- `syntax_valid`: Boolean.  
- `functional_equivalence_verified`: Boolean (true if unit‑test coverage ≥ 90 % **or** semantic similarity ≥ 0.85).  
- `raw_content`: String (the source code).  
- `language`: `"python"` | `"c"` | … (derived from file extension).  

### VulnerabilityFinding
- `finding_id`: UUID string.  
- `code_sample_id`: UUID referencing `CodeSample`.  
- `tool_source`: `"semgrep"` | `"sonarqube"`.  
- `vulnerability_type`: String (e.g., `"SQL Injection"` – aligns with OWASP Top 10).  
- `severity`: `"LOW"` | `"MEDIUM"` | `"HIGH"` | `"CRITICAL"`.  
- `line_number`: Integer.  
- `confidence_score`: Float in `[0, 1]` (Semgrep `confidence` or mapped SonarQube severity).  
- `rule_id`: String (tool‑specific rule identifier).  
- `validated_by_audit`: Boolean (optional; filled after manual audit).  

### AnalysisResult
- `result_id`: UUID string.  
- `vulnerability_type`: String.  
- `human_count`: Integer (number of human samples flagged).  
- `llm_count`: Integer (number of LLM samples flagged).  
- `total_pairs`: Integer (size of the paired set for this type).  
- `p_value`: Float (raw p‑value from McNemar’s test).  
- `p_value_adj`: Float (Bonferroni‑adjusted p‑value).  
- `is_significant`: Boolean (adjusted p < 0.05).  
- `test_method`: String (`"McNemar"` or `"Exact McNemar"`).  
- `confidence_threshold`: Float (the threshold used for this row; `null` for primary analysis).  

### PairOutcome *(new)*
- `pair_id`: UUID string (matches the `functionality_id` of the two `CodeSample`s).  
- `vulnerability_type`: String.  
- `human_flag`: Boolean (1 = vulnerability detected in human code, 0 = not).  
- `llm_flag`: Boolean (1 = vulnerability detected in LLM code, 0 = not).  

These definitions are formally captured in the YAML contracts below, with `PairOutcome` added as a new contract file.

# Quickstart: Running the Code‑Generation Security Study

## Prerequisites
1. **GitHub Actions runner** (or local Linux env with at least 2 CPU cores, ~7 GB RAM).  
2. **Python 3.11** (installed via `pyenv` or system).  
3. **Docker** (required for Semgrep & SonarQube).  
4. **Hugging Face token** (optional, only needed if you hit rate limits on the CodeGen‑350M model). Set as environment variable `HF_TOKEN`.

## Setup
```bash
# Clone the repository (assumes you are in the project root)
git clone <repo-url>
cd PROJ-347-evaluating-the-impact-of-code-generation

# Create a virtualenv and install pinned dependencies
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt   # pins exact versions, including transformers

# Verify Docker images are available (will be pulled automatically on first run)
docker pull returntocorp/semgrep:1.46.0
docker pull sonarqube:9.9-community
```

## Execute the Full Pipeline
```bash
# Run the orchestrator script (all steps are logged under logs/)
python -m src.run_pipeline \
    --seed 42 \
    --max-pairs 300 \
    --confidence-thresholds 0.0 0.5 0.9
```
- `--seed` fixes all randomness.  
- `--max-pairs` caps the number of paired samples (default set according to the power analysis).  
- `--confidence-thresholds` triggers the sensitivity sweep.

The script performs:
1. Data download & LLM generation (Phase 0) using the lightweight **CodeGen‑350M‑multi** model.  
2. Syntax & functional checks.  
3. Static analysis with Semgrep & SonarQube (Phase 1).  
4. Aggregation, bias‑corrected paired statistical testing, and sensitivity analysis (Phase 2).  
5. Random audit of **≥ 20 %** flagged findings with calibration (Phase 3).  
6. Report generation (`reports/report.md`) and figure export (`reports/figures/`).

## Inspect Results
- **Aggregated counts**: `data/outputs/vuln_counts.csv`  
- **Statistical table**: `data/outputs/analysis_results.csv`  
- **Sensitivity sweep**: `data/outputs/sensitivity.csv`  
- **Final report**: `reports/report.md` (open in any markdown viewer).  

## Re‑running / CI Integration
The same command can be placed in a GitHub Actions workflow (`.github/workflows/research.yml`). The workflow automatically enforces a timeout and RAM limit; failures will be reported as CI errors.
