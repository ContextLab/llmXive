# Implementation Plan: Evaluating the Impact of Code Generation on Software Security

**Branch**: `001-eval-llm-code-security` | **Date**: 2026-10-12 | **Spec**: [spec.md](../specs/001-eval-llm-code-security/spec.md)  
**Input**: Feature specification from `/specs/001-eval-llm-code-security/spec.md`

## Summary
The project must compare vulnerability profiles of human‑written vulnerable code with code generated by a public LLM for the same functionality.  
The plan builds a paired dataset (human ↔ LLM), validates functional equivalence, runs two open‑source static analysis tools (Semgrep, SonarQube) inside Docker, aggregates findings, performs paired statistical tests (McNemar’s / exact McNemar’s), conducts a confidence‑threshold sensitivity sweep, audits a random 10 % subset, and finally produces a reproducible markdown report with tables and figures.

## Technical Context
**Language/Version**: Python 3.11  
**Primary Dependencies**: `datasets`, `openai`, `semgrep`, `sonarqube-scanner` (Docker), `pandas`, `numpy`, `scipy`, `statsmodels`, `matplotlib`, `sentence-transformers` (all CPU‑compatible), `pytest` (for unit tests)  
**Storage**: File‑based under `data/` (raw, derived, outputs)  
**Testing**: `pytest` for unit‑test execution of generated code; `pytest` also validates pipeline steps.  
**Target Platform**: Linux GitHub Actions runner (2 CPU cores, ~7 GB RAM, ~14 GB disk)  
**Project Type**: Research library / CLI tool  
**Performance Goals**: Entire pipeline ≤ 6 h, peak RAM ≤ 6 GB (safety buffer)  
**Constraints**: All external datasets must be fetched from the verified URLs listed below; Docker images for Semgrep and SonarQube must match versions documented in the methodology; random seeds pinned for reproducibility.  
**Scale/Scope**: Minimum 100 paired samples (≥ 50 human + 50 LLM) to satisfy SC‑001 and enable paired tests.

## Constitution Check
| Principle | Compliance Statement |
|-----------|----------------------|
| I. Reproducibility | All steps are scripted, random seeds are fixed (`numpy.random.seed(42)`, `torch.manual_seed(42)`, OpenAI temperature = 0). Data is downloaded from the same canonical URLs on every runner execution. |
| II. Verified Accuracy | Citations are limited to the three verified dataset URLs (see Research.md). No unverified external references are introduced. |
| III. Data Hygiene | Raw dataset files are checksum‑verified (SHA‑256 recorded in `data/checksums.json`). Every transformation writes a new file (`*_derived.csv/json`) with provenance metadata. |
| IV. Single Source of Truth | Every figure/table in the final report references a specific row in the aggregated CSVs (`data/aggregated/vuln_counts.csv`, `data/analysis/results.csv`). |
| V. Versioning Discipline | All artifacts are stored under `data/` with content hashes in `state/projects/PROJ-347-evaluating-the-impact-of-code-generation.yaml`. |
| VI. Static‑Analysis Tool Fidelity | Semgrep and SonarQube are executed via official Docker images (`returntocorp/semgrep:latest`, `sonarqube:community`). JSON outputs are parsed directly without manual editing. |
| VII. Statistical Significance Threshold | McNemar’s test results are reported with raw p‑values; Bonferroni‑adjusted p‑values are compared against the < 0.05 threshold. Non‑significant results are labeled “inconclusive”. |

## Complexity Tracking
All functional requirements (FR‑001 … FR‑007) are covered by the phased steps below. No constitution violations remain; the only deviation from the original spec is the substitution of the OWASP‑top‑10 LLM dataset for the unavailable Devign/CodeXGLUE sources (see Research.md for justification).

## Phase‑wise Implementation Plan (maps FR/SC)

| Phase | Step | Description | FR/SC addressed |
|-------|------|-------------|-----------------|
| **0 – Data Acquisition & Pairing** | 0.1 | Download OWASP top‑10 LLM dataset from the three verified URLs; verify SHA‑256 checksums. | FR‑001, FR‑007 |
| | 0.2 | Filter to rows that contain a `code` field and a `vulnerability_label`. Exclude unlabeled rows. | FR‑007 |
| | 0.3 | For each human code sample, call OpenAI `gpt‑3.5‑turbo` with a deterministic prompt (temperature = 0, max_tokens = 1024). Retry up to 3 times on error. | FR‑001 |
| | 0.4 | Syntax validation using language‑specific parsers (Python `ast`, C `clang -fsyntax-only`). Flag invalid samples; log count. | FR‑001 |
| | 0.5 | Functional equivalence: if unit tests are present, run them (`pytest --maxfail=1`). Otherwise compute semantic similarity with `sentence‑transformers/all‑mpnet‑base‑v2`; accept ≥ 0.85. Record `functional_equivalence_verified`. | FR‑001 |
| | 0.6 | Compute SC‑001 metric: `valid_llm / total_prompts`. | SC‑001 |
| **1 – Static Analysis Execution** | 1.1 | Pull Semgrep Docker image, run with OWASP rule set on both code directories, output JSON (`semgrep_results.json`). | FR‑002 |
| | 1.2 | Pull SonarQube community Docker image, start scanner, run analysis, export findings via SonarQube REST API to `sonarqube_results.json`. | FR‑002 |
| | 1.3 | `memory_monitor.py` watches each tool; if RAM > 6 GB, terminate process, log OOM, continue. | FR‑002 |
| | 1.4 | Parse both JSONs, normalise fields to `VulnerabilityFinding` schema (add `confidence_score` from Semgrep `confidence` or map SonarQube severity → numeric). | FR‑003 |
| **2 – Aggregation & Statistical Comparison** | 2.1 | Aggregate counts per `vulnerability_type` and `source` (human vs. LLM) into `vuln_counts.csv`. | FR‑003 |
| | 2.2 | For each vulnerability type, run paired McNemar’s test (`statsmodels.stats.contingency_tables.mcnemar`). If any cell = 0, switch to exact McNemar’s (`scipy.stats.binom_test`). | FR‑004 |
| | 2.3 | Apply Bonferroni correction across all tested types; store adjusted p‑values. | SC‑002, VII |
| | 2.4 | Sensitivity sweep: repeat 2.1‑2.3 for confidence thresholds 0.0, 0.5, 0.9; record variation. | FR‑006, SC‑003 |
| **3 – Manual Audit / Fuzzing Sub‑sample** | 3.1 | Randomly select ≥ 10 % of flagged findings (stratified by type) using a fixed seed; run a lightweight fuzzing harness (`afl‑fast` in Docker) or manual reviewer script; set `validated_by_audit`. | FR‑004 |
| **4 – Reporting** | 4.1 | Generate `report.md` with: (a) table of raw counts, (b) adjusted p‑values, (c) significance flags, (d) SC‑001 compliance, (e) memory/time summary. | FR‑005 |
| | 4.2 | Create bar‑chart PNGs (`figures/vuln_rate_comparison.png`) via `matplotlib`. | FR‑005 |
| | 4.3 | Export final CSVs (`data/outputs/vuln_counts.csv`, `data/outputs/analysis_results.csv`). | FR‑005 |
| **Cross‑cutting** | X.1 | All scripts log to `logs/` with timestamps; logs are version‑controlled via content hash. | I, III |
| | X.2 | `requirements.txt` pins exact versions (e.g., `semgrep==1.46.0`, `torch==2.2.0+cpu`). | I, V |

**Success‑Metric Checks (SC‑004, SC‑005)**  
- After Phase 1, a CI step asserts `max_memory_used <= 6 GB` and total runtime `<= 6 h`.  
- After Phase 2, verify that `vuln_counts.csv` contains ≥ 5 distinct `vulnerability_type` values (OWASP Top 10 subset).  

---

**Decision / Rationale (Research.md)**  
All heavy computation runs on CPU; no GPU is required. LLM calls are external API calls (network I/O, not GPU‑bound). Semgrep and SonarQube are pure CPU Docker containers, comfortably fitting the 2‑core runner.
