# Implementation Plan: Evaluating the Efficacy of Code Summarization Techniques for Bug Localization

**Branch**: `001-evaluating-code-summarization-bug-localization` | **Date**: 2025-01-15 | **Spec**: `spec.md`
**Input**: Feature specification from `/specs/001-evaluating-code-summarization-bug-localization/spec.md`

## Summary

This project evaluates the **feasibility and correctness of the statistical analysis pipeline** for a study on code summarization. Due to CI constraints (6h runtime, CPU-only), the project does not recruit real human subjects or generate LLM summaries in real-time within the CI runner. Instead, it:
1.  **Validates the Data Pipeline**: Downloads and verifies the Defects4J v2.0 dataset (using community mirrors, with schema verification).
2.  **Simulates Human Interaction**: Uses a deterministic simulation to generate interaction logs that follow a Latin-square design, allowing the pipeline to be tested for correct handling of repeated measures and missing data.
3.  **Validates the Statistical Engine**: Runs McNemar's tests and LME models on the simulated data to ensure the pipeline correctly computes p-values, effect sizes, and confidence intervals.
4.  **Handles LLM Generation Offline**: The `codellama/CodeLlamab-hf` summaries are generated in an offline step (requiring a GPU) and stored as static artifacts. The CI pipeline loads these artifacts to analyze the "LLM condition" without re-running the generation.

**Scope Clarification**: The p-values and effect sizes derived from the simulated data are **not** claims about human efficacy. They are validation metrics confirming that the pipeline correctly recovers the parameters programmed into the simulation. The study is a **Pipeline Validation and Feasibility Study**.

## Complexity Tracking

| Violation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|-------------------------------------|
| Simulated Human Study | Real recruitment is impossible in CI (6h limit, no external network for forms). | A real web form would require a running server and external participants, violating the "reproducible on CI" constraint. Simulation allows rigorous statistical testing of the pipeline logic without external dependencies. |
| LLM Fallback Logic | LLM inference on CPU may timeout; spec requires fallback. | Hard-failing on LLM timeout would result in missing data for a condition, biasing the study. Fallback ensures balanced data per task. |
| Bootstrapping for CIs | Parametric assumptions for small N (a limited number of participants) are weak. | Standard t-tests/normal approximations may be inaccurate; bootstrapping provides robust CIs without distributional assumptions. |
| Offline LLM Generation | Running `CodeLlama-7b` on CI CPU is infeasible (hours per sample). | A "proxy" model would violate the spec's requirement for `codellama/CodeLlama-7b-hf`. The solution is to generate the summaries once (offline, GPU) and commit the artifacts, ensuring the CI pipeline analyzes the *actual* LLM outputs. |

## Startup & Validation Gate

**Phase 0: Startup & Validation** (Mandatory)
Before any data collection or simulation begins, the system MUST perform a local loopback latency test.
1.  **Latency Calibration**: Execute `code/simulation/latency_calibrator.py`.
2.  **Threshold Check**: The system MUST verify that the measured latency is ≤100ms.
3.  **Blocking Behavior**: If the test fails, `main.py` MUST abort with a non-zero exit code and an error message. No further steps (data download, simulation, analysis) are executed.
4.  **Integration**: This check is hardcoded into `code/main.py` as the first operation.

## CI Verification Mechanism

To satisfy SC-005 (Compute Feasibility), the `test_reproducibility.yml` workflow will:
1.  **Resource Monitoring**: Use `psutil` to log RAM and CPU usage at regular intervals during the analysis script execution.
2.  **Timeout Enforcement**: Set a `timeout` of an appropriate duration in the GitHub Actions job definition.
3.  **Failure Criteria**: The job MUST fail if:
    - The analysis script exceeds a substantial duration.
    - RAM usage exceeds a substantial threshold at any point.
    - The latency calibration fails.

To satisfy Constitution Principle V:

3.  **Output**: It MUST write the SHA-256 hashes to `state/.../artifact_hashes.yaml`.
4.  **Validation**: The CI pipeline MUST verify that the hashes in the YAML file match the current file contents.

## Dataset Versioning Protocol

To satisfy Constitution Principle VII:
1.  **Version Extraction**: The `fetch_defects4j.py` script MUST extract the commit hash or version tag from the HuggingFace response.
2.  **Recording**: It MUST write this value to `data/defects4j_version.txt`.
3.  **Validation**: The CI pipeline MUST verify that `data/defects4j_version.txt` exists and is non-empty.
