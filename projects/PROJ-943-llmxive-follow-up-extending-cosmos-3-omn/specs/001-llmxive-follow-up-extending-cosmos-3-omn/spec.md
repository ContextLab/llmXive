# Project Specification: llmXive follow-up: extending "Cosmos 3: Omnimodal World Models for Physical AI"

## 1. Introduction

### 1.1 Background
This project extends the research findings of "Cosmos 3: Omnimodal World Models for Physical AI" by investigating the "modality gap" between symbolic reasoning and continuous physical control in AI agents. The original study utilized synthetic datasets generated by the Cosmos 3 framework. However, due to availability constraints and the need for real-world grounded data, this project has pivoted to utilize the Bridge-to-Worlds dataset.

### 1.2 Objectives
- Transform continuous action vectors into discrete symbolic tokens.
- Train a lightweight proxy model (DistilBERT) to perform symbolic reasoning on these tokens.
- Compare the proxy model's performance on symbolic tasks versus continuous control tasks.
- Identify specific failure modes (Action Noise, Context Mismatch, Visual Ambiguity) in the model's predictions.

## 2. Scope

### 2.1 In Scope
- Data ingestion and transformation of the **Bridge Data** (bridge-to-worlds/bridge-data).
- Training of a single Hard Proxy model on CPU.
- Comparative statistical analysis of symbolic vs. physical performance.
- Error analysis and visualization of misclassified samples.
- Generation of a final research report and visualizations.

### 2.2 Out of Scope
- Training of large-scale foundation models (e.g., full Cosmos 3 retraining).
- Real-time deployment in a physical robot environment.
- Synthetic data generation (the project uses real data exclusively).

## 3. Assumptions and Requirements

### 3.1 Assumptions
- **Data Source Pivot**: The project assumes the availability and accessibility of the **Bridge-to-Worlds dataset** (`bridge-to-worlds/bridge-data`) as the primary data source. The original "Cosmos 3 synthetic dataset" mentioned in preliminary designs has been formally replaced. The Bridge Data provides real-world robotic interaction logs containing `actions` (continuous vectors) and `text_description` fields necessary for the symbolic transformation logic.
- **Hardware Constraints**: All training and inference must be executable on a standard CPU environment with ≤ 7 GB RAM and ≤ 6 hours total runtime for the training phase.
- **Streaming Capability**: The `datasets` library supports streaming large datasets without loading them entirely into memory, enabling processing within the RAM constraints.
- **Reward Signal**: The Bridge Data contains a `physics_reward` field (or equivalent) required for the continuous domain baseline validation. If this field is missing, the evaluation phase will abort as per strict data hygiene protocols.

### 3.2 Requirements
- **FR-001 (Data Ingestion)**: The system MUST fetch data from `bridge-to-worlds/bridge-data` using `streaming=True` and fail loudly if the source is unreachable (no synthetic fallbacks).
- **FR-002 (Transformation)**: The system MUST apply the composite rule defined in `code/data/schema/action_schema.json` (L2 norm of first 3 dims > 0.5 AND text keyword match) to label data as "constraint_violated" or "constraint_satisfied".
- **FR-003 (Model Training)**: The system MUST train a single DistilBERT model (Hard Proxy) on the transformed symbolic data.
- **FR-004 (Evaluation)**: The system MUST perform a statistical significance test (Shapiro-Wilk -> t-test/Wilcoxon) comparing symbolic and physical domain metrics.
- **FR-005 (Error Analysis)**: The system MUST categorize misclassified samples into "visual ambiguity", "logical complexity", and "context mismatch".
- **NFR-001 (Memory)**: Peak memory usage must not exceed 7 GB during any processing stage.
- **NFR-002 (Reproducibility)**: All scripts must be deterministic given fixed seeds, and the entire pipeline must be reproducible via `quickstart.md`.

## 4. Data Model

### 4.1 Input Data Schema (Bridge Data)
- `actions`: List[float] (Continuous action vector)
- `text_description`: str (Contextual text describing the step)
- `physics_reward`: float (Continuous reward signal for physical baseline)
- `observation`: dict (Visual/State observation, if available)

### 4.2 Intermediate Schema (Unified Dataset)
- `actions`: List[float]
- `text_description`: str
- `label`: str ("constraint_violated" | "constraint_satisfied")
- `norm_value`: float (Computed L2 norm)
- `keyword_match`: bool (Whether text matched schema keywords)
- `physics_reward`: float

### 4.3 Output Artifacts
- `code/data/processed/unified_dataset.jsonl`: Labeled dataset.
- `code/models/proxy_hard/model.pt`: Trained model weights.
- `code/data/results/comparative_analysis.json`: Statistical comparison results.
- `code/data/results/error_analysis_report.md`: Qualitative and quantitative error report.

## 5. Methodology

### 5.1 Data Transformation Pipeline
1. **Fetch**: Stream data from `bridge-to-worlds/bridge-data`.
2. **Filter**: Retain samples with valid `actions` and `text_description`.
3. **Compute**: Calculate L2 norm of the first 3 dimensions of `actions`.
4. **Check**: Verify if `text_description` contains keywords from `action_schema.json`.
5. **Label**: Apply composite logic (Norm > Threshold AND Keyword Match -> Violated).

### 5.2 Proxy Model Training
- **Architecture**: DistilBERT (base).
- **Input**: Tokenized `text_description` + embedded `norm_value`.
- **Task**: Binary classification (Violated vs. Satisfied).
- **Optimizer**: AdamW with learning rate scheduling.
- **Constraints**: CPU-only training, strict memory monitoring.

### 5.3 Comparative Analysis
- **Symbolic Domain**: Accuracy/F1 on the binary classification task.
- **Physical Domain**: Accuracy/F1 on predicting high/low `physics_reward` (thresholded).
- **Statistical Test**: Compare the distribution of errors or metric differences between domains using non-parametric tests if normality fails.

### 5.4 Error Analysis
- Extract samples where `predicted_label != true_label`.
- Categorize based on heuristics:
 - **Visual Ambiguity**: Low confidence in observation (if applicable).
 - **Logical Complexity**: High norm but no keyword match (or vice versa).
 - **Context Mismatch**: Text description contradicts action vector.

## 7. Risks and Mitigations

- **Risk**: Bridge Data `physics_reward` field is missing or inconsistent.
 - *Mitigation*: Implement strict validation in `evaluate.py` to abort with a clear error message if the field is not found (no proxy fallback).
- **Risk**: Memory overflow during streaming.
 - *Mitigation*: Enforce `streaming=True` and batch processing; implement memory monitoring in `train.py` to kill the process if >7GB.
- **Risk**: Synthetic data temptation.
 - *Mitigation*: Strict "fail loudly" policy in `download.py` and `transform.py`; no `try/except` blocks that fallback to `np.random` or mock data.

### 9.2 Statistical Test Logic
- **Normality Check**: Shapiro-Wilk test on the difference of metrics (Symbolic - Physical).
- **If Normal**: Paired t-test.
- **If Not Normal**: Wilcoxon signed-rank test.
- **Significance Level**: α = 0.05.
