## Unresolved concerns

- T035 (SHAP Consistency) depends on T020 (Training Code) but explicitly states it re-trains 'from scratch' on a sample. However, T035 is placed in Phase 4.5, which is parallel to T022 (Model Save). T035 requires the 'best configuration' from T023 (output of T021). T021 depends on T020. The dependency chain T020 -> T021 -> T023 -> T035 is valid, BUT T035 is marked as [P] (parallel-safe) in the header 'Phase 4.5: ... (Parallel Task)'. It cannot run in parallel with T022 because it requires the *hyperparameters* selected by T022/T023 logic to re-train the 'primary model configuration'. If T022/T023 are not complete, T035 does not know *which* configuration to re-train. This violates the 'Producer before consumer' rule for the configuration artifact.
- T030 (Verify artifact existence) depends on T036, T037, T027, T028, T038. T027 (Aggregate sensitivity) depends on T036 and T037. T036 and T037 depend on T022 (Best Model). T028 depends on T016. T038 depends on T016 and T022. The ordering is logically sound (T022 -> T036/37/38 -> T027 -> T030). However, T030 is listed as a task *within* the implementation block of US3, but it is a verification step that logically belongs *after* all US3 implementation tasks (T026, T029, T036, T037, T028, T038) are complete. Placing it inside the implementation block suggests it might be run before T029 or T036 are finished. It should be moved to a 'Post-Implementation Verification' sub-phase or explicitly ordered after T027/T038.
- T029 (Perturbation study) depends on T022 (Best Model) and T026 (SHAP values). T026 depends on T022. The dependency T022 -> T026 -> T029 is correct. However, T029 is described as 'Implement perturbation study in code/analysis/interpret.py'. T026 is also 'Implement ... in code/analysis/interpret.py'. While the dependency on the *output* of T026 is clear, the task description implies T029 is a separate implementation step. If T026 and T029 are both 'Implement' tasks in the same file, they should be ordered strictly: T026 (generate SHAP) MUST complete before T029 (use SHAP for masking) can begin. The current text lists them as separate items but the dependency 'DEPENDS ON: T026' is present. The risk is that a developer might implement T029's logic before T026's logic is finalized, leading to integration errors. The ordering is technically present but the 'Implementation' grouping is ambiguous.
- T035 is labeled as a 'Parallel Task' in the Phase 4.5 header, but the task description explicitly states it depends on T023 (hyperparameter search results) and T016. While it can run in parallel with T022 (Model Save) *if* T023 is already done, the header implies it is parallel to the entire Phase 4 (US2). If T023 is not complete, T035 cannot start. The 'Parallel' tag is misleading without a specific note that it is only parallel *after* T023 completion.
- T039 requires aggregating 'final_report.md' as an input artifact, but this artifact is the *output* of T039 itself. The task description creates a circular dependency where the task cannot begin because its required input (the report it is supposed to generate) does not exist. The task must be rewritten to aggregate raw metrics (metrics.json, csvs) directly, not a pre-existing final report.
- T040 depends on T039. If T039 fails to generate the 'final_report.md' due to the circular dependency noted above, T040 cannot execute its validation logic which relies on comparing results against the report. The task chain is broken. T040 must be redefined to validate against the raw artifacts (T022, T028, etc.) directly, independent of T039's output.
- T035 instructs the implementer to 'Re-train the primary model configuration... from scratch multiple times' but does not specify the exact hyperparameter values to use for this re-training. It references 'the best configuration' from T023, but T023 is a CSV file. The task must explicitly state: 'Load the row with the highest validation R² from artifacts/hyperparameter_search.csv and use those specific values (LR, Dropout, etc.) for the re-training loop.' Without this, the task is non-deterministic.
- T012 defines a 'steric_hindrance_proxy' formula and a threshold of 2.0. However, it does not specify the unit or scale of the input features (LogP, rotatable bonds) to ensure the threshold 2.0 is meaningful. While the Plan mentions this is a 'project-defined proxy', the task must explicitly state: 'Calculate proxy = CalcNumRotatableBonds(mol) + CalcCrippenDescriptors(mol)[0] (LogP). Filter if proxy > 2.0.' The current text is slightly ambiguous about whether the LogP value needs normalization before addition. Explicitly defining the raw calculation steps is required for deterministic execution.
- T036 describes sweeping 'top-k descriptors' where k ranges from 1 to total. This is a coarse description of a sensitivity sweep. While the logic is present, the task should explicitly define the step size or the specific set of k values to test (e.g., 'k = [1, 5, 10, 20, ..., N]') to ensure the implementer knows exactly how many iterations to run. The current 'ranges from 1 to total' could be interpreted as a loop of N iterations (potentially thousands), which might violate the 6-hour CI constraint if N is large. Specify the sampling strategy for k.
- T028 implements a 'static dictionary' to generate chemical descriptions for VIF pairs, which exceeds the spec's FR-007 requirement for 'descriptive joint analysis'. The spec requires flagging pairs for analysis, not inventing specific chemical interpretations (e.g., 'Electrophilic potential') that are not derived from the data or external citations, risking hallucination and violating the 'Verified Accuracy' principle.
- T036 implements a sensitivity sweep on 'top-k descriptors' (count-based), whereas FR-006 and the spec require sweeping 'descriptor inclusion cutoffs' (threshold-based). This is a semantic weakening of the requirement; the experimental variable (threshold vs. count) is different, failing to validate robustness against the specific cutoff parameter defined in the spec.
- T035 re-trains the model on a small stratified sample (N=2000/500) to measure SHAP consistency (SC-004), whereas the spec requires measuring consistency of rankings for the model trained on the full dataset. Using a different data subset introduces a confounding variable that weakens the validity of the consistency claim, effectively relaxing the SC-004 requirement.
- T012 defines a custom 'proxy' (sum of rotatable bonds and LogP) with a hardcoded threshold of 2.0 to filter steric hindrance, but the spec's Edge Cases require filtering based on a 'steric hindrance index'. The task lacks a verification step to validate that this specific proxy/threshold combination actually correlates with the exclusion of non-SN1 mechanisms, leaving the chemical validity of the filter unverified and the requirement semantically weakened.
