# Scheduler Trace Explanation

## Overview

The `data/processed/scheduler_trace.json` file serves as the primary audit log for the State-Guided Curriculum Scheduler (User Story 1). It records every decision made by the `CurriculumScheduler` during the training pipeline, enabling reproducibility, debugging, and post-hoc analysis of the curriculum selection strategy.

## Purpose

This trace file satisfies **Constitution Principle VI** (Transparency) and **FR-003** (Experimental Control) by:
1. Recording the exact state coverage vector at the time of selection.
2. Logging the specific metrics that triggered a task selection.
3. Capturing the fallback logic path if the primary criteria were not met.
4. Providing a deterministic record for replaying curriculum decisions.

## File Location

- **Path**: `data/processed/scheduler_trace.json`
- **Format**: JSON Lines (one JSON object per line) or JSON Array (depending on configuration).
- **Checksum**: Managed via `data/raw/.checksums.txt` and `code/scheduler/update_checksums.py`.

## Schema Definition

Each entry in the trace file corresponds to a single scheduler invocation (typically per batch of rollouts).

```json
{
 "timestamp": "2023-10-27T14:30:00.000Z",
 "phase": "phase_1" | "phase_2" | "fallback_entropy" | "fallback_random",
 "batch_id": 12,
 "current_coverage_vector": [0, 1, 0, 0,...],
 "coverage_ratio": 0.45,
 "selected_task_params": {
 "task_id": "mobilegym_dark_mode_toggle",
 "difficulty_seed": 42,
 "target_metric": "dark_mode_coverage"
 },
 "metrics_triggered": [
 {
 "variable_name": "dark_mode",
 "transition_type": "uncovers",
 "reason": "Targeting low coverage variable for Phase 1 expansion"
 }
 ],
 "fallback_reason": null,
 "entropy_score": 0.82,
 "scheduler_config_snapshot": {
 "phase_1_threshold": 0.05,
 "phase_2_target_range": [0.10, 0.90],
 "max_entropy_fallback": true
 }
}
```

## Key Fields Explained

### `phase`
Indicates which logic branch of the scheduler was active:
- **`phase_1`**: Targeting variables with coverage < 5% (Exploration).
- **`phase_2`**: Targeting the "sweet spot" (10-90% success rate) for optimization.
- **`fallback_entropy`**: No tasks met criteria; selected via maximum entropy.
- **`fallback_random`**: Deadlock prevention; purely random selection.

### `metrics_triggered`
A list of objects describing exactly **why** a specific task was chosen.
- **`variable_name`**: The semantic proxy (e.g., `dark_mode`, `unread_count`) that influenced the decision.
- **`transition_type`**: How the metric influenced the selection (e.g., `uncovers`, `optimizes`, `balances`).
- **`reason`**: A human-readable explanation derived from the scheduler's internal logic (e.g., "Targeting low coverage variable for Phase 1 expansion").

This field is critical for **FR-005** (Transfer Evaluation) as it links curriculum decisions to specific state variables.

### `current_coverage_vector`
The binary vector representing the cumulative state coverage across all previous rollouts at the moment of this decision. This allows researchers to reconstruct the exact state of the environment when a task was selected.

### `fallback_reason`
If the scheduler entered a fallback mode (entropy or random), this field contains the string explaining why the primary logic failed (e.g., "No tasks found with success rate between 0.10 and 0.90").

## Generation Process

The trace is generated by `code/scheduler/curriculum_scheduler.py` via the `log_metrics_triggered` function in `code/scheduler/trace_logger.py`.

1. **Initialization**: `data/processed/scheduler_trace.json` is created with an empty array or header by `code/setup_scheduler_trace.py`.
2. **Logging**: During every batch execution, `CurriculumScheduler` calls `log_metrics_triggered` with the selected task and the reasoning context.
3. **Persistence**: The entry is appended to the JSON file.
4. **Validation**: Post-run, `code/scheduler/update_checksums.py` verifies the integrity of the trace file.

## Usage Examples

### Debugging Curriculum Bias
If the model fails to learn a specific state (e.g., `dark_mode`), inspect the trace for entries where `metrics_triggered` contains `dark_mode`. If the count is low, the scheduler may have prematurely exited Phase 1.

### Reproducibility
To reproduce an experiment exactly:
1. Load the `scheduler_trace.json` from the run.
2. Extract the `selected_task_params` and `scheduler_config_snapshot`.
3. Re-run the training pipeline with these parameters to verify identical outcomes.

### Sensitivity Analysis
Correlate the `entropy_score` and `phase` with the final success rate in `data/processed/sensitivity_report.md` to determine if the dynamic curriculum outperforms static baselines.

## Maintenance

- **Schema Updates**: Any changes to the trace schema must be reflected in `code/utils/scheduler_trace_schema.py`.
- **Versioning**: Major schema changes should increment the version number in the trace header to ensure backward compatibility with analysis tools.
- **Rotation**: For long-running experiments, the trace file may be rotated (e.g., `scheduler_trace_batch_001.json`, `scheduler_trace_batch_002.json`) to prevent file size issues.
