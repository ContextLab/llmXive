# Scheduler Trace Explanation

## Overview

The `scheduler_trace.json` file is a critical artifact generated by the `CurriculumScheduler` during the training process. It provides a detailed, chronological record of every decision made by the state-guided curriculum scheduler, enabling reproducibility, debugging, and analysis of the training dynamics.

This document explains the structure, purpose, and usage of the scheduler trace.

## File Location

- **Path**: `data/processed/scheduler_trace.json`
- **Format**: JSON Lines (one JSON object per line) or a single JSON array (depending on configuration).
- **Creation**: Generated automatically by `code/scheduler/curriculum_scheduler.py` and `code/scheduler/trace_logger.py` during training runs.

## Purpose

The trace serves three primary purposes:

1. **Reproducibility**: Allows exact reconstruction of the curriculum sequence for a given training run, given the same initial state and random seed.
2. **Debugging**: Enables developers to inspect why specific tasks were selected, helping identify issues in the scheduler logic (e.g., deadlocks, incorrect coverage calculations).
3. **Analysis**: Provides data for post-hoc analysis of the curriculum's effectiveness, such as correlation between state coverage transitions and model performance improvements.

## Trace Entry Structure

Each entry in the trace represents a single scheduling decision (i.e., the selection of a batch of tasks). A typical entry contains the following fields:

```json
{
 "timestamp": "2023-10-27T10:15:30.123456Z",
 "run_id": "exp_001",
 "phase": "phase_2_expansion",
 "metrics_triggered": [
 {
 "metric": "dark_mode_coverage",
 "current_value": 0.15,
 "target_range": [0.10, 0.90],
 "action": "targeting_low_coverage"
 },
 {
 "metric": "unread_count_coverage",
 "current_value": 0.85,
 "target_range": [0.10, 0.90],
 "action": "avoiding_high_coverage"
 }
 ],
 "selected_tasks": [
 {
 "task_id": "mobilegym_task_123",
 "difficulty_score": 0.45,
 "state_vector": [0, 1, 0, 0,...]
 }
 ],
 "reasoning": "Selected tasks to maximize entropy in low-coverage regions.",
 "entropy_score": 0.82,
 "fallback_applied": false
}
```

### Field Descriptions

- **`timestamp`**: ISO 8601 timestamp of when the decision was made.
- **`run_id`**: Unique identifier for the training run (e., `exp_001`).
- **`phase`**: The current phase of the curriculum (e., `phase_1_initial`, `phase_2_expansion`, `phase_3_convergence`).
- **`metrics_triggered`**: A list of objects describing which state coverage metrics triggered the selection logic.
 - **`metric`**: The name of the semantic proxy (e., `dark_mode`, `unread_count`).
 - **`current_value`**: The current coverage ratio (0.0 to 1.0) for this metric.
 - **`target_range`**: The desired range for this metric in the current phase.
 - **`action`**: The specific action taken based on the metric (e., `targeting_low_coverage`, `avoiding_high_coverage`).
- **`selected_tasks`**: The list of tasks chosen for this batch, including their IDs, difficulty scores, and the state vector they are expected to cover.
- **`reasoning`**: A human-readable string explaining the scheduler's logic for this specific decision.
- **`entropy_score`**: A numerical measure of the diversity of the selected batch.
- **`fallback_applied`**: Boolean indicating whether the scheduler had to fall back to maximum entropy or random selection because no tasks met the strict criteria.

## How the Trace is Generated

The trace is generated by the `code/scheduler/trace_logger.py` module, which hooks into the `CurriculumScheduler` (located in `code/scheduler/curriculum_scheduler.py`).

1. **Initialization**: At the start of a training run, `ensure_trace_file_exists()` creates or opens the `data/processed/scheduler_trace.json` file.
2. **Logging**: During each scheduling cycle, `log_metrics_triggered()` is called with the current state coverage vector and the resulting decision.
3. **Writing**: The entry is serialized to JSON and appended to the trace file.

## Usage Examples

### Debugging a Deadlock

If the scheduler appears to stall or select the same tasks repeatedly, inspect the trace for entries where `fallback_applied` is `true` or where the `reasoning` field indicates "Deadlock Prevention".

```bash
grep -A 5 "fallback_applied.*true" data/processed/scheduler_trace.json
```

### Analyzing Phase Transitions

To understand when the curriculum transitions from Phase 1 (exploration) to Phase 2 (exploitation), filter entries by the `phase` field.

```bash
jq 'select(.phase == "phase_2_expansion")' data/processed/scheduler_trace.json | head -n 10
```

### Correlating with Performance

The trace can be joined with `data/processed/convergence_results.json` (from `code/analysis/convergence.py`) using the `run_id` to analyze how specific scheduling decisions impacted model success rates.

## Schema Validation

The structure of the trace entries is validated against `contracts/coverage.schema.yaml` (specifically the `semantic_proxies` and `coverage_vector` sections) to ensure consistency. The `code/utils/scheduler_trace_schema.py` module provides validation utilities.
