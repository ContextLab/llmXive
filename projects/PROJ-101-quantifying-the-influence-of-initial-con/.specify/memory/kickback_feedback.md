## Unresolved concerns

- FR-007 and the Edge Cases section explicitly define the 'unphysical' flagging threshold as sigma_noise > 0.1 (checking if trajectory leaves attractor). However, the Edge Cases section also states: 'What happens if the noise level is so high (sigma_noise > 1.0)...' creating a conflict. More critically, T016 implements the check against 'sigma_noise > 0.1' which matches FR-007 but contradicts the Edge Case text's '1.0' example. The spec is internally inconsistent (0.1 vs 1.0), and the task follows the FR-007 text (0.1) but fails to address the ambiguity or the specific '1.0' scenario mentioned in Edge Cases. This leaves a requirement gap: if the spec intends 1.0 as the hard limit for 'leaving the attractor' (as implied by the Edge Case question), T016 is insufficient. If 0.1 is the limit, the Edge Case text is misleading. A task must resolve this specific threshold ambiguity to satisfy FR-007.
- FR-006 requires the system to 'validate numerical stability... before proceeding to noisy analysis'. The tasks separate this into T024 (compute baseline) and T025 (validation logic). However, there is no explicit task to implement the *gating mechanism* in the pipeline orchestrator (T009/T036) that enforces this dependency. T025 describes the logic, but without a task to wire this logic into the main execution flow to 'abort' or 'halt' if validation fails, the requirement 'before proceeding' is not fully covered by a discrete task. The implementation of the fail-stop mechanism is missing.
- US-1 Acceptance Scenario 3 specifies a performance constraint: 'process completes within 30 seconds on a standard CPU' for N=5. While T018 covers generating trajectories for N=5, there is no specific task to implement a *validation test* or *benchmark* to verify this 30-second runtime constraint. The 'Independent Test' for US-1 mentions verifying dimensions and noise stats, but not the runtime. A task is missing to ensure this measurable outcome (SC-004) is tested.
- Task T021 is tagged '[US2]' but references 'tests/unit/test_baseline.py'. The spec's US-2 Independent Test and Acceptance Scenarios focus on FTLE convergence and baseline computation. The 'non-chaotic detection' (rho < 24.74) is listed under 'Edge Cases' and FR-006/FR-007 context, not explicitly as a core part of US-2's primary goal (computing FTLE). While related, the task description 'Unit test for "non-chaotic" detection... and abort' seems to conflate the validation logic (FR-006) with the baseline computation (US-2). A clearer mapping or a separate task for the 'non-chaotic abort' logic (distinct from baseline computation) would improve traceability, though the current tag is not entirely wrong.
- Task T024 (compute asymptotic baseline) and T025 (validate stability) are listed as independent implementation tasks within Phase 4. However, FR-006 and Constitution Principle VI mandate that the clean system's baseline MUST be validated as stable BEFORE proceeding to noisy analysis (US2/US3). The current ordering allows T022/T023 (FTLE on noisy data) to potentially execute before T025 confirms the baseline is valid. A hard dependency or gating task is required to enforce 'Baseline Validated' -> 'Noisy Analysis' flow.
- Task T016 implements 'unphysical' detection for US1, but the spec (Edge Cases) and FR-007 define the threshold as sigma_noise > 1.0 for leaving the attractor, while T016/T026 descriptions imply a check against 0.1. While this is a logic error, it creates an ordering violation: if T016 aborts valid high-noise trials (sigma=0.5) prematurely, downstream tasks (T022-T036) that depend on that specific data range will never receive the required input artifacts, breaking the data-flow for the full parameter sweep.
- Task T018 (orchestrate generation) is placed after T017 (loader). While T018 logically depends on T013-T016 (generator logic), it also implicitly depends on T017 (loader) to save the results. The current linear listing is acceptable, but the description should explicitly state that T018 triggers the full loop (N, sigma) and relies on T017's save logic to produce the artifacts consumed by Phase 4.
- Task T016 ('Implement ... "unphysical" detection logic') lacks a concrete deliverable and verification criteria. It does not specify the output artifact (e.g., a flag in the trajectory metadata, a specific exception type, or a log entry format) nor how to verify the abort mechanism (e.g., 'verify that the pipeline raises `UnphysicalTrajectoryError` when sigma_noise > 0.1 and bounds are violated'). Without this, an implementer cannot deterministically execute or test the task.
- Task T026 ('Implement ... logic to detect non-chaotic regimes') is not self-contained. It references 'rho < 24.74' but does not specify the input source for `rho` (config file? argument?) nor the exact failure artifact (e.g., 'raise `NonChaoticSystemError` with message X'). The task fails to name the specific error class or exit code required for the implementer to build the verification test.
- Task T024 ('Implement ... Richardson extrapolation to compute ... asymptotic baseline') is too coarse and lacks a concrete deliverable definition. It does not specify the output file format (e.g., 'save to `data/processed/baseline_{N}_{D}.json` with keys `lambda_max`, `error_estimate`') or the convergence criterion to be used in the implementation (e.g., 'stop when relative change < 1e-6'). The implementer cannot determine when the task is 'done' without guessing the output schema.
- Task T001 ('Create project structure per implementation plan') is too coarse. It covers an entire phase of file creation. The `task_atomizer` will need to split this into individual file creation tasks (e.g., 'Create `code/__init__.py`', 'Create `tests/unit/` directory'). Flagging now to trigger downstream atomization.
- Task T037 ('Documentation updates in `docs/` and `quickstart.md`') is too coarse and vague. It does not specify which sections to update or the exact content to generate (e.g., 'Update `quickstart.md` with the new CLI arguments for `--noise-level`'). This requires atomization into specific documentation generation tasks.
- Task T016 and T012 implement the 'unphysical' flagging check against `sigma_noise > 0.1`. However, spec.md Edge Cases and FR-007 explicitly define the threshold for flagging 'unphysical' trajectories (leaving the attractor) as `sigma_noise > 1.0`. The task implementation silently relaxes the spec's constraint, causing premature aborts for valid high-noise experiments (0.1 < sigma <= 1.0) and violating the requirement to only flag data as unphysical when it leaves the attractor.
- Spec FR-006 and US-2 require validating that the clean system's maximum Lyapunov exponent is stable (converged) *before* proceeding to noisy analysis. Tasks T024 (baseline computation) and T025 (validation logic) are listed as separate items without a defined gating dependency or fail-stop mechanism in the pipeline orchestrator (T009/T036). This creates a risk where the pipeline could execute noisy analysis on an unstable baseline, violating the constitutional requirement for numerical stability validation before analysis.
- Task T018 covers the generation of trajectories for N in {1, 3, 5, 10} as required by the plan. However, spec.md US-1 Acceptance Scenario 3 explicitly includes a performance constraint: 'process completes within 30 seconds on a standard CPU' for N=5. The tasks list lacks a specific verification step or test task to validate this runtime constraint, leaving a measurable acceptance criterion without a corresponding verification task.
