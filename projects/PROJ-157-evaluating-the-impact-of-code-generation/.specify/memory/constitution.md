# Evaluating the Impact of Code Generation Models on Code Security: A Fuzzing Study — Research Project Constitution

## Core Principles

### I. Reproducibility (NON-NEGOTIABLE)

Every result reported in this project MUST be reproducible by re-running the
project's `code/` against the project's `data/` on a fresh GitHub Actions
runner. Random seeds MUST be pinned in `code/`. External datasets MUST be
fetched from the same canonical source on every run.

### II. Verified Accuracy (inherits parent Principle II)

Every external citation in `idea/`, `technical-design/`,
`implementation-plan/`, or `paper/` MUST be verified by the
Reference-Validator Agent against the primary source before contributing
review points. Title-token-overlap with the cited source MUST be ≥
`CITATION_TITLE_OVERLAP_THRESHOLD` (default 0.7).

### III. Data Hygiene

Datasets MUST be checksummed and the checksum recorded under `data/`. No
data may be modified in place; every transformation MUST produce a new file
with a documented derivation. Personally identifying information MUST NOT
appear in committed data.

### IV. Single Source of Truth (inherits parent Principle I)

Every figure, statistic, or interpretation in the paper MUST trace back to
exactly one row in this project's `data/` and one block in this project's
`code/`. Derived numbers MUST NOT be hand-typed into the paper.

### V. Versioning Discipline

Every artifact under this project carries a content hash. The
Advancement-Evaluator Agent invalidates stale review records when the
hashed artifact changes. Every research-stage artifact change updates this
project's `state/projects/PROJ-157-evaluating-the-impact-of-code-generation.yaml` `updated_at` timestamp.

### VI. Deterministic Compilation & Fuzzing Isolation

All code snippets generated by LLMs and all human baseline solutions MUST be compiled using deterministic compiler flags (`-O0 -g`) inside a Docker container to ensure that binary behavior differences are attributable to source code logic rather than environment variance. Fuzzing execution MUST occur in isolated GitHub Actions runners with a fixed time budget (e.g., 30 minutes per binary) using the `timeout` utility to prevent resource exhaustion and ensure comparable crash detection windows.

*Justification*: This principle is grounded in the "Compilation pipeline" and "Fuzzing execution" sections of the idea body, which explicitly mandate Docker-based compilation with specific flags and fixed-budget execution on GitHub Actions to ensure reproducibility and fair comparison between LLM-generated and human-written code.

### VII. Quantitative Vulnerability Triage & Statistical Rigor

Vulnerability analysis MUST rely on parsing crash logs to map unique stack traces to specific vulnerability types (e.g., buffer overflow, use-after-free) and assign severity scores via a simplified CVSS-like rubric. Comparative analysis between LLM-generated and human groups MUST utilize non-parametric statistical tests (Mann-Whitney U, Kolmogorov-Smirnov) at α = 0.05 and compute effect sizes (Cliff's Δ) to validate hypotheses regarding bug frequency and severity.

*Justification*: This principle is explicitly grounded in the "Bug triage" and "Statistical analysis" sections of the idea body, which define the methodology for classifying vulnerabilities, scoring severity, and applying specific statistical tests (Mann-Whitney U, Kolmogorov-Smirnov) to the crash count and severity distributions.

## Reproducibility Requirements

- A `requirements.txt` (or `pyproject.toml`) at `projects/PROJ-157-evaluating-the-impact-of-code-generation/code/`
  pins every Python dependency.
- The Code-Execution Agent runs each task in an isolated virtualenv built
  from this requirements file; no global packages are assumed.
- Every notebook or script under `code/` is runnable end-to-end without
  manual intervention.

## Data Hygiene

- Every file under `data/` is checksummed in the project's
  `state/projects/PROJ-157-evaluating-the-impact-of-code-generation.yaml` `artifact_hashes` map.
- Raw data is preserved unchanged; derivations are written to new
  filenames.
- No commits are accepted that fail the Repository-Hygiene Agent's PII
  scan.

## Verified Accuracy Gate

The Reference-Validator Agent runs at three points:

1. On every artifact write that introduces or modifies citations.
2. Inside the Advancement-Evaluator before awarding any review point.
3. As a blocking gate on the `research_review` → `research_accepted`
   transition.

A reviewer's score MUST be set to 0.0 if the reviewed artifact has any
citation in `unreachable` or `mismatch` status.
