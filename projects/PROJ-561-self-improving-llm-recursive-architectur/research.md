# Research: Self-Improving LLM Recursive Architecture

## Introduction
This document outlines the research methodology, design constraints, and operational definitions for the recursive self-improvement pipeline of large language models. The goal is to establish a formal framework where an LLM can propose, validate, and execute architectural modifications to itself, subject to strict external verification.

## Methodology for Parameter Limits
### Determining MAX_PARAM_INCREASE_RATIO
The limit on parameter growth is determined by research into parameter efficiency curves and memory constraints. The specific value for `MAX_PARAM_INCREASE_RATIO` is currently **[deferred]** pending empirical analysis of the trade-off between model capacity and inference latency on the target hardware. The methodology involves:
1. Profiling the baseline model's memory footprint.
2. Simulating architectural expansions.
3. Calculating the ratio of new parameters to old parameters that keeps the system within the 7GB RAM safety constraint (SC-005).
4. Selecting the maximum ratio that satisfies these constraints without triggering immediate termination.

## External Oracle Protocol
To prevent the model from optimizing for its own hallucinated benchmarks, we enforce an **External Oracle** protocol.
- **Immutable Evaluation**: The evaluation metrics and datasets used to judge a proposed modification are immutable during the cycle.
- **Held-Out Data**: Benchmarks (GSM8K, ARC-Challenge, BoolQ) are strictly held-out from the model's proposal generation process. The model cannot see the test data or the evaluation script when generating architecture proposals.
- **Verification**: The oracle acts as a deterministic, external judge that compares the modified model's performance against the baseline. No internal metrics generated by the model itself are accepted as proof of improvement.

## External Validation Protocol
The **External Validation Protocol** ensures the integrity of the recursive loop.
- **Strict Separation**: The generative process (proposal) and the evaluative process (validation) are logically and physically separated.
- **Reproducibility**: Every evaluation run uses the same fixed seed and dataset subset to ensure that score changes are due to architectural changes, not stochastic variance.
- **Audit Trail**: All validation runs are logged with a hash of the evaluation environment to guarantee that the oracle has not been tampered with.

## Operational Definition of "Lasting Improvement"
To distinguish between transient gains (overfitting to a specific cycle's noise) and genuine architectural advancement, we define **lasting improvement** operationally:
- **Persistence Requirement**: A modification is considered to yield "lasting improvement" only if the performance gain persists across at least **two subsequent training cycles** (the "Turing Review" period).
- **Single-Epoche Gains**: A spike in performance during a single epoch or cycle that reverts in the following cycle is classified as a "transient gain" and does not trigger a permanent state update or model replacement.
- **Turing Review**: The system must demonstrate stability in the new architecture by successfully completing two full cycles of training and evaluation with the new weights before the new architecture is promoted to the "stable" baseline for the next iteration.

## Rollback Mechanism
To ensure system safety and prevent degradation, a **Rollback Mechanism** is enforced:
- **Threshold Check**: If the performance of a modified model drops below a defined threshold (e.g., >5% degradation from baseline) or fails to show lasting improvement after the Turing Review period, the system MUST revert to the previous stable checkpoint.
- **State Reversion**: The rollback process restores the model weights, configuration, and state file to the last known stable cycle `N-1`.
- **Failure Logging**: The failed cycle is logged as a negative data point for the scaling law analysis, and the pipeline proceeds to the next proposal without halting the entire process.

## Scaling Law Analysis
As per the West Review, we define a **Scaling Law Analysis** section to track the trajectory of improvements:
- **Power-Law Decay**: We expect the magnitude of improvement gains (Δperformance) to decay as a power law relative to the iteration count, reflecting the diminishing returns of recursive optimization.
- **Thermodynamic Bounds**: The analysis will also track the computational cost (FLOPs) vs. performance to identify the thermodynamic bounds of the recursion. If the cost of improvement exceeds the value of the gain, the recursion is deemed inefficient.

## Computational Irreducibility
Addressing the Wolfram Review, we explicitly acknowledge **Computational Irreducibility**:
- **No Closed-Form Prediction**: There is no closed-form mathematical prediction for the improvement trajectory of the recursive system. The complexity of the architecture search space cannot be reduced to a simple formula.
- **Empirical Mining**: The methodology relies entirely on the empirical mining of the architecture rule space. We must run the cycles to discover the outcomes; we cannot simulate the result of the recursion without executing it.

## Recursive Improvement vs. Adaptation
Per the Krakauer Review, we distinguish between two modes:
- **Recursive Improvement**: Optimization within a fixed environment (e.g., lowering loss on GSM8K).
- **Recursive Adaptation**: Evolutionary navigation of changing environments or blind-spots.
- **Stupidity Metric**: We define a "stupidity" or error cost metric to measure the system's failure to adapt when the environment shifts, ensuring the system does not over-optimize for a static benchmark at the cost of generalization.

## Success Criteria
- **SC-001**: The system must successfully complete at least one full cycle of proposal, validation, training, and evaluation.
- **SC-002**: The system must demonstrate "lasting improvement" as defined above.
- **SC-003**: The trajectory of improvements must be recorded and analyzed for scaling laws.
- **SC-004**: The system must operate within the defined computational budget (RAM/FLOPs).
- **SC-005**: The system must include a functional rollback mechanism.
