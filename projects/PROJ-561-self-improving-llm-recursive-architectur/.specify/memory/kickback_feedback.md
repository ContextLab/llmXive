## Unresolved concerns

- Task T005a depends on T005b but the verification step 'Verify that loading a non-existent dataset raises FileNotFoundError' is ambiguous. It does not specify which dataset file path to use for the test (e.g., 'data/raw/non_existent.json'). Without a specific path, the test is non-deterministic.
- Task T013b verification requires a 'subprocess.run' test that spawns a worker, modifies state, kills it, and restarts. The task does not specify the exact command to run in the subprocess or the specific state key to modify. This makes the test implementation non-deterministic.
- Task T015 requires creating 'templates/modification_proposal.j2' but does not provide the content or a reference to where the prompt template string is defined. The task says 'Create... containing the exact prompt string' but the string itself is missing from the task description, making it impossible to implement without hallucinating the prompt.
- Task T029 requires creating 'results/trajectory_schema.py' with a Pydantic model 'TrajectoryEntry'. The task lists the keys (cycle_number, param_count, etc.) but does not specify the exact data types (e.g., float vs int, precision) or the full schema definition. This leaves the implementation open to interpretation.
- Tasks T072 through T082 are too coarse and lack concrete deliverables. They describe high-level philosophical concepts ('Source of Authority', 'Stupidity Metric') without defining the exact metric formula, the specific log format, or the precise code structure. These need to be atomized into specific function signatures and output formats.
- Task T032 verification requires 'Unit test mocking utils.memory.get_ram_usage'. The task does not specify the exact mock return value or the threshold logic to verify. It says 'asserting batch_size is reduced' but does not define the initial vs reduced batch size values, making the test assertion ambiguous.
- Task T059 verification requires an oracle test that 'asserts the oracle returns consistent results... and cannot be patched'. The task does not define the 'patching' mechanism or the specific input/output pairs to test. This is a conceptual requirement, not an executable test specification.
- Tasks T072-T082 implement philosophical metrics ('Stupidity Metric', 'Bird vs. Frog', 'Rule Space Mining') attributed to simulated reviewers (Krakauer, Dyson, Wolfram) that are NOT present in spec.md or plan.md. This constitutes unrequested scope creep and violates the constraint that tasks must not introduce features without spec/plan anchoring.
- Task T067 implements a 'Rollback Mechanism' to revert to previous stable architecture. The spec's Edge Cases only mandate an 'Early-stop condition' (terminate if degradation ≥5%). Implementing a rollback logic that contradicts the spec's 'terminate and log' approach is a semantic weakening of the defined failure mode.
- Task T029 explicitly excludes 'plateau_cycle' and 'degradation_cycle' from `results/trajectory.json`, directing them to a separate file. However, spec.md User Story 2 Acceptance Scenario 2 mandates that `results/trajectory.json` MUST contain 'the cycle number where performance first plateaus'. This task violates the acceptance criterion by splitting the required data.
- Task T015 requires limiting 'prompt attempts to a reasonable number' for invalid modifications. The spec's Edge Cases define retry logic for training failures but do not specify a retry limit for the *modification proposal* itself. Implementing an arbitrary limit without spec authorization risks violating the requirement to 'prompt the model again' indefinitely until a valid proposal is found.
- Task T004 implements a memory watchdog that kills the process if RAM exceeds 7.0GB. Spec SC-005 requires 'peak RAM usage ≤7 GB'. If the watchdog triggers *after* the threshold is crossed, the peak usage technically exceeded the constraint. The task must ensure the check prevents the threshold from being breached (e.g., at 6.9GB) or the spec must define a tolerance window.
