## Unresolved concerns

- The plan uses Wikitext-2 for 'Calibration Benchmark' (ECE). Wikitext-2 is a language modeling dataset, not a calibration dataset. Expected Calibration Error (ECE) requires a classification task with known ground truth labels to compare predicted probabilities against actual accuracy. Using a generative language modeling task (next-token prediction) on Wikitext-2 to calculate ECE is a construct validity failure; the metric does not measure what the spec claims (calibration of reasoning). The plan must either switch to a classification benchmark with known labels or redefine the metric to 'Perplexity' (which measures generative confidence, not calibration in the classification sense).
- The plan proposes running GPT-2 124M training on a GitHub Actions free-tier runner (2 cores, 7GB RAM) for 3 cycles within 6 hours. Training a transformer, even a small one, for 1 epoch on a meaningful subset of OpenWebText (even 10k samples) on CPU alone will likely exceed the 6-hour wall-clock budget significantly. The power analysis is missing: there is no estimate of the number of training steps or time-per-step required to detect a 'statistically significant' improvement. If the training is too short to learn, the effect size is zero; if it is long enough to learn, the time budget is violated. The sample size (dataset subset) and training duration are not calibrated to the statistical power required to detect the hypothesized effect.
- The assumption that 'Verification logic... is logically separate from generative logic' is violated by the proposed method. The model proposes modifications based on its *own* analysis of previous performance. If the model's internal analysis is flawed (which is likely for a 124M model on OOD tasks), the modification will be flawed. The 'verification' is not an independent oracle but a feedback loop from the same system being modified. This creates a circular validation risk where the system optimizes for its own flawed self-assessment rather than true benchmark performance, invalidating the causal claim of 'improvement'.
- FR-009 requires fitting an exponential decay model and reporting the specific cycle number where performance plateaus or degrades. The plan.md 'Technical Context' and 'Modification Strategy' sections describe the iterative loop but contain no explicit task, phase, or data-model entity dedicated to performing this curve-fitting analysis or outputting the specific 'plateau/degradation cycle' index. The 'Data Flow' in data-model.md mentions 'Trajectory Data' but does not specify the analysis step required to derive the cycle number mandated by FR-009.
- FR-010 requires computing 'performance-per-FLOP' and 'performance-per-hour' metrics. While 'ModelCheckpoint' and 'PerformanceMetric' entities exist in data-model.md, the plan.md lacks a specific phase, contract, or quickstart step that defines the calculation logic for these derived trade-off metrics. The 'Technical Context' mentions 'Performance Goals' but does not outline the implementation of the trade-off analysis engine required to satisfy FR-010.

- The plan proposes using the LLM itself to 'propose modifications based on its analysis of the previous cycle’s performance.' Without an external, fixed oracle or a distinct validation set that was NOT used in the training loop or the modification prompt, the 'improvement' is definitionally guaranteed to be a result of overfitting to the evaluation criteria, not a structural gain. The 'modification proposal' is effectively a gradient ascent step on the evaluation metric, making the 'experiment' a confirmation of overfitting rather than a test of self-improvement.
