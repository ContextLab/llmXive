# MobileForge Logic Distillation: Specification

## 1. Introduction

This document outlines the requirements for extending the MobileForge framework with CPU‑tractable logic distillation. The goal is to train a lightweight model capable of generating corrective hints and action sequences for Android task automation based on UI states, while adhering to strict resource constraints (CPU‑only, <6 h training time) and statistical validation standards that are faithful to the original research question.

## 2. User Stories

### US-1: Data Extraction and Dataset Construction
As a researcher, I want to extract and filter `(UI_state, Corrective_Hint, Action)` triples from MobileForge logs, ensuring "failed‑then‑success" trajectories and purely linguistic hints, so that I can train a distilled model on high‑quality, coordinate‑free reasoning data. **(See SC-002)**

### US-2: CPU‑Tractable Model Training
As a researcher, I want to train a lightweight Encoder‑Only model (e.g., DistilBERT or a small LLaMA) on CPU to predict action sequences from UI states and hints, so that I can deploy the model in resource‑constrained environments without requiring GPU hardware.

### US-3: Evaluation and Statistical Validation
As a researcher, I want to evaluate the distilled model against a Random‑policy baseline and the full MobileForge visual policy on a representative set of **500** unseen AndroidWorld tasks, performing statistical significance testing with a **paired two‑tailed t‑test** on the binary success differences per task, so that I can rigorously validate the performance improvement of the distilled model. **(See FR-005, FR-007, SC-004)**

### US-4: Sensitivity Analysis & Robustness
As a researcher, I want to verify the robustness of results against "inconsistency tolerance" threshold variations and perform stress tests, so that I can ensure the model's performance is stable across different evaluation parameters. **(Justified as essential for assessing robustness of the hint‑driven approach.)**

### US-5: Hint Ablation Study
As a researcher, I want to run an ablation where the hint input is replaced with a generic "retry" prompt, keeping all other inputs identical, so that I can quantify the specific contribution of the corrective hint to model performance. **(See FR-009) (Justified to isolate the hint signal, directly addressing the core research question.)**

## 3. Functional Requirements

### FR-001: Data Pipeline
The system must extract triples from **MobileForge logs** (available via the internal repository `git@internal:mobileforge/logs.git`), filter for "failed‑then‑success" trajectories, and validate that hints are purely linguistic (no coordinate‑based visual grounding).  
*Validation Procedure*: each hint is scanned with a regular expression that matches common coordinate patterns (e.g., `\d+\s*x\s*\d+`, the words “pixel”, “coord”, or numeric tuples). Any hint containing a match is flagged as non‑linguistic. **Acceptance Criterion**: zero flagged hints in the final dataset.  
*Constraint*: Only logs generated by the MobileForge instrumentation are permitted as source data.

### FR-002: Model Architecture
The distilled model must utilize an **Encoder‑Only architecture** (e.g., DistilBERT, small LLaMA).  
*Justification*: Encoder‑only models keep the parameter count low while encoding UI state and hint jointly, satisfying the CPU‑only resource goal.  
*Constraint*: The model must be trainable on a **standard CPU runner** (8‑core Intel Xeon @2.5 GHz, 32 GB RAM) within 6 hours and have ≤100 M parameters.

### FR-003: Evaluation Dataset
The evaluation must use a set of **500 unseen AndroidWorld tasks** drawn from MobileForge log trajectories (failed‑then‑success with linguistic hints). The tasks must be logically disjoint from the training set.  
*Constraint*: Fixed N = 500 tasks as stipulated; dataset is sampled directly from the logs referenced in FR‑001.

### FR-004: Baseline Comparison
The system must compare the distilled model against **two baselines** on the exact same set of tracked tasks:
1. **Random‑policy baseline** – selects actions uniformly at random. The random seed is fixed (`seed=42`) to ensure reproducibility.  
2. **Full MobileForge visual‑policy baseline** – predictions are pre‑computed offline on GPU and loaded from disk during evaluation, preserving the paired‑design because the same task instances and seeds are used for all models.  
*Constraint*: The "paired" nature of the data is established by evaluating the **exact same task instance** (same UI state, same seed) by all baselines under identical conditions.

### FR-005: Statistical Significance
The system must perform a **paired two‑tailed t‑test** on the binary success differences (distilled vs. each baseline) to determine statistical significance.  
*Justification*: With N = 500 binary outcomes, the difference distribution approximates normality (by the Central Limit Theorem), making the paired t‑test appropriate.  
*Constraint*: Significance level α = 0.05 (two‑tailed).

### FR-006: Sensitivity Analysis
The system must perform a sensitivity sweep across "inconsistency tolerance" thresholds to measure variance in success rates.  
*Definition*: "Inconsistency tolerance" is the **maximum allowable Levenshtein edit distance** between the generated action sequence and the ground truth.  
*Sweep Parameters*: thresholds = {0, 1, 2, 3, 4, 5}. For each threshold, a task is considered "successful" if the edit distance ≤ threshold. The resulting binary outcomes are fed to the same paired t‑test framework for reporting variance.  
*Constraint*: The sweep must evaluate all thresholds and report the resulting success‑rate variance.  
*Justification*: Sensitivity to inconsistency tolerance is essential to demonstrate that the model’s performance is stable across reasonable variations of the evaluation metric, directly supporting the research question of robust hint‑driven action prediction.

### FR-007: Power Analysis
The system must conduct an **a‑priori power analysis** for the paired t‑test to verify that the chosen sample size (N = 500) provides sufficient power.  
*Parameters*: Target power ≥ 0.8, effect size **Cohen’s d = 0.5** (medium), significance level α = 0.05.  
*Prohibition*: Post‑hoc power analysis is explicitly prohibited.

### FR-008: Resource Constraints
All **training** of the distilled model must run on CPU. Any detection of CUDA usage during training must trigger an immediate failure. Baseline evaluation may use pre‑computed results stored on disk and therefore does not violate the CPU‑only rule.

### FR-009: Hint Ablation Requirement
The system must run the ablation described in US‑5, recording performance metrics for the model when the hint input is replaced by a generic "retry" prompt.  
*Constraint*: All other inputs (UI state, random seed) remain identical to the main evaluation runs. (See US‑5)

### FR-010: Emulator Determinism Control
To mitigate nondeterministic emulator behavior, the system must:
1. Use a fixed random seed for the Android emulator for every task execution (`seed=12345` plus a run‑index offset to ensure distinct seeds per replicate).  
2. Execute each task **three times** and record **each run’s binary outcome separately** (no majority‑vote aggregation).  
*Justification*: Treating each run as an independent observation preserves within‑task variability and satisfies the independence assumption required for a paired two‑tailed t‑test. The paired t‑test will be applied across all [deferred] per‑run observations, pairing each model’s outcome with the same seed and run index of the baselines.
*Constraint*: This procedure is required for all model evaluations (see US‑3).

## 4. Non-Functional Requirements

### SC-001: Reproducibility (See US‑3)
All experiments must be reproducible via random seed management, artifact versioning, and a **Reproducibility Checklist** script (`scripts/check_reproducibility.sh`) that re‑runs the full pipeline and asserts identical outputs within a tolerance of 1 % for success rates.

### SC-002: Data Integrity (See US‑1)
Data loaders must fail loudly on missing or corrupted real data; no synthetic fallbacks are permitted.

### SC-003: Performance
Training must complete within 6 hours on a **standard CPU runner** (8‑core Intel Xeon @2.5 GHz, 32 GB RAM).

### SC-004: Statistical Rigor (See US‑3)
All claims of improvement must be backed by statistically significant results (**p < 0.05, two‑tailed**) from the **paired two‑tailed t‑test** with the alternative hypothesis that the distilled model performs better than each baseline.

### SC-005: Sensitivity Reporting
Sensitivity analysis results must be reported as variance across thresholds, without hard pass/fail cutoffs.

### SC-006: Statistical Power Reporting
Statistical power reporting must document the **a priori power calculation parameters** (Power ≥ 0.8, d = 0.5, α = 0.05) and confirm that the fixed sample size N = 500 satisfies these criteria. Post‑hoc power measurements derived from test results are not permitted.

### SC-007: Hint Ablation Success (See US‑5)
The performance difference between the full model and the ablated version (hint replaced by “retry”) must be statistically significant (**p < 0.05**) according to the paired t‑test.

## 7. Appendix

### A. Justification for Architecture Choice (FR-002)
The original idea proposed an encoder‑only model (e.g., DistilBERT) to keep parameter count low while still encoding the UI state and hint jointly. Encoder‑only models are well‑suited for classification‑style embeddings and, when paired with a simple decoding head for sequence generation, meet the resource constraints. This choice aligns with the research goal of a lightweight, CPU‑only solution.

### B. Justification for Statistical Test Choice (FR-005)
The research plan requires a paired comparison of binary success outcomes across models. With a large sample (N = 500), the difference of paired binary outcomes approximates a normal distribution (Central Limit Theorem), making the paired two‑tailed t‑test appropriate and preserving the original hypothesis testing framework.

### C. Justification for Power Analysis Parameters (FR-007)
For a paired t‑test, Cohen’s d = 0.5 is a conventional medium effect size. Using standard power‑analysis formulas (e.g., G*Power) with α = 0.05 and power = 0.8 yields a required sample size well below 500, confirming that the fixed N = 500 tasks provides ample power.
