# MobileForge Logic Distillation: Specification

## 1. Introduction

This document outlines the requirements for extending the MobileForge framework with CPU-tractable logic distillation. The goal is to train a lightweight model capable of generating corrective hints and action sequences for Android task automation based on UI states, while adhering to strict resource constraints (CPU-only, <6h training time) and statistical validation standards.

## 2. User Stories

### US-1: Data Extraction and Dataset Construction
As a researcher, I want to extract and filter `(UI_state, Corrective_Hint, Action)` triples from MobileForge logs, ensuring "failed-then-success" trajectories and purely linguistic hints, so that I can train a distilled model on high-quality, coordinate-free reasoning data.

### US-2: CPU-Tractable Model Training
As a researcher, I want to train a lightweight Encoder‑Only model (e.g., DistilBERT or a small LLaMA) on CPU to predict action sequences from UI states and hints, so that I can deploy the model in resource‑constrained environments without requiring GPU hardware.

### US-3: Evaluation and Statistical Validation
As a researcher, I want to evaluate the distilled model against a TinyLlama baseline, a random‑policy baseline, and the full MobileForge visual policy on a representative set of **500** unseen AndroidWorld tasks, performing statistical significance testing with a paired design (paired t‑test), so that I can rigorously validate the performance improvement of the distilled model.

### US-4: Sensitivity Analysis & Robustness
As a researcher, I want to verify the robustness of results against "inconsistency tolerance" threshold variations and perform stress tests, so that I can ensure the model's performance is stable across different evaluation parameters.

### US-5: Hint Ablation Study
As a researcher, I want to run an ablation where the hint input is replaced with a generic "retry" prompt, keeping all other inputs identical, so that I can quantify the specific contribution of the corrective hint to model performance. (See FR-009)

## 3. Functional Requirements

### FR-001: Data Pipeline
The system must extract triples from **MobileForge logs**, filter for "failed‑then‑success" trajectories, and validate that hints are purely linguistic (no coordinate‑based visual grounding).  
*Constraint*: Only logs generated by the MobileForge instrumentation are permitted as source data.

### FR-002: Model Architecture
The distilled model must utilize an **Encoder‑Only architecture** (e.g., DistilBERT, small LLaMA).  
*Justification*: The original research idea proposes an encoder‑only model to keep the parameter count low while still encoding the UI state and hint jointly; this aligns with the resource‑constrained goal.  
*Constraint*: The model must be trainable on CPU within 6 hours and have ≤100M parameters.

### FR-003: Evaluation Dataset
The evaluation must use a sufficiently large set of unseen AndroidWorld tasks drawn from MobileForge log trajectories (failed‑then‑success with linguistic hints). The tasks must be logically disjoint from the training set.  
*Constraint*: Fixed N = 500 tasks as stipulated in the original methodology; no dynamic power‑analysis‑driven sizing.

### FR-004: Baseline Comparison
The system must compare the distilled model against **three baselines** on the exact same set of tracked tasks:
1. TinyLlama (decoder‑only) baseline.  
2. Random‑policy baseline (random action selection).  
3. Full MobileForge visual policy baseline.  
*Constraint*: The "paired" nature of the data must be established by evaluating the **exact same task instance** (same UI state, same seed) by all four models under identical conditions.

### FR-005: Statistical Significance
The system must perform a **paired t‑test** on the continuous performance metric (e.g., per‑task success probability) to determine statistical significance between the distilled model and each baseline.  
*Justification*: The original design specified a paired t‑test; we retain this to stay faithful to the research plan.  
*Constraint*: The test assumes a two‑tailed hypothesis with significance level α = 0.05.

### FR-006: Sensitivity Analysis
The system must perform a sensitivity sweep across "inconsistency tolerance" thresholds to measure variance in success rates.  
*Definition*: "Inconsistency tolerance" is defined as the **maximum allowable Levenshtein edit distance** between the generated action sequence and the ground truth.  
*Constraint*: A task is considered "successful" within the sweep if the edit distance is ≤ the current threshold. This links the continuous metric to the binary outcome required for the statistical test.

### FR-007: Power Analysis
The system must conduct an **a priori power analysis** for the paired t‑test to verify that the chosen sample size (N = 500) provides sufficient power.  
*Parameters*: Target power ≥ 0.8, effect size **Cohen’s d = 0.5** (medium), significance level α = 0.05.  
*Prohibition*: Post‑hoc power analysis is explicitly prohibited.

### FR-008: Resource Constraints
All training and evaluation must run on CPU. Any detection of CUDA usage during training must trigger an immediate failure.

### FR-009: Hint Ablation Requirement
The system must run the ablation described in US‑5, recording performance metrics for the model when the hint input is replaced by a generic "retry" prompt.  
*Constraint*: All other inputs (UI state, random seed) remain identical to the main evaluation runs.

### FR-010: Emulator Determinism Control
To mitigate nondeterministic emulator behavior, the system must:
1. Use a fixed random seed for the Android emulator for every task execution.  
2. Execute each task **three times** and record the majority vote (≥2 successes) as the final binary outcome.  
*Constraint*: This procedure is required for all model evaluations (see US‑3). (See US‑3)

## 4. Non-Functional Requirements

### SC-001: Reproducibility (See US-3)
All experiments must be reproducible via random seed management and artifact versioning (Constitution Principle III).

### SC-002: Data Integrity
Data loaders must fail loudly on missing or corrupted real data; no synthetic fallbacks are permitted.

### SC-003: Performance
Training must complete within 6 hours on a standard CPU runner.

### SC-004: Statistical Rigor (See US-3)
All claims of improvement must be backed by statistically significant results (**p < 0.05, two‑tailed**) from the paired t‑test with the alternative hypothesis that the distilled model performs better than each baseline.

### SC-005: Sensitivity Reporting
Sensitivity analysis results must be reported as variance across thresholds, without hard pass/fail cutoffs.

### SC-006: Statistical Power Reporting
Statistical power reporting must document the **a priori power calculation parameters** (Power ≥ 0.8, d = 0.5, α = 0.05) and confirm that the fixed sample size N = 500 satisfies these criteria. Post‑hoc power measurements derived from test results are not permitted.

## 5. Data Models

### ExtractionDataset
- `triples`: List of `(UI_state, Corrective_Hint, Action)`
- `metadata`: Source log information, filtering criteria used

### DistilledModel
- `architecture`: Encoder‑Only (DistilBERT or small LLaMA)
- `weights`: Path to saved model weights
- `config`: Model configuration parameters

### EvaluationResult
- `metrics`: Success Rate, Step Efficiency
- `statistical_test`: Paired t‑test p‑value
- `power_analysis`: A priori power validation results
- `sensitivity_report`: Variance across thresholds

## 7. Appendix

### A. Justification for Architecture Choice (FR-002)
The original idea proposed an encoder‑only model (e.g., DistilBERT) to keep parameter count low while still encoding the UI state and hint jointly. Encoder‑only models are well‑suited for classification‑style embeddings and, when paired with a simple decoding head for sequence generation, meet the resource constraints. This choice aligns with the research goal of a lightweight, CPU‑only solution.

### B. Justification for Statistical Test Choice (FR-005)
The research plan originally specified a paired t‑test to compare per‑task success probabilities across models. Retaining this test respects the intended experimental design and allows direct comparison of continuous performance metrics derived from repeated runs (see FR‑010).

### C. Justification for Power Analysis Parameters (FR-007)
For a paired t‑test, Cohen’s d = 0.5 is a conventional medium effect size. Using standard power‑analysis formulas (e.g., G*Power) with α = 0.05 and power = 0.8 yields a required sample size well below 500, confirming that the fixed N = 500 tasks provides ample power.
