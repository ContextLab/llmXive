## Unresolved concerns

- The plan states it "Computes required sample size **N** using the McNemar‑specific power formula (target power = 0.8, effect size = Cohen’s h = 0.2, baseline p0 = 0.5, α = 0.05)". Cohen’s h is a measure for differences between two proportions, not the standard effect‑size parameter for McNemar’s test, which depends on the expected discordant proportion (b + c) and the odds ratio between models. Using h may yield an inaccurate N, risking under‑ or over‑powered study. The power analysis should be reformulated to use the McNemar‑specific parameters (e.g., expected discordant proportion and odds ratio) or cite a validated formula/library that implements it correctly.
- Success is defined as the emulator reporting task completion, producing a binary outcome. However, the Android emulator can exhibit nondeterministic behavior (timing, background processes) that may cause the same model input to succeed on one run and fail on another. The plan does not specify any mechanism (e.g., fixed random seed for the emulator, multiple runs per task with majority vote) to ensure that the binary outcome is deterministic. Without controlling this source of variance, the contingency table may reflect emulator noise rather than true model differences, threatening internal validity.
- The plan cites the dataset `OSTShushack/ExtractionDataset` as the source for training data. However, the research goal requires extracting `(UI_state, Corrective_Hint, Action)` triples specifically from MobileForge logs (failed‑then‑success trajectories). The cited ExtractionDataset does not appear to be the MobileForge log dataset, making it an inappropriate data source for the intended logic distillation task.
- Principle I (Single Source of Truth) requires an explicit SSoT designation (e.g., a declared artifact that is the authoritative source for figures/tables). The plan only lists a compliance table but does not declare any SSoT artifact, violating Constitution Principle I.
- The evaluation schema (`contracts/evaluation.schema.yaml`) expects the `sensitivity_report` field to be embedded inside `evaluation_results.json`. The plan instead writes a separate `outputs/sensitivity_report.json` (Phase 5) and does not include it in `evaluation_results.json`, creating a mismatch between the data model and the plan.
- The power‑analysis step computes the required sample size N using a McNemar‑specific formula but specifies the effect size as Cohen’s h = 0.2. Cohen’s h is defined for differences between two independent proportions, not for the paired‑binary setting of McNemar’s test, which relies on the proportion of discordant pairs (b + c). Using h may lead to a mis‑estimated N and undermines the claimed 0.8 power. The plan should employ a power calculation based on the expected discordant proportion (or use an established McNemar power calculator) rather than Cohen’s h.
