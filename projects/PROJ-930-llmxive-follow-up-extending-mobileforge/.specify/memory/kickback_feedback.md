## Unresolved concerns

- The plan specifies using McNemar’s test for paired binary outcomes, but the evaluation schema (`contracts/evaluation.schema.yaml`) and the specification require a paired t‑test (`test_type: "paired_t_test"`). This mismatch means the analysis will not validate against the declared contract, breaking methodological consistency.
- Power analysis is performed for a paired t‑test (using Cohen’s d) while the actual statistical test is McNemar’s test. The required sample size for McNemar’s test differs, so the a‑priori power calculation may be invalid for the chosen test.
- The full MobileForge visual‑policy baseline is omitted due to CPU constraints, yet FR‑004 explicitly requires comparison against three baselines, including the full visual policy. Excluding it removes a key paired comparison and introduces a confound, weakening the claim of superiority.
- Success is defined as a majority vote over three emulator runs per task. This binary aggregation may obscure variability and does not align with the Levenshtein‑based sensitivity thresholds, leading to ambiguous construct validity for the ‘success’ outcome used in the statistical test.
- The random‑policy baseline’s stochastic nature is not adequately controlled; using a fixed emulator seed does not affect the randomness of action selection. Without multiple seeds or runs, the baseline may be biased, confounding the paired comparison.
- FR-001 requires extraction of triples from *MobileForge logs*. The plan admits that no public MobileForge logs are available, uses the ExtractionDataset as a placeholder, and explicitly requests a spec revision to either provide an open MobileForge log source or relax the restriction. No real MobileForge data pipeline is implemented, so the functional requirement is unfulfilled.
- FR-003 mandates evaluation on 500 unseen AndroidWorld tasks drawn from MobileForge log trajectories. The plan again falls back to the ExtractionDataset parquet and flags a data‑availability mismatch, requesting a spec amendment. Consequently the evaluation dataset does not satisfy the required source, leaving the requirement unmet.
- FR-004 calls for baseline comparison against three baselines, including the *full MobileForge visual policy* baseline. The plan omits this baseline, citing CPU‑only constraints, and documents the omission while asking for a spec revision. The missing baseline means the functional requirement is not satisfied.
- The plan cites the open ExtractionDataset parquet (https://huggingface.co/datasets/OSTShushack/ExtractionDataset/…) as the data source, but FR‑001 explicitly requires MobileForge instrumentation logs. Using a stand‑in dataset violates the functional requirement and will not answer the research question.
- Phase 4 proposes running the Android emulator three times for each of 500 tasks across four models (distilled, TinyLlama, random‑policy, visual‑policy). On the specified GitHub Actions runner (2 CPU cores, ~7 GB RAM) this amounts to ~6 000 emulator executions, which is highly unlikely to complete within the 6 h wall‑clock limit and exceeds realistic CPU resource constraints.
- The TinyLlama‑1.1B‑Chat baseline referenced in the plan far exceeds the ≤ 100 M parameter limit and cannot be feasibly fine‑tuned or even inference‑run on the designated CPU‑only runner within the allotted time, making the baseline choice infeasible under the project’s resource constraints.
- The plan specifies using McNemar’s test for paired binary outcomes, but the `contracts/evaluation.schema.yaml` schema enforces `statistical_test.test_type` to be the constant "paired_t_test". This creates a contradiction between the implementation plan and the contract definition, violating the requirement that every plan element matches a defined contract.
- The plan states that McNemar’s test will be used for paired binary outcomes, but the evaluation schema (`contracts/evaluation.schema.yaml`) requires `statistical_test.test_type` to be the constant string "paired_t_test" and the a‑priori power analysis is based on Cohen’s d for a paired t‑test. This mismatch means the reported power calculation and schema validation are inconsistent with the actual statistical test, rendering the significance claim methodologically unsound.
- The power analysis computes required sample size using effect size *d* (Cohen’s d) appropriate for a paired t‑test, yet the downstream analysis uses McNemar’s test for binary outcomes. Power calculations for McNemar differ; using the t‑test parameters leads to an invalid claim that N = 500 provides ≥ 0.8 power for the actual test.
