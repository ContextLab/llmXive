## Unresolved concerns

- The plan claims >90% power to detect r=0.4 with N=500. However, the target variable CAPE is a derived ratio (PC_raw / avg_vdW_volume). If the denominator (avg_vdW_volume) is highly correlated with the numerator's components (atom count), the resulting CAPE may have a restricted range or non-normal distribution, violating the assumptions of the power calculation which assumes a standard bivariate normal distribution. The plan does not address how the distribution of the derived target variable affects power.
- The plan proposes running a permutation test with 10,000 shuffles (FR-016) in Phase 3. On a 2-CPU GitHub runner, 10,000 shuffles of a correlation test on 500 records is computationally feasible, but the plan does not specify the parallelization strategy (e.g., joblib, multiprocessing) or the time budget for this specific step. If the permutation test is not parallelized, it may exceed the 6-hour total pipeline limit (SC-005), forcing a reduction in shuffles which invalidates the p-value resolution (0.0001) required by FR-016.
- FR-009 (VIF diagnostics) is scheduled in Phase 1, but FR-004 and FR-012 (fingerprint + 3D descriptors) are generated in Phase 0. However, the 'Unresolved concerns' block explicitly flags a producer-consumer violation: T028 (VIF) requires the 'full feature matrix' including 'fingerprint dimensions' (T060-T067). The plan's Phase 1 executes VIF *before* the full feature set (specifically the fingerprint dimensions from the frozen transformer) is guaranteed to be present in the matrix used for diagnostics. The plan states 'Execute VIF Diagnostics... on the *full* feature matrix' but the phase order implies VIF runs before the final feature engineering steps are complete. This risks the VIF being calculated on an incomplete set, violating FR-009's requirement to check 'all predictor variables'.
- FR-014 (Partial Correlation Analysis) is listed in Phase 3 (Evaluation), but FR-011 and FR-014 require controlling for 'atom-type composition features'. The plan's Phase 0 computes descriptors, but the specific 'atom-type count features' (mentioned in data-model.md as `atom_type_counts`) are not explicitly listed as a distinct generation step in the Phase 0/1 flow before VIF or Model Training. If these are not in the 'full feature matrix' at Phase 1, the VIF (FR-009) is incomplete. If they are added later, the VIF is wrong. The plan lacks a clear step for generating/including these specific confounders before the VIF step.
- FR-017 requires recording the COD dataset source URL and version identifier. The plan mentions 'verified COD JSONL datasets' and 'armand0e/claude-fable-5-claude-code' in the 'Compute Feasibility' section, but there is no explicit task or phase step dedicated to 'Recording and verifying the source URL/version' as a distinct artifact or log entry required by FR-017. While implied by 'download_cod.py', the specific requirement to 'record and verify' against the official repository (Constitution Principle II) needs an explicit plan element (e.g., a validation step or log output) to ensure this is not just a comment but a measured output.
- FR-016 mandates 10,000 shuffles for the permutation test. The plan mentions '10k shuffles' in Phase 3, but the 'Compute Feasibility' section notes 'Estimated time: ~2-4 hours'. The plan does not explicitly address the contingency required by the spec's Assumptions: 'if runtime exceeds a predefined time threshold, the number of permutations may be reduced... (recorded as a deviation)'. There is no plan element (e.g., a timeout check or adaptive logic) to handle this deviation and record it, which is required to satisfy the spec's assumption and FR-016's strictness.
- The plan schedules VIF diagnostics (FR-009) in Phase 1 on the 'full feature matrix'. However, the 'full feature matrix' definition in the data-model.md includes `fingerprint_vector` (SMILES transformer embedding). The plan states in 'Compute Feasibility' that the frozen transformer inference is CPU-tractable for batch sizes of ~50-100. If the dataset size is >500 records (as required by SC-001), generating the full fingerprint vector for all records before VIF calculation may exceed the 7GB RAM limit of the GitHub Actions free-tier runner if the transformer model is large (e.g., >500MB) and the batch processing is not strictly streaming. The plan assumes 'streaming' will handle this, but streaming a transformer embedding generation for 500+ records into a single CSV for VIF analysis is a high-risk memory operation that needs explicit validation of the transformer model size and batch strategy to ensure it fits within the 7GB constraint.
- The plan states: 'Execute VIF Diagnostics (FR-009): Run on the *full* feature matrix... before model training.' However, the 'Phase Execution Order' lists VIF in Phase 1, but the 'Compute Feasibility' section and 'Phase 0' imply the 'full feature matrix' (including fingerprint vectors from FR-004) is generated in Phase 0. The plan text says 'Phase 0: ... Compute 3D descriptors (FR-012) and CAPE (FR-011)' but does not explicitly list 'Encode SMILES (FR-004)' in Phase 0, yet Phase 1 VIF requires the fingerprint vector. This creates a producer-consumer gap: VIF (Phase 1) requires FR-004 output, but FR-004 is not explicitly scheduled in Phase 0 or Phase 1 before VIF. The plan must explicitly schedule FR-004 (SMILES encoding) in Phase 0 to ensure the 'full feature matrix' exists for VIF.
- The plan mentions 'verified COD JSONL datasets (e.g., `armand0e/claude-fable-5-claude-code`)'. The spec (FR-017) and Constitution (Principle VI) require the source URL to be recorded and verified. The plan uses a placeholder/example dataset name that may not be the official COD source or a verified mirror. The plan must explicitly state the exact verified dataset loader string (e.g., `datasets.load_dataset("cod/cod", ...)` or the specific verified HF repo ID) to satisfy Constitution Principle II (Verified Accuracy) and FR-017, rather than using an example that might be unverified.
- The plan proposes a partial correlation analysis to 'disentangle compositional vs. geometric effects' (FR-014). However, since the target (CAPE) is constructed from the very compositional and geometric variables being controlled for, the partial correlation will be statistically unstable and conceptually flawed. You cannot control for the variables that define the target to prove the target isn't just those variables; the analysis is circular by design.
