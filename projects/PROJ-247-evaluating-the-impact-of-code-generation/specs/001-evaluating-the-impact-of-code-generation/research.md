# Research: Evaluating the Impact of Code Generation on Long-Term Code Maintainability

## Research Question
Does code generated by large language models exhibit different long‑term maintainability characteristics compared to human‑written code, as measured by **code churn**, **bug‑fix latency**, and **structural complexity** over a six‑month (primary) or nine‑month (sensitivity) observation window, when controlling for initial complexity and project size?

## Dataset Strategy
| Source | Access Method | Reason for Inclusion |
|--------|---------------|----------------------|
| **GitHub API** (public repositories) | Programmatic `PyGithub` queries | Provides commit history, issue links, and full source code needed for longitudinal metrics. |
| **CodeBERT model** (`microsoft/codebert-base`) | Downloaded from HuggingFace (`https://huggingface.co/microsoft/codebert-base`) | Proven transformer for code representation; used in prior classification work (cited on HuggingFace). |
| **Verified static‑analysis tool** (`radon`) | Python package `radon` | Generates cyclomatic complexity and nesting depth required for matching. |

*No external static datasets are used because they lack the necessary commit/issue timeline.*

### Repository Selection Criteria
- Language: Python **or** JavaScript.  
- Activity: ≥ 1 commit in the recent period **and** ≥ 5 stars.  
- Tagging: `topic:llm-generated`, `topic:copilot`, or keyword search `"LLM generated code"` / `"Copilot generated"` (expanded if < 50 repos).  
- Target size: **≤ 20** repositories (adjusted for feasibility; early stop if insufficient blocks).  

All raw API responses are saved under `data/raw/` with SHA‑256 checksums (Constitution III).

## Methodology

### 1. Data Curation & Extraction (FR‑001, FR‑002, FR‑003)
1. **Search & Clone** – `01_data_curation.py` queries the GitHub Search API, writes `repo_list.csv` and `repo_metadata.csv`, then shallow‑clones each repo (depth = 100) into `data/raw/clones/`.  
2. **Block Extraction** – `02_code_block_extraction.py` parses each `.py` / `.js` file and extracts top‑level functions/classes, recording file path and line numbers.  
3. **Static Metrics** – `radon` computes cyclomatic complexity, nesting depth, and LOC for every block.  
4. **Classification** – `03_classification.py` loads the ONNX‑converted CodeBERT model, predicts “LLM” vs. “Human” with confidence. Blocks with confidence < 0.8 are excluded; exclusion rates are logged and later corrected with inverse‑probability weighting.  
5. **Output** – `tagged_blocks.csv` contains one row per block with all metrics and the label (FR‑002).

### 2. Ground‑Truth Verification (FR‑007, SC‑006)
- Randomly select **≥ 100** blocks (stratified by predicted label) for manual labeling; export source snippets to `data/ground_truth/manual_labels.csv`.  
- Human annotators label each as “LLM” or “Human”.  
- Compute precision and recall with 95 % confidence intervals; both must be ≥ 0.85.  
- The observed mis‑classification rate is later used for bias correction in the analysis (inverse‑probability weighting and effect‑size adjustment).

### 3. Propensity‑Score Matching (FR‑008)
- **Covariates**: block‑level (complexity, nesting depth, LOC) + repo‑level (stars, age, total LOC) **plus** developer experience (author commit count), test‑coverage proportion (when coverage file exists), prior bug density (bugs per LOC in the preceding 3 months), and optional code‑domain tags.  
- **Model**: Logistic regression (scikit‑learn) to estimate propensity scores.  
- **Matching**: 1:1 nearest‑neighbor *within the same repository* when possible; otherwise, blocks are matched in a global pool.  
- **Filtering**: Repositories lacking ≥ 5 LLM‑generated and ≥ 5 Human‑written blocks after tagging contribute their blocks to the global pool rather than being discarded.  
- **Result** – `matched_pairs.csv` (MatchedPair) with paired block IDs, propensity scores, and repository metadata.

### 4. Longitudinal Metric Extraction (FR‑004)
- **Introduction Commit** – First commit where the block appears (detected via `git log --diff-filter=A`).  
- **Window** – Six months after that timestamp (primary) and also compute a nine‑month window for sensitivity analysis.  
- **Code Churn** – Sum of `lines_added` + `lines_deleted` for each block within the window, excluding the introduction commit.  
- **Bug‑Fix Latency** –  
  1. Primary linkage via commit messages containing `Fixes #N` or `Closes #N`.  
  2. Heuristic fallback: GitHub Issues events, PR–issue cross‑references, and fuzzy matching of issue titles/descriptions within ±3 days of the commit.  
  3. If still unlinked, latency is recorded as `null` and treated as a right‑censored observation; such cases are excluded from the latency test but retained for churn analysis, and the censoring proportion is reported.  
- **Output** – `metrics_per_pair.csv` (per‑pair churn & latency, conforms to `contracts/metrics.schema.yaml`) and `maintenance_events.csv` (individual churn/bug‑fix events, conforming to the `MaintenanceEvent` entity).

### 5. Statistical Analysis & Visualization (FR‑005, FR‑006)
- **A‑priori Power Analysis** – Paired Wilcoxon, effect size d = 0.5, α = 0.05, power = 0.80 → requires **≥ 34** matched pairs; we target **≥ 40** pairs before data collection (computed with `statsmodels`).  
- **Cluster‑Robust Wilcoxon** – Perform signed‑rank tests **within each repository**, then combine via a weighted Z‑method that accounts for intra‑repo correlation.  
- **Multiple‑Comparison** – Benjamini‑Hochberg FDR correction across the two outcomes (churn, latency).  
- **Effect Size** – Report **rank‑biserial correlation (rᵣ)** derived from the Wilcoxon statistic (consistent with the non‑parametric test).  
- **Bias Adjustments** – Apply inverse‑probability weighting for the confidence‑filter exclusion and adjust effect sizes using the mis‑classification rate from the ground‑truth sample.  
- **Sensitivity Analyses** –  
  - Vary observation window (6 vs 9 months).  
  - Re‑weight results using the inverse‑probability weights.  
  - Correct effect sizes for classifier error.  
- **Figures** – Box‑plots and kernel‑density plots for churn and latency, saved as PNG under `data/analysis/figures/` (≤ 10 MB, CPU‑only `matplotlib`).  

### 6. Edge‑Case Handling
| Situation | Handling |
|-----------|----------|
| Repository becomes private or is deleted during the 6‑month window? | API call returns 404; the repo is logged and removed from all downstream files. |
| Block is moved via `git mv` or extensive refactoring? | `git log --follow` is used; if the path cannot be resolved, the block is excluded and noted. |
| Classifier confidence < 0.8? | Block excluded from `tagged_blocks.csv`; exclusion reason logged and later corrected with inverse‑probability weighting. |
| No linked issue in the 6‑month window? | Latency set to `null`; treated as right‑censored, excluded from latency test, proportion reported. |
| Insufficient matched pairs (< 5 per repo) | Blocks are added to the global matching pool; the repository is still included in the analysis. |
| Runtime exceeds 6 h | Automatic down‑sampling of low‑importance blocks (e.g., highest complexity) and re‑run; logs indicate the reduction. |

## Statistical Rigor & Assumptions
- **Observational** – No random assignment; claims are *associational* only.  
- **Multiple Testing** – Benjamini‑Hochberg applied (FR‑005).  
- **Power** – A‑priori calculation (≥ 40 pairs) guides sample size; post‑hoc power reported for transparency.  
- **Collinearity** – Covariates checked for VIF < 5; any violating covariate is dropped.  
- **Cluster Dependence** – Intra‑repo correlation handled via cluster‑robust stratified Wilcoxon.  
- **Measurement Validity** – CodeBERT’s classification is a proxy; large ground‑truth sample quantifies mis‑classification.  
- **Latency Validity** – Primary explicit links plus heuristic fallback and censored‑data treatment reduce systematic missingness; residual bias is documented and explored in sensitivity analyses.  

## Compute Feasibility (CPU‑first)
- **ONNX Runtime** enables CodeBERT inference on CPU within ~0.5 s per block (vectorized per repo).  
- **Batch Processing** – Repositories processed sequentially; peak RAM ≤ 5 GB (verified on a local 8 GB VM).  
- **No GPU Required** – All steps run on CPU; optional down‑sampling of blocks if wall‑clock exceeds 6 h.
