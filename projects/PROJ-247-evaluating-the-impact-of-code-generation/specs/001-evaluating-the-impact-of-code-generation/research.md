# Research: Evaluating the Impact of Code Generation on Long-Term Code Maintainability

## Research Question
Does code generated by large language models exhibit different long‑term maintainability characteristics compared to human‑written code, as measured by **code churn**, **bug‑fix latency**, and **structural complexity**, over a six‑month observation window (primary) and a three‑month window (sensitivity), when controlling for initial complexity and project size?

## Dataset Strategy
| Source | Access Method | Reason for Inclusion |
|--------|---------------|----------------------|
| **GitHub public repositories** (Python & JavaScript) | Programmatic queries via `PyGithub` | Provides full commit history, issue data, and source files needed for longitudinal metrics. |
| **CodeBERT model** (`microsoft/codebert-base`) | Downloaded from HuggingFace (`https://huggingface.co/microsoft/codebert-base`) | State‑of‑the‑art transformer for code representation; documented in *Zhang et al., 2023* (≥ 80 % accuracy for LLM vs. Human code). |
| **radon** (static‑analysis tool) | Python package `radon` | Generates cyclomatic complexity and nesting depth required for propensity‑score matching. |

*No external static datasets are used because the study requires time‑resolved commit and issue data that only live repositories can provide.*

### Repository Selection (FR‑001)
- Language: Python **or** JavaScript.  
- Activity: ≥ 1 commit in the last recent period **and** ≥ 5 ★.  
- Tagging: `topic:llm-generated`, `topic:copilot`; if < 50 repos, expand to keywords `"LLM generated code"` and `"Copilot generated"`.  
- Minimum **50** repositories (≥ 250 matched pairs overall).  
- All raw API responses are stored under `data/raw/` with SHA‑256 checksums (Constitution III).

## Methodology

### 1. A‑priori Power Analysis (FR‑009)
Using `statsmodels.stats.power` for a paired Wilcoxon Signed‑Rank test, a medium effect size (rank‑biserial ≥ 0.3) with α = 0.05 requires **a substantial number of matched pairs** under complete data. To account for **right-censored latency observations** and **missing churn values**, we perform a **simulation-based power analysis** that models these missingness mechanisms. The resulting target is **≥ 300 matched pairs** before data collection begins.

### 2. Data Curation & Extraction (FR‑001, FR‑003)
1. **Search & Clone** – `code/01_data_curation.py` queries the GitHub Search API, writes `repo_list.csv` and `repo_metadata.csv` to `data/raw/`, then shallow‑clones each repo (depth = 100) into `data/raw/clones/`.
2. **Block Extraction** – `code/02_code_block_extraction.py` parses each `.py` / `.js` file, extracts top‑level functions/classes, and records file path, start/end lines.
3. **Static Metrics** – `radon` computes cyclomatic complexity, nesting depth, and LOC for every block.

### 3. Classification (FR‑002, FR‑011)
- `code/03_classification.py` loads the ONNX‑converted CodeBERT model, predicts “LLM” vs. “Human”, and retains only predictions with confidence ≥ 0.8.
- Accuracy is based on the validated performance reported in *Zhang et al., 2023* (≥ 80%).
- Blocks below the threshold are excluded from matching but recorded for later **inverse‑probability weighting**.

### 4. Ground‑Truth Verification (FR‑007, FR‑017, SC‑006)
- Randomly select **≥ 100** blocks (stratified by predicted label).
- Export source snippets to `data/ground_truth/manual_labels.csv`.
- Human annotators label each block; compute precision, recall, and 95 % confidence intervals. Both metrics must be ≥ 0.85.

### 5. Propensity‑Score Matching (FR‑008)
- **Covariates**: block complexity, nesting depth, LOC; repository stars, age, total LOC; **developer count**, **test‑coverage proxy**, **prior bug density**, **average contributor tenure**, and **code domain**.
- **Model**: Logistic regression (scikit‑learn) estimates propensity scores.
- **Matching**: 1:1 nearest‑neighbor *within the same repository* when at least **2 LLM** and **2 Human** blocks remain; otherwise, a pooled global matching pool is used.

### 6. Longitudinal Metric Extraction (FR‑004, FR‑010)
- **Introduction Commit** – first commit where the block appears (`git log --diff-filter=A`).
- **Observation Windows** – primary **six‑month** window; secondary **three‑month** window for sensitivity analysis.
- **Code Churn** – sum of lines added + deleted **and** compute a **normalized churn rate** `churn_rate = churn_lines / loc` to control for the effect of block size.
- **Bug‑Fix Latency** –  
  1. Primary linkage via commit messages containing `Fixes #N` or `Closes #N`.  
  2. Heuristic fallback: GitHub Issues events, PR–issue cross‑references, fuzzy title matching.  
  3. If still unlinked, record `latency_days = null` and treat the observation as **right‑censored**.
- Output: `metrics_per_pair.csv` and `maintenance_events.csv`.

### 7. Statistical Analysis & Visualization (FR‑005, FR‑006, FR‑013, FR‑014)
- **Latency** – perform a **survival analysis** using Kaplan‑Meier estimators and a **log‑rank test** to compare distributions, treating `null` values as right-censored.
- **Churn** – use a **stratified within‑repo paired permutation test** (permuting labels within pairs and aggregating across repositories) or a **Linear Mixed-Effects Model (LMM)** on the paired differences (with repository as a random effect) to account for intra‑repo clustering.
- **Multiple‑Comparison** – apply **Benjamini‑Yekutieli** FDR correction across the two outcomes.
- **Effect Size** – report **rank‑biserial correlation** with 95 % CIs.
- **Bias Adjustments** – inverse‑probability weighting for the ≥ 0.8 confidence filter and correction of effect sizes using the mis‑classification rate from the ground‑truth sample.
- **Sensitivity Analyses** – compare results from the 3‑month vs. 6‑month windows.
- **Figures** – CPU‑only box‑plots and kernel‑density plots for churn and latency.

### 8. Post‑hoc Power Verification (SC‑001)
- Using the observed number of matched pairs, recompute achieved power via simulation; report whether ≥ 0.80 power is maintained.

### 9. Reporting & Documentation (SC‑002 – SC‑009)
- All results are stored in `data/analysis/wilcoxon_results.json`.

## Edge‑Case Handling
| Situation | Handling |
|-----------|----------|
| Repository becomes private or deleted during the observation window | API returns 404; the repo is logged and removed from all downstream files. |
| Block is moved via `git mv` or extensive refactoring | `git log --follow` is used; if the path cannot be resolved, the block is excluded. |
| Classifier confidence < 0.8 | Block excluded from matching; confidence recorded for inverse‑probability weighting. |
| No linked issue within the window | Latency set to `null`; treated as right‑censored in survival analysis. |
| Insufficient LLM/Human blocks in a repo (less than 2 each) | Blocks are added to the global matching pool. |
| Runtime exceeds 6 h | Automatic down‑sampling of low‑importance blocks and re‑run. |
| Covariate collinearity | Covariates checked for VIF < 5; offending covariates dropped. |
| Multiple testing | Benjamini‑Yekutieli correction (FR‑014). |
| Non‑independence of pairs | Stratified within‑repo paired permutation or LMM (FR‑013). |
| Lack of open dataset for LLM‑generated code | Use classifier on live GitHub repos; ground‑truth verification provides empirical validity. |

## Statistical Rigor & Assumptions
- **Observational** – No random assignment; all claims are *associational*.  
- **Multiple Testing** – Benjamini‑Yekutieli applied (FR‑014).  
- **Power** – A‑priori simulation-based calculation (≥ 300 pairs) guides data collection.  
- **Collinearity** – Covariates checked for VIF < 5.  
- **Cluster Dependence** – Intra‑repo correlation handled via stratified within‑repo permutation or LMM.  
- **Measurement Validity** – CodeBERT classifier’s performance quantified by the ≥ 100‑block ground‑truth sample.  
- **Latency Validity** – Primary explicit links plus heuristic fallback and right‑censoring reduce systematic missingness.  

## Compute Feasibility (CPU‑first)
- **ONNX Runtime** enables CodeBERT inference on CPU (~0.5 s per block).  
- **Sequential processing** keeps peak RAM ≤ 5 GB.  
- **No GPU required**; the pipeline will run on the GitHub Actions free tier.
