## Unresolved concerns

- The origin_label relies on a CodeBERT classifier with confidence ≥ 0.8, but the plan provides only a minimal ground‑truth check (≥ 10 blocks, precision/recall ≥ 0.85). This sample is far too small to establish construct validity of the LLM/Human label for the full dataset.
- Power analysis is performed post‑hoc only. There is no a priori sample‑size calculation, so the study may be under‑powered to detect effects smaller than d = 0.5, contrary to the claim that power ≥ 0.80 will be achieved.
- Excluding blocks with classifier confidence < 0.8 introduces selection bias; the plan does not discuss how this may affect the comparability of LLM vs Human groups or how to adjust for it.
- Bug‑fix latency is measured only for commits whose messages contain “Fixes #N” or “Closes #N”. Many fixes are not linked this way, leading to systematic missingness that can bias latency estimates; the plan does not propose a mitigation (e.g., issue‑commit linking heuristics).
- A six‑month observation window may be too short to capture meaningful maintenance patterns for many repositories, increasing the proportion of null latency values and reducing statistical power. No justification for the window length is provided.
- Propensity‑score matching uses only block‑level complexity, LOC, and repo‑level stars/age/total LOC. Important confounders such as developer experience, code domain, test coverage, or prior bug density are omitted, risking residual confounding.
- The plan requires each of the ~50 selected repositories to contain **at least 5 LLM‑generated and 5 Human‑written blocks after tagging** (see "Target ≈ 50 active Python/JavaScript repos; minimum 5 LLM + 5 Human blocks per repo after filtering"). In practice, public repositories rarely expose LLM‑generated code via topics or keywords, and the classifier’s confidence filter (≥ 0.8) will further prune blocks. This makes the dataset requirement highly optimistic and likely unattainable, jeopardizing the matching step (FR‑008) and the validity of the downstream analysis.
- The pipeline is slated to run on the **GitHub Actions free tier (2 CPU cores, ≈ 7 GB RAM, ≤ 6 h)** while processing up to 50 repositories, performing radon static analysis on all source files, ONNX CodeBERT inference on every extracted function/class, and propensity‑score matching. Even with shallow clones (depth = 100), the cumulative CPU time for classification (≈ 0.5 s per block) and radon analysis can easily exceed the 6‑hour wall‑clock limit, making the compute plan infeasible under the free‑tier constraints.
- The plan states that `data/processed/metrics.csv` contains per‑block churn and latency values, but the `contracts/metrics.schema.yaml` expects a per‑pair schema (fields like `pair_id`, `llm_block_id`, `human_block_id`, etc.). This mismatch means the produced CSV would not validate against the contract.
- The data model defines a `MaintenanceEvent` entity, yet the plan never mentions extracting or storing individual maintenance events (e.g., churn or bug‑fix events). The metrics step should reference this entity or produce a file that conforms to its definition.
- The plan computes Cohen’s d effect sizes directly from the Wilcoxon signed‑rank statistic. Cohen’s d assumes normally distributed differences, which is inconsistent with the non‑parametric Wilcoxon test. This mismatch can produce misleading effect‑size magnitudes.
- Power analysis is performed post‑hoc on the observed sample size and effect size. Post‑hoc power does not inform the adequacy of the study design and can be circular; an a‑priori power calculation should be used to justify sample size.
- Matching is done 1:1 within each repository, but the analysis treats all matched pairs as independent observations. Pairs from the same repository are likely correlated, violating the independence assumption of the Wilcoxon test and potentially inflating Type I error.
- Bug‑fix latency is used as a proxy for maintainability, yet only commits with explicit “Fixes #N” or “Closes #N” messages are considered. This selective inclusion can bias latency estimates because many fixes are not linked in commit messages, making the outcome dependent on developer practices rather than code origin.
- The classifier’s precision/recall requirement (≥ 0.85) is evaluated on a minimum of 10 manually labeled blocks. Such a tiny sample provides very low statistical confidence and cannot reliably validate the classifier’s performance for the full dataset.
