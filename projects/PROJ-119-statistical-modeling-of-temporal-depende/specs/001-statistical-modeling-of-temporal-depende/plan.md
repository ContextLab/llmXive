# Implementation Plan: Statistical Modeling of Temporal Dependence in Cryptocurrency Price Fluctuations

**Branch**: `feat/001-crypto-regime-switching` | **Date**: 2026-10-24 | **Spec**: [spec.md](../spec.md)  
**Input**: Feature specification from `specs/001-statistical-modeling-of-temporal-depende/spec.md`

## Summary
The project will (1) download daily price data for Bitcoin and Ethereum from **verified open‑source datasets** (see Dataset Strategy), (2) compute log‑returns and two volatility proxies, (3) identify low‑ and high‑volatility regimes via a 2‑state Hidden Markov Model (HMM) that uses *squared returns* as its emission feature, (4) fit a Regime‑Switching Vector Autoregression (RS‑VAR) with regime‑specific coefficient and covariance matrices, (5) compare the RS‑VAR to a stationary VAR using **parametric bootstrap likelihood‑ratio tests** and BIC, (6) run robustness checks (3‑state RS‑VAR, alternative volatility proxy), (7) validate regime distinctness on an **independent volatility proxy** (10‑day rolling absolute returns), (8) generate tables/figures, and (9) validate all artefacts against YAML contracts. All steps are wrapped in a single Jupyter notebook `notebooks/analysis.ipynb` that runs end‑to‑end on the GitHub Actions free‑tier runner.

## Constitution Check
| Principle | Satisfaction |
|-----------|---------------|
| I. Reproducibility | Fixed random seeds; data fetched from deterministic open URLs; notebook runs end‑to‑end on a fresh runner. |
| II. Verified Accuracy | All external data come from the verified URLs listed in the “Verified datasets” block. |
| III. Data Hygiene | SHA‑256 checksums are recorded in `data/checksums.json`; raw files never overwritten; each transformation writes a new file. |
| IV. Single Source of Truth | Every reported number is extracted from CSV/JSON artefacts generated by the notebook. |
| V. Versioning Discipline | Platform‑wide hashing of artefacts ensures version traceability. |
| VI. Regime Integrity | (a) Bootstrap LR test (5 000 resamples) compares 1‑ vs 2‑state HMM; (b) an **independent** volatility proxy (10‑day rolling absolute returns) is used in a second bootstrap LR test to confirm regimes differ on a metric not used for fitting. |
| VII. Stationarity | All correlation calculations are performed on log‑returns; Augmented Dickey‑Fuller tests are run per regime before VAR fitting. |

## Risk & Mitigation
| Risk | Mitigation |
|------|------------|
| **Dataset‑Variable Fit** – No verified source provides full OHLCV. | Use the verified BTC JSON and ETH Parquet datasets for closing prices; compute returns from closes only. Document the limitation and flag FR‑001 as partially satisfied; if full OHLCV is required, a scope revision is needed. |
| **Compute Budget** – 10 000‑sample bootstrap could exceed 6 h. | Vectorised NumPy implementation + `joblib.Parallel` across 2 cores; a wall‑time guard aborts after 5 h and automatically reduces resamples to 2 000, logging the fallback. |
| **HMM Convergence** – EM may not converge within 100 iterations. | Notebook logs “HMM convergence not achieved” and falls back to a stationary VAR, satisfying US‑3 edge case. |
| **API Failure** – Not applicable (data are downloaded from static URLs). | N/A – static download wrapped in retry logic; persistent failure aborts with clear error. |
| **Statistical Validity** – Circular validation of regimes. | Independent volatility proxy (`vol_abs_10d`) and separate bootstrap LR test break circularity (SC‑009). |
| **Bootstrap Time Limit** – Excessive runtime. | Wall‑time monitor automatically reduces the number of resamples and records the change, ensuring compliance with SC‑007. |
