# Contributing to the Bounded Confidence Project

Thank you for your interest in contributing to this research project. This document outlines the standards for code, data, and documentation to ensure reproducibility and scientific rigor.

## Code Style

- **Python**: Follow PEP 8 guidelines. Use `black` for formatting and `flake8` for linting.
- **Type Hints**: All functions must have type hints for arguments and return values.
- **Docstrings**: Use NumPy-style docstrings for all public functions and classes.
- **Imports**: Import from the project's internal modules (e.g., `utils.metrics`) rather than reinventing functionality.

## Data Management

- **Real Data Only**: Do not fabricate data. All simulation outputs must be generated by running the code.
- **File Paths**: Adhere strictly to the directory structure:
 - `data/raw/`: Intermediate, unprocessed outputs (e.g., network files, raw simulation traces).
 - `data/processed/`: Final analysis results, aggregated metrics, and figures.
- **Checksums**: All data files must have corresponding SHA-256 checksums stored in `state/projects/...yaml`.

## Testing

- **Test First**: Write tests before implementing features (Red-Green-Refactor).
- **Determinism**: All tests must use a fixed random seed. The `conftest.py` fixture provides this.
- **Contract Testing**: Validate JSON outputs against the schemas in `code/contracts/` using the contract testing framework.

## Documentation

- **Methodology**: Update `docs/methodology.md` when the experimental design or theoretical assumptions change.
- **Results**: Summarize new findings in `docs/results_summary.md`.
- **Comments**: Code comments should explain *why* a decision was made, not just *what* the code does.

## Review Process

- **Self-Review**: Before submitting a task, ensure it passes all local tests and linting.
- **Research Alignment**: Ensure your implementation aligns with the research goals and addresses the specific critiques from the review board (e.g., Turing, Wolfram, West, Krakauer).
- **Verification**: The next step in the pipeline will run a verification agent. Ensure your artifacts are complete and non-fabricated.

## Workflow

1. Select a task from `tasks.md`.
2. Create a branch for the task (e.g., `feature/T044-docs`).
3. Implement the task, write tests, and update documentation.
4. Run the full test suite: `pytest tests/`.
5. Commit your changes with a descriptive message.
6. Push the branch and update the task status in `tasks.md`.

## Contact

For questions regarding the project scope, data, or methodology, please refer to the `README.md` or contact the project lead.
