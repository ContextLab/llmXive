# Research: llmXive follow-up: extending "AdaPlanBench: Evaluating Adaptive Planning in Large Language Model Age"

## Executive Summary

This research investigates whether a dual-track agent architecture (SLM generator + deterministic constraint store) significantly outperforms a monolithic SLM baseline in tasks with progressive constraint accumulation. We focus on the "context management under accumulation" failure mode, hypothesizing that explicit constraint tracking mitigates violation rates as the number of constraints increases.

## Dataset Strategy

### Primary Dataset: AdaPlanBench (or Synthetic Proxy)
**Source**: The AdaPlanBench dataset is the primary target.  
**Status**: **NO VERIFIED SOURCE FOUND** in the provided verified datasets block.  
**Strategy**: 
1. **Fetch Attempt**: The pipeline will attempt to fetch the dataset using the standard HuggingFace `datasets` library with the repository ID `adaplanbench/adaplanbench` (or the specific ID provided in the official repository documentation if available).
2. **Validation**: If the fetch succeeds, the system validates the presence of the `progressive_constraints` field.
3. **Synthetic Proxy**: If the fetch fails OR the required field is missing, the pipeline will **NOT** halt. Instead, it will execute a deterministic script (`code/dataset/generate_proxy.py`) to generate a synthetic dataset with the exact structure required (task prompts, progressive constraints list, constraint counts). This proxy is designed to mimic the statistical properties of the target dataset for the purpose of architectural testing.
**Constraint**: The synthetic proxy is generated with a fixed random seed to ensure reproducibility.
**Variable Fit**: The dataset (real or proxy) MUST contain the `progressive_constraints` field (a list of constraints revealed over time) and `task_prompt`.

### Secondary Data: Human Annotation Sample
**Source**: Generated by `code/dataset/annotator.py` via stratified random sampling from the filtered dataset.  
**Size**: 50 tasks (FR-010).  
**Purpose**: To validate the rule-based detection logic (SC-001, SC-005) and specifically the exclusion logic for implicit constraints.

## Methodology

### 1. Data Preparation
- **Filtering**: Select tasks where `len(progressive_constraints) >= 5`.
- **Validation**: Verify the `progressive_constraints` field exists and is a list.
- **Stratification**: Create a stratified sample for human annotation based on constraint count bins (5, 6, 7+).

### 2. Agent Execution
- **Dual-Track**:
  - **Generator**: Phi-3-mini (loaded locally, CPU-only, 4-bit quantized).
  - **Resolver**: Deterministic key-value store checking generated actions against active constraints.
  - **Logic**: If a violation is detected (exact match, case-insensitive substring, or explicit negation), the resolver forces a revision. Implicit constraints are logged as `implicit_unverified` and excluded from the primary violation rate (FR-009).
- **Monolithic Baseline**:
  - **Generator**: Same SLM (Phi-3-mini) running in a loop without the resolver.
  - **Logic**: Generates plan directly; no constraint checking.
  - **Note**: This is a local-only execution to satisfy CI constraints. API-based models (GPT-4) are out of scope.

### 3. Statistical Analysis
- **Model**: Generalized Linear Mixed Model (GLMM) with binomial link.
- **Fixed Effects**: `Architecture` (Dual vs. Monolithic), `Constraint_Count` (continuous or categorical), `Interaction` (Architecture * Constraint_Count).
- **Random Effects**: `Task_ID` (to account for repeated measures). The model formula is: `violation_detected ~ Architecture * Constraint_Count + (1 | Task_ID)`.
- **Hypothesis**: Significant interaction effect ($p < 0.05$) indicating Dual-Track mitigates degradation.
- **Power Analysis**: Conducted on the filtered subset to ensure $Power \ge 0.80$ for detecting a medium effect size ($f^2 \ge 0.15$) (FR-011).
- **Validation of Exclusion Logic**: The `implicit_unverified` exclusion logic is validated against the human annotation sample (T034b) to ensure it does not systematically bias the results.

## Statistical Rigor & Assumptions

- **Multiple Comparisons**: If multiple sub-hypotheses are tested (e.g., per constraint bin), family-wise error correction (Bonferroni or Holm) will be applied.
- **Sample Size**: Power analysis (FR-011) confirms sufficiency. If $N < 100$ tasks after filtering, the study will explicitly report the power limitation.
- **Causal Inference**: This is an experimental comparison of two architectures on the same dataset. Claims will be framed as "causal within the experimental design" due to the controlled manipulation of the architecture.
- **Measurement Validity**: The rule-based detection logic is validated against human annotation (SC-005).
- **Collinearity**: `Constraint_Count` and `Task_Complexity` may be correlated. The model will treat `Constraint_Count` as the primary independent variable.
- **Sparsity Handling**: The GLMM analysis will include diagnostics for sparse data (near-zero violation rates in Dual-Track). If convergence fails, a Firth's penalized likelihood method will be used.
- **Implicit Constraint Proportion**: The proportion of implicit constraints in the dataset will be estimated. If significant, the primary hypothesis will be explicitly limited to "explicit constraints only".

## Compute Feasibility

- **CPU-First**: All models (Phi-3-mini) and statistical tests (GLMM) are planned to run on CPU.
- **Memory**: Estimated peak memory < 6GB (model weights with 4-bit quantization + dataset + logs).
- **Time**: Target < 6 hours for full execution (data fetch + 100 tasks * 2 architectures + analysis).
- **Quantization**: Phi-3-mini will be loaded with `load_in_4bit=True` to ensure it fits within 7GB RAM.
- **Batch Size**: Tasks will be processed one at a time to minimize memory footprint.

## Data Availability & Risks

- **Risk**: AdaPlanBench dataset is not verified in the provided list.
- **Mitigation**: The pipeline includes a `fetch_and_validate` step followed by a `generate_proxy` step if the real dataset is unavailable. This ensures the study can proceed with a valid, reproducible dataset.
- **Streaming**: If the dataset is large, `datasets.load_dataset(..., streaming=True)` will be used to avoid RAM overflow.

## Decision Rationale

- **Why GLMM?** The data structure involves binary outcomes (violation/no violation) repeated across tasks with varying constraint counts. GLMM handles the non-independence of observations better than standard logistic regression.
- **Why Rule-Based Resolver?** To isolate the "memory" effect from the "reasoning" effect of the LLM, a deterministic check is required.
- **Why Exclude Implicit Constraints?** FR-009 mandates that implicit constraints (requiring common sense) be excluded from the binary violation rate to avoid false positives in rule-based detection. This exclusion is validated against human annotation.
