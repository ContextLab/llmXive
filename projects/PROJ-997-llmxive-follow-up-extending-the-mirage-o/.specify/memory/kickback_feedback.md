## Unresolved concerns

- FR-006 requires a statistical comparison (paired t-test) between the proxy-based MIPU loop and the 'full-hardware-sync baseline'. Task T028 defines the baseline policy as '100% (or fixed threshold)' rather than the actual hardware-synced loop. There is no task to implement the 'full-hardware-sync baseline' policy execution required to generate the comparison data for the t-test mandated by FR-006 and US-003.
- FR-007 and SC-004 require verifying the theoretical bound consistency across 'at least three different quantization bit-widths (INT4, INT8, and FP8)' and reporting consistency. Task T027 describes verifying the bound for these levels but lacks a specific task to aggregate results across all three levels to prove 'consistency' or to generate the specific report metrics required by SC-004 (robustness measured against consistency of correlation coefficient across levels).
- FR-004 mandates training the model 'jointly on data from INT4, INT8, and FP8 quantization levels'. Tasks T021 and T022 describe loading the dataset and training but lack an explicit task to ensure the training split preserves stratification or representation of all three quantization levels. Without this, the model risks being trained on a subset of levels, failing the 'jointly' requirement of FR-004.
- Task T016 hardcodes a validation logic to ensure `calculated_kl_divergence` is non-zero for '>5% of samples'. The spec (US-001) requires a 'statistically significant portion' and the Assumptions section mentions a sensitivity analysis. Hardcoding a 5% threshold in the task without a statistical justification or reference to the sensitivity analysis creates a rigid criterion that may not align with the research findings or the spec's intent.
- Task T030 implements latency instrumentation to 'calculate reduction percentage'. SC-002 specifically targets a '≥ 90% reduction' in the 'policy evaluation step'. The task description is vague on whether it measures the entire pipeline or just the specific evaluation step, potentially leading to a metric that does not directly verify the SC-002 threshold.
- Task T028 ('Simulate MIPU loop... Proxy Policy vs. Baseline Policy') violates the 'Producer before Consumer' and 'Foundational tasks first' principles regarding the definition of the Baseline. The spec (FR-006) and plan mandate a comparison against a 'full-hardware-sync baseline'. However, the task description implies the baseline is a static rule ('100% or fixed threshold') rather than a task that executes the actual hardware-synced inference loop to generate the ground-truth acceptance rates. The task that *generates* the baseline metrics (the hardware-sync run) is missing or conflated with the proxy simulation, creating a semantic dependency violation where the comparison consumes a non-existent artifact.
- Task T027 ('Verify |predicted - actual| < 0.1... for INT4, INT8, and FP8') lacks a clear producer for the 'actual' values per quantization level if the dataset generation (T015) does not explicitly structure the output to support per-level aggregation. While T015 generates the dataset, T027 assumes the ability to filter and verify bounds *simultaneously* across three levels without a preceding task that explicitly aggregates or validates the stratification of the dataset by quantization level. This risks a consumer (T027) attempting to read an artifact structure that hasn't been semantically prepared for multi-level consistency checks.

While the data exists, the task order implies a linear flow that might skip the necessary data-preprocessing step to ensure the 'joint training' requirement is met if the raw parquet isn't pre-shuffled or stratified. - Task T016 ('Add validation logic to ensure... >5% of samples') introduces a hardcoded threshold that contradicts the spec's 'statistically significant portion' requirement. While this is primarily a requirement issue, it creates an ordering risk: if T016 fails (because the 5% threshold is arbitrary and the data doesn't meet it), the downstream tasks (US2, US3) which depend on the *existence* of a valid dataset (T015) might be blocked or proceed with invalid data.
