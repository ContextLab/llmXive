# Implementation Plan: 001-static-dynamic-gap-analysis

**Branch**: `001-static-dynamic-gap-analysis` | **Date**: 2026-10-15 | **Spec**: [spec.md](../specs/001-static-dynamic-gap-analysis/spec.md)  
**Input**: Feature specification from `/specs/001-static-dynamic-gap-analysis/spec.md`

## Summary
The project will build a reproducible pipeline that (1) ingests the open‑source SWE‑Gym and Multi‑SWE‑RL datasets, (2) extracts static structural representations (Control‑Flow Graphs and Call Graphs) for every Python and C++ patch using `pycg` and `clang-query`, (3) derives a concise numerical feature vector from each graph, (4) trains a lightweight classifier (Random Forest / Logistic Regression) to predict the dynamic execution outcome (pass/fail), (5) evaluates predictive performance (AUC, precision, recall) and statistical significance (Wald test), (6) measures the semantic‑gap (FP + FN rate), and (7) mines error cases to categorize the concrete code behaviours that cause static‑dynamic divergence. All steps are designed to run on the GitHub Actions free‑tier CPU runner; a GPU off‑load is not required.

## Technical Context
- **Language/Version**: Python 3.11
- **Primary Dependencies**: `datasets>=2.18.0`, `pycg>=0.2.0`, `clang>=16.0.0`, `networkx`, `pandas`, `scikit-learn`, `statsmodels`, `matplotlib`, `tqdm`
- **Storage**: Files on the runner’s filesystem (`data/` for raw/downloaded datasets, `interim/` for intermediate JSON graphs, `features/` for CSV vectors, `models/` for serialized classifiers, `reports/` for figures/tables)
- **Testing**: `pytest` (unit tests for each pipeline stage)
- **Target Platform**: Linux (Ubuntu) GitHub Actions runner
- **Project Type**: Research library / CLI pipeline
- **Performance Goals**: Complete end‑to‑end run < 6 h, peak RAM < 7 GB
- **Constraints**: No GPU required; all external tools must install from PyPI or apt‑get on the runner
- **Scale/Scope**: ~3.7 k patches (Python + C++), full‑dataset processing; if memory exceeds limits, fallback to stratified random sample (10 % with fixed seed)

> Domain‑specific empirical specifics (exact counts, dataset sizes, measured quantities) are deferred to the research/implementation phase. All quoted numbers will be sourced from the verified dataset URLs.

## Phased Implementation Plan
| Phase | Description | FR/SC Addressed | Expected Output |
|-------|-------------|------------------|-----------------|
| **0 – Environment Setup** | Install dependencies, pin seeds, create output directories. | – | `requirements.txt`, empty `data/`, `interim/`, `features/`, `models/`, `reports/`. |
| **1 – Data Ingestion** | Programmatically download SWE‑Gym (`train-00000-of-00001.parquet`) and Multi‑SWE‑RL (`OpenMathLib__OpenBLAS_dataset.jsonl`). Verify SHA‑256 checksums; extract `patch_id`, `language`, `source_code`, `exec_result`. | FR‑001, SC‑004 | `data/raw_swe_gym.parquet`, `data/raw_multi_swe_rl.jsonl`. |
| **2 – Static Graph Extraction** | For each patch: <br>• If `language == "python"` → run `pycg` to emit CFG & CG JSON. <br>• If `language == "cpp"` → invoke `clang-query` with a pre‑written AST matcher to produce CFG & CG JSON. <br>Unparsable patches are logged and skipped. | FR‑002, FR‑001 (edge case handling), SC‑004 | `interim/{patch_id}_cfg.json`, `interim/{patch_id}_cg.json`. |
| **3 – Feature Engineering** | Load each JSON graph; compute: <br>• Node degree statistics (mean, max, std) <br>• Average shortest‑path length <br>• Recursion depth (detected via back‑edges) <br>• Count of external call nodes (`"external": true`). <br>Assemble a fixed‑length vector; write to CSV. | FR‑003, SC‑001, SC‑002 | `features/static_features.csv` (one row per parsable patch). |
| **4 – Model Training & Evaluation** | Split data (stratified 80/20 train/test, `random_state=42`). <br>• Train Random Forest (n_estimators=200, max_depth=None) and Logistic Regression (liblinear). <br>• Predict on test set; compute AUC, Precision, Recall, Confusion Matrix. <br>• Store model artifacts (`models/rf.pkl`, `models/lr.pkl`). | FR‑004, SC‑001, SC‑004 | `reports/evaluation.csv`, `reports/roc_curve.png`. |
| **5 – Statistical Significance** | Fit a Logistic Regression on the full feature set; extract Wald z‑statistics and p‑values for each coefficient. Apply Bonferroni correction across all features. | FR‑006, SC‑005 | `reports/wald_test.csv`. |
| **6 – Divergence Rate & Error Mining** | Identify FP (pred = pass, true = fail) and FN (pred = fail, true = pass). For each error case, run a rule‑based matcher on the CFG/CG to tag taxonomy: <br>• `dynamic_dispatch` (calls via function pointers, virtual methods) <br>• `external_api` (calls to unknown symbols) <br>• `concurrency_race` (presence of `std::thread`, `async`, `multiprocessing`) <br>• `mocked_io` (file/DB access nodes flagged as mocks). | FR‑005, SC‑002, SC‑003 | `reports/error_cases.csv`, `reports/error_category_distribution.png`. |
| **7 – Performance Monitoring** | Wrap each phase with a timer (`time.perf_counter`) and memory profiler (`psutil`). Summarize total runtime and peak RAM. Abort with clear message if > 6 h or > 7 GB. | FR‑007, SC‑004 | `reports/performance.yaml`. |
| **8 – Reporting** | Assemble a single Markdown report (`reports/final_report.md`) containing: <br>• Dataset statistics (parsed vs skipped) <br>• Feature‑importance plot <br>• Evaluation metrics (AUC, Precision, Recall) vs baseline <br>• Wald test summary <br>• Divergence rate & error‑category breakdown <br>All numbers trace back to rows in `features/` or `reports/`. | All SC, all FR (output generation) | `reports/final_report.md`. |

Each phase will be executed sequentially by the CLI entry point `src/cli/run_pipeline.py`. Failures in any phase abort the pipeline with a logged reason, satisfying the edge‑case requirements.
