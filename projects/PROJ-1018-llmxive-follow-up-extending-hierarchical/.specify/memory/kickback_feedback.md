## Unresolved concerns

- Spec FR-001 requires extracting retrieval score matrices for 'every chunk in the validation set'. Task T005 filters documents to retain only those with token count ≥ 32,000, but there is no explicit task to define or load the 'validation set' split from the PG-19 dataset. Without a task to load/define the validation split (distinct from the test set used in US-3), the system cannot satisfy the requirement to process the correct data subset.
- Spec FR-001 and US-1 require aggregating retrieval scores into 'canonical relevance profiles'. Task T014 implements 'aggregate_profiles', but T012b (Execute Dynamic Baseline Inference) is described as aggregating results into `data/interim/relevance_profiles.json` directly. T014 appears redundant or its dependency on T012b is unclear. If T012b already aggregates, T014 is missing a clear input source. If T012b only extracts raw scores, T014 is missing a dependency to the raw output of T012b. The flow between T012b and T014 is ambiguous, risking a gap in the aggregation logic required by FR-001.
- Spec FR-008 requires a sensitivity analysis sweeping K over {50, 100, 200} and reporting trade-offs. Task T031 implements the sweep and file generation, but there is no task to 'generate the report' of trade-offs (perplexity vs QA accuracy) mentioned in FR-008. T032 generates an 'EvaluationReport', but it depends on T033a (single-run evaluation) and does not explicitly consume the multiple K-sweep outputs from T031 to produce the comparative trade-off report required by FR-008.
- Spec SC-005 requires measuring memory footprint using `tracemalloc` to isolate the retrieval module. Task T030b proposes using a 'separate process' or 'isolated tracemalloc context'. While it mentions tracemalloc, the task description prioritizes the 'separate process' method. If the implementer chooses the separate process method, the specific `tracemalloc` constraint from SC-005 might not be satisfied. A task explicitly mandating the use of `tracemalloc` within the retrieval module context is missing to ensure SC-005 compliance.
- Task T029b is tagged as [US3] but its description is 'Resolve Plan Contradiction: Update plan.md...'. This is a documentation/plan update task, not a code implementation task for User Story 3. While necessary, it should not be grouped under 'Implementation for User Story 3' as it does not produce code artifacts for the story. It should be moved to a 'Polish' or 'Plan Correction' phase, or clearly marked as a non-code task.
- T005 (filtering) and T006 (error handling) are marked [P] (parallel-safe) but depend on T004 (data loader) establishing the stream. T006 cannot run in parallel with T004 as it requires the stream context to handle fetch failures. T005 explicitly depends on T004. The [P] tag on T006 is semantically incorrect as it shares the data stream state with T004.
- T014 (aggregation), T016 (validation), and T015 (serialization) are all marked as depending on T012b (inference execution). However, T014 logically requires the output of T013 (chunking) to define the 'chunks' input. The dependency chain is broken: T014 should depend on T013 AND T012b, or T012b should explicitly include the chunking step. Without T013's output, T014 cannot aggregate profiles per chunk.
- T031 (sensitivity analysis) depends on T020 (K-Means) and T022 (Static Index). However, T031's description states it 'rebuilds the index for each K'. This implies it must re-run the clustering logic (T020) for each K value. The current dependency only points to the *output* of a single K run (T022). The task order implies T031 can run after T022, but T031 actually requires the *logic* of T020 to be re-executed. This is a semantic ordering violation: the consumer (T031) assumes the producer (T020) has already run for all K values, but the plan only produces one index.
- T029b (Resolve Plan Contradiction) is marked as depending on T029 (Statistical Tests). This is a logical inversion. T029b is a documentation/plan update task that should be resolved *before* or *concurrently* with T029 implementation to ensure the code implements the correct test (paired t-test vs Wilcoxon). Making the plan update depend on the code execution creates a circular dependency risk where the code might be written with the wrong test if the plan isn't fixed first.
- Task T004 lacks a concrete deliverable file path for the streaming logic. It describes 'Implement robust data loader... in src/data_loader.py' but does not specify the exact function name or class structure to be created. An implementer cannot deterministically execute this without guessing the API signature (e.g., `def load_streaming_dataset() -> Iterable` vs a class `StreamingLoader`). Needs explicit function/class name and signature.
- Task T005 specifies outputting to `data/interim/filtered_pg19.json` but does not define the exact schema for the JSON list of dicts beyond the keys. It lacks the specific data types (e.g., is `token_count` an integer? is `document_id` a string or UUID?) and the exact logging format string for the warning message (e.g., 'WARNING: Skipping document {id}: length {N} < 32000' vs 'WARNING: Skipping document {id} (length {N})'). This ambiguity prevents deterministic implementation and verification.
- Task T014 defines the input as `List[Chunk]` but the `Chunk` entity is not defined in the task description or referenced from a prior task (T013 produces text chunks, T011 defines `RelevanceProfile`). The task assumes a `Chunk` data structure that does not exist in the provided context, making it impossible to implement without guessing the schema. Needs explicit definition of the `Chunk` type or a reference to an existing data model.
- Task T029b ('Resolve Plan Contradiction') is a documentation update task, not a code implementation task. It asks to 'Update plan.md' but does not specify the exact text to replace, the line number, or the verification step (e., 'Verify plan.md contains "paired t-test"'). Documentation tasks must be as concrete as code tasks to be executable. Needs specific diff instructions or a verification command.
- Task T030b requires measuring memory of `DynamicHiLSWrapper` using a 'separate process' or 'isolated tracemalloc context'. It does not specify which method to use (process vs context) or how to isolate the specific `extract_scores` call without capturing model weights. The instruction 'Wrap the ... method call' is ambiguous for an implementer: does this mean `subprocess.run`? `tracemalloc`? Without a specific implementation pattern or library call, the task is not deterministic.
- Task T031 is too coarse. It combines 'sweep_k_values', 'rebuild index', 'write unique files', AND 'generating a structured report' into one task. The 'report generation' is a distinct deliverable from the 'file generation'. This should be split into two tasks: one for the sweep/index generation and one for the report aggregation. The atomizer will likely split this, but flagging it now ensures clarity.
- Task T001b lists specific package versions but does not specify the exact file path relative to the project root (e.g., `projects/.../code/requirements.txt`). While implied, the task description should explicitly state the full path to ensure the implementer knows exactly where to create the file, especially given the complex project structure defined in `plan.md`.
- Tasks T004-T006 enforce a strict 'raise exception' policy for data fetch failures, explicitly forbidding any fallback. This contradicts Spec Assumptions ('Compute Feasibility') which authorize 'sampling the dataset if necessary to fit memory constraints' to ensure the analysis runs on GitHub Actions free-tier. The tasks silently weaken the spec's contingency plan for memory limits, risking a hard failure where the spec allows a graceful degradation (sampling).
- Task T028 hardcodes `hotpotqa` as the *only* allowed QA benchmark with a strict error if unavailable. Spec FR-007 and Assumptions state the system must evaluate on 'a downstream long-context QA task (e.g., HotpotQA subset)', implying flexibility if the primary dataset is inaccessible. The task introduces a brittle constraint not present in the spec, violating the 'e.g.' allowance and potentially blocking execution if HotpotQA is temporarily unavailable.
- Task T030b proposes measuring memory in a 'separate process' or 'isolated context'. Spec SC-005 explicitly mandates using `tracemalloc` to isolate the retrieval module. While a separate process isolates memory, it does not satisfy the specific tooling requirement (`tracemalloc`) mandated by the success criterion. This is a semantic weakening of the measurement method.
- Task T029b is a documentation update task ('Update plan.md') to resolve a contradiction between the plan and spec. While the task correctly identifies the issue, the task itself does not implement the required statistical test (paired t-test) in the code. The code task T029 implements the test, but the plan contradiction remains in the plan artifact until T029b is executed. However, the more severe issue is that T029b is a 'plan update' task, not a 'code implementation' task, yet it is listed as a dependency for T029 (which implements the code). This creates a logical dependency where code depends on a doc update, but the code implementation (T029) already satisfies the spec. The real violation is that the Plan's 'Test Coverage Matrix' still lists 'Wilcoxon test' (a spec violation) and the tasks do not explicitly flag the Plan as 'broken' until T029b runs, leaving the Plan in a state of active non-compliance during the implementation phase.
- Task T013 allows padding documents to `chunk_size` if specified in config. Spec Edge Cases state the system must 'skip these or pad them', implying a choice. The task does not explicitly define the configuration flag or logic to choose between skipping (the preferred default in the spec) vs. padding, potentially leading to ambiguous behavior that could violate the 'skip' preference if not explicitly configured. This is a potential weakening of the default behavior.
