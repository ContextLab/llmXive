## Unresolved concerns

- The plan uses gas‑phase ion‑pair interaction energies (raw or scaled D3 term) as predictors for bulk‑phase properties (density, viscosity). This construct validity is weak because bulk properties emerge from many‑body collective effects that are not captured by a single pairwise interaction energy. Correlating these quantities may yield spurious associations, limiting the scientific relevance of the reported correlations.
- No explicit power analysis is provided. With a maximum of 100 ion pairs, the study may be under‑powered to detect modest correlations (e.g., |r|≈0.3). The absence of a power calculation means the risk of Type II errors is unquantified, which undermines confidence in non‑significant results.
- Reference interaction energies and experimental bulk‑property measurements have inherent uncertainties, yet the bootstrap confidence intervals for MAE and correlation coefficients are generated without propagating these measurement errors. Ignoring input uncertainties can lead to overly narrow CIs and inflated significance claims.
- Fitting a single scalar ‘s’ to the D3 term may improve MAE but lacks a physical justification; the scalar could be compensating for multiple systematic biases (basis‑set error, functional inadequacy, BSSE residuals). The plan does not include any diagnostic to assess whether a simple scaling is appropriate versus a more nuanced correction (e.g., pair‑specific or functional‑dependent adjustments).
- The plan relies on a *synthetic fallback* `IL‑Benchmark‑local.zip` as the source of CCSD(T)/CBS reference interaction energies (see “The spec notes the lack of an open CCSD(T)/CBS dataset … synthetic fallback is used”). This dataset is **not** a genuine high‑level ab initio benchmark, violating FR‑001 which requires benchmarking against real CCSD(T)/CBS data. Using a synthetic placeholder prevents the study from answering the core research question about DFT‑D3 transferability.
- The `raw_energies.csv` schema (contracts/raw_energies.schema.yaml) requires the columns `error_signed` and `dispersion_only_error`, but the plan only states that total energy, D3 contribution, and BSSE correction are written. It does not describe computing or storing these two error fields, creating a mismatch between the plan and the data‑model/contract.
- The plan declares “Never relies on external network calls at runtime” while the specification (FR‑001, FR‑008) explicitly requires attempting to retrieve the benchmark and bulk‑property data from Zenodo and the NIST API, falling back only on failure. This wording contradicts the functional requirements and should be clarified (e.g., “attempt retrieval; if it fails, use the local fallback”).
- The scaling factor *s* is fitted on the full benchmark set (train + test) and then the same *s* is applied to the entire dataset before the bulk‑property correlation (Phase 5). Because *s* is derived from the same observations that are later used to assess correlation with density/viscosity, the correlation results may be optimistically biased. A more rigorous approach would reserve a completely held‑out subset (or use only the test split) for any downstream analysis that involves the scaled D3 term, or employ nested cross‑validation so that the parameter fitting and correlation assessment are performed on independent data.
