## Unresolved concerns

- The plan runs inference sequentially for each sparsity configuration (global, 64, 32, 16, optional 1) without randomizing the order. This can introduce systematic warm‑up or caching effects that confound the measured mIoU differences, threatening internal validity. Randomize or counterbalance the order of sparsity runs, or explicitly control for any order‑related latency/accuracy drift.
- The plan describes the API for the sparsity knob as `SparsityConfig(window_size)` with a method `get_mask(num_tokens)`. Unit tests (see task T003) expect the constructor to accept `num_patches` and a method `get_mask()` (no arguments). This mismatch will cause test failures unless the implementation is adjusted or the plan is updated to reflect the correct signature.
- Phase 7 states that all tables/figures draw from the master inference table `data/results/master_inference.parquet` to satisfy the Single Source of Truth principle, but the plan never includes an explicit step that merges the per‑window inference files (`inference_<window>.parquet`) into this master table. Adding a consolidation step would make the SSoT claim concrete and avoid a hidden inconsistency.
- The plan proposes computing Pearson and Spearman correlations between the numeric `window size` (values 0, 64, 32, 16, 1) and mIoU. Since `window size` is a categorical treatment of attention sparsity (with 0 representing global attention, which is not on the same numeric scale as patch counts), treating it as a continuous numeric predictor can produce misleading correlation coefficients. A more appropriate approach would be to treat sparsity levels as an ordered factor and use non‑parametric trend tests (e.g., Jonckheere‑Terpstra) or to model the relationship with a mixed‑effects regression that respects the categorical nature of the predictor.
