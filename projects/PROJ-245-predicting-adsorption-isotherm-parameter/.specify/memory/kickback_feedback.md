## Unresolved concerns

- The plan states: 'Cluster-aware: Shuffles feature values within groups of the same adsorbent_id.' This approach tests if the feature varies *within* a material, not if the feature predicts the target *across* materials. For adsorption, the target is often specific to the material-adsorbate pair. If the dataset has multiple adsorbates per material, this might work, but if the dataset is sparse (one adsorbate per material), this method yields no variance to test. The methodology does not guarantee the ability to detect the effect size claimed.
- The plan relies on a heuristic to filter 'Type I' isotherms (regex on string or numeric column). If the source data lacks a reliable 'isotherm_type' column (common in raw NIST exports), the plan defaults to 'exclude all rows'. This creates a 'zero-data' failure mode where the research question cannot be answered at all, rather than a graceful degradation to a broader isotherm type analysis or a different dataset. The methodology is brittle to schema variations.
- FR-002 requires filtering for 'Type I' isotherms. The plan (Section 2.2) acknowledges the column name is unknown and proposes a heuristic/fail-safe to exclude all rows if not found. This does not guarantee the FR is satisfied; it risks satisfying the 'remove entries' part by removing ALL entries, failing the 'include only Type I' intent. The plan lacks a concrete mapping or fallback dataset strategy to ensure Type I data is actually retained.
- SC-003 requires measuring R² of a model trained *only* on the top 3 molecular descriptors against a null model. The plan (Section 3.3) lists training Linear, RF, and GB models, and Section 3.4 mentions a 'Null Model' (mean). However, the plan does not explicitly describe a task or phase to train a *reduced* model using only the top 3 features identified by SHAP (from FR-005) and compare it to a null model. This specific success criterion appears unbacked by a distinct plan element.
- The plan assumes the existence of Hugging Face datasets named 'nist-adsorption' and 'mof-1000' and states: 'If these fail, the pipeline will halt... preventing fabrication.' However, the NIST Adsorption Database is a proprietary/registration-required resource not available as a direct Hugging Face dataset, and 'mof-1000' is not a standard HF dataset name (likely referring to a specific Zenodo or GitHub repo). Relying on non-existent HF dataset names as the primary fetch strategy makes the pipeline infeasible as written. The plan must cite the actual accessible source (e.g., specific Zenodo DOI, GitHub repo, or a verified open proxy like QMOF/CoRE MOF) rather than assuming a canonical HF name that does not resolve.
- The research plan explicitly acknowledges that the 'Verified datasets' block contains URLs for unrelated datasets (cybersecurity, doctor-patient) and proposes a fallback of 'halting' if the assumed HF names fail. This creates a fatal feasibility gap: the project cannot proceed without a verified, accessible source for adsorption data. The plan must identify a specific, real, open-access dataset (e.g., QMOF, CoRE MOF, or a specific NIST mirror with a valid URL) that matches the required schema (Type I isotherms, Henry's constant, Langmuir capacity) before the pipeline can be considered viable.
- Constitution Principle VII (Physicochemical Plausibility Validation) requires testing on 'independent literature datasets (such as Kr adsorption on carbon nanotubes)'. The Plan's 'Technical Context' and 'Methodology' sections only describe training on NIST/MOF-1000 and do not include a step to fetch, process, or evaluate against this specific independent dataset. This violates the constitutional requirement for external validation.
- The Plan states: 'The plan assumes the names of these datasets are correct but the URLs... are placeholders'. It further states: 'If these fail, the pipeline will halt'. This violates Constitution Principle II (Verified Accuracy) which mandates that citations must be verified against primary sources before contributing to the project. A plan that halts on unverified data sources without a fallback to a verified proxy (as suggested in research.md) fails the 'Verified Accuracy' gate.
- The 'Complexity Tracking' table mentions 'Cluster-aware Permutation (FR-007)' but the Plan's 'Methodology' section (Section 3.4) describes 'Cluster-aware: Shuffles feature values *within* groups of the same `adsorbent_id`'. The data model (data-model.md) defines `adsorbent_id` as a string key, but the contract `dataset.schema.yaml` requires `adsorbent_id` while `dataset_schema.yaml` uses `adsorbent_material`. The Plan does not explicitly state which column name the permutation logic will use, risking a runtime mismatch.
- The plan proposes 'Cluster-aware Permutation' where feature values are shuffled *within* groups of the same `adsorbent_id`. This is scientifically invalid for testing feature importance. Adsorbent properties (surface area, pore volume) are constant within a cluster; shuffling adsorbate descriptors *within* a cluster does not break the correlation between the descriptor and the target if the target varies by adsorbate. More critically, if the goal is to test the adsorbent's contribution, shuffling adsorbate features within a fixed adsorbent cluster destroys the physical pairing (adsorbate-adsorbent interaction) required to predict the isotherm parameter. The permutation strategy described does not generate a valid null distribution for the *interaction* effect or the *global* feature importance in a paired dataset. It risks producing p-values that are either trivially 1.0 (if the target is constant within the cluster) or meaningless (if the target varies but the shuffle breaks the physical mechanism). A valid approach requires permuting the *pairing* (shuffling adsorbate IDs across adsorbents) or using a leave-one-cluster-out cross-validation for significance testing, not intra-cluster shuffling of features.
- The plan states: 'Compare top 3 features against `LiteratureConsensusList`... Report highlighting convergence... and divergence'. This creates a circular validation risk if the `LiteratureConsensusList` is derived from the same physical principles used to select the RDKit descriptors (e.g., polarizability is in the list *because* it is known to correlate with adsorption). If the model selects polarizability, the 'convergence' is a tautology of the feature selection process, not an independent validation of the model's predictive power. The plan must explicitly define the `LiteratureConsensusList` as an *external* benchmark derived from independent experimental studies (not the same dataset or derived from the same theoretical assumptions as the descriptors) to avoid confirming the hypothesis by definition. If the list is just 'known physics', the analysis is trivial. The plan needs to specify that the validation is against *unseen* experimental data or a distinct theoretical framework, not just a list of descriptors that are physically plausible by construction.
