## Unresolved concerns

- The plan states: 'training a Linear SVM to test for linear separability (US-01)'. This approach conflates the *existence* of a linear separator with *geometric disentanglement*. A high accuracy on a linear classifier only proves the classes are linearly separable in the current projection; it does not prove the latent space is *disentangled* (i.e., that dimensions correspond to independent factors). The methodology must explicitly define how 'disentanglement' is measured beyond simple separability (e.g., via disentanglement metrics like DCI or by demonstrating that the direction of separation is orthogonal to other semantic axes).
- The plan proposes 'Vector arithmetic ($z_{new} = z_{doc} - \mu_{text\_old} + \mu_{text\_new}$)' to swap text. This assumes the latent space is linear and that the 'text' direction is a single global vector. If the 'text' concept is distributed non-linearly or varies by font/layout, this arithmetic will fail or produce artifacts. The methodology lacks a validation step for the *linearity assumption* itself before applying the arithmetic. Without verifying that the vector difference $\mu_{text\_new} - \mu_{text\_old}$ consistently maps to text changes across diverse samples, the editing claim is methodologically unsound.
- The plan relies on 'ground-truth bounding boxes' to extract 'text-only' and 'image-only' regions. However, document images often contain mixed modalities (e.g., text over images, icons within text). The plan does not specify a methodology to handle 'mixed' regions or to verify that the crops are truly 'pure' modalities. If the training data contains mixed labels, the 'linear separability' result will be an artifact of the dataset noise rather than true latent disentanglement, invalidating the causal claim.
- The plan uses 'Masked SSIM' to verify layout preservation. SSIM measures structural similarity but is sensitive to texture and noise. If the VAE reconstruction introduces high-frequency noise, SSIM will drop even if the layout (geometry) is preserved. The methodology should include a geometry-specific metric (e.g., edge alignment, corner detection consistency) in addition to SSIM to robustly validate 'layout preservation' as defined in the spec.
- The 'GPU Escape Hatch' (Kaggle) is proposed if CPU fails. However, the hypothesis (US-02) claims 'zero-shot semantic editing' is feasible on CPU. If the model *requires* GPU to run at all (due to memory constraints), the 'CPU-first' claim is falsified. The methodology should explicitly state that if the GPU escape hatch is triggered, the 'CPU feasibility' hypothesis is rejected, rather than treating it as a mere implementation detail. The current plan risks conflating 'model feasibility' with 'editing feasibility'.
- The plan cites 'OmniDoc-TokenBench' and provides a URL to 'Omni-Doc-1' (https://huggingface.co/datasets/omnineura/Omni-Doc-1/...). The dataset name in the text ('OmniDoc-TokenBench') does not match the repository name in the URL ('Omni-Doc-1'). While the URL may reach, the plan fails to confirm that 'Omni-Doc-1' is the correct source for the 'OmniDoc-TokenBench' benchmark required by the spec. If 'Omni-Doc-1' is a general document dataset lacking the specific 'TokenBench' modality labels or ground-truth bounding boxes required for the geometric analysis, the dataset is inappropriate for the research question.
- The plan assumes the 'Qwen-Image-VAE-2.0' model is available and runnable on CPU within 7 GB RAM. The plan does not cite a specific source (e.g., Hugging Face model ID, GitHub repo) for this model weights. Without a verified source, it is impossible to confirm the model exists, its architecture (which determines memory footprint), or its license. Assuming a specific VAE version exists and fits the constraints without a citation is a methodological risk; if the model is not publicly available or requires >7GB RAM, the entire CPU-first approach fails.
- The plan lists 'paddlepaddle (CPU)' as a dependency but does not specify the version or the source for the PaddleOCR model weights. The spec (US-02) requires PaddleOCR for text verification. The plan must cite the specific PaddleOCR version and model configuration to ensure the tooling is reproducible and fits the CPU constraints.
- Constitution Principle II (Verified Accuracy) is marked PASS, but the plan references 'Verified Datasets' without explicitly listing the dataset URL or accession ID in the plan text itself, relying on an external block. Principle II requires every external citation in the plan to be verified. The plan must explicitly cite the dataset URL (e.g., 'https://huggingface.co/datasets/omnineura/Omni-Doc-1/...') within the plan text to satisfy the 'Verified Accuracy' gate without relying on implicit context.
- The plan lists 'paddlepaddle (CPU)' as a dependency. However, the Spec (FR-002) and Constitution (Principle VII) mandate a 'CPU-First' environment with strict memory constraints (7 GB). PaddlePaddle is a heavy framework often requiring significant overhead. The plan must explicitly justify why PaddlePaddle is necessary over lighter alternatives (like OpenCV for OCR) or confirm that the specific CPU-only wheel fits within the 7 GB RAM constraint, otherwise it risks violating the 'CPU-First' and 'Data Hygiene' (memory overflow) principles.
- The 'Project Structure' section lists `contracts/` as 'Phase 1 output', but the `plan.md` itself is a 'Phase 0' or 'Planning' artifact. The plan should not list contracts as outputs of the *plan* phase if they are generated later; rather, the plan should *reference* the existence of these contracts as inputs or targets. This creates a minor temporal confusion in the document flow, though not a fatal logic error.
- The 'GPU Fallback Logic' justification states 'VAEs can be memory-intensive'. While true, the plan must explicitly reference the specific 'Escape Hatch' mechanism defined in the Spec (US-02, Assumptions) to ensure the fallback is not just a 'scaled-down run' but a specific, reproducible procedure (e.g., 'Kaggle GPU with N=100 subset'). The current text is vague on the *reproducibility* of the fallback, which conflicts with Constitution Principle I (Reproducibility).
- The plan validates the 'linear separability' hypothesis by training a Linear SVM on latent vectors labeled with ground-truth modality (text/image). This is a tautological validation: the 'ground-truth' labels are derived from the bounding box annotations (text region vs. image region) which define the input crops. If the VAE is a standard convolutional encoder, it will trivially separate these crops based on low-level texture/edge statistics (e.g., text has high-frequency edges, images have smooth gradients) rather than 'semantic disentanglement' of the latent space. The analysis confuses 'input modality classification' with 'latent space geometric structure'. A valid test requires the classifier to be trained on *unlabeled* crops (as per FR-003) and the 'ground truth' to be an *independent* semantic property not trivially encoded in the crop's pixel statistics, or the plan must explicitly control for trivial pixel-based separability (e.g., via a 'triviality_flag' in output.schema.yaml).
- The plan proposes validating 'layout preservation' via Masked SSIM and Keypoint Matching between an 'edited' image and a 'baseline reconstruction'. However, the 'baseline reconstruction' is generated by encoding and decoding the *original* image ($z_{baseline} = 	ext{decode}(	ext{encode}(z_{doc}))$). The 'edited' image is generated by $z_{edited} = z_{doc} - \mu_{text old} + \mu_{text new}$. If the vector arithmetic fails to change the text content (i.e., the edit is null), the edited image will be nearly identical to the baseline, yielding high SSIM/Keypoint scores. This creates a circular validation where a *failed* edit (no change) is scored as a *successful* layout preservation. The plan lacks a control where the text content is *known* to have changed (e.g., via OCR verification) before assessing layout preservation, or it must compare the edited image against the *original* image (not the baseline reconstruction) to isolate the effect of the arithmetic on the non-text regions.
- The plan applies Bonferroni correction to the family of p-values derived from 'accuracy, F1, SSIM, and Keypoint Score' (FR-009). However, SSIM and Keypoint Score are continuous metrics with thresholds (≥0.85, ≥0.80) and are not hypothesis tests with p-values in the current design. The plan invents p-values for these metrics without defining the null distribution or the statistical test (e.g., permutation test) used to generate them. Applying Bonferroni correction to non-existent or undefined p-values is methodologically unsound. The plan must either define a valid statistical test for SSIM/Keypoint (e.g., comparing against a null distribution of random edits) or remove them from the multiple-comparison family.
- The plan assumes the VAE encoder/decoder can run on CPU for 'small batches or single images' and that the 'Linear SVM' is trivial. However, the 'Qwen-Image-VAE-2.0' (implied to be a large model) likely has a latent dimension and architecture that makes CPU inference prohibitively slow for the required sample size (N) to achieve statistical power (Power ≥ 0.8). The plan does not provide a power analysis for the *runtime* constraint, only for the statistical power. If the CPU runtime exceeds 6 hours (SC-004) before N is reached, the statistical power will be < 0.8, rendering the result 'inconclusive' by design. The plan fails to address the trade-off between statistical power and computational feasibility on the constrained hardware, potentially leading to a study that is scientifically valid in theory but impossible to execute within the constraints.
