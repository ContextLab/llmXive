# Implementation Plan: llmXive follow-up: extending "SpatialClaw: Rethinking Action Interface for Agentic Spatial Reasoning"

**Branch**: `001-llmxive-spatialclaw-restriction` | **Date**: 2026-08-02 | **Spec**: `spec.md`

## Summary

This feature implements a **Restricted Execution Kernel** to evaluate the "loss ceiling" of agentic spatial reasoning when constrained to 2D geometric operations. The system enforces a strict whitelist of 2D libraries (`shapely`, `numpy`) and blocks all 3D libraries (`trimesh`, `pytorch3d`). It executes the agent on a **Synthetic SpatialClaw Proxy** (verified, self-contained data source) that preserves 3D geometric invariants, re-runs the 3D baseline on identical task instances for paired comparison, and performs rigorous statistical analysis (McNemar's test for binary outcomes, Wilcoxon for continuous errors, Bonferroni correction) and sensitivity analysis on depth-estimation thresholds using independent ground truth. The entire pipeline is designed to run on CPU-first infrastructure (GitHub Actions free-tier) with a GPU escape hatch only if the baseline model requires CUDA.

## Phase Plan

### Phase 0: Data Strategy, Power Analysis & Feasibility (Research)
- **Goal**: Verify data availability, define generative constraints, and calculate sample size.
- **Steps**:
  1. **Citation Resolution**: Explicitly document that "SpatialClaw" is a conceptual benchmark; the data source is the "Synthetic SpatialClaw Proxy" (self-contained, verified).
  2. **Generative Constraints**: Define the `generator.py` logic to ensure 3D invariants (occlusion, depth variance) are preserved. Use procedural generation logic based on [Citation: Prior Spatial Reasoning Benchmarks] to ensure geometric complexity.
 3. **Power Analysis**: Calculate minimum N required to detect a clinically significant degradation effect size with [deferred] power for McNemar's test. Set N to a maximum of the calculated N and a predefined minimum threshold.
  4. **Validity Check**: Generate a pilot set (N=10) and verify that 2D projection loses critical information for a subset of tasks (e.g., occlusion tasks where 2D overlap is high but 3D depth is distinct). If not, adjust generator parameters.
  5. Define the `RestrictedActionError` mechanism.
  6. Define the 2D projection math (bounding boxes, depth histograms) for FR-002.
- **Deliverables**: `research.md`, `data-model.md`, `contracts/dataset.schema.yaml`, `contracts/baseline_run.schema.yaml`.

### Phase 1: Kernel & Agent Implementation
- **Goal**: Build the restricted execution environment and the agents.
- **Steps**:
  1. Implement `restricted_kernel.py` to intercept imports and function calls (FR-001).
  2. Implement `agent_2d.py` using `shapely`/`numpy` (FR-002).
  3. Implement `baseline_3d.py` to re-run the 3D logic (FR-007).
  4. Integrate stochasticity control (seeds, temperature=0) (FR-008).
- **Deliverables**: `code/` scripts, `contracts/agent.schema.yaml`.

### Phase 2: Metrics & Statistical Engine
- **Goal**: Collect data and perform analysis.
- **Steps**:
  1. Implement `collector.py` for latency/success logging (FR-003).
  2. Implement `comparator.py` for paired comparison (FR-004).
  3. Implement `tests.py`:
     - **Binary Outcomes**: McNemar's test for paired success/failure.
     - **Continuous Outcomes**: Wilcoxon signed-rank for depth estimation error (meters).
     - **Correction**: Bonferroni correction for multiple comparisons across multiple task types.
  4. Implement `sensitivity.py` (FR-006) using **independent ground truth** (synthetic generator's known geometric parameters) to avoid circular validation.
- **Deliverables**: `contracts/results.schema.yaml`, `contracts/statistical.schema.yaml`, `stats/` modules.

### Phase 3: Integration & Validation
- **Goal**: Run the full pipeline and verify constraints.
- **Steps**:
  1. Run N independent runs per task instance (N from the initial planning phase).
  2. Verify `grep` for "trimesh" returns 0 in logs.
  3. Generate summary CSVs and statistical reports.
  4. Validate against `quickstart.md` instructions.
- **Deliverables**: Final results, `tasks.md` (for next stage).
