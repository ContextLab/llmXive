## Unresolved concerns

- Task T031b handles sensitivity failure by logging a warning if variation > 0.05. SC-002 states the variation *must* be ≤ 0.05. The tasks lack a mechanism to explicitly *fail* or *block* the pipeline if this success criterion is not met, treating a mandatory success criterion as a non-fatal warning. This leaves the implementation unable to satisfy the mandatory 'measurable outcome' of SC-002.
- The spec's Edge Cases explicitly require treating species with 'zero predicted BGCs' as valid data points. Task T017 ('align_data') mentions 'filtering partial rows' but does not explicitly state a logic step to *preserve* zero-count rows while filtering only rows with missing data in either modality. Without this explicit instruction, the implementation risks filtering out valid biological data (zero BGCs), violating the spec's edge case handling.
- FR-005 mandates '5-fold cross-validation'. The tasks implement a conditional logic (T023a-LOO for N<20, T023b for N>=20) to switch to Leave-One-Out. While the Plan.md justifies this, the tasks themselves do not contain the explicit justification or a reference to the Plan's 'Complexity Tracking' table explaining why FR-005 is being deviated from. This creates a traceability gap where the task appears to contradict the spec without internal justification.
- Task T026 (run_phylogenetic_permutation) is scheduled to 'execute before T024 evaluation', but T024 is the *training* task (train_pgls). A permutation baseline requires a trained model or a specific evaluation context to compare against. The dependency graph is inverted: T026 (baseline generation) must logically follow the model training (T024/T023) and precede the final comparison/evaluation (T025/T027). Current order makes the baseline calculation impossible.
- Task T024 (train_pgls) depends on PCA-reduced features from T023a-PCA, but the dependency is not explicitly enforced in the task list. The plan states PCA is required to prevent overfitting (N < 50), yet T024 could theoretically run on raw data if the execution engine ignores the implicit dependency. A clear 'T024 depends on T023a-PCA' marker or reordering is needed to ensure the dimensionality reduction constraint is met before model training.
- Tasks T012 and T013 (download) are marked with 'FAIL LOUDLY' logic (no fallback), while T017 (align_data) expects to filter partial rows. If T012/T013 fail immediately, T017 never runs, and the 'alignment success rate' (SC-004) cannot be calculated against the original input list as required. The flow assumes partial success (some species fail, some succeed) but the download tasks are binary (all or nothing). The ordering/logic creates a gap where the success metric cannot be computed if the primary source fails for any species.
- Task T023a-LOO contains conditional logic ('if N >= 20, run T023b instead') that contradicts the standard sequential flow. While the logic is sound, the task ID 'T023a-LOO' implies it is a sub-task of 'T023a', yet it acts as a gatekeeper for T023b. This creates ambiguity in the execution order: does T023a-LOO run *before* T023b to decide, or are they mutually exclusive? The dependency graph should explicitly state 'T023b depends on T023a-LOO (N>=20 check)' to clarify the flow.
- Task T012 describes a fallback logic ('Attempt RefSeq first; if RefSeq fails... fallback to Phytozome') that contradicts the 'REVISION' note at the bottom of the file which mandates 'FAIL LOUDLY' and removing fallbacks. The task description is internally contradictory and unexecutable: an implementer cannot know whether to implement the fallback or the strict failure.
- Task T013 describes fetching from 'PMDB/MetaboLights' but the 'REVISION' note explicitly mandates removing fallback logic and raising an error if the primary source fails. The task description lacks a specific 'primary source' definition and contradicts the revision note, making the execution logic ambiguous.
- Task T026 states it must 'execute before T024 evaluation' but T024 is defined as a 'training' task. The dependency graph is logically broken: a permutation baseline (evaluation) cannot be computed before the model is trained (T024). The task description fails to define the correct execution order relative to T024, making the workflow impossible to execute as described.
- Task T007 claims to implement 'checksum verification logic' and 'update the updated_at timestamp' but does not specify the exact file paths for the output artifacts (e., `data/processed/aligned_matrix.csv`) whose checksums must be recorded. Without naming the specific output files, the task is not self-contained and the implementer cannot determine which files to checksum.
- FR-005 mandates '5-fold cross-validation' for regression models. Tasks T023a-LOO and T023b implement conditional logic to use Leave-One-Out (LOO) for N < 20. While the Plan.md justifies this in 'Complexity Tracking', the Spec.md (FR-005) does not explicitly allow this deviation. The task list enforces a method that contradicts the explicit functional requirement without a documented exception in the spec itself.
- Constitution Principle III requires 'every transformation MUST produce a new file' and 'checksummed'. Task T007 describes infrastructure for checksums but does not explicitly include a task step to generate and record checksums for the *transformed* output files (e.g., aligned_matrix.csv, pca_features.csv). This creates a gap in the Data Hygiene verification chain for derived artifacts.
- FR-010 defines PGLS as the 'primary regression model'. The Plan.md mandates 'Dimensionality Reduction (PCA)' before multivariate modeling to prevent overfitting. Task T024 (train_pgls) does not explicitly state it MUST consume the PCA-reduced features from T023a-PCA. Without this explicit dependency, PGLS could run on raw high-dimensional data, violating the Plan's constraint and risking statistical instability.
- FR-006 requires comparing model performance against a 'Phylogenetic Permutation baseline'. Task T026 (run_phylogenetic_permutation) is scheduled to 'execute before T024 evaluation', but T024 is the *training* task. The permutation baseline must be calculated *after* model training to compare the model's R² against the null distribution. The dependency graph is logically inverted, making the comparison impossible.
- SC-002 states the variation in R² across thresholds 'must be ≤ 0.05'. Task T031b handles 'sensitivity failure' (variation > 0.05) by logging a warning and recording the metric, rather than treating it as a blocking verification failure. This allows the pipeline to complete with a robustness metric that technically violates the Success Criterion.
- The Spec's Edge Cases explicitly require handling species with 'zero predicted BGCs' as valid data points.
