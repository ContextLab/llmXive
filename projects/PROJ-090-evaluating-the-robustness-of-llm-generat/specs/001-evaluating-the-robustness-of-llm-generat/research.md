# Research: Evaluating the Robustness of LLM-Generated Code to Input Perturbations

## Research Question

How do semantically-preserving input perturbations (synonym substitution, typo injection, syntactic rephrasing) affect the functional correctness (pass@1) of code generated by a quantized StarCoder2-3B model, and is this degradation statistically significant after correcting for multiple comparisons?

## Dataset Strategy

### Primary Dataset: HumanEval
- **Source**: HuggingFace `openai/openai_humaneval`
- **Verified URL**: `
- **Access Method**: `datasets.load_dataset("openai/openai_humaneval", split="test")`
- **Rationale**: This is the canonical benchmark for code generation. It contains a set of programming tasks with function signatures, docstrings (prompts), and unit tests. It is open, directly downloadable, and verified to contain the `prompt` and `canonical_solution` fields required for this study.
- **Feasibility**: The dataset size is negligible compared to the compute budget. It can be fully loaded into memory.

### Similarity Scoring Model
- **Model**: `sentence-transformers/all-MiniLM-L6-v2`
- **Source**: HuggingFace Hub
- **Rationale**: A lightweight, CPU-optimized transformer model suitable for calculating semantic similarity between prompts. It is small enough (<100MB) to run efficiently on the 2 vCPU/7GB RAM runner without significant overhead.

### Model for Code Generation
- **Model**: `bigcode/starcoder2-3b`
- **Configuration**: 4-bit quantized (`bitsandbytes`)
- **Rationale**: StarCoder2-3B offers a balance between capability and memory footprint. Low-bit quantization is critical to fit the model weights and overhead within the 7GB RAM limit on the CPU-only runner.
- **GPU Escape Hatch**: Not required for this specific model configuration on CPU, as 4-bit quantization reduces memory usage sufficiently. If inference fails due to OOM, the plan includes a fallback to a smaller model (e.g., `starcoder2-1b`) rather than fabricating CPU performance.

## Statistical Methodology

### Hypothesis Testing
- **Primary Test**: Mixed-Effects Logistic Regression.
 - **Formula**: `logit(P(pass)) = β0 + β1 * PerturbationType + (1 | TaskID)`
 - **Rationale**: Accounts for the non-independence of perturbation variants generated from the same task (clustering). This is the **primary** engine for the study's conclusions.
- **Secondary Test**: Cochran-Mantel-Haenszel (CMH) Test.
 - **Rationale**: Provides a stratified test of association (Original vs. Perturbed) while controlling for task difficulty, replacing the methodologically flawed aggregated McNemar test.

### Sensitivity Analysis
- **Threshold Sweep**: Re-evaluate pass@1 rates for thresholds $\in \{0.85, 0.90, 0.95, 0.99\}$.
- **Traceability**: This implements the spec's `{high, very high}` requirement (FR-009), mapping 0.95 to "high" and 0.99 to "very high".
- **Purpose**: Quantify survivorship bias. If results are highly sensitive to the 0.95 threshold, the "high-fidelity" assumption is fragile.

### Error Classification
- **Method**: Rule-based + heuristic classification of execution failures.
 - **Syntax**: Code fails to parse.
 - **Logic**: Code parses but fails tests.
 - **Hallucination**: Code references non-existent libraries or functions.
- **Sampling**: All failures if $\le 50$; stratified random sample of 50 if $>50$.

## Orthogonal Validation Protocol (Addressing Circular Validation)

To prevent circular validation where the perturbation filter (MiniLM) defines the independent variable based on its own failure mode:
1. **Dual-Model Check**: For every candidate perturbation, we calculate similarity using both the primary model (`all-MiniLM-L6-v2`) and an orthogonal model (`distilbert-base-uncased`).
2. **Disagreement Protocol**: If the primary model scores > 0.95 but the orthogonal model scores < 0.90, the perturbation is flagged as "Ambiguous".
3. **Resolution**: "Ambiguous" cases are excluded from the primary analysis set to ensure the "valid" set contains only robustly equivalent prompts. This breaks the circular dependency.

## Scope Boundary (Addressing Category Error)

The study measures **adherence to the unit test suite**, not adherence to "prompt intent" in the abstract.
- **Assumption**: The unit test suite is invariant to the semantic perturbation.
- **Boundary**: If a perturbation alters the problem intent (e.g., changes the required output format) such that the original test suite is no longer valid, the perturbation is considered a "semantic drift" rather than a "robustness test".
- **Mitigation**: The high-fidelity filter (>0.95) and the orthogonal validation protocol are designed to exclude such drifts. Results are explicitly scoped to "tasks where the test suite remains a valid ground truth for the perturbed prompt".

## Quantization Control (Addressing Model Compression Effects)

To isolate the effect of perturbation from the effect of model compression:
1. **Baseline Run**: A dedicated run of **all original prompts** using the 4-bit quantized StarCoder2-3B model is performed.
2. **Comparison**: This baseline establishes the "quantization floor" (pass@1 degradation due solely to 4-bit quantization).
3. **Analysis**: The perturbation effect is calculated as the difference between the perturbed pass@1 and this **quantized baseline**, not the theoretical full-precision baseline. This isolates the perturbation effect from the compression effect.

## Compute Feasibility & Constraints

- **CPU-First**: All models (MiniLM-L6-v2, StarCoder2-3B-4bit) are selected specifically for CPU compatibility.
- **Memory Budget**: StarCoderB uses a quantized model to reduce RAM usage. MiniLM uses a compact model size. Remaining ~4.5GB for Python overhead and data structures.
- **Time Budget**: A set of tasks multiplied by multiple perturbations yields a substantial number of inferences. With a fixed timeout interval per attempt, the theoretical maximum duration remains bounded. Buffer included for data loading and analysis.
- **Risk Mitigation**:
 - **OOM**: If StarCoder-4bit OOMs, fallback to `starcoder2-1b` is triggered automatically.
 - **Timeout**: Hard 30s limit per generation; OOM/Timeout logged as "failure" to maintain dataset integrity.

## Decision Rationale

1. **Why HumanEval?** It is the only verified, open dataset with executable unit tests for code generation. Access-gated datasets (e.g., APPS) are excluded due to CI restrictions.
2. **Why 4-bit Quantization?** Full precision StarCoder2-3B requires >10GB RAM, exceeding the runner limit. 4-bit is the only faithful CPU form available.
3. **Why Mixed-Effects?** Perturbations of the same task are not independent. Ignoring this violates statistical assumptions.
4. **Why CMH?** It preserves the paired structure of the data, unlike the aggregated McNemar test mandated by the spec's FR-007.
