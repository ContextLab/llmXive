## Unresolved concerns

- The plan generates host‑molecule fingerprints and RDKit descriptors (FR‑002) but never encodes the halide identity (F⁻, Cl⁻, Br⁻, I⁻) as a predictor. Without a halide feature the model cannot learn halide‑specific effects, making per‑halide R²/RMSE claims invalid.
- Task T001b creates a simulated dataset using a deterministic linear formula (logK = 0.5*charge_density + 0.3*cavity_volume + N(0,0.2)). This construction guarantees that the model will perform well on the simulated data, but it does not test the ability of the workflow to predict real halide binding affinities. The fallback therefore cannot answer the primary comparative research question.
- Task T011 appends an “independent‑evaluation” section that uses a feature‑independent target set (random N(0,1) values). This is not a genuine external validation; performance on random noise provides no evidence of model generalisation and may give a false sense of robustness.
- The power check (FR‑012) requires ≥10 hosts per halide, yet the bootstrap CI step proceeds even when the sample size is at this minimum. With such small N the bootstrap confidence intervals are unstable, and the plan does not include any formal power analysis or guidance on when results should be considered unreliable.
- Success Criterion SC-003 (Model training runtime measured against the documented compute budget) is not addressed by any task or metric in the plan. The plan describes the compute environment but provides no artifact, log, or measurement that records model training duration to verify compliance with the ≤6‑hour, ≤7 GB RAM budget.
- The plan cites only generic SMILES, WebBook metadata, PubChem, and RDKit parquet files as “Verified Datasets”, none of which contain the required experimental halide binding constants (host‑SMILES + halide_identity + binding_constant). This means the primary data source required by FR‑001 is missing, making the real‑data branch of the workflow unsupportable and forcing reliance on the simulated fallback. Add a citation to a dataset that actually provides halide‑binding measurements (or acknowledge that no such open dataset exists and redesign the research question accordingly).
- The plan writes `output_summary.json` intended to conform to `contracts/output.schema.yaml` (FR‑014) but does not include a validation step (e.g., jsonschema check). This means the contract is never exercised, violating the ‘every contract must be exercised by a plan element’ rule.
- Constitution Principle IV requires an explicit SSoT designation (a single artifact that all figures, statistics, and interpretations trace back to). The plan’s SSoT table mentions that metrics are computed from `data/processed/halide_binding_data.csv` and figures reference script lines, but it does not name a concrete SSoT artifact (e.g., a master results JSON or a designated report file). This omission may be interpreted as missing the required SSoT designation.
- The plan validates model performance (R² > 0.5, SC‑001) on a *simulated* target that is defined as a linear combination of the very features used for prediction (logK = 0.5*charge_density + 0.3*cavity_volume + N(0,0.2)). This creates a circular/tautological validation: the outcome (model R²) is guaranteed to be high because the target is *by definition* predictable from the predictors. The independent‑evaluation step uses a feature‑independent random target, but the primary success criterion remains tied to the circular simulated target, making the claimed result non‑trivial only by definition rather than empirical evidence.
