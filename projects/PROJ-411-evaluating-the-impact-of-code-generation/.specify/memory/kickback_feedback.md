## Unresolved concerns

- The plan’s opening summary frames the work as ‘evaluating the impact’ which implies a causal effect of LLM‑generated code on review burden, yet the design is purely observational. The methodology must explicitly state that only associational differences will be inferred, or add a causal identification strategy (e.g., propensity‑score matching) if causal claims are intended.
- Power analysis is mentioned only in the research document, not in the implementation plan. The plan should include a concrete power calculation (expected effect size, α, desired power) and a minimum required sample size for each group before proceeding to hypothesis testing.
- The primary outcome metrics (review_active_seconds, comment_density, issue_severity) are treated as direct proxies for reviewer burden, but issue_severity is a categorical label that may not reflect effort. The construct validity of issue_severity as a burden measure is not justified; the plan should either provide a rationale or replace it with a more direct effort indicator.
- Confounding variables such as PR size (lines_changed), author experience, or repository popularity are not modeled beyond a random intercept for repo. Without adjusting for these known predictors of review effort, the estimated differences between LLM‑generated and Human‑written groups may be biased. Include them as fixed effects or stratify analyses.
- Mixed‑provenance PRs are excluded from the primary binary comparison, which could introduce selection bias if mixed PRs differ systematically in size or complexity. The plan should assess and report any bias introduced by this exclusion.
- The `review_active_seconds` metric (time from first review comment to PR merge) requires a timestamp for the first review comment, but the `Raw PR Dataset Schema` (`raw_prs.schema.yaml`) does not include any field capturing comment timestamps (only `comment_count`). Without this variable the metric cannot be computed as described in the plan, making the chosen dataset inappropriate for that part of the analysis. Add a field (e.g., `first_comment_timestamp`) to the raw schema or adjust the metric to use only available data.
- The plan claims compliance with Principle IV (Single Source of Truth) but does not explicitly designate which artifact serves as the SSoT (e.g., `data/processed/processed_prs.csv`). An explicit statement is required to satisfy the constitution.
- Phase 0 describes downloading and converting parquet files but never references the `raw_prs.schema.yaml` defined in `data-model.md`. This creates a gap between the data model and the implementation plan.
- The statistical analysis step mentions outputting `stats_summary.csv` but does not state that this file must conform to `contracts/statistical_results.schema.yaml`. Explicit linkage to the contract is needed for schema validation.
