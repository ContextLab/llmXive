# Plan Alignment: `structure_config.json` vs `model_config.json`

## Issue
The `plan.md` document references `structure_config.json` in the "Contract Mapping" section and other locations. However, the implementation tasks (specifically **T021b**) generate `model_config.json` as the single source of truth for design structure and family type. Task **T021c** generates `structure_config.json` as an alias (copy) of `model_config.json` specifically to maintain backward compatibility with the plan's existing contract mapping references.

## Resolution
This document acknowledges the implementation strategy:
1. **Primary Artifact**: `data/processed/model_config.json` is the canonical configuration file generated by `code/analysis.py` (T021b).
2. **Compatibility Alias**: `data/processed/structure_config.json` is generated by `code/analysis.py` (T021c) as a direct copy of `model_config.json`.
3. **Plan Reference**: The `plan.md` references to `structure_config.json` are now satisfied by the alias generation step. No further changes to `plan.md` text are required as the file exists and contains identical data to `model_config.json`.

## Implementation Details
The logic in `code/analysis.py` (Task T021c) ensures:
```python
import shutil
#... after writing model_config.json...
shutil.copy('data/processed/model_config.json', 'data/processed/structure_config.json')
```

This ensures that any downstream process or contract test looking for `structure_config.json` (as per the original plan) will find a valid, up-to-date file with the same content as `model_config.json`.
