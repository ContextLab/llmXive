# Reproduction Guide
This document provides step‑by‑step instructions for reproducing **all user stories** in the
*llmXive Geometry Extension* project. It assumes a fresh clone of the repository on a
Linux/macOS/Windows machine with Python 3.11 installed.

## 1. Environment setup

1. **Create a virtual environment** (optional but recommended)
 ```bash
 python -m venv.venv
 source.venv/bin/activate # Windows:.venv\Scripts\activate
 ```

2. **Install the project dependencies**
 ```bash
 pip install -r requirements.txt
 ```

3. **Create the required directory layout**
 The project layout (`src/`, `tests/`, `data/`, `results/`, `contracts/`) is created by the
 helper script `setup_project_layout`.
 ```bash
 python -m setup_project_layout
 ```

## 2. Data acquisition & verification

The experiments use the **GSM8K** benchmark dataset.

1. **Download the dataset (streaming) and cache it**
 ```bash
 python -m src.data.download_gsm8k
 ```
 This script streams the three splits (`train`, `validation`, `test`) from the
 Hugging‑Face hub and stores them under `data/gsm8k/`.

2. **Validate the SHA‑256 checksums** (generated by `src/data/checksums`)
 ```bash
 python -m src.data.checksums validate
 ```
 The command aborts if any file’s checksum does not match the entries in
 `data/checksums.txt`.

3. **Split the dataset into experimental subsets**
 The split script stratifies by estimated difficulty and writes three split files
 (`train_split.jsonl`, `eval_split.jsonl`, `heldout_split.jsonl`) into `data/gsm8k/`.
 ```bash
 python -m src.data.split_gsm8k
 ```

## 3. Core preprocessing

1. **Compute per‑layer weight deltas (OPD baseline)** – runs a 3‑epoch TinyLlama
 training and stores the deltas under `data/baseline_deltas/`.
 ```bash
 python -m src.train.opd_baseline
 ```

2. **Perform randomized SVD on the deltas**
 The script reads the deltas, computes a layer‑wise SVD, and determines the minimal
 rank `k` that explains ≥ 95 % of the variance. Results are written to
 `results/svd_sensitivity.csv` and the binary masks (`mask_opd_{seed}.pt`) are saved
 under `data/masks/`.
 ```bash
 python -m src.data.svd_compute
 ```

## 4. Reproducing the user stories

### 4.1 User Story 1 – Subspace Sufficiency Verification

The full US‑1 pipeline orchestrates the OPD baseline, mask generation, frozen‑subspace
training, evaluation on the held‑out GSM8K split, and statistical analysis.

```bash
python -m src.pipeline.run_us1
```

- **Outputs**
 - `results/us1_summary.csv` – aggregated statistics (power, TOST decision, etc.)
 - `data/masks/` – the OPD masks used in the runs
 - Log files (`logs/*.jsonl`) containing timestamps, RAM usage, and wall‑clock time.

### 4.2 User Story 2 – Comparative Geometric Distinctness

This pipeline repeats the training with **random masks** (generated with the same
dimensionality as the OPD mask) and compares the results against the OPD‑derived masks.

```bash
python -m src.pipeline.run_us2
```

- **Outputs**
 - `results/frozen_sft_accuracy.csv` – per‑run accuracies for OPD and random masks.
 - `results/us2_summary.csv` – mean accuracy drop, paired t‑test/Wilcoxon statistics,
 power analysis (effect size δ = 0.03, σ = 0.015, α = 0.05).
 - Updated `data/masks/` with random mask files (`mask_random_{seed}.pt`).

### 4.3 User Story 3 – Resource Feasibility & Reproducibility

The top‑level pipeline runs US‑1 and US‑2 sequentially and merges all result CSVs into a
unified experiment summary.

```bash
python -m src.pipeline.run_all
```

- **Outputs**
 - `results/experiment_summary.csv` – merged CSV conforming to `contracts/experiment.schema.yaml`.
 - `ci_metrics.json` – JSON summary of peak RAM (GB) and total wall‑clock time (minutes).
 - `state.yaml` – final state artifact (generated by `src.pipeline.export_state_yaml`).

## 5. Seed management & reproducibility

- **Seed definitions** live in `src/config.py` as two lists:
 - `MASK_DERIVATION_SEEDS` – seeds used for generating OPD masks.
 - `EVAL_SEEDS` – seeds driving the evaluation loops for both user stories.
- All scripts import the helper `src.utils.random_seed` (once implemented) to set the
 seeds for `numpy`, `torch`, and Python’s `random`. This guarantees deterministic
 behaviour across runs.

## 6. Resource limits

The `src.utils.resource_monitor` module is automatically activated by each pipeline
script (via a context manager). It enforces the project‑wide constraints:

- **Peak RAM ≤ 7 GB** – otherwise a `ResourceLimitError` is raised.
- **Wall‑clock ≤ 360 minutes** per script – exceeding this aborts the run.

## 7. Verification

The repository includes contract‑style tests that validate:

- Presence and schema compliance of all generated CSV/JSON/YAML artifacts.
- Correct seed usage (tests in `tests/contract/test_reproduction_md.py`).
- Resource‑monitor limits (`tests/contract/test_resource_limits.py`).

Running the full test suite after following the steps above should result in **all
tests passing**:

```bash
pytest -q
```

## 8. Clean‑up (optional)

To start from a clean state, you can delete the generated data directories:

```bash
rm -rf data/gsm8k/ data/baseline_deltas/ data/masks/ results/ logs/
```

Then repeat the steps from **2. Data acquisition** onward.
