# Implementation Plan: Socratic Transformers (Negative Selection on Belief)

**Branch**: `582-socratic-transformers` | **Date**: 2026-06-29 | **Spec**: `spec.md`
**Input**: Feature specification from `specs/582-socratic-transformers/spec.md`

## Summary

This plan implements a selectionist framework for LLM reasoning, replacing "self-teaching" with **negative selection on belief**. The system generates multiple reasoning paths, applies an adversarial critique to identify logical contradictions (selection pressure), and fine-tunes a model to reject the "belief space" associated with failed outputs. We compare three conditions: **Selection** (adversarial critique), **Ablation** (fixed neutral placeholder), and **Static** (no critique). The implementation adheres to strict CPU-first constraints (4-bit quantization, streaming data) and rigorous statistical validation to isolate the effect of the selection signal.

## Implementation Constraints (Plan-Level Requirements)

The following constraints are **mandatory** to satisfy the spec and address panel concerns:

1.  **Regeneration Loop**: Max 3 regeneration attempts per sample. If all fail, the sample is discarded and logged. This ensures the curriculum contains genuine pedagogical signal.
2.  **Token Length Equivalence**: The Ablation condition enforces token-length equivalence via a 'Token Counter' step that pads/truncates the fixed neutral string to match the critique's token count.
3.  **Frozen Critic**: The Critique mechanism must use a **frozen** model (weights not updated during generation) to ensure stability.
4.  **Dynamic Critique**: The Critique must be generated **dynamically** per sample (not pre-computed).
5.  **Syntactic Distractor**: The Ablation placeholder is a **fixed, human-curated** neutral string (syntactic distractor) to avoid stylistic confounds.
6.  **Static Tuple Format**: Static Tuples are **standard (Question, Answer) pairs** generated directly from source datasets (GSM8K/MATH).
7.  **Negative Selection Signal**: The Critique serves as the **negative selection signal**.
8.  **4-bit Quantization**: **Mandatory** for all model loading and training steps.
9.  **Hard Timeout & Memory Monitoring**: Hard timeout of **5 hours**; memory monitoring via `psutil`.
10. **OOM Fallback Mechanism**: If OOM is detected, reduce batch size significantly and retry up to 3 times. If failed, save checkpoint and exit with code 1.
11. **Fallback Model Strategy**: If the primary model (Mistral-7B) exceeds memory, switch to a smaller model (Phi-3-mini) as a mandatory fallback.
12. **Statistical Rigor**: **Family-wise error rate control (Bonferroni)** and **Power Limitation Analysis** are mandatory.
13. **Independent t-test**: Analysis uses **Independent Samples t-tests** (correcting spec's 'paired' error) to compare conditions.
14. **Data Generation Policy**: Generated fields are **Derived Data** (from real source tuples), not **Synthetic Data** (fully artificial).

## Methodology & Statistical Rigor

### 1. Data Generation (US1)
- **Static**: `(Question, Answer)` generated directly from source datasets (GSM8K/MATH).
- **Dialogue (Selection)**: `(Question, Initial Answer, Critique, Revised Answer)`
  - *Critique*: Generated by a **frozen** 4-bit model (e.g., Llama-3-8B) to identify logical errors.
  - *Revised Answer*: Generated by the same model, conditioned on the critique.
- **Ablation**: `(Question, Initial Answer, [Fixed Neutral Placeholder], Revised Answer)`
  - Placeholder is a **fixed, human-curated** string (e.g., "The model considers this answer.") padded/truncated to match the critique's token count.

**Regeneration Loop**: To satisfy Constitution Principle VII, if a generated dialogue fails the quality gate (e.g., lacks logical keywords, too short), the system re-prompts the critic up to **3 times**. If all attempts fail, the sample is logged as "failed" and skipped, ensuring the curriculum contains only valid signal.

### 2. Training (US2)
- **Model**: Base LLM (e.g., `mistralai/Mistral-7B-v0.1` or `Phi-3-mini` as fallback).
- **Method**: LoRA (Low-Rank Adaptation) fine-tuning.
- **Conditions**:
  - **Condition A (Selection)**: Train on Dialogue Tuples.
  - **Condition B (Ablation)**: Train on Ablation Tuples.
  - **Condition C (Static)**: Train on Static Tuples.
- **Compute**: 4-bit quantization (`bitsandbytes`). If CUDA is detected (via Kaggle offload), use GPU; otherwise, CPU.

### 3. Evaluation & Analysis (US3)
- **Metrics**: Accuracy on held-out GSM8K and MMLU STEM subsets.
- **Statistical Test**: **Independent Samples t-tests** (Welch's t-test) comparing Condition A vs. B and A vs. C.
  - *Note*: The source spec's mention of "paired t-tests" is corrected here to "independent" as the groups are independent.
- **Correction**: **Bonferroni correction** applied for multiple comparisons (family-wise error rate control).
- **Power Limitation**: Acknowledged that sample size (N ~ 500-1000) may limit power for small effect sizes (d=0.3).
  - *Mitigation*: Pool data across GSM8K and MATH to increase N where feasible.
  - *Justification*: Target effect size d=0.5, alpha=0.05 (Bonferroni), Power=80% requires N~128 per group. Current N is sufficient for medium effects.
- **Causal Claims**: Claims are strictly **associational** unless randomization of the critique content is proven. The design isolates the *effect of the critique content* via the Ablation condition (fixed placeholder), but does not claim causal generalization beyond the specific model/dataset context.

## Compute Feasibility & Escape Hatch

- **CPU-First**: The plan uses 4-bit quantization and streaming to fit within 7GB RAM.
- **GPU Escape Hatch**: If the fine-tuning step fails due to memory constraints on CPU, the execution stage automatically offloads to a Kaggle GPU. The plan is scaled down (e.g., fewer epochs, smaller batch size) to fit the limited VRAM of a free-tier Kaggle GPU.
- **Numerical Stability**: Use `torch.backends.cpu.enable_quantization=True` and explicit mixed-precision fallbacks. CPU/GPU training dynamics may differ slightly but will be controlled by using the same random seeds and batch sizes across conditions.
- **Data Leakage Prevention**: A **Strict ID Filtering** step hashes every question in the source dataset and compares against the test set IDs before generation. Any match results in immediate exclusion from the training pool.

## Resource Fallback Strategy

- **Hard Timeout**: 5-hour limit with graceful shutdown signal.
- **Memory Monitoring**: `psutil` monitors RSS. If RSS > 6.5GB, trigger fallback.
- **OOM Fallback**: Reduce batch size by [deferred] and retry up to 3 times. If failed, save checkpoint and exit with code 1.
- **Model Fallback**: If Mistral-7B exceeds memory, switch to Phi-3-mini as a mandatory fallback.

## Data Generation Policy

- **Derived Data**: Generated fields (Critique, Revised Answer) are **Derived Data** from real source tuples.
- **Synthetic Data**: Fully artificial data is **forbidden**.
- **Static Tuples**: Generated directly from source datasets (GSM8K/MATH) as standard (Question, Answer) pairs.
