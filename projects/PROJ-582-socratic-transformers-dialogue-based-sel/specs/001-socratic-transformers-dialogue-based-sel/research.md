# Research: Socratic Transformers (PROJ-582)

## 1. Problem Context & Theoretical Framework

This project investigates whether **negative selection on belief**—a process analogous to thymic selection in the immune system—can improve LLM reasoning without explicit "self-teaching." The core hypothesis is that exposing a model to its own erroneous reasoning traces, coupled with an **adversarial critique** that highlights logical contradictions, creates a selection pressure that shifts the model's output distribution away from "false belief" states.

### 1.1 The Socratic Mechanism as Selection
Unlike instruction tuning, which adds new knowledge, this approach relies on **elimination**.
- **Variation**: The model generates multiple reasoning paths.
- **Adversarial Critique**: A separate, frozen "Critic Model" identifies logical flaws (unsupported assumptions, contradictions).
- **Negative Selection**: The training signal penalizes the model for generating the flawed path *in the presence of the critique*, effectively teaching the model to avoid that region of the belief space.

This aligns with David Krakauer's feedback: the system does not "originate" truth but executes ordered operations to filter low-quality outputs.

### 1.2 Cognitive Biases & Heuristics
Per Daniel Kahneman's feedback, the system must address **availability heuristics** and **over-confidence**. By forcing the model to generate a justification *after* an initial answer, and then critique that justification, we simulate a "System 2" check. The adversarial critique serves as the external validator that the model lacks internally, preventing it from reinforcing its own biases.

## 2. Dataset Strategy

We utilize two primary datasets, verified for public accessibility and programmatic download.

### 2.1 Verified Datasets

| Dataset | Source URL | Usage | Verification Status |
|---------|------------|-------|---------------------|
| **GSM8K** | `https://huggingface.co/datasets/openai/gsm8k` | Primary training and evaluation. Contains grade-school math word problems with reasoning steps in the train split. | **Verified**: Official source, programmatic download via `datasets`. |
| **MATH** | `https://huggingface.co/datasets/hendrycks/math` | Secondary training/evaluation for higher-complexity reasoning. | **Verified**: Official canonical benchmark, programmatic download. |

*Note: We do not use access-gated datasets (e.g., MATH full set via API) as they cannot be fetched by the CI runner. We rely on the verified HuggingFace mirrors.*

### 2.2 Data Processing Strategy

1. **Streaming**: We use `datasets.load_dataset(..., streaming=True)` to avoid loading full datasets into RAM.
2. **Sampling**: For the training loop, we will sample a fixed number of examples (e.g., 500 per condition) to ensure the training completes within the 6-hour window on CPU. The sample will be drawn with a fixed seed to ensure reproducibility.
3. **Generation**:
   - **Static Tuples**: `(Question, Answer)` extracted directly.
   - **Dialogue Tuples**: `(Question, Initial Answer, Critique, Revised Answer)`. The critique is generated by a **separate, frozen Critic Model** (e.g., Llama-3-8B) prompted to identify errors in the initial answer. The prompt explicitly asks for "logical contradictions" and "unsupported assumptions".
   - **Ablation Tuples**: Same as Dialogue, but `Critique` is replaced with a **Syntactic Distractor**—a sentence of equivalent length and *syntactic complexity* (e.g., similar parse tree depth) but with randomized word order or irrelevant semantic content. This controls for context window complexity and attention dilution, isolating the *logical content* of the critique.

## 3. Methodology & Experimental Design

### 3.1 Conditions

| Condition | Input Data | Critique Content | Hypothesis |
|-----------|------------|------------------|------------|
| **A: Selection** | Dialogue Tuples | Adversarial critique (logical errors, contradictions) from frozen Critic Model. | Model learns to avoid error patterns. |
| **B: Ablation** | Ablation Tuples | Syntactic Distractor (equivalent length/complexity, no logical content). | Improvement is due to *logical content*, not token count or context complexity. |
| **C: Static** | Static Tuples | No critique. | Baseline performance. |

### 3.2 Training Protocol
- **Model**: `mistralai/Mistral-7B-Instruct-v0.2` (or similar 7B model) loaded with 4-bit quantization (`bitsandbytes`).
- **Fine-tuning**: LoRA (Low-Rank Adaptation) with `r=16`, `lora_alpha=32`.
- **Hardware**: CPU-first (2 cores, 7GB RAM). If OOM occurs, the execution stage auto-offloads to a Kaggle GPU (scaled down: fewer epochs, smaller batch size).
- **Epochs**: 1-2 epochs (sufficient for LoRA on small samples).
- **Batch Size**: 1 (gradient accumulation if needed).
- **Validation Loop**: A held-out validation set ([deferred] of training data) is used for **Early Stopping**. Training stops if validation loss does not improve for a predefined number of epochs.

### 3.3 Evaluation
- **Metrics**: Accuracy on held-out GSM8K test set and MMLU STEM subset.
- **Statistical Analysis**: **Independent Samples t-tests** (or Mann-Whitney U test) comparing Condition A vs. B and A vs. C.
- **Correction**: Bonferroni correction applied for multiple comparisons (family-wise error rate control).
- **Power Analysis**: Acknowledged limitation: Small sample size (due to CPU constraints) reduces power. We will report effect sizes (Cohen's d) and Minimum Detectable Effect Size (MDES).

## 4. Statistical Rigor & Constraints

### 4.1 Multiple Comparison Correction
We run two primary comparisons (A vs. B, A vs. C). We will apply **Bonferroni correction** to the significance threshold ($\alpha = 0.05 / 2 = 0.025$) to control the family-wise error rate.

### 4.2 Sample Size & Power
Due to the 6-hour CPU constraint, we cannot train on the full dataset. We will use a **fixed seed random sample** of 500 examples per condition.
- **Power Analysis**: For N=500 per group, alpha=0.025 (Bonferroni), power=0.80, the Minimum Detectable Effect Size (MDES) is approximately **0.45** (Cohen's d).
- **Limitation**: Effects smaller than 0.45 may not be detected.
- **Stop-Rule**: If the observed effect size is < 0.45 and p > 0.025, the study will report the result as "Inconclusive due to power" rather than claiming a null effect. This prevents Type II errors from being misinterpreted as evidence of no effect.

### 4.3 Causal Inference
The study is observational in nature (we observe the effect of the training condition). We do not claim causal mechanisms beyond the training intervention. The "negative selection" is a computational process, not a biological one; we frame results as "associational" improvements in performance due to the specific training signal.

### 4.4 Measurement Validity
- **GSM8K/MATH**: Standard benchmarks with established validity for mathematical reasoning.
- **Critique Quality**: We implement a **Quality Gate** (Constitution Principle VII) to discard dialogues where the critique is trivial or non-adversarial. This ensures the training signal is meaningful.
- **Selector Independence**: The Critic Model is a separate, frozen model (not the one being trained), ensuring the selection pressure is external.

## 5. Compute Feasibility & Escape Hatch

### 5.1 CPU-First Strategy
- **Model**: Large language models in -bit quantization occupy approximately 5 GB RAM.
- **Overhead**: Data loading, tokenization, and LoRA overhead add a non-negligible amount of memory usage.
- **Total**: Fits within 7GB limit.
- **Strategy**: Use `datasets` streaming to avoid memory spikes.

### 5.2 GPU Escape Hatch
If the training loop fails with OOM on CPU (unlikely with 4-bit + LoRA but possible with batch accumulation):
- **Action**: The execution stage detects the error and re-runs on a Kaggle GPU.
- **Scaling**: On GPU, we will use a slightly larger batch size (e.g., 4) but keep the sample size small to ensure the run finishes within the 9-hour kernel limit.
- **No Fabrication**: We do not simulate GPU training on CPU; we plan for the real scaled-down GPU run if necessary.

### 5.3 Hard Timeouts (FR-008)
- **Implementation**: `train_loop.py` uses `signal.signal(signal.SIGALRM, timeout_handler)` and `timeout` decorators.
- **Limit**: 5 hours per condition.
- **Behavior**: On timeout, the script exits with code 124, logs the last checkpoint, and reports "TIMEOUT" in metrics.

## 6. Decision Rationale

| Decision | Rationale |
|----------|-----------|
| **Independent T-Test** | Samples are independent across conditions (different models, different training sets). Paired tests are invalid. |
| **Syntactic Distractor** | Controls for context window complexity and token count, isolating the *logical content* of the critique. |
| **Frozen Critic Model** | Ensures the selection pressure is external to the model being trained, avoiding circularity. |
| **Hard Timeouts** | Satisfies FR-008 by preventing hanging processes on free-tier runners. |
| **Power Analysis** | Acknowledges limitations of small N; uses MDES to interpret null results correctly. |
| **Early Stopping** | Prevents overfitting on small datasets by monitoring validation loss. |
