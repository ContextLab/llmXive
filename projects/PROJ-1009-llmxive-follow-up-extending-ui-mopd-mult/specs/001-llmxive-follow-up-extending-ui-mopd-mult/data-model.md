# Data Model: llmXive follow‑up – Structural Adapter

## Overview
The analysis revolves around three core entities. All files are stored under `data/` (raw) and `data/derived/` (processed).  

### 1. `StructuralRecord`
A single UI‑screen observation derived from the **synthetic dataset**.

| Field | Type | Description |
|-------|------|-------------|
| `record_id` | string | UUID for the record (generated). |
| `widget_depth` | integer | Maximum depth of the widget tree (≥ 1). |
| `branching_factor` | float | Average number of children per internal node (≥ 0). |
| `graph_connectivity` | float | Ratio of actual edges to maximum possible edges in the navigation graph (0 – 1). |
| `platform_id` | string | Identifier of the target platform (e.g., `android`, `ios`, `web`). |
| `task_success` | integer | **Binary** indicator (0 = failure, 1 = success) generated by the logistic model. |
| `structural_ambiguity` | boolean | Flag when identical topology maps to divergent outcomes (FR‑008). |

### 2. `PolicyHead`
Pre‑computed UI‑MOPD policy for a given platform (synthetically generated to match the synthetic test set).

| Field | Type | Description |
|-------|------|-------------|
| `head_id` | string | Unique identifier (e.g., `head_android_v1`). |
| `platform_id` | string | Platform the head is trained for. |
| `artifact_path` | string | Relative path to the serialized policy checkpoint. |
| `checksum` | string | SHA‑256 hash of the artifact file. |

### 3. `AdapterModelOutput`
Result of applying the lightweight adapter to a `StructuralRecord`.

| Field | Type | Description |
|-------|------|-------------|
| `record_id` | string | Links to the originating `StructuralRecord`. |
| `predicted_success_prob` | float | Model output in [0, 1]. |
| `selected_head_id` | string | ID of the policy head chosen by the adapter (lookup table). |
| `inference_latency_ms` | float | Wall‑clock latency for this prediction. |
| `memory_usage_mb` | float | Peak RSS memory during inference. |

## Schema Files
- `contracts/structural_record.schema.yaml` – validates `StructuralRecord` CSV rows.  
- `contracts/policy_head.schema.yaml` – validates `PolicyHead` manifest.  
- `contracts/adapter_output.schema.yaml` – validates `AdapterModelOutput` inference logs.

All schemas enforce non‑null critical predictor fields and numeric ranges, satisfying FR‑001 and FR‑008 data‑cleaning rules.
