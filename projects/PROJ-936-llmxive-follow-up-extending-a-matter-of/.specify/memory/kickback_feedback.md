## Unresolved concerns

- McNemar’s test is applied to compare baseline success on original tasks with baseline success on evolved tasks (Phase 9). These are not paired observations of the same task, violating the test’s requirement for matched binary outcomes and rendering the primary significance claim invalid.
- The efficiency‑penalty metric uses `tool_diversity_k` as the denominator, a heuristic proxy for optimal path length. This does not directly measure the true minimal number of tool calls, compromising construct validity of the “efficiency” construct.
- Training the difficulty regression tree on the **full** task set (including high‑penalty tasks) and then using its predictions to generate evolved tasks creates a leakage loop: the model is both fitted and evaluated on overlapping data, inflating apparent predictive power and confounding the trade‑off analysis.
- The logistic‑regression model includes `baseline_penalty` and `difficulty_score` as predictors, but `difficulty_score` is itself derived from a model trained on the same data, introducing circularity and violating independence assumptions.
- No formal power analysis is performed to justify the ≤ 200‑task cap. Given the expected effect size (odds‑ratio ≈ 2.5) and the paired‑test design, the sample may be under‑powered, especially after filtering to high‑penalty tasks, risking false‑negative conclusions.
- Point‑biserial correlation between penalty and binary success conflates efficiency with task difficulty because penalty itself is partially driven by the same features that affect success, leading to a potential confound that is not controlled.
- The plan states that the DecisionTreeRegressor is trained on the **full** task set (Phase 5), but the specification (FR‑007) requires training on the **filtered** high‑penalty task set. This contradicts the functional requirement and the associated success criterion (SC‑007).
- The plan validates the ‘penalty increase’ claim by training a decision‑tree model to predict a difficulty (or penalty) score, then generating evolved tasks that *maximize the model’s predicted score* and subsequently asserting that the average predicted penalty has increased ≥ 10 %. This is circular: the model is trained to predict the very metric it is later used to certify as having increased, guaranteeing the result by construction rather than providing independent evidence.
- McNemar’s test is applied to “paired success outcomes (baseline vs. evolved)”. However, the baseline and evolved tasks are *different* tasks (evolved variants are newly generated), not repeated measurements on the same items. McNemar’s test requires paired binary outcomes on the same subjects; using it on non‑paired data violates its assumptions and yields invalid inference.
- The efficiency penalty uses `tool_diversity_k` as the denominator, and the same `tool_diversity_k` feature is also fed into the difficulty‑prediction decision tree (used for task evolution). This creates a dependency between the predictor (penalty) and a covariate used for controlling difficulty, potentially inflating the observed relationship and violating the independence assumption required for the correlation and logistic‑regression analyses.
