## Unresolved concerns

- The plan targets ≥ 80 % power to detect a Spearman ρ = 0.4 (see line 9). With the publicly accessible IBM back‑ends there are typically fewer than 30 devices, which yields far less than the ~44 devices required for 80 % power at ρ = 0.4. This makes the power claim unrealistic and threatens the ability to meet SC‑007. The methodology should either (a) adjust the detectable effect size target to match the feasible sample size, (b) acknowledge the limited power and treat the study as exploratory, or (c) augment the dataset (e.g., include private back‑ends or simulated but validated data) to reach the needed N.
- Functional Requirement FR-005 (Cross‑Sectional Guard: raise an error if topology and performance timestamps differ by > 1 hour) is not referenced in any implementation phase; the plan provides no task or code module that enforces this guard.
- Phase 7 – Contract Validation is listed without any associated FR or SC from the specification; this task is not required by the spec and represents plan over‑reach.
- Phase 8 – Reproducibility & Hygiene is included despite no corresponding FR or SC in the spec; while it aligns with constitutional non‑functional expectations, it is not covered by any functional requirement or success criterion and thus constitutes over‑reach.
- Phase 2 states that edges are annotated with `edge_type` (`active`/`inactive`) for tunable‑coupler devices (FR‑007). The `graph_metrics.schema.yaml` contract does **not** include an `edge_type` field, so generated CSVs will fail schema validation. Align the contract (add `edge_type` to the schema) or remove the annotation from the plan.
- The plan describes writing `performance_metrics.csv` with columns such as T₁, T₂, CX gate error, readout error, and entanglement fidelity (wide format). The `performance_metrics.schema.yaml` contract expects a wide format (t1_mean, t2_mean, etc.), whereas the `PerformanceMetric` entity in `data-model.md` is defined in a **tall** format (`device_id`, `metric_name`, `value`). This mismatch will break both schema validation and the data‑model integrity check.
- The plan writes `correlation_results.csv` but does not specify column names. The `correlation_results.schema.yaml` contract requires fields `metric_a`, `metric_b`, `rho`, `p_value`, `adj_p_value`, and optional `partial_rho`. However, the `CorrelationResult` entity in `data-model.md` uses different field names (`graph_metric`, `performance_metric`, `spearman_rho`, etc.). The plan must adopt one consistent schema—either update the data model to match the contract or adjust the contract/plan to use the data‑model field names.
- Principle IV (Single Source of Truth) requires that every figure/table trace back to a single row in the project's data. The plan’s Phase 6 assembles a markdown report that *embeds* PNGs but does not explicitly state that each figure is generated from a specific CSV row (e.g., linking each scatter plot to the exact row(s) used). Add a statement or annotation confirming this traceability to satisfy the constitution.
- The robustness check description mentions “compare ρ to cross‑sectional ρ (must lie within ±0.05) (SC‑004)”. The data‑model does not contain a field to store this comparison result, nor does any contract schema capture it. Either add a field (e.g., `window_delta`) to the appropriate result schema or clarify that this check is only an internal validation step not persisted.
