- **Access Method**: `datasets.load_dataset(..., streaming=True)` to handle potential size constraints, or direct download if the file fits within the 7GB RAM limit (expected to be small, <1GB).
- **Data Fit Verification**:
 - **Required Variables**: Interaction logs (text commands), turn sequence, ground truth context.
 - **Availability**: The parquet file contains `instruction`, `response`, and `turn_id` fields.
 - **Gap Analysis**: The dataset does *not* contain pre-computed complexity scores; this is the output of our pipeline. It does *not* contain video outputs; these are generated by our inference step.
 - **Dependency Depth Calculation**: The 'dependency depth' metric is **not** calculated from the raw text of the generated variants. It is derived from the **original semantic intent** of the commands using a pre-trained semantic parser (e.g., `roberta-base` from HuggingFace for action chaining) on the *original* un-manipulated WBench instructions. This ensures the depth metric reflects the *task structure* and is constant across all variants of a given case, breaking the circularity with the entropy manipulation.
 - **Fallback for Depth**: If a specialized parser is unavailable, a **rule-based heuristic** (counting explicit causal connectors like 'then', 'after', 'because') will be used as a proxy for `Dependency Depth`.

### 1.2 Dataset Variants Generation (FR-001)
To create the independent variable (Entropy Level), we will generate variants from the WBench logs using a **Token Substitution & Truncation** strategy to preserve semantic validity:
- **Low Entropy**: Replace diverse command tokens with high-frequency synonyms (e.g., "move forward" -> "go ahead") and truncate non-essential steps, **while preserving the core action chain**.
- **High Entropy**: Introduce diverse, semantically distinct tokens and complex reordering of non-essential steps.
- **Semantic Plausibility & Task Validity Protocol**: To ensure 'Low Entropy' variants are valid instructions and not semantic loops or nonsense, every generated sequence must pass a two-stage check:
 1. **Semantic Similarity Check**: Pass the reordered sequence through a frozen, lightweight BERT-based intent classifier (e.g., `roberta-base`). The cosine similarity between the intent vector of the reordered sequence and the original sequence must be **> 0.85**.
 2. **Task Validity Validator (NEW)**: A lightweight action-sequence classifier (or rule-based checker) verifies that the sequence contains a valid **progression of states** (e.g., "open door" followed by "walk through", not "open door" followed by "open door"). This ensures the sequence remains a coherent task instruction, not just a high-similarity text block.
 - **Action**: If either check fails, the sequence is rejected and regenerated (up to 20 retries).
 - **Purpose**: This ensures that 'Low Entropy' variants are valid, low-complexity instructions, not semantically broken commands or loops.

## 2. Statistical Methodology

### 2.1 Complexity Score & Predictor Definition (FR-002)
- **Predictor Variable**: The primary independent variable is the **Entropy Level** (Categorical: Low, Medium, High), which is experimentally manipulated.
- **Covariate**: The **Dependency Depth** ($D_{graph}$) is calculated from the *original* un-manipulated text and serves as a covariate (or stratification factor) to control for task difficulty.
- **Formula**: $S_{complexity}$ is **not** a weighted sum of $H_{token}$ and $D_{graph}$ for the primary analysis. Instead:
 - $H_{token}$ is used as a **manipulation check** (to confirm Low < 0.3, High > 0.7).
 - $D_{graph}$ is the **structural complexity** of the task.
 - The analysis tests the effect of **Entropy Level** on Fidelity, controlling for **$D_{graph}$**.
 - The 'Sequence Complexity Score' variable for the regression is effectively the **Entropy Level** (or a numeric encoding of it), not the constant $D_{graph}$.
- **Validation**: Variance of $H_{token}$ across variants must be > 0.05 (SC-005).

### 2.2 Correlation & Trend Analysis (FR-005, FR-006)
- **Primary Test**: **One-Way ANOVA** (or Kruskal-Wallis if normality assumptions fail) comparing Fidelity scores across the three Entropy groups (Low, Med, High). This respects the discrete nature of the manipulated variable.
- **Secondary Test**: Pearson correlation ($r$) between the *continuous* $H_{token}$ values and Fidelity scores is reported descriptively, but **not** used for the primary hypothesis test due to the discrete grouping.
- **Correction**: Bonferroni correction applied for $N$ models to control family-wise error rate (SC-003).
- **Significance Threshold**: $p < 0.05$ (after correction).
- **Causal Inference**: The study is a **Controlled Experiment** (we actively manipulate the input entropy). Claims will be framed as **causal effects of entropy level on fidelity**, assuming the semantic plausibility check holds and the proxy metric (if used) is valid. Randomization of variant order is implemented to mitigate order effects.
- **Conditional Hypothesis**: The hypothesis statement is conditional on the `execution_mode`:
 - If `execution_mode == 'video'`: "Higher entropy degrades video fidelity."
 - If `execution_mode == 'proxy'`: "Higher entropy degrades proxy fidelity metrics."

## 3. Compute Feasibility (CPU-First)

### 3.1 CPU-Optimized Strategy & Sub-sampling
- **Constraint**: GitHub Actions Free Tier (multiple CPU, ~7GB RAM, 6h limit).
- **Full Dataset**: 289 cases × 3 variants × N models ≈ 1.5k runs. **Infeasible** in 6 hours.
- **Solution**: **Stratified Sub-sampling**.
 - Select a random sample of **base cases** (stratified by original task complexity if possible).
 - Total runs: 50 cases × 3 variants × N models (theoretical max).
 - This reduces the runtime to a feasible window while maintaining statistical power for a pilot study.
- **Inference**: Only models with `device="cpu"` support and memory footprint <7GB will be used. If none exist, the **Proxy Metric Mode** is activated.
- **Profiling**: A dry-run step (FR-002) will measure peak RAM. If >6.5GB, the model is skipped.
- **Streaming**: Data loading uses `streaming=True` to avoid loading the entire dataset into RAM.

### 3.2 GPU Escape Hatch (Not Required)
- **Decision**: No GPU escape hatch is planned. The methodology is explicitly designed to be CPU-tractable (or use proxy metrics).
- **Rationale**: Using a GPU for this specific analysis would violate the "CPU-first" constraint unless a model *strictly requires* CUDA. If a required model only exists in a CUDA-only form, it will be skipped, and the analysis will proceed with the remaining CPU models or the proxy metric. No "simulated" GPU runs are planned.

## 4. Risk Mitigation

- **Risk**: Model fails to generate video (hangs/crashes).
 - **Mitigation**: Implement timeout and exception handling; mark specific turns as "NaN" and exclude from correlation (Edge Case).
- **Risk**: Sequence Complexity Score has no variance.
 - **Mitigation**: Pre-analysis check for variance > 0.05; abort if failed (Edge Case).
- **Risk**: Dataset not accessible.
 - **Mitigation**: Use verified HuggingFace URLs; fallback to local cache if available; fail gracefully if network error.
- **Risk**: No CPU-optimized world models <7GB exist.
 - **Mitigation**: Activate **Proxy Metric Mode** (Frame-Difference or VQA model) to estimate fidelity degradation without full video generation.
- **Risk**: Semantic parser unavailable.
 - **Mitigation**: Use rule-based heuristic for `Dependency Depth` if `roberta-base` or similar is not available.
- **Risk**: Task Validity Validator fails to find valid variants.
 - **Mitigation**: Relax the "Task Validity" thresholds slightly or increase the retry limit; if still failing, log a warning and proceed with a reduced sample size.
