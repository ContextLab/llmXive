# Implementation Plan: Evaluating the Impact of Code Generation Models on Code Vulnerability Density

**Branch**: `001-eval-code-vuln-density` | **Date**: 2026-06-27 | **Spec**: `specs/001-eval-code-vuln-density/spec.md`

## Summary

This feature implements a reproducible pipeline to evaluate the vulnerability density of code generated by Large Language Models (LLMs) compared to human-written reference solutions. The approach involves: (1) downloading open-source models (StarCoder, CodeGen) and benchmarks (HumanEval, MBPP); (2) generating code samples for a **fixed set of tasks** until a target of 64 valid samples (passing benchmark tests) are obtained per model; (3) running static analysis (Bandit) to count vulnerabilities; (4) performing a **Permutation Test on raw counts** as the primary statistical analysis; and (5) conducting a **sensitivity analysis** using a Reference-Validator Agent to estimate False Positive Rates (FPR) and calculate adjusted counts, which are reported but **excluded from the primary hypothesis test** to avoid circularity.

## Technical Context

**Language/Version**: Python 3.11  
**Primary Dependencies**: `transformers`, `datasets`, `bandit`, `scipy`, `statsmodels`, `pandas`, `matplotlib`, `seaborn`, `pytest`  
**Storage**: Local file system (`data/raw`, `data/generated`, `data/processed`, `results`, `state`, `tests`)  
**Testing**: `pytest` (unit, integration, contract)  
**Target Platform**: Linux (GitHub Actions free-tier: 2 CPU, ~7 GB RAM, no GPU)  
**Project Type**: Research pipeline / CLI  
**Performance Goals**: ≤ 6 hours runtime, ≤ 7340 MB RAM  
**Constraints**: CPU-only execution; strict reproducibility via pinned seeds and versions; **primary metric is raw count**; FPR adjustment is sensitivity only.

> **Compute Feasibility Note**: StarCoder (medium-scale) and CodeGen (B) are large for CPU inference. To fit within the 7GB RAM limit, the plan uses **8-bit quantization** (`load_in_8bit=True`). **Acknowledged Limitation**: Quantization introduces numerical noise and alters model behavior compared to full precision. This violates the 'Functional Equivalence' principle if the baseline (Human) is not subjected to the same noise. To ensure internal reproducibility, the *same* quantization configuration is applied to *all* LLM runs. The comparison is strictly between LLM (quantized) and Human (natural), with the quantization bias explicitly acknowledged as a limitation in the final report.

### Statistical Design

- **Primary Test**: **Permutation Test** on raw vulnerability counts (LLM vs Human). This is chosen over ZINB because 64 samples per group is likely insufficient for ZINB convergence with high zero-inflation.
- **Secondary Test**: ZINB regression attempted only if sample size > 128; otherwise skipped.
- **Unit of Analysis**: Individual code sample (n=64 per group).
- **Multiple Comparison Correction**: **Benjamini-Hochberg (FDR)** with α=0.05 applied to p-values when testing across vulnerability categories (FR-007).
- **Power Analysis**: Post-hoc power calculated using `statsmodels.stats.power.tt_ind_solve_power` (alpha=0.05, effect_size=0.5, observed n). Result recorded in `stats_results.json` with a flag if power < 0.80 (FR-009).
- **Cross-Benchmark Analysis**: Results stratified by benchmark (HumanEval vs MBPP). Separate tests run for each; pooled analysis if heterogeneity is low (FR-011).
- **Cross-Model Analysis**: Separate permutation test for StarCoder vs CodeGen (LLM vs LLM) to satisfy FR-013.
- **FPR Adjustment (Sensitivity Only)**: A Reference-Validator Agent (rule-based heuristic) estimates FPR on a stratified sample (n=20). `adjusted_count = raw_count * (1 - group_FPR)` is calculated but **excluded from the primary statistical test** to avoid circularity (group-level scalar applied to individual samples induces collinearity). This is reported as a sensitivity metric.
- **Selection Bias Mitigation**: Mean code complexity (Cyclomatic Complexity) is calculated for both groups. If significantly different, a stratified analysis by complexity bins is performed.

## Complexity Tracking

No violations detected. Complexity is managed by:
- Using 8-bit quantized models for CPU feasibility (with acknowledged bias).
- Using Permutation Test as primary method to ensure robustness with small samples.
- Explicit power analysis and under-power flagging.
- FPR adjustment moved to sensitivity analysis only to avoid circularity.
- Complexity measurement added to control for selection bias.
- Fixed task list to prevent time-based sampling bias.
