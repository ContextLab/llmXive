# Evaluating the Impact of Code Generation Models on Code Vulnerability Density

**Field**: computer science

## Research question

Do code samples generated by large language models exhibit a higher density of static-analysis-detected vulnerabilities compared to equivalent human-written reference solutions for the same programming tasks, and does this disparity vary significantly across model families?

## Motivation

As LLMs become standard tools in software development, quantifying their security footprint is critical. While functional correctness is heavily benchmarked, systematic evidence comparing the security posture of AI-generated code against human baselines remains fragmented. This work addresses that gap to provide empirical data for security policies in AI-assisted development workflows.

## Related work

- [Security Degradation in Iterative AI Code Generation -- A Systematic Analysis of the Paradox (2025)](https://arxiv.org/abs/2506.11022) — Provides a systematic analysis of how security vulnerabilities evolve in AI-generated code, establishing a precedent for measuring security degradation in iterative generation contexts.

## Expected results

We expect to observe a statistically significant difference in vulnerability density between model-generated and human-written code, with the magnitude of the difference varying by model architecture. The measurement will be confirmed by counting distinct static-analysis warnings per 1,000 lines of code, with effect sizes calculated via confidence intervals to ensure the results are not artifacts of sample size.

## Methodology sketch

- **Data Acquisition**: Download reference solutions for the HumanEval dataset (Python) from the official OpenAI repository and generate 1,000 new code samples using open-source models (e.g., StarCoder2-3B, CodeGen-2B) hosted on HuggingFace, ensuring generation is performed locally to avoid API bias.
- **Ground Truth Preparation**: Extract the canonical human-written solution for each task from the HumanEval dataset to serve as the control group; ensure code formatting is normalized (e.g., PEP8) for both groups to remove style-based static analysis noise.
- **Static Analysis Execution**: Run `bandit` (Python-specific static analyzer) on both the generated and human code samples in a Dockerized environment to ensure consistent rule sets and versioning across all scans.
- **Metric Calculation**: Parse the JSON output from `bandit` to count unique vulnerability IDs per file; calculate "vulnerability density" as `(total unique vulnerabilities / lines of code) * 1000` for each sample.
- **Statistical Testing**: Perform a non-parametric Mann-Whitney U test to compare the distribution of vulnerability densities between the generated group and the human group, as static analysis counts often follow non-normal distributions.
- **Stratified Analysis**: Repeat the density calculation and statistical test stratified by specific vulnerability categories (e.g., SQL injection, hardcoded secrets, weak cryptography) to identify if certain flaw types are disproportionately generated.
- **Robustness Check**: Run the analysis with different random seeds for the LLM generation to ensure observed differences are consistent across stochastic variations and not artifacts of a single generation run.
- **Reproducibility Artifacts**: Save the raw `bandit` JSON logs and the generated source files to the project artifact store to allow independent re-execution of the counting logic.
