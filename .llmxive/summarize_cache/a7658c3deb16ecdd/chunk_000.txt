## Unresolved concerns

- FR-002 and US-2 require generating a 'natural language counterfactual explanation' validated against a schema. T023 (fallback) is defined to return a 'TemplateExplanation object OR a scalar_reward signal'. The task description does not explicitly mandate generating the required natural language text (e.g., 'You failed because X...') in the fallback path, only a template object or scalar. This risks violating the core deliverable of US-2 if the LLM fails.
- FR-001 requires extending '16 existing EvoPolicyGym environments'. T013d implements logic to proceed with *any* discovered count (logging a warning if not 16) and only fails if count is 0. The task does not enforce the specific scope of 16 environments mandated by the spec, creating a gap where the system could run with fewer than 16 environments without halting, potentially invalidating the study's statistical power assumptions.
- T015b requires defining a schema for `sensitivity_report.csv` but lacks a task to generate a tangible schema artifact (e.g., a `.schema.json` file or header definition) to serve as the ground truth for T013f and T015c. Without a concrete schema artifact, the 'Verified Accuracy' and 'Data Hygiene' principles (Constitution III) cannot be enforced for the generated CSV.
- T036 (Statistical Analysis) depends on `data/evolution_results.csv` (T032b), which depends on T015c (`sensitivity_report.csv`). If T015c fails (due to upstream T013d/e/f failures), T036 raises a `RuntimeError`. The task list lacks a 'graceful degradation' or 'fallback' path for the statistical analysis if the environment validation step fails, risking an empty research output rather than a report of 'insufficient data'.
- T021d enforces a 200-token limit and discards the data point if exceeded. The spec (US-2) requires the system to 'flag as exceeds limit'. T021d's logic to 'raise an exception' or 'return a failure flag' is vague and does not explicitly mandate writing the 'exceeds_token_limit' event to `data/fallbacks.log` as required by SC-004, risking loss of traceability for failed generations.
- T013d (Enforce Environment Count) depends on T001e (Install Dependencies), but T013e (Programmatically Iterate) depends on T013d. However, T013d's logic to write `data/discovered_envs.json` is conditional on the import succeeding. If the import fails (T013d raises RuntimeError), T013e cannot proceed. The dependency chain T013d -> T013e is valid, but T013d's failure mode (RuntimeError) blocks the entire US1 flow without a graceful degradation path defined in the task order, violating the 'Producer before consumer' principle for the `discovered_envs.json` artifact which T013e requires.
- T015a (Create wrapper script) depends on T013e, T013f, T015b, T015c. T015c (Populate Sensitivity Report) depends on T013f and T014. T013f (Run Static Agent) depends on T013e and T015b. This creates a circular dependency: T015a waits for T015c, T015c waits for T013f, T013f waits for T015b (schema definition). While T015b is a definition task, T013f's logic explicitly checks for `data/discovered_envs.json` (from T013d) and T015b's schema. The order T013f -> T015c -> T015a is correct, but T015a's dependency on T015b (schema definition) is redundant if T015b is just a comment/task description and not an artifact producer. If T015b produces a file, it must precede T013f. The current order implies T013f can run before T015b completes if T015b is just a 'define' task, which risks T013f using an undefined schema.
- T032a (Create EvolutionaryHarness) depends on T021b (Retrieve Action and Generate Text), T013e, T033, T034, T015c. T021b is part of US2 (Counterfactual Generation), while T032a is US3 (Evolutionary Harness). The spec states US3 depends on US1 and US2 completion. However, T032a's logic requires `data/sensitivity_report.csv` (from T015c, US1) and `data/evolution_results.csv` (from T032b, US3). The dependency on T021b (US2) is correct for the full harness, but T032a's description says 'Must depend on T013e to ensure it iterates only over registered environments'. T013e produces `data/discovered_envs.json`. T032a reads `data/sensitivity_report.csv` (T015c). The order T015c -> T032a is correct. However, T032a depends on T021b, which is a US2 task. If US2 is not complete, T032a cannot run. This is a valid dependency, but the task order in Phase 5 lists T032a before T021b is marked complete in the phase flow, potentially causing a deadlock if US2 is not finished before US3 starts.
