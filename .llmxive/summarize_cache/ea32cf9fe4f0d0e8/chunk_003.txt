- Task T008f (pair_episodes) is marked [P] (parallel-safe) and placed in Phase 2 (Foundational). However, its description states: 'Input must be two lists of results (Gatekeeper, Baseline) with matching episode_id keys'. These result lists are produced by T016 (Gatekeeper) and T017c (Baseline) in Phase 3. A task that *consumes* artifacts from Phase 3 cannot be placed in Phase 2 as a 'Foundational' task, even if it is a function definition. The [P] tag implies it can be run/developed in parallel with other Phase 2 tasks, but it is logically dependent on the *existence* of Phase 3 artifacts. This violates the 'Producer before consumer' semantic layer. T008f should be in Phase 3 or 4, or the [P] tag should be removed and the dependency clarified.
- Task T006d requires verifying a checksum in `state/artifact_hashes.yaml` before processing, but T006a (which writes this checksum) is listed as a dependency. However, T006d also depends on T004/T005 (schema validation). The task description assumes the file `state/artifact_hashes.yaml` exists and contains the key `gatemem_test` at the moment of execution. If T006a fails or is skipped, T006d has no fallback or error handling for a missing checksum file, making it non-deterministic to execute without a specific 'file exists' check or a clear error path defined in the task text.
- Task T008b defines a fallback logic: 'If LMM fails due to insufficient data (not singularity), raise InfeasibleError. DO NOT fallback on SingularMatrixError alone; attempt regularization or data checks first.' The task does not define what 'attempt regularization' entails (e.g., specific penalty parameters, data subsampling, or covariance structure changes). An implementer cannot deterministically execute 'attempt regularization' without specific algorithmic steps or parameters, leading to ambiguous implementation.
- Task T029a defines failure sampling logic: 'If total failure count N > 50, use random.sample with stratification... If N <= 50, use simple random sampling (select all).' The task does not specify the stratification variable for the 'N > 50' case beyond 'domain'. It does not specify the random seed value to be used for this sampling, which is critical for reproducibility (Constitution Principle I). Without a fixed seed or a defined method to derive one, the output `data/samples/failure_cases.json` will be non-deterministic across runs.
- Task T001 'Create project structure' is too coarse. It lists multiple directories and files across `src/`, `tests/`, `data/`, `contracts/`, `state/`, `logs/`, and `templates/`. This covers the entire project initialization phase. The downstream `task_atomizer` will need to split this into individual file/directory creation tasks to be executable by a single LLM step.
- Tasks T008a through T008f (stats functions) are grouped under a single 'Phase 2' block but listed as individual items. While granular, T008e ('run_full_stats_pipeline') is an orchestration task that depends on the successful implementation of T008a-d. The task description for T008e is vague on the 'orchestration logic' details (e.g., how to handle the transition between LMM and fallbacks programmatically). It risks being too coarse for a single atomic implementation step without further breakdown of the control flow.
- Task T014a mandates: 'Verify `torch.cuda.is_available()` is False or ignored; do not attempt to move model to CUDA.' The verification step 'Verify... is False' is ambiguous. Does the task require the code to assert this and crash if True? Or just log a warning? The task description says 'Explicitly enforce CPU execution' but the verification clause is passive. A concrete deliverable requires explicit code behavior (e.g., 'Raise RuntimeError if CUDA is available') to be deterministically testable.
- Task T026a requires implementing `run_statistical_comparison()` which calls `pair_episodes()` (T008f). The task states 'Input must be two lists of results... with matching episode_id keys.' It does not specify the exact data structure (e.g., list of dicts, pandas DataFrame, JSON string) for these inputs. Without a defined schema for the input data structure, the implementer cannot deterministically write the function signature or parsing logic.
- Task T008b states: 'DO NOT fallback on SingularMatrixError alone; attempt regularization or data checks first.' This creates a semantic violation of FR-005 and Constitution Principle VI. FR-005 mandates: 'If LMM is not feasible, a domain-stratified analysis MUST be performed.' By explicitly forbidding a fallback on the exact error condition (SingularMatrixError) that renders LMM infeasible, the task logic blocks the required fallback path, causing the system to crash instead of satisfying the spec's statistical requirement.
- Task T014a hardcodes a specific external model ID 'distilbert-base-uncased-finetuned-sst-2-english' with arXiv ID '2501.00241' as a fallback. FR-002 requires a 'frozen DistilBERT intent classifier' but does not authorize this specific external model. This introduces a silent constitution drift (Constitution Principle I: Reproducibility) by binding the project to an unverified external artifact not present in the GateMem benchmark's canonical setup, risking a failure to reproduce if that specific model ID changes or is removed.
