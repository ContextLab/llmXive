- Task T008e (run_full_stats_pipeline) depends on T008a-f. However, T008f (pair_episodes) requires input data (Gatekeeper vs Baseline scores) which is not produced until Phase 3 (US1/US2 implementation, e.g., T016, T017, T023). T008e is listed in Phase 2 (Foundational) as a standalone utility, but its description ('orchestration logic returning...') implies it consumes the *results* of the pipeline, not just the statistical functions. If T008e is meant to be a pure function library, it should not depend on T008f (which pairs *results*). If it is an orchestration task, it cannot be in Phase 2. This creates a circular or premature dependency.
- Task T026a (run_statistical_comparison) depends on T023, T024, T024c, T025 (metric calculations) AND T008a-f (stats functions). However, T026a also depends on T008f (pair_episodes). T008f requires 'two lists of results (Gatekeeper, Baseline)'. These results are generated by T017c (Baseline) and T016 (Gatekeeper) in Phase 3. The dependency chain is correct (T026a -> T017c/T016), but T026a is placed in Phase 4 (US2) while T017c is in Phase 3 (US1). This is acceptable for US2, BUT T026a is described as the 'Statistical Comparison' for US2. The dependency on T008f is valid, but the task T008f itself is in Phase 2. The issue is that T008f (pair_episodes) is marked as [P] (parallel-safe) in Phase 2, but it *cannot* be executed or tested in Phase 2 because the data it pairs (results) does not exist yet. It is a function definition, not an execution task. The [P] tag is misleading if interpreted as 'can be run in parallel now'. It should be 'can be defined in parallel'. This is a semantic ordering violation of the [P] tag definition.
