## Unresolved concerns

- FR-001 requires downloading the GateMem dataset and extracting 'leak-target', 'roles', 'domains', 'outcome', 'predictors', 'covariates'. Tasks T006a-d cover fetching, parsing, and validation, but T006d explicitly mentions verifying checksums against 'state/artifact_hashes.yaml' which is created by T006a. However, the spec FR-001 also mandates ensuring 'all required variables... are present for the analysis'. While T006c extracts fields, there is no explicit task to validate that the *values* of these fields (e.g., specific domain names or role formats) match the expected schema defined in the spec's 'Key Entities' or 'Assumptions' before processing, only that the keys exist. This risks processing malformed data that passes key-existence checks but fails semantic validation.
- FR-004 and SC-002/SC-005 require calculating 'Utility', 'Access Control', and 'Forgetting'. Tasks T018 (Access Control), T023 (Utility), T024 (Forgetting) exist. However, FR-004 also explicitly requires calculating 'Conditional Utility' (task success among allowed queries) and 'Overall Task Success Rate' (net success). Task T024c calculates 'Overall Task Success Rate', but there is NO task explicitly tagged or described to calculate 'Conditional Utility'. This metric is critical for the 'Governance-Utility Trade-off Validation' (Constitution Principle VI) and is missing from the task list.
- FR-005 and SC-004 require statistical comparison using LMM with 'Domain' as the *only* random intercept, with a fallback to domain-stratified analysis if LMM is infeasible. Task T026a implements the statistical pipeline. However, the task description states: 'DO NOT fallback on SingularMatrixError alone; attempt regularization first.' This contradicts the spec's requirement to fallback to domain-stratified analysis if LMM is 'not feasible' (which includes singularity). The task logic creates a potential deadlock where the code refuses to fallback on the exact error condition that necessitates the fallback, leaving the statistical verification step without a valid path if regularization fails. This is a coverage gap in the *logic* required to satisfy FR-005.
- FR-006 and SC-003 require profiling and reporting wall-clock time and peak RAM. Task T035 aggregates profiling data. Task T036 generates the final report. However, FR-006 and the Constitution Principle VII require that these metrics be recorded for *both* the Gatekeeper and Baselines. While T033a and T034 profile Baseline and Gatekeeper respectively, there is no explicit task to *aggregate* these specific profiling results into a single comparative structure (e.g., a table or JSON) that is then consumed by T036. T035 aggregates 'profiling data', but the description is vague on whether it produces the specific comparative output required by the report generator to satisfy the 'percentage reduction' requirement in SC-003.
- Task T008b is tagged with [FR-005] and correctly implements the LMM with 'Domain' as the random intercept. However, the task description includes a constraint: 'Do NOT include Episode_ID in the random intercept formula.' This is a negative constraint (what *not* to do) rather than a positive task description of what *to* do. While the intent is clear, the task description should explicitly state the formula to be implemented (e.g., 'Implement LMM with formula: score ~ method + (1|Domain)') to ensure positive coverage of the requirement.
- Task T029a implements failure case sampling. The description states: 'If N > 50, use random.sample with stratification by domain'. However, FR-007 requires the sample to be 'stratified by domain if N > 50'. The task description does not explicitly mention the 'fixed random seed' requirement from FR-007, which is critical for reproducibility (Constitution Principle I). While T029a mentions 'fixed random seed' in the logic, the explicit requirement from the spec is not clearly mapped in the task description, creating a risk of non-reproducible sampling.
- Task T006d (validate_episode) lists dependency on T006a, T006b, T006c, but also T004 and T005. T004/T005 are schema generation/validation tasks. While T006d logic implies reading the schema, the explicit dependency list is incomplete regarding the *contract* files themselves. More critically, T006d claims to verify checksums in `state/artifact_hashes.yaml` (produced by T006a), but T006a is marked as a *function* generation task, not the *execution* task that populates the state file. The task order implies T006d can run before the data is actually fetched and hashed, creating a logical impossibility for the checksum verification step described in T006d.
