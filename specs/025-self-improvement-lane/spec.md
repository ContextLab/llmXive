Intents now resolve to FOUR dispositions — `landed` (observed; always conclusive), `rejected` (external precondition makes landing impossible), `contained` (may still land, but only where it is HARMLESS — reclaim proceeds on harmlessness, not absence), `ambiguous` (→ quarantine) — because the two-way split is what produced both errors. ## Overview

llmXive advances research projects through a ~34-state lifecycle. Those projects are **sandboxed** under `projects/`: their agents never modify the platform. This feature adds a **self-improvement lane** whose successful output is a **branch/PR against llmXive itself**. Its safety case rests on data contracts, trust boundaries, and a versioned numeric policy — never on adjectives:

- **Global serialization** — a singleton **LaneCoordinator** record with a global `lane_revision`; all claims compare-and-swap against it (fixing the per-Problem CAS gap). The pre-merge pipeline is a strict singleton; post-merge monitoring is concurrent.
- **Problem vs. attempt identity** — a stable `problem_id` aggregates evidence; each fix try is a separate `ImprovementAttempt`.
- **Eight isolated trust domains** — discovery, persistence, claiming, implementation, **candidate-publisher**, candidate-testing, trusted-evaluation, promotion — so candidate code never touches a secret, a repo-write token, or the evaluator, and only non-candidate-executing domains hold credentials.
- **A paired-run operational canary** — a trusted controller on `main` materializes an immutable workload bundle and runs it against the control SHA and the candidate SHA in isolated namespaces; every metric is a **paired difference over identical inputs** (dissolving volume-normalization problems).
- **A safely-executable harness** — trusted harness (pinned `main`) runs the untrusted system-under-test (candidate head) in a hardened, network-denied, digest-pinned container; `base_reproducer`s are allowlisted/structured, never free-form commands.
- **A versioned, protected numeric policy** — every threshold, formula, and the issue-ranking function are concrete defaults, immutable by candidate branches.

Live auto-merge to `main` is gated behind a **default-off flag** *and* explicit shadow-mode quality thresholds; until then the loop runs for real against a disposable canary branch and never mutates `main`.

Governed by the constitution ([.specify/memory/constitution.md](../../.specify/memory/constitution.md)): Single Source of Truth (I), Verified Accuracy (II), Real-World Testing (III), Cost Effectiveness / Free-First (IV), Fail Fast (V), Convergent Review (VI). See "Constitution Compatibility."

**026 contract (FINAL — as delivered, not the earlier provisional guess):**
- **Import**: `from llmxive.model_selection import route_chat, select, execute, build_requirement, ModelRequirement, ModelChain, RuntimeSnapshot, ModelUnavailable, ChainExhausted` (the package is `llmxive.model_selection`, NOT `backends.model_selection`).
- **Chokepoint**: lane LLM calls go through **`route_chat(messages, *, profile, max_tokens, overrides=None, …) -> ChatResponse`**, which acquires the runtime snapshot, runs the pure `select(requirement, snapshot) -> ModelChain`, and `execute()`s the chain under the breaker / retry / failure-classification / credit-guard safeguards. `select` + `execute` are the underlying primitives; the lane MUST NOT call the router or backends directly (statically enforced by `model_selection/enforcement.py`).
- **Intent, never a model id**: each call names one of the six capability **profiles** (`cheap_structured`, `standard_generation`, `deep_review`, `deep_code`, `vision`, `independent_review`) via `profile=`; `build_requirement(profile, call_budget, **overrides)` builds the `ModelRequirement`. No model-id literal ever appears in lane code.
- **Types (as delivered)**: `ModelRequirement` carries `call_budget: CallBudget`, `required_features`, `required_independence`/`preferred_independence: frozenset[IndependenceDim]`, `exclude_{models,families,vendors,endpoints}`, `allow_paid`/`require_paid`, `max_credits`, `max_catalog_age_s`, `max_candidates`, `require_fresh_snapshot`. `ModelChain` carries `candidates: tuple[Candidate, …]` (each with a `model_ref`), `resolved_at`, `snapshot_digest`, `selection_policy_version`, `explanation`. (NOT the provisional `models: list[str]`.)
- **Errors**: `ModelUnavailable` (fail closed — no eligible candidate) and `ChainExhausted` (the chain ran, none succeeded); a `PricingUnverifiable` (a `TransientBackendError`) means the catalog price is temporarily undeterminable so the call retries/advances — an availability condition, never a cost decision (FR-027).
- **Availability**: the `RuntimeSnapshot` is timestamped (`observed_at`, per-component `age_s`, `source ∈ {live, last_known_good, unavailable}`, `snapshot_digest`); a live-catalog outage falls back to the bounded last-known-good store and, past `max_catalog_age_s`, fails closed. Availability is re-checked per call. The lane **uses** 026's independence machinery (`build_requirement(profile="independent_review", …, independence_against=IndependenceBaseline(…))`, `required_independence: frozenset[IndependenceDim]`) for the family-independent patch verifier — see FR-002.

**Constitution Compatibility (governance — RESOLVED by maintainer ruling 2026-07-16: route via `run_convergence`)**: Constitution VI governs "every step that produces reviewable work," including code patches. Per the ruling, the lane's two **judgment reviews** — (1) the **proposal** ("is this a valid, worthwhile improvement to pursue?", before implementation) and (2) the **implemented patch** ("does this diff correctly and safely implement it?", before promotion) — route through the **shared `run_convergence`** mechanism (Constitution I + VI), NOT a bespoke assessor. The lane registers a self-improvement `ReviewSpec` (a new reviewable stage) with a code-patch reviewer panel; the **proposal** review calls `run_convergence(spec, artifacts={proposal, evidence}, producer=<proposer>)` and the **patch** review calls `run_convergence(spec, artifacts={proposal, diff, evidence}, producer=<implementer>)`, each returning `converged` (unanimous panel acceptance within the round cap) as its review gate. Reviewer independence is NOT the name-based `producer` exclusion alone (which is necessary-not-sufficient — `engine.py:421`); it is the **model-family constraint of FR-002** (patch verifier fail-closed family-independent; proposal assessor family-preferred). The **deterministic policy pre-gates** (diff envelope, blast-radius, base-failure, evidence floor) and the **empirical trusted-evaluation harness** (offline paired tests + canary + trusted-App checks) are NOT "reviewable work" — they are mechanical/empirical guards that run alongside and compose with the convergence review. This satisfies Constitution VI with no category exception.
Separately, v1 evaluation is **offline-only** (FR-024): candidate code is exercised only against recorded response fixtures. Any change that cannot be exercised offline — notably changes to live model/provider-calling paths, or anything requiring a live external call to reproduce — is **`unsupported_scope`** in v1 (routed to humans), not merely "credential-touching source files." A trusted external-call broker is deferred to a future version.

**Reuse (Constitution I)**: `advance_ledger.classify_message`; `web_data._activity_severity`/`_recent_activity`; the `gh` wrapper; `credits.paid_opt_in_enabled()`; `project_lease.py` (in-host contention only — NOT cross-runner correctness); `scripts/ci/commit-and-push.sh` (append-only event/blob writes only — NOT the CAS mechanism).

## User Scenarios & Testing *(mandatory)*

Stories map 1:1 to delivery slices; each is independently testable.

### User Story 1 - Observation-only discovery (Priority: P1)

Both crons produce **proposal-verified candidate attempts** — clustering real errors, ranking real issues (by the policy's deterministic formula), passed through the deterministic policy pre-gates and then the shared `run_convergence` review panel — with **no issue/branch/PR/promotion side effects** (it does commit Problem/Attempt state through the privileged persistence domain).

**Acceptance Scenarios**:

4. **Given** a proposal failing a deterministic policy pre-gate, **Then** `rejected` with a machine-readable reason (pre-review); **Given** a proposal that clears the pre-gates but the **proposal `run_convergence` panel** does not accept within the round cap, **Then** it does not reach `claimed`.
5. **Given** paid opt-in ON and two concurrent panel reviewers reserving against the last remaining Attempt credits (FR-033), **When** both reserve, **Then** the Attempt-ledger CAS admits at most the remaining budget — exactly one reservation succeeds (or both are refused); the loser's call fails closed; the sum of reserved envelopes never exceeds `attempt_budget_credits`.

### User Story 4 - Trusted paired promotion into a canary branch (Priority: P2)

A trusted controller on `main` runs the Attempt's `EvaluationContract` **paired** (control SHA vs candidate SHA) over an immutable workload bundle in isolated namespaces, proving **fails-at-base / passes-at-head** via an allowlisted `base_reproducer` with no material paired regression; the promoter verifies every required check (head_sha, conclusion, trusted-App id, policy_version, non-stale) and merges with an App token that never executes candidate code.

**Independent Test**: In shadow mode, assert promotion only when the paired run shows base-fails/head-passes with no material regression, and every required check passes the full verification algorithm; a free-form `base_reproducer` or a spoofed/stale check blocks promotion.

**Acceptance Scenarios**:

2. **Given** a check whose creating App id is not on the trusted allowlist, or whose head_sha ≠ candidate head, or whose `policy_version` is wrong, **Then** it is not accepted and promotion is blocked.
3. **Given** a free-form command `base_reproducer`, **Then** it is refused (never executed).
4. **Given** paired target improvement but a newly-failing trusted regression check, **Then** blocked.

### User Story 5 - Concurrent post-merge monitoring & attributed auto-revert (Priority: P2)

After promotion, monitoring is **concurrent** (many merged Attempts monitored at once; only the pre-merge pipeline is singleton). Each Attempt's exposure interval + intervening changes are recorded; the lane corroborates attribution (transient class alone is insufficient), checks ancestry, and auto-reverts genuine, causally-attributed regressions. Repeated failures trip the breaker.

**Independent Test**: Inject a regression on a merged canary Attempt and assert an ancestry-checked, corroboration-backed revert within the window; a provider outage without corroboration does not revert; a candidate-caused transient failure with corroboration does; two reverts in the breaker window disable promotion while discovery continues; assert two Attempts can be monitored concurrently.

**Acceptance Scenarios**:
1. **Given** a merged Attempt whose paired target worsens beyond the policy thresholds over ≥ the minimum mature observations, **Then** an ancestry-checked revert is created + merged.
2. **Given** post-merge transient-class failures, **Then** a revert occurs ONLY with ≥1 corroboration signal (control fails on identical W; provider health; same failure on unrelated main/canary; failure before candidate code is reached).
3. **Given** a human change landed after the autonomous merge, **Then** no blind revert — re-derive against head (ancestry) or escalate.
4. **Given** two auto-reverts in the breaker window, **Then** promotion disabled (discovery continues) until manual re-enable.
5. **Given** a candidate whose change makes the request malformed/unsupported so evaluation raises `ChainExhausted`, and control on identical W does NOT raise it, **Then** the failure is attributed to the candidate (a corroborated candidate regression), NOT auto-excluded as a provider outage (FR-027).

### User Story 6 - Live-main promotion, metric-gated (Priority: P3)

**Acceptance Scenarios**:
1. Flag on, App/protection absent → refuse (fail-closed).
2. Flag on, configured, shadow metrics ≥ policy → merge to `main` via the App (author ≠ merger).
3. Shadow metrics below threshold → withheld, reason recorded.

### Edge Cases

- **Recurrence after `retained`**: same fingerprint returns → a NEW Attempt under the same `problem_id` with fresh base/branch/PR/contract; lineage distinguishes "first fix failed" from "problem recurred."
- **Freshness/drift**: before implement/promote, if `main` moved past the freshness bound from `base_sha` or any touched file changed, the old Attempt is terminated (`superseded`) and a new Attempt recreated + re-evaluated.
- **Global race on different Problems**: serialized by CAS on the singleton coordinator (blocker-1 test).
- **Persistence egress**: persistence commits to GitHub (GitHub-API egress only) — it is not `network:none`; only candidate-testing is `--network none`.
- **Artifacts crossing trust boundaries**: any artifact a candidate could influence (patch bundle, test output) is treated as untrusted by the privileged domain that consumes it and re-validated.
- **Harness import safety**: the trusted harness runs from a pinned-`main` checkout with a clean import path that excludes candidate-controlled paths; candidate code is imported only as the isolated SUT.
- **PR tampering**: a PR whose head_sha ≠ the recorded validated head, or manually modified, fails check verification → the Attempt is quarantined, not promoted.
- **No independent family for the patch verifier**: fail closed — the Attempt does NOT promote (a partial catalog outage that leaves only the producer's family live delays merges, never merges unreviewed). The proposal assessor, by contrast, degrades + records (discovery continues).
- Plus: escalation-is-hard; transient≠outage; sentinel scope; observational never auto-promotes; incomplete-pagination fails closed; only real classifier classes; recursive-self-reference forbidden.

### Proposal gate, evaluation & sentinels
- **FR-019**: Lifecycle + legal transitions are defined by the **Transition Table**. The two judgment reviews — the **proposal** (before implementation, gating `proposal_verified`) and the **implemented patch** (before promotion, gating `EvaluationPassed`) — MUST route through the shared `run_convergence` via a self-improvement `ReviewSpec` (`producer=<implementer>` excludes the producer by NAME — necessary but NOT sufficient, and it is NOT the independence guarantee; model-family independence per FR-002 is); `converged` (unanimous acceptance within the cap) is the review gate. The **deterministic policy pre-gates** (rubric thresholds, blast-radius max, reproducible base failure unless `observational`, supported diff surface, file/line + budget bounds) run BEFORE convergence as mechanical eligibility guards with a machine-readable rejection; they are not themselves "review."
- **FR-020**: Each Attempt carries a typed `EvaluationContract` (`base_reproducer`, `head_expectation`, `target_metric`{name, numerator, denominator, direction, min_effect}, `regression_suite` = trusted pinned-`main` checks, `replay_mode` ∈ {deterministic_replay, mirrored_workload, not_replayable}). `base_reproducer` MUST be (a) a trusted test id from an allowlist, (b) a structured harness invocation, or (c) a fixture in the protected replay corpus — a **free-form command string MUST NEVER be executed**. The data model MUST distinguish **candidate-authored tests (advisory/untrusted)** from **trusted regression fixtures**.
- **FR-021**: Promotion requires paired fails-at-base/passes-at-head where `replay_mode` supports it; "tests pass" alone is insufficient; an `observational` Attempt is draft-PR + human-lane only and MUST NOT auto-promote in v1; historical run logs MUST NOT be a canary signal.
- **FR-022**: Evidence MUST be **redacted** (secret/PII scrubbing), size-capped, and retention-bounded before it is committed; compact logs may still carry secrets/PII.
- **FR-023**: High-severity sentinels (`InvariantEvent` from the `invariant` class; explicitly-defined deterministic `SecurityEvent`/`DataIntegrityEvent` sources) MAY ONLY block promotion, trip a breaker, quarantine an Attempt, revert a causally-attributed change, or notify/escalate — NEVER bypass the proposal/implementation/evaluation/merge gates.

### Operational canary (paired-run)
- **FR-024**: The operational canary MUST be a **paired-run** controlled from a trusted workflow on `main` (not by "creating a branch" — GitHub schedules run on the default branch, so the controller checks out/dispatches the recorded SHAs). v1 evaluation is **offline-only**: the controller (1) materializes an **immutable workload bundle W** = recorded real inputs + **recorded model/provider responses** harvested by the trusted controller from real recent runs (candidate code makes NO live external calls); (2) runs W against the **control SHA** and the **candidate SHA** via offline replay; (3) writes results to an **isolated per-Attempt namespace** (`state/self-improvement/canary/<attempt-id>/{control,candidate}/`) that MUST NOT mutate production/project state; (4) performs a **trusted paired comparison**. Control and candidate MUST see identical W. Replay fixtures MUST be keyed by a **canonical request digest** with **exact-match** replay by default; a missing request digest is a **replay miss** that fails closed (no fabricated response); a candidate that changes live-call request construction (so recorded responses no longer match) is `unsupported_scope`. The 026 acquisition/serving files (`backends/{dartmouth,local,router}.py`) are ALSO in the `PROTECTED_MODEL_EXECUTION_SURFACE` registry (FR-013), so a candidate edit to pricing extraction or the FREE/PAID/UNVERIFIABLE verdict is rejected **before publish** (defense-in-depth) — not merely caught later as `unsupported_scope` at eval time.
- **FR-025**: The canary MUST use **immutable per-Attempt refs** `self-improvement/canary/<attempt-id>` (NOT one shared, reset branch — that would delete a still-monitored revision and make "revert" ambiguous). Monitoring targets the recorded candidate SHA; the ref is deleted only after the Attempt reaches `retained`/`reverted`. In live mode, paired monitoring uses the immutable base/candidate SHAs while `main` advances. **Retention** statistics come ONLY from `mirrored_workload` runs where W is **successively refreshed** across the window from real recent inputs (a single static corpus repeated for 30 days is NOT retention evidence); `deterministic_replay` is used ONLY for pre-merge base/head evaluation and MUST NOT count as retention. An Attempt whose change is exercisable only via a change to live-call paths (not reproducible offline) is `unsupported_scope` in v1.

### Rollback, attribution & rollout
- **FR-026**: Rollback thresholds + all formulas come from the Policy Contract (paired-difference `target_metric`, `material_regression`, absolute+relative dual-gate with volume normalization via identical W, min **mature** observations, censored 7/30-day cohorts, zero-denominator = withhold/fail-closed).
- **FR-027**: A revert MUST be causally attributed: excluding a failure as a provider/model outage REQUIRES ≥1 corroboration signal (FR/US5); error class alone is insufficient either direction. A 026 `PricingUnverifiable`/`ModelUnavailable`/`ChainExhausted` during a candidate's evaluation is **attribution EVIDENCE, not a conclusive exclusion** — a candidate can CAUSE these (change the requested profile/overrides/features/token budget/message content → `ModelUnavailable`; emit malformed or unsupported requests → `ChainExhausted`). Each MUST be located relative to candidate execution: `PricingUnverifiable` is a strong provider/pricing signal (still record timing + control behavior); `ModelUnavailable` requires checking whether the candidate changed the requirement and comparing against control on identical W/snapshot; `ChainExhausted` requires inspecting the per-candidate notes/dispositions and reproducing against control. **Exclude from candidate-regression metrics ONLY when an independent corroborator exists** (as the rest of this FR requires); a candidate-induced `ChainExhausted` (the candidate changed the request) IS attributed to the candidate. A revert MUST pass an ancestry check and MUST NOT blind-revert over **any later intervening change (human OR automated — another bot can create the same conflict)**; it re-derives against current head or escalates.
- **FR-028**: Circuit breakers per the Policy Contract (≤1 active pre-merge Attempt; ≤1 autonomous merge/24h; N auto-reverts in the breaker window → promotion disabled until manual re-enable; M failed Attempts/Problem → cooldown).
- **FR-029**: Live auto-merge to `main` gated by the default-off `LLMXIVE_SELF_IMPROVEMENT_LIVE` flag AND the Policy's live-eligibility thresholds. Flag off → canary branch target; `main` untouched. Flag on but App/branch-protection absent → fail closed.
- **FR-030**: Both crons idempotent, bounded, least-privilege, individually dispatchable, sharing one concurrency group; all provenance is immutable append-only.
- **FR-031**: About page + docs describe the lane (behavior, safety envelope, eight domains, policy, flag/identity); a step-by-step GitHub App setup walkthrough is provided.
- **FR-032**: The Policy Contract is a **versioned, protected module** (`policy_version`); candidate branches MUST NOT modify it; changes are normal reviewed human PRs.

### Operational abort of a judgment review (rev 17)
- **FR-034**: A judgment review (proposal or patch) that cannot be ADJUDICATED for operational reasons MUST terminate the Attempt at **`review_aborted`**, never at `rejected` and never at `*_failed`. The distinction is **substantive negative determination vs. operational inability to obtain one** — NOT "panel vs. not-panel" (rev 18 correction): `rejected` covers BOTH a substantive **panel** determination (convergence non-acceptance) and a substantive **machine** determination (a deterministic policy pre-gate refusal, US1/FR-019), and describing it as only a panel judgment contradicted this FR's own next paragraph. An operational abort produced NEITHER kind of determination, so recording `rejected` would fabricate a negative finding nothing actually reached.
  - **Classification (exhaustive for v1).** Operational — hence `review_aborted`:
    - (i) **`ModelUnavailable`, stage-aware (rev 18).** This is 026's central fail-closed signal and was missing from rev 17's list. On the proposal review's **primary** (`independent_review`) leg it is NOT terminal — it triggers the FR-002 reroute. It IS terminal when the review has no routing options left: the proposal review's **fallback** (`deep_review`) leg raising it (both legs exhausted); the **patch** review raising it (which the patch gate does DELIBERATELY when no independent family is live, FR-002 — so #1242's required fail-closed path terminates here, and before rev 18 that exact path had no legal Attempt outcome); or a **reviser** call raising it (the producer takes no reroute).
    - (ii) `ChainExhausted` on either leg or on a reviser call.
    - (iii) a route-fatal `route_audit` failure (FR-033a — explicitly NOT a `ModelUnavailable`, so it does not take the FR-002 reroute).
    - (iv) a route-replay error (FR-033a finding #3).
    - (v) unresolved dispatch (`dispatch_started` with no `dispatch_completed` → `dispatch_unknown`).
    - (vi) Attempt budget-ceiling or LLM-call-ceiling exhaustion during the review.
    - (vii) **expiry of the review's wall-clock budget** (rev 18 — wall-clock is the PRIMARY bound per the ceiling row, so omitting it while listing the credit and call ceilings left the likeliest bound unclassified).

    Substantive — hence `rejected` (proposal) or the existing `*_failed` (patch): the panel ran and did not converge within `max_rounds` (substantive **panel** determination), or a deterministic policy pre-gate refused the proposal (substantive **machine** determination). A proposal reviewer that took the FR-002 fallback leg and SUCCEEDED is NOT an abort: the reroute is a successful degraded review and records `independence_degraded`.

    **Explicitly NOT in this classification: authoritative lane-log integrity or availability failure.** Rev 17 listed it here, which was incoherent — see FR-035.
  - **Reconcile before deciding.** `review_aborted` is a claim ABOUT durable state, so it may only be written while the authoritative lane ref is healthy (FR-035); if it is not, FR-035 governs and no Attempt terminal is written at all. Given a healthy log, the Attempt outcome MUST NOT be written while any dispatch is unresolved: every `dispatch_started` without a terminal event is first driven to `dispatch_unknown` per FR-033a, and only then is `review_aborted` recorded. Reservations left by an aborted review stay **`retained`** (never `released` — the original dispatch may have landed) and reconcile through the FR-033 saga. The reconciliation timeout MUST be derived with `reconcile_timeout_s()` from the SAME `deadline_s` + `retries` the lane call used; a timeout chosen independently of the real call configuration cannot support "never before it could have finished".
  - **Idempotent + crash-safe.** `(attempt_id,"reviewabort")` is the idempotency key; re-running after a crash re-derives the same terminal from the durable event stream rather than appending a second one. `ClaimReleased` fires only if a claim was held (`proposed` holds none), so the pre- and post-claim paths share one event.
  - **Bounded, with defined counter semantics (rev 18).** `review_aborted` is NOT counted toward the per-Problem quality cooldown (FR-001: a transient/availability condition is not an Attempt-quality failure), so it MUST carry its own bound — the Policy Contract's **operational aborts/Problem** threshold — otherwise a persistent outage re-proposes the same Problem forever. The counter is:
    - **Consecutive, not lifetime.** It counts `review_aborted` terminals since that Problem's last SUBSTANTIVE determination. Lifetime counting would eventually cool down a healthy Problem that merely outlived enough unrelated outages; consecutive counting isolates "this Problem reliably aborts."
    - **Reset by any substantive determination** for the Problem (`ProposalVerified`, `Rejected`, or any `*_failed`) — the lane demonstrably got an answer, so the operational streak is over. Reset ALSO on expiry of an operational cooldown, so the Problem re-enters with a full fresh window rather than re-tripping on its next single abort.
    - **Independent of the quality counter, in both directions.** A `review_aborted` never advances the quality counter and a quality failure never advances this one; they have separate thresholds, separate durations, and separate `cause` values.
    - **Serialized by the same CAS discipline** as every other per-Problem write (FR-008): the threshold is evaluated against the freshly-rebuilt projection, so two Attempts terminating concurrently converge — the loser recomputes and sees the winner's terminal before deciding whether the threshold is crossed. Crossing it emits `Cooldown` with `cause="operational"` exactly once per epoch by the idempotency key below.
    - **Projected** onto the Problem snapshot as `cooldown_until` + `cooldown_cause ∈ {quality, operational}` + `cooldown_epoch`, so a reader can tell WHY a Problem is resting and for how long.

  Correlated lane-wide outages remain the circuit breaker's job (FR-028); this counter catches a Problem that reliably aborts on its own.

- **FR-035 (rev 18)**: **An authoritative-log failure is a RUN-level fail-closed + quarantine, never an Attempt terminal.** Rev 17 listed "lane event-log replay/integrity failure" among the conditions that produce `review_aborted`, which cannot be implemented: recording `ReviewAborted`, reconstructing unresolved dispatches, and even determining whether a claim is held ALL require reading and appending to the very log declared untrustworthy. An implementation would have had to write into a store it just called corrupt, trust a projection it just called unrebuildable, or claim a terminal it never durably recorded. The lane therefore MUST separate:
  - **Ordinary CAS contention** (a rejected precondition because another writer advanced the ref) → NOT a failure at all: discard, re-sync, rebuild, retry, exactly as FR-008 already requires.
  - **Operational LLM / routing / budget failure while the authoritative stream remains usable** → `ReviewAborted` per FR-034. This is the only category that yields an Attempt terminal.
  - **Authoritative-ref integrity or availability failure** (unreachable/unbootstrapped ref, failed `expected_anchor` identity check, a projection that cannot be rebuilt, malformed or schema-invalid events, or CAS retries exhausted against a ref that is not merely contended) → **quarantine**: the run fails closed immediately, performs NO further lane work, writes NO Attempt terminal and NO coordinator mutation (it could not do so honestly), and escalates via the existing deduped engine-failure GitHub issue path. The Attempt stays in whatever state it was in — genuinely UNRESOLVED, which is the truth — and is resolved only after the store is repaired and an authoritative replay succeeds. Quarantine is a lane-level condition, not an Attempt outcome, precisely because its blast radius is every Problem rather than one.
  - **Recovery MUST be able to free the lane.** A quarantine (or any crash) between `ClaimGranted` and a terminal leaves `active_problem_id` set with no live run — and because a claim CAS requires `active_problem_id is None`, the lane would stay wedged forever once the log is healthy again. `project_lease` does NOT close this (it is in-host contention only, explicitly NOT cross-runner correctness), and no reaper exists. **This hole predates rev 17** — any crashed run wedges the lane the same way — but FR-035's "the Attempt remains unresolved until repair" makes closing it mandatory. A claim therefore records `claimed_at`, and a later run MAY reclaim via the normal coordinator CAS when the claim has exceeded the Policy Contract's **claim expiry** AND the claimed Attempt has no terminal event, by appending an explicit **`ClaimExpired`** coordinator event (never a silent overwrite) that releases the slot and terminates the abandoned Attempt at `attempt_abandoned` (rev 21 — it is valid from every claim-holding state, so it must not borrow `review_aborted`'s name). **Liveness is a renewable heartbeat, not one long timeout (rev 20).** A single expiry has to be longer than the entire post-claim lifetime (else it reclaims live runs), which makes crash recovery correspondingly slow — and rev 19's value did not actually cover that lifetime (see below). Instead the claim-holder RENEWS: it appends a generation-stamped `ClaimHeartbeat` every `heartbeat_interval`, and a claim is reclaimable once it has missed `claim_expiry` worth of beats. A live-but-slow run is not reclaimed by the HEARTBEAT bound, because it keeps beating — so crash recovery no longer trades off against slow-run safety. It is still reclaimed by `max_claim_hold_time`; "indefinitely" (rev 21) contradicted the hard cap stated in the very next bullet and is withdrawn. Two independent bounds then apply, and a claim is reclaimable if EITHER trips:
    - **`claim_expiry`** — no heartbeat within the window (the run is gone).
    - **`max_claim_hold_time`** — the total post-claim lifetime cap, which reclaims a run that is heartbeating forever without progressing. Rev 19 derived expiry from `implementation + patch_review + evaluation` only, which does NOT cover the post-claim path: publishing (which had NO wall-clock cap at all) and candidate testing (a separate 20-min container cap) were both omitted, so the "expiry exceeds the Attempt's complete wall-clock budget" requirement was not actually met. `max_claim_hold_time` is the single authoritative sum over EVERY post-claim phase plus bounded overhead, defined once in the Policy Contract and referenced here — and since rev 21 extended the claim through `promoting`/`promotion_requested`, that sum now necessarily includes promotion and intent reconciliation (rev 22, finding #4).
  - **Exactly one terminal per Attempt, and the reclaim race (rev 19).** A liveness-based reclaim means the ORIGINAL run may still be alive and may append its own terminal concurrently with the reclaimer's `ClaimExpired` — which would give one Attempt two terminals, and worse, let a run that has been reclaimed keep operating as though it still held the lane. Ref-level CAS alone does not prevent this: it ORDERS the two appends, it does not reject either. So:
    - **Every Attempt-terminal append is CAS-conditioned on the Attempt having NO terminal event in the freshly-rebuilt projection.** First writer wins; the loser discards its own terminal rather than appending a second. This applies to all terminals, not just `ClaimExpired` — it is the invariant that makes reclaim safe, and it is worth stating explicitly because the transition table's per-transition idempotency keys guard REPEATS of one transition, not two DIFFERENT terminals racing.
    - **The reclaimer re-verifies inside the same CAS.** "Past expiry" and "no terminal" are re-checked against the projection the CAS commits against, never a stale read, so a terminal that landed while the reclaimer was deciding defeats the reclaim.
    - **The loser stops.** A run whose terminal is rejected because the Attempt is already terminal MUST perform no further side effect and MUST NOT proceed to claim or publish; it exits and lets the recorded terminal stand.
    - **FENCING, not a pre-flight check (rev 20).** Rev 19 said a run must "re-confirm it still holds the claim immediately before each irreversible side effect". That is check-then-act and does NOT close the window: `ClaimExpired` can land AFTER the confirmation and BEFORE the GitHub call, so a superseded worker still mutates the external system. "Immediately" narrows the race; it cannot remove it. The protocol is instead:
      - **Claim generation.** The coordinator's claim carries a monotonically increasing `claim_generation`, incremented by every `ClaimGranted` AND every `ClaimExpired`, never reset. It is the fencing token and accompanies every operation.
      - **Generation-stamped appends.** Every lane-log append carries the generation it was produced under, and an append whose generation ≠ the coordinator's current generation is REJECTED by the CAS. This part is fully fenceable because the lane log is ours: a superseded worker can never record lane state, no matter how late its write arrives.
      - **One ref, many subtrees (rev 23).** The coordinator stream and every per-Problem stream are SUBTREES of the single authoritative ref `refs/llmxive/self-improvement`, not separate refs. A commit may add blobs to several subtrees at once, and the ref compare-and-swap covers the whole commit, so any mutation spanning the claim and an Attempt is ONE transaction evaluated against ONE parent. The generation check is consequently BINDING, not advisory: a predicate that reads the coordinator's current `claim_generation` and writes an Attempt event is deciding against the exact parent its commit is built on, so a generation that moved underneath loses the CAS and the transaction is recomputed against the new tip. This is a genuine fencing token in the single-writer sense — unlike an expected-`head_sha` on an external API, which constrains WHICH COMMIT merges and never WHICH ACTOR (rev 22). The distinction is the substrate: the lane owns this ref and serializes every writer through it; it owns nothing about GitHub's merge endpoint.
      - **Side-effect intents.** Before any external mutation the run durably appends `<Effect>Requested{claim_generation, idempotency_key}` — the saga's existing intent step, now generation-stamped — and `<Effect>Observed` after.
      - **Reclaim BLOCKS on an unreconciled intent.** `ClaimExpired`'s CAS precondition gains "no `*Requested` lacking its matching `*Observed`". A reclaimer facing an outstanding intent MUST first reconcile it, append the `*Observed`, and only then reclaim in a SUBSEQUENT CAS — so the reclaimer never starts a competing mutation while one is outstanding.
      - **Observation is ASYMMETRIC, and rev 20 got this wrong (rev 21).** Rev 20 called reconciliation "deterministic and terminating, because every side effect is keyed". That holds only for a POSITIVE observation. Observing that an effect is PRESENT is conclusive. Observing that it is ABSENT is **not**: it cannot distinguish "never landed" from "has not landed YET", because a delayed worker's already-issued call may still be in flight. A reclaimer that treats absence as proof would close the intent as not-landed, reclaim, and then have the delayed call land against a lane that has recorded the opposite — the delayed-worker impossibility, unresolvable by observation alone. **Rev 21 identified the asymmetry and then mis-sorted its own two mechanisms into the decidable half (rev 22).** An outstanding intent resolves to EXACTLY ONE of FOUR dispositions — a two-way "decidable vs ambiguous" split is what produced both errors:
        - **`landed`** — the effect is conclusively OBSERVED present. Positive observation is always conclusive and needs no precondition. Reconcile by adopting it.
        - **`rejected`** — an external precondition, evaluated BY THE EXTERNAL SYSTEM at effect time, now makes landing IMPOSSIBLE, and the reclaimer confirmed that precondition was in force BEFORE it reclaimed. This is the ONLY disposition in which absence may be read as "did not land, and never will".
        - **`contained`** — the effect MAY still land, arbitrarily late, but only somewhere it cannot affect live state. Reclaim proceeds NOT because the effect is absent but because its landing is HARMLESS. Distinct from `rejected`, and rev 21 wrongly merged the two.
        - **`ambiguous`** — none of the above → **quarantine** (FR-035): no reclaim, no terminal, the Attempt stays honestly unresolved.
      - **(a) Generation-scoped namespaces give CONTAINMENT, not decidability (finding #2, rev 22).** Candidate branches become `bot/self-improvement/<problem-id>/<attempt-id>/g<claim_generation>`. A delayed worker can only ever write inside its OWN generation's namespace, which the new owner never touches — so a stale push cannot corrupt live state. That is real and valuable, and it needs no external cooperation. But it does NOT make the push's absence decidable: a stale push can still arrive, arbitrarily late, in its dead namespace. Rev 21's sentence that an enforceable precondition means "a call which has not landed can no longer land" was FALSE as applied to pushes. A push intent's disposition is therefore **`contained`**, never `rejected`. Two obligations follow: a generation's namespace is NEVER reused (which the monotonic, never-reset `claim_generation` already guarantees), and dead-namespace GC MUST be idempotent and MUST NOT treat the absence of a dead ref as evidence of anything — a late push simply recreates it and it is collected again.
      - **(b) Expected-SHA is a CONTENT precondition, not a fencing token (finding #1, rev 22).** Rev 21 claimed "a merge issued under a superseded generation fails at GitHub". It does not. GitHub documents the merge endpoint's `sha` as *"SHA that pull request head must match to allow merge"*, failing with *"Conflict if sha was provided and pull request head did not match"* — it constrains WHICH COMMIT is merged, never WHICH ACTOR issues the merge, and GitHub has no knowledge of `claim_generation`. A stale worker merging its own generation's PR passes the check (nobody touched that dead head) and the merge lands in the SHARED target. Generation-scoped namespaces cannot help here either: they isolate the SOURCE, and the target is `main` by definition. Non-forced ref updates are likewise content preconditions. **So merge and revert intents are `ambiguous` → quarantined. That is the v1 rule.**
      - **The bar for ever promoting merge/revert out of `ambiguous`.** A precondition qualifies only if it (i) is evaluated by GitHub at effect time, (ii) can be flipped to the blocking state BY THE RECLAIMER, and (iii) reads back a state that is TERMINAL, so the read-back is itself conclusive. Candidates worth testing: closing the PR, deleting the generation-scoped head ref, and a required status check on the head commit that only the current generation can set green. None may be relied on until a REAL-CALL test pins the behavior against live GitHub — the docs specify 405 only as *"Method Not Allowed if merge cannot be performed"* and say nothing about closed pull requests, so "a closed PR cannot be merged" is exactly the kind of unverified inference this section forbids. Until such a test exists and is cited here, quarantine stands.
      - **Honest limit (rev 22).** GitHub does not accept a fencing token of ours, and no restatement changes that. Precisely: the lane never has two actors ISSUING concurrently; a superseded worker can never record LANE state (that half is fully fenced, because the log is ours); a stale PUSH is contained to a dead namespace; anything that landed is discovered rather than orphaned; and a stale MERGE or REVERT is not prevented at all — it is quarantined, so the lane records honest uncertainty instead of a wrong answer. "A stale worker cannot mutate GitHub" is false and is not claimed anywhere.
    - Artifacts a reclaimed Attempt already published are adopted by `head_sha` through the existing publish reconciliation, so a reclaim never orphans a branch or PR.

  - **Terminal and release are ONE transaction (rev 23).** Every path that ends an Attempt while holding the claim — a normal terminal, and `ClaimExpired` on reclaim — writes the Attempt terminal and the coordinator's `ClaimReleased` in a SINGLE commit on the shared ref. There is therefore no state in which an Attempt is terminal while its claim is still held, and no compensating "release a terminal Attempt's claim" transition exists or is needed. A crash at any point leaves either both facts durable or neither. The exactly-one-terminal rule is unchanged and still decides a reclaim race: the reclaimer's transaction and the original run's terminal contend for the same slot at the same parent, and the loser's ENTIRE transaction — terminal and release alike — is discarded.

  - **Cross-stream invariant matrix (rev 23; NORMATIVE).** Every operation that touches MORE THAN ONE stream is listed here. An operation not on this list touches exactly one stream and uses a single-stream append. Adding a cross-stream operation later means adding a row here FIRST — a transaction whose invariants were never written down is how half-states are reintroduced.

    Read the columns as: what lands, what is re-checked against the commit's own parent (never a stale read), what must be true afterwards, and what a crash BEFORE the commit point leaves behind. That last column is the same for every row on purpose — the identical answer is the property the design buys.

    |# |Operation|Events in the ONE commit, IN ORDER|Precondition, re-evaluated at the parent|Post-state invariant|Crash BEFORE the commit point|
    |-|-|-|-|-|-|
    |1|**Claim grant** — `cas_claim`|coordinator `ClaimAcquired`; Problem `ClaimGranted`|lane free **AND** the Attempt is `proposal_verified`|the lane is held by exactly `(P,A)`; the Attempt is `claimed`; BOTH records carry the identical generation + terms|neither record; lane free; Attempt still `proposal_verified`|
    |2|**Terminal + release** — `cas_attempt_transition`|Problem terminal; coordinator `ClaimReleased` **iff the Attempt held the lane** (see below)|the Attempt has NO terminal and its state is in `from_states`; **if that state is claim-holding**, the lane must still be held by that exact `(P,A)` pair|exactly one terminal; the lane is free if this Attempt held it, and otherwise UNTOUCHED|neither; Attempt non-terminal; lane unchanged|

    **The commit point, and what happens after it.** "All or nothing" is a claim about VISIBILITY, and visibility changes at exactly one instant: the ref compare-and-swap — the fast-forward push when the log has a remote, the local ref update when it does not. "A crash at ANY seam leaves no events" is FALSE after that instant: once the push succeeds the whole transaction is durable, and only the local acknowledgement is missing. The contract has three parts:

    - **Before the commit point:** no event of the transaction is visible to any reader. The commit object may exist and be unreachable; unreachable is not visible.
    - **After the commit point:** EVERY event of the transaction is visible. Never a subset — that is what one commit buys.
    - **A retry after a lost acknowledgement** (the process died between the successful push and its local ref update, or anywhere later) observes its own events already present and returns the STORED result marked as not-newly-created, writing nothing and changing nothing.

    The third part is what makes the second survivable: a durable transaction whose caller never learned it landed is indistinguishable, to that caller, from one that never ran — so the recovery path has to be the ordinary retry, and the retry has to be a no-op. There is no separate "reconcile a lost acknowledgement" path, for the same reason there is no compensating release: an operation that needs one is built wrong. This applies to EVERY row, including reclaim, where "the lane is free" is the durable result being retried for and must never be reported as a failure.

    **A row's declared coordinator effects are CONDITIONAL.** Several marked rows are reachable from pre-claim states, where there is nothing to release and the effect is correctly skipped. So "this row declares `ClaimReleased`" does NOT mean "a `ClaimReleased` exists"; it means one exists **iff the Attempt held the lane**. The condition is derivable, and NOT from the coordinator: an Attempt holds the lane iff its own state is claim-holding (`claimed`/`implementing`/`promoting`/`promotion_requested`). Both the writer and any consistency check MUST read it that way, from the Attempt's own timeline — two readings of "is a release required" is how a writer ends up manufacturing precisely the half-state a checker is looking for. Where the two disagree, the write is REFUSED; it is never downgraded to a single-stream terminal.

- **FR-036 (rev 21)**: **Authoritative time and clock skew.** Revs 18–20 introduced bounds that are all TIME comparisons — heartbeat renewal, `claim_expiry`, `max_claim_hold_time`, `streak_started_at`, `cooldown_until` — while lane runs execute on independent GitHub runners with independent clocks. A naive comparison lets a fast-skewed runner evict a live claim-holder early, which is precisely the dangerous direction.
  - **`seq` remains the SOLE ordering authority** (FR-009). Timestamps are NEVER used to order events, only to measure DURATIONS. Any rule that would sort by timestamp is a defect.
  - **Writer clocks are UNTRUSTED, and rev 21's validation did not establish otherwise (finding #3, rev 22).** Rev 21 rejected an append whose timestamp was "more than `max_clock_skew` ahead of the appending process's own clock" — but the appending process is the one that GENERATED the timestamp, so that compares a clock with itself and can never detect skew. Its second half (rejecting an event that trails the ref's latest) is worse than useless: a fast-skewed runner's first event passes, poisons the ref's latest recorded time, and thereafter every correctly-timed runner appears "behind" and is rejected indefinitely — one bad clock wedges the lane. Both rules are withdrawn.
  - **The authority is the GitHub server clock, not any runner's.** The lane is GitHub-native: every run already calls the API. A run reads the server instant from the `Date` response header of an authenticated API response (`GET /rate_limit` supplies one without consuming rate limit if the run has not yet made a call). The request MUST be authenticated: the unauthenticated allowance is 60/hr per IP and is shared with every other tenant of that runner's address, so depending on it would make "the lane has no trusted time" a condition another workload could induce at an unpredictable moment. A run with no token therefore has no trusted time and does no lane work, by the fail-closed rule below; offline and local work injects a fixed-anchor clock instead. EVERY instant the run records is authority-derived. All runners are then measuring against ONE clock, which is what makes their durations comparable at all — the property rev 21 assumed but never provided.
  - **Sampling (rev 23).** The offset is established by bracketing the authority request with a MONOTONIC clock (`time.monotonic()`): read `t0`, issue the request, read `t1`, and take the authoritative instant to be the `Date` value at the midpoint `(t0+t1)/2`. An RFC 7231 `Date` names a WHOLE SECOND, so the header for second N means the true instant lay at or after `N` and strictly before `N + 1`: the anchor is centred at `N + 0.5 s` and the sample's uncertainty is `(t1−t0)/2 + 0.5 s`. That 0.5 s is a FLOOR no round trip can beat, and omitting it would both bias every anchor half a second early and understate the margin — each in the direction of evicting a live holder sooner. Emitted time is additionally floored at the highest value already emitted: a refresh installs a new measurement of a remote clock, and the elapsed time since the PREVIOUS anchor has already advanced the emitted instant, so a new anchor even slightly behind the old one regresses what callers see. That floor is BOUNDED by `max_clock_regression` = `max_clock_skew`: while clamped, emitted time stands still and every duration the lane derives stands still with it, so an unbounded clamp would convert an authority fault into a lane that appears healthy and makes no progress — expiry never approaching, cooldowns never maturing. A regression past the bound is not imprecision to absorb but an absence of trusted time, and the run therefore does no lane work. A sample whose round trip exceeds `max_sample_rtt` (2 s) is DISCARDED and retried; a run that cannot obtain a sample inside that bound has no trusted time and performs no lane work. Between samples, elapsed time is measured with the monotonic clock ONLY — never the wall clock — so emitted authority time is monotonic by construction and no system-clock adjustment can move it backward or forward. Refresh scheduling (each `heartbeat_interval`, so a long run cannot drift) uses the same monotonic elapsed measurement, so a clock change cannot suppress a refresh. Sample uncertainty is charged against the safety margin: the effective skew allowance is `max_clock_skew + sample_uncertainty`, always padding toward NOT evicting a live holder.
  - **No trusted offset ⇒ no lane work (fail closed).** A run that cannot establish an offset MUST NOT claim, heartbeat, reclaim, or terminalize. It cannot honestly perform any time-based step, and it needs no special handling: the claim it does not take cannot wedge, and a claim it already holds is recovered by the ordinary expiry path.
  - **Validated at append against the SAME authority.** An append is rejected when its authority-derived timestamp is more than `max_clock_skew` from the appending run's authority-derived now, or precedes the ref's latest by more than `max_clock_skew`. Because every writer shares the authority, a violation no longer indicates ordinary skew — it indicates a bug, a forged event, or a lost offset. To keep this from re-creating the wedge it replaces, repeated rejection at the same ref position escalates to FR-035 quarantine (bounded, visible, human-repairable) rather than silently blocking healthy writers forever.
  - **`max_clock_skew` now bounds API round-trip plus re-measurement drift, NOT NTP divergence** — a far smaller quantity, so the 5-minute default is very generous rather than merely plausible.
  - **Skew padding always favours the safe error.** Every safety-critical duration comparison pads by `max_clock_skew` in the direction that avoids the WORSE outcome. For reclaim the worse outcome is evicting a live holder, so it requires `elapsed ≥ claim_expiry + max_clock_skew`; `max_claim_hold_time` and the operational-cooldown floor pad the same way. Padding is never applied in the direction that would make a bound trip sooner.
  - **Heartbeats are counted as well as timed.** Because beats are events, "missed beats" is also observable through `seq` without trusting any clock at all; the wall-clock window is the padded cross-check, not the only signal. This is the one liveness input that survives even a total loss of trusted time.

### Per-Attempt credit reservation (paid path)
- **FR-033**: When `LLMXIVE_PAID_OPT_IN` is on, per-Attempt paid spend is bounded by an **Attempt-scoped reservation ledger** (`AttemptCreditLedger`) enforced INSIDE the `route_chat`→`execute` path, layered above 026's daily reservation ledger — `route_chat` (per-call `max_credits` + daily reservation) does NOT bound a multi-call Attempt on its own.
  - **(a) An authorization hook + a mandatory audit sink, NOT post-hoc attribution (F2, a 026 follow-up).** The Attempt budget cannot be enforced by the lane *before* `route_chat` (candidate + `worst_case_credits` unknown until `select` runs) nor *after* it (the paid call already happened); and `route_chat` today returns only `ChatResponse`, discarding the `ExecutionResult` AND the whole `ModelChain` provenance (`route.py:241`). Bypassing `route_chat` to call `execute()` directly is forbidden (`enforcement.py` + FR-001), so `route_chat`/`execute` gain TWO threaded params:
    - **`reservation_authority`** — an ENFORCEMENT hook the lane injects that `execute` consults **before dispatching each paid candidate** (the pre-dispatch reservation step inside `execute._open_paid_reservation`, `execute.py:119-195`); it can DENY. The Attempt-ledger CAS and the 026 Git-backed ledger mutation are **separate transactions, NOT one atomic critical section** — cross-ledger consistency comes from the saga + compensating release ((b)/(d)), never a shared lock.
    - **`route_audit`** — a MANDATORY, SYNCHRONOUS, durable audit sink (deliberately NOT named "observer": it cannot deny a candidate, but it is NOT best-effort telemetry either). Invoked for EVERY candidate AND for selection failures, not just the winner: once with the resolved chain provenance (`snapshot_digest`, `selection_policy_version`, `resolved_at`, `explanation`, candidate `model_ref`s); once per paid-candidate reservation event (`reservation_id`, `reserved_credits`); once per candidate terminal outcome (success / skip / advance / abort + reason); AND once per **selection failure** (a `ModelUnavailable` with its structured reason — so the failed first leg of the proposal reroute is auditable, F2/F3). Events carry stable, idempotent ids. It is THE trusted structured channel that populates **both** `InvocationIdentity` (chain provenance + the winning candidate's `model_ref` → model/backend/family) **and** the Attempt credit reconciliation (the reservation events — including a paid candidate that reserved, failed, then advanced to another). **Failure semantics (F1/F2/F3):** a `route_audit` exception is NEVER silently swallowed, and audit is an **outbox-style durable lifecycle** — `selected → reservation_opened → dispatch_started → {dispatch_completed | dispatch_unknown}` — whose pre-dispatch events (selection provenance + any reservation) MUST be durably recorded BEFORE the backend is invoked. A **pre-dispatch** audit failure is **route-fatal (F1)**: it ABORTS the logical `route_chat` call (a distinct route-fatal audit error, NOT a `ModelUnavailable`/`ChainExhausted`) and NEVER advances to another candidate — candidate advancement stays limited to the model/backend/credit dispositions, so an audit outage can never silently change which model executes. Because it is not a `ModelUnavailable`, an audit-abort does NOT trigger the proposal reroute; it is a failed logical call (Attempt fails closed). If a paid candidate's reservations already opened, the Attempt reservation is marked `retained` or `released` (per whether dispatch definitively did not occur) with the matching 026 transition, the route fails, and the saga reconciles. **Post-dispatch the guarantee is weaker and honest (F2):** a synchronous sink makes the pre-dispatch intent + reservation durable, but it CANNOT guarantee the terminal outcome is recorded — a sink/process crash right after the backend call leaves a durable `dispatch_started`; reconciliation converts an unresolved `dispatch_started → dispatch_unknown`, fails the Attempt closed, and leaves the reservation `retained` for the credit saga. So pre-dispatch evidence is never lost; the post-dispatch outcome may be, but only crash-safely — the earlier "never a dispatch whose evidence was lost" overclaimed and is dropped. Optional best-effort telemetry, if ever added, is a SEPARATE non-durable channel outside this safety contract. **Route-replay disposition (finding #3):** because the dispatch boundary is an ATOMIC claim (`route_audit.claim_dispatch`), a retried OR concurrent call for an `(route_id, candidate)` that already crossed the dispatch boundary is a REPLAY — surfaced as a distinct route-replay error that is NOT a `ModelUnavailable`, NOT a `RouteAuditError`, and NOT a backend exception. The lane MUST classify it as a **failed logical call** that: (i) NEVER triggers the proposal independence fallback/reroute (FR-002); (ii) NEVER advances the model chain; (iii) leaves any paid reservation `retained` — the ORIGINAL dispatch owns it, so it is never released and never double-charged; (iv) is reconciled ONLY from durable dispatch state — an unresolved `dispatch_started` with no `dispatch_completed` becomes `dispatch_unknown` and the Attempt fails closed. It MUST NOT be retried as an ordinary transient backend error (that would risk an unbounded re-dispatch loop). Relatedly, `execute` derives the paid `reservation_id` from `route_id` ONLY when a `route_audit` sink (hence the claim gate) is present; a no-sink call mints a fresh per-call id, so a stable `route_id` without an audit sink cannot collapse two paid calls onto one reserved envelope. `ExecutionResult` additionally exposes the winner's `reservation_id`, but `route_audit` is the complete channel. `ChatResponse.cost_estimate_usd` is NOT the reserved worst-case envelope and MUST NOT be used for budgeting.
  - **(b) Ordered reservation + defined rollback.** Per paid candidate `execute` (i) runs the existing twice-checked paid guard; (ii) reserves `worst_case_credits × retries` (the retry envelope, matching the 026 reserve at `execute.py:155`) against the Attempt budget via `reservation_authority` — **CAS on the Attempt-ledger revision** (coordinator discipline, FR-008); (iii) reserves the same against 026's daily ledger; (iv) dispatches. Outcomes:
    - Attempt reserve would exceed `attempt_budget_credits` → **refused**; skip candidate (advance), no 026 reservation opened. If the whole chain exhausts this way → `ChainExhausted` → `review_aborted` during either judgment review, else `eval_failed`/`impl_failed` (over-budget fails closed, never silently unpriced). The stage-correct target matters: before rev 17 this row named only `eval_failed`/`impl_failed`, neither of which is reachable from `proposed`, so a proposal-review budget exhaustion had NO legal transition (FR-034).
    - Attempt reserved but the 026 reserve is refused/errors → **release the Attempt reservation**, skip candidate.
    - both reserved, dispatch fails (advance) → both holds are RETAINED (026 `settle→settling`, `execute.py:317-325`); the reconciler/sweeper finalizes against observed spend, and the Attempt hold is marked **`retained`** (reconciliation-pending, still counting against the cap) and later moves to `reconciled` by the same event reconciliation ((c)).
    - a 026 provider-level transient retry inside `chat_one_candidate` **re-uses the same `reservation_id`** on BOTH ledgers (the `worst_case × retries` envelope was already reserved) — never a new charge.
    - the chain advances to a **differently-priced** paid candidate → each candidate opens its OWN `worst_case × retries` reservation on both ledgers. Before advancing: a candidate that NEVER dispatched (paid-guard skip / reservation refusal) is **`released`**; a candidate that DISPATCHED but failed is marked **`retained`** (reconciliation-pending) — never `released`. The next candidate may `open` while the prior `retained` envelope keeps counting against the Attempt cap; 026 reconciliation later moves the retained hold to `reconciled` (execution never waits on lagged provider spend).
  - **(c) Reconciled envelope, NOT actual cost (F3).** 026's ledger does not obtain authoritative per-call actual cost — its reconciliation attributes **lagged aggregate observed spend** to whole reservations and is explicitly approximate (`reservations.py:434`, `reconcile_settled`: never partial, prefix-covered by observed spend). So a dispatched candidate's Attempt reservation transitions **`open → retained → reconciled`** (`retained` = reconciliation-pending after dispatch; `reconciled` when its corresponding 026 reservation reconciles), while a candidate that never dispatched goes **`open → released`**; throughout, it **accounts the reserved worst-case envelope** — it does NOT claim an exact actual cost. `attempt_budget_credits` therefore bounds worst-case *reserved* spend (conservative: it can never UNDER-count real spend). Authoritative per-call billing/usage attribution is out of scope for v1.
  - **(d) Event-sourced + crash-safe.** `budget_usage` and `credit_reservations[]` are projections rebuilt from append-only events; a crash **between the two ledger mutations, or between reserving and recording the result,** reconciles by replaying events + observing the durable 026 ledger reservation (saga: reserve-Attempt → reserve-026 → call → reconcile/release both). The Attempt ledger is per-Attempt: a crashed Attempt is a failed Attempt whose reservations reconcile against the 026 ledger — the platform-wide spend guard is never weakened by an Attempt-ledger loss.
  - **(e) Free-first inert.** Free candidates (cost 0) reserve 0 on both ledgers, so the whole mechanism is a no-op under the default (opt-in OFF).

A marked row emits coordinator events in the SAME transaction as the Attempt transition: `†` a `ClaimReleased`, `◇` a `MonitorStarted`. Marked rows are mostly pre-merge off-ramps, but not only: `PromotionObserved` is `†◇` and is neither an off-ramp nor terminal — the merge has landed and the monitoring window is unattended, so continuing to hold the singleton lane through it would block every other Problem for the length of the window. **Markers:** `†` the row emits the coordinator's `ClaimReleased` in the same transaction (whenever a claim is held); `◇` it emits the coordinator's `MonitorStarted`; `‡` the row is a lane transition but NOT an Attempt transition, so it moves no Attempt through the state machine.

`unsupported_scope`, `*_failed`, `promotion_aborted`, `review_aborted`, `attempt_abandoned`, `retained`, `reverted`, `cooldown`, `circuit_broken` are terminal for that Attempt; a genuinely new proposal is a new Attempt (never a back-edge). `attempt_count` increments at `Implementing`. **Counted** toward the per-Problem failure cap (→ cooldown): `impl_failed`, `publish_failed`, `test_failed`, `eval_failed`, `reverted`; **not counted**: `rejected`, `unsupported_scope`, `superseded`, `review_aborted`, `attempt_abandoned`.

**`attempt_abandoned` (rev 21).** `ClaimExpired` needed a stage-correct terminal. `review_aborted` would have been wrong twice over — it is misnamed at `promoting`/`promotion_requested`, where no review runs, and re-introduces exactly the `claimed` mislabeling rev 18 removed. `impl_failed` would be worse still: abandonment is operational, and counting it would let a crashed runner consume a Problem's quality-failure budget, the very thing FR-001 forbids. So a reclaimed Attempt terminates at its own operational, UNCOUNTED terminal, valid from every claim-holding state. Like `review_aborted` it feeds the OPERATIONAL streak counter, not the quality one.

**One `Cooldown` event, discriminated by `cause` (rev 25).** The table declared `Cooldown` and `OperationalCooldown` as separate rows carrying identical fields and differing only in a value rev 18 had already made part of the key. Two schemas for one record is a Constitution I duplication, and it produced a real divergence: the implementation declared only `Cooldown`, and the drift test — which excludes `‡` rows because they are not Attempt transitions — never compared their names, so `OperationalCooldown` sat in the spec naming a record no writer would ever produce. Unified here, with `cause ∈ {quality, operational}` as the discriminator it already was in the idempotency key, and the drift test now checks every `‡` row's event name against the writable vocabulary. The same check caught a second row: `PromotionReenabled (manual)` also named no record — the coordinator event that re-enables promotion after a breaker is slice-1A's `PromotionEnabledSet` with `promotion_enabled=true`, which is what the row now names.

**Cooldown is repeatable and cause-bearing (rev 18).** The key was `(problem_id,"cooldown")`, which admits exactly ONE cooldown per Problem for all time — a Problem that cooled down once could never cool down again — and conflated the quality and operational causes into one slot. It is now `(problem_id,"cooldown",cause,epoch)` where `cause ∈ {quality, operational}` and `epoch` is the count of prior cooldowns of THAT cause for that Problem, so repeated cooldowns get distinct keys while a retry of the same crossing stays idempotent.

**`_failed` vs `_aborted` (rev 17, reachability corrected in rev 18).** `ReviewAborted` is reachable only from states where a judgment review actually runs — `proposed` (proposal review) and `implementing` (patch review). Rev 17 also allowed it from `claimed`, where no review runs at all; that would have let an unrelated implementation-start failure be recorded as a review failure. Operational failures between claim and implementation take their stage-appropriate outcome instead. A reclaim does NOT produce `review_aborted` — it produces `attempt_abandoned` (rev 21), the one case where an Attempt is terminalized by a DIFFERENT run than the one that abandoned it. The vocabulary already distinguishes these and `review_aborted` follows it: a `*_failed` state means the lane REACHED a substantive negative answer, while `*_aborted` (`promotion_aborted`, now `review_aborted`) means the lane COULD NOT reach an answer for operational reasons. `rejected` is likewise substantive — it is a panel judgment. Conflating the two would be wrong in both directions: routing an infrastructure abort to `rejected` records a verdict no panel gave and (being uncounted) retries forever, while routing it to `eval_failed`/`impl_failed` burns a Problem's quality-failure budget for a provider outage. FR-001 already forbids the latter for the analogous case — a `PricingUnverifiable` "does NOT by itself count as an Attempt-quality failure or a cooldown event" — so rev 17 supplies the state that principle presupposed but the table never defined. `review_aborted` is NOT counted toward the quality cap; it has its OWN bound (Policy Contract: operational aborts/Problem), because an uncounted terminal with no bound is a live-lock. The intent/observed split closes the crash gap between the App merge/revert side effect and the recorded state. The measured floor is what actually carries the property, because tick arithmetic assumes an even cadence that skipped, retried, or manually-dispatched runs violate. Boundary cases: 5 aborts with the 5th at exactly `T+24h00m` → **trips** (both conditions met, `≥` is inclusive); 5 aborts with the 5th at `T+23h50m` (a tick ran early) → **does not trip**, and waits for a later abort past the floor; 5 aborts crammed into 2 h by manual re-dispatch → **does not trip**, which is precisely the case a count-only rule got wrong; 6 aborts spanning 30 h → already tripped at the 5th. **Issue-ranking formula** (deterministic; missing value ⇒ 0; each term normalized to [0,1]):
`score = 0.30·label_weight + 0.20·recency + 0.20·repro_signal + 0.15·surface_match + 0.10·min(comment_count,10)/10 + 0.05·(1 − scope_estimate)`
Term definitions (all deterministic; NO model in the ranking):
- `label_weight` = max over the issue's labels of a fixed map `{security:1.0, data-loss:1.0, bug:0.9, regression:0.85, enhancement:0.5, documentation:0.3, question:0.2}`, default `0.4` for unmapped labels, `0.4` if none.
- `recency` = `exp(−age_days/30)`, `age_days` from `updated_at` (UTC).
- `repro_signal` = 1 if the body case-insensitively matches ANY of the fixed set {`"steps to reproduce"`, both `"expected"` and `"actual"`, a fenced code block ```` ``` ````, or `"Traceback (most recent call last)"`}, else 0.
- `surface_match` = |{`src/`,`tests/`,`.github/`} literally present in body| / 3.
- `scope_estimate` = `min(1, (min(distinct_file_paths_mentioned,8)/8 + min(body_len,8000)/8000)/2)` — a deterministic function of mentioned paths + body length (NOT model-derived).

## Success Criteria *(mandatory)*

- **SC-001**: `problem_id` invariant under evidence growth/reorder while `evidence_digest`/`revision` change; recurrence after `retained` yields a new Attempt under the same `problem_id`.
- **SC-002**: Two workers claiming **different** Problems serialize on the singleton coordinator (exactly one wins; the other recomputes); kill-between-commit-and-label reconciles idempotently; every pre-merge off-ramp (reject/unsupported/stale/`*_failed`/`review_aborted`/`attempt_abandoned`/breaker) releases the coordinator so the lane is never permanently occupied (pre-claim off-ramps hold none to release); a crash between the App merge/revert side effect and its recorded event reconciles via the saga's observed step; an Attempt NEVER acquires two terminals — a reclaiming `ClaimExpired` and the original run's own terminal race on the same terminal-slot CAS, exactly one lands, and the loser performs no further side effect (FR-035).

- **SC-006**: A causally-attributed harmful change is auto-reverted within the v1 window (provider outages without corroboration excluded; candidate-caused transient failures with corroboration included) with ancestry checks; two Attempts monitor concurrently; repeated failures trip the breaker.
